  • Can I preview how each podcatcher will show an episode's HTML show notes before publishing?

    • AI Answer

      • Researched by Anthropic/Model/Claude/5/5/Opus on 2026-11-25 Wed for GitP, whose feed Person/codekiln/GitHub/gitpa builds with scripts/build_rss.py.
      • Short answer: No tool previews show notes app by app. The validators check that a feed is well formed and has the required tags; none of them render the description the way Apple Podcasts or Spotify do. What can run in CI is a test of the feed against the HTML subset the platforms document. Seeing the real rendering means subscribing to a test feed in each app.
      • What the platforms document
        • Apple Podcasts: the episode <description> takes up to 10,000 characters and "rich text formatting and some HTML (<p>, <ol>, <ul>, <li>, <a>) if wrapped in the <CDATA> tag". The channel description is capped at 4000 bytes. Apple's guide does not mention <itunes:summary> or <content:encoded> at all. A Podcaster's Guide to RSS
          • <br> is not in Apple's list. A 2021 Podnews test found that Apple does not honor plain line breaks, while Spotify does. Podnews, episode notes in all players
          • Since iOS 14.5 the Apple app shows notes from Apple's crawler, not straight from the feed, per the same Podnews article. That means a feed change can take a crawl cycle to show.
        • Spotify: for shows hosted elsewhere, Spotify lists <a> (https only, "not http"), <h1>, <h2>, <ul>, <ol>, <li>, <p> and <br>. It passes the HTML through unchanged to other listening platforms. Formatting your show notes
          • Spotify reads <description> before <itunes:summary>, and when <content:encoded> is present it should carry the full description too. Show Descriptions and Hyperlinks
          • The show description has a 60,000 character limit. Incorrect show description on client
          • The Podcast Delivery Specification v1.9 (November 2021) describes <content:encoded> as allowing "a subset of html tags" without listing them.
        • YouTube and YouTube Music: RSS-delivered podcasts do not allow "invalid characters in podcast and episode titles or descriptions, such as “>”,“<" or any HTML". Episodes arrive as private videos first, which works as a preview before making them public. Deliver podcasts using an RSS feed
        • PSP-1, the Podcast Standards Project's RSS spec, caps the episode description at 4000 bytes and permits <p>, <ol>, <ul>, <li>, <a>, <b>, <i>, <strong> and <em> in CDATA. It does not define <itunes:summary>. PSP-1
        • Apple, Spotify and PSP-1 all accept <p>, <a>, <ul>, <ol> and <li>. The strictest length is 4000, from Apple's channel description and PSP-1's episode description.
      • What the open-source apps do with the HTML
        • AntennaPod keeps whichever of <description>, <content:encoded> and <itunes:summary> is longest (FeedItem.setDescriptionIfLonger). An HTML description beats a plain summary of the same text because the tags add length. FeedItem.java · Itunes.java
          • ShownotesCleaner has no tag allow-list. It turns \n into <br /> only when the notes contain neither <br> nor <p>, removes CSS color declarations, links bare URLs, and makes timestamps such as 14:42 seek links. The result renders in a WebView. ShownotesCleaner.java
          • Running the cleaner in a test would show little, because it strips almost nothing. It needs an Android Context, so its own test runs under Robolectric inside AntennaPod's repo.
        • Pocket Casts (Android) fetches show notes from its own server at /mobile/show_notes/full/{podcastUuid} and renders them in a WebView with its own CSS. It hides images whose URL contains coverart. The server code that picks the feed field is closed, so the app source cannot answer which field Pocket Casts shows. PodcastCacheService.kt · ShowNotesFormatter.kt
        • Overcast, Castro, Apple Podcasts, Spotify and YouTube Music are closed source. Overcast's podcaster page says nothing about show notes. Overcast for podcasters
      • Hand-made rendering tests
        • Transistor, June 2024: Apple Podcasts renders paragraphs, links and lists (with spacing problems) and drops headings, bold, italic and block quotes. Spotify mobile adds bold headings. YouTube Music renders paragraphs with double spacing and shows links as plain URLs. Pocket Casts, Overcast and Castbox render nearly everything. Its advice is paragraphs, links and bulleted lists, with <p> over <br>. Formatting your podcast's show notes for different apps
          • Transistor's test feed is public and can be followed in any app as a reference. Transistor test feed · Apple listing
        • Podnews, 2019, tested about 40 apps. Only 14% displayed <itunes:summary> anywhere. Its advice then was HTML in <content:encoded> and plain text in <description>; its 2021 article moved to simple HTML with <p> in <description>. Podnews now points readers to the Transistor test. A full test: how do show notes display in podcast apps?
      • Validators
        • W3C Feed Validation Service is open source Python and runs locally. It warns when <description> contains a tag outside its safe list or a link URL with characters a URI does not allow, when <itunes:summary> contains HTML (ContainsHTML), and when <itunes:summary> passes 4000 characters. It does not know any app's rendering rules. w3c/feedvalidator · Install and run
        • Livewire validator is a Deno feed and media validator with a CLI that covers the podcast namespace tags. Whether it inspects description HTML was not checked. skymethod/livewire-validator
        • Podbase and Cast Feed Validator are hosted checkers that Apple itself recommends for troubleshooting. Podbase checks that a summary or description exists. Neither page describes a show notes preview or an API. Validate your podcast RSS feed · Podbase · Cast Feed Validator
        • Apple Podcasts Connect validation is "strictly a technical evaluation" of tags, artwork and media. It needs an Apple ID and has no CI interface. Validate your podcast RSS feed
        • Spotify for Creators has a rich text editor and an HTML switch for shows hosted on Spotify. No preview for externally hosted RSS was found.
      • What can be automated for GitP
        • A unit test in gitpa's tests/test_build_rss.py that parses each item's <description> and fails on any tag outside <p>, <a>, <ul>, <ol>, <li>, on any link that is not absolute https, and on a description over 4000 characters.
        • The same test can check that <itunes:summary> contains no tags and stays under 4000 characters.
        • A CI step running the W3C validator locally against the built rss.xml.
        • The current build already wraps the poem lines inside a <p> with <br>. Spotify supports <br>; Apple does not list it, and Podnews saw Apple ignore plain line breaks. Whether Apple drops <br> or honors it has not been tested.
        • The build writes HTML as escaped text rather than CDATA. An XML parser reads both as the same string, so this should not matter, but Apple's ingestion has not been tested with escaped HTML.
      • What still needs a human looking at a screen
        • A second feed carrying <itunes:block>Yes</itunes:block> stays out of the Apple directory, and Overcast treats such feeds as private. Followed by URL in each app, it gives a preview before the episode reaches the main feed. AntennaPod fetches the feed on the device. Overcast and Pocket Casts parse feeds on their own servers, so the test feed must be on a public URL.
        • GitP did not appear in an iTunes Search API query for "Ghost in the Patch" on 2026-11-25, so there is no Apple Podcasts web page for the show to compare against yet.
      • Open: Pocket Casts' and Podcast Index's choice between <description> and <content:encoded>, Apple's handling of <br>, and whether Livewire checks description HTML.
