1Password/Environment/AWS Secrets Manager

  • Sync secrets from 1Password to AWS Secrets Manager (beta)

    • Overview

      • A beta integration that copies the variables of a 1Password/Environment into a single secret in AWS Secrets Manager and keeps it current. 1Password stays the place where the values are edited; AWS holds a copy that workloads on AWS can load with any of AWS's own methods.
      • Source: the 1Password Developer page, read on 2026-10-02.

    • Context

      • It is the opposite end of the Environment's other outputs. A 1Password/Environment can be mounted as a local .env file or read through the CLI, SDKs and 1Password/Environment/MCP on a developer machine. This integration pushes it to a cloud secret store instead.
      • Requirements: the desktop app, an Environment, and an AWS account where you can create IAM resources.

    • Key Principles

      • One-way. Changes made in AWS Secrets Manager are never synced back to 1Password.
      • One definitive copy. 1Password recommends keeping a single authoritative copy of each secret, either as an item or as an Environment variable, since several copies drift.
      • Set up once per Environment. Only the person creating the IAM resources needs AWS credentials. Afterwards, teammates invited to edit the Environment can change variables without any AWS access.
      • Anything that auto-rotates in AWS should stay managed there, otherwise the two sides disagree. See AWS/Secrets Manager/Secret/Rotation.

    • Mechanism

      • 1Password does the syncing from its Confidential Computing platform, built on AWS Nitro Enclaves, so the sync runs always-on and not from anyone's laptop.
      • It authenticates to AWS with SAML federation, not with stored access keys. Setup creates these pieces:
        • 1. A SAML identity provider in AWS IAM, registered from a saml-metadata.xml file downloaded from 1Password.
        • 2. An IAM policy that allows secretsmanager:DescribeSecret, RestoreSecret, PutSecretValue, CreateSecret, DeleteSecret, TagResource and UpdateSecret.
        • 3. An IAM role that trusts the SAML provider, constrained by a SAML:sub StringEquals condition holding the subject 1Password shows on its configuration page.
      • In 1Password the role and provider ARNs are pasted into the Environment's AWS Secrets Manager card, along with a target region and a target secret name. The name defaults to the Environment's name and must be unique within AWS. An optional KMS key ID or ARN makes AWS encrypt with that key; the role then needs KMS permissions too.
      • Test connection creates and immediately deletes a placeholder secret, to confirm the permissions work. Then the toggle enables syncing.
      • After that, saving a change to the Environment triggers another sync.
      • The Environment's variables land together in one AWS secret, so the Environment, not each variable, is the unit that maps to a secret.

    • Examples

      • Stopping: toggle the integration to Disabled to pause it, or use the ellipsis menu and Delete integration to remove it.
      • Size: a 64 KB limit applies. A large Environment can be split into several, each with its own integration and its own target secret.
      • Common failures the page lists: missing role permissions, a failed role assumption (SAML provider or trust policy wrong), a SAML subject that doesn't match the trust policy, a target name already used in AWS, an invalid KMS key, and an exceeded Secrets Manager quota.

    • Misconceptions

      • It does not keep AWS as a source of truth. Edits made in AWS are never copied back to 1Password. The page doesn't say what a later sync does to them, so treat them as unsafe.
      • Deleting the integration is how you stop syncing. The page doesn't say whether the AWS secret is removed when you do.
      • It is not part of the local .env mount feature, so the ten-mount limit per device does not apply to it.

AWS/Secrets Manager/Q/What terms does AWS Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?

  • What terms does AWS/Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?

    • AI Answer

      • Answer/Official from Create an AWS Secrets Manager secret, CreateSecret API reference, and Pass Secrets Manager secrets through Amazon ECS environment variables:
      • Short answer: there is no distinct secret type for this at the API level — every secret is one opaque AWS/Secrets Manager/Secret. Answer/Official from CreateSecret API reference: "Either SecretString or SecretBinary must have a value, but not both." "Single vs. multi-valued" is codekiln's own shorthand, mapped onto two garden pages: AWS/Secrets Manager/Secret/SecretString (AWS's Plaintext tab — one raw string) is single-valued; AWS/Secrets Manager/Secret/KeyValue (AWS's Key/value pairs tab — the same field holding a JSON object) is multi-valued.
      • Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs, or choose the Plaintext tab and enter the secret in any format." Its examples: an API key → key/value pairs (ClientID, ClientSecret); an OAuth token, certificate, or private key → plaintext.
      • What only AWS/Secrets Manager/Secret/KeyValue (multi-valued) can do:
        • AWS's ready-made rotation Lambda templates. Direct citations and the full picture — including a third, Lambda-less "managed rotation" path that's gated by how a secret was created, not by its shape: AWS/Secrets Manager/Secret/Rotation. Core citation: CreateSecret API reference: "you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret" for those templates to work. AWS/Secrets Manager/Secret/SecretString (single-valued/plaintext) can still be rotated, but only with a fully custom Lambda — there's no ready-made template for it.
        • Pulling one field without app-side parsing. Pass Secrets Manager secrets through Amazon ECS environment variables: "Specifies the name of the key in a key-value pair with the value that you want to set as the environment variable value. Only values in JSON format are supported." AWS/Secrets Manager/Secret/SecretString has no key to address this way. (fnox mirrors this client-side with its json_path option, per its provider docs, including dotted nested paths.)
        • Fewer resources for related values, at lower cost. AWS Secrets Manager pricing: worked example prices a secret "@ $0.40 / secret / month" — four related values as one AWS/Secrets Manager/Secret/KeyValue secret cost the same as one AWS/Secrets Manager/Secret/SecretString, versus 4x if split into four single-valued secrets.
      • What single-valued buys you that multi-valued doesn't: nothing capability-wise — it's a strict subset. Its only edge is simplicity for a value that's genuinely atomic (a bare API key, a cert, a private key), where there's no field to key on and no rotation Lambda will ever need named subfields.
AWS/Secrets Manager/Secret

  • AWS/Secrets Manager secret

    • A secret is one opaque value in a single field — SecretString (text) or SecretBinary (bytes), never both. CreateSecret API reference: "Either SecretString or SecretBinary must have a value, but not both."
    • That one field can hold either shape:
      • AWS/Secrets Manager/Secret/SecretString — one raw string, no internal structure (codekiln's single-valued; AWS console's Plaintext tab).
      • AWS/Secrets Manager/Secret/KeyValue — a JSON object serialized into that same field (codekiln's multi-valued; AWS console's Key/value pairs tab).
    • The console nudges toward the key/value shape even outside a recognized database type. CreateSecret API reference: "If you create a secret by using the Secrets Manager console then Secrets Manager puts the protected secret text in only the SecretString parameter. The Secrets Manager console stores the information as a JSON structure of key/value pairs that a Lambda rotation function can parse."
    • The / in a name like myapp/database-url is not a path into a JSON object — it is one ordinary allowed character in one flat secret name. CreateSecret API reference: "The secret name can contain ASCII letters, numbers, and the following characters: /_+=.@-." There is no parent/child relationship between secrets in Secrets Manager; / is purely a naming convention people use to group related names, the same way S3 object keys use / without real folders existing.
AWS/Secrets Manager/Secret/KeyValue

Page reference

  • AWS/Secrets Manager key/value secret

    • The same AWS/Secrets Manager/Secret field (SecretString) holding a JSON object instead of a bare string, e.g. {"username":"admin","password":"secret"}. AWS's console calls this the Key/value pairs tab. Answer/Official from Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs..." — its example: an API key entered as ClientID / ClientSecret pairs.
    • codekiln's term for this: multi-valued. There is still exactly one SecretString — "multi-valued" describes how many named fields live inside that one JSON value, not a second storage mechanism.
    • Setting it: console → Store a new secret → Other type of secret → Key/value pairs tab. CLI → aws secretsmanager create-secret --name <name> --secret-string '{"key":"value", ...}' — any valid JSON object string. (Create an AWS Secrets Manager secret)
    • What this unlocks that AWS/Secrets Manager/Secret/SecretString (plaintext) can't:
      • AWS's ready-made rotation Lambda templates for known database-credential shapes — but only one of three rotation paths, and only when the JSON matches the expected schema. Full breakdown with citations: AWS/Secrets Manager/Secret/Rotation.
      • Extracting one field by ARN suffix without app-side JSON parsing. Pass Secrets Manager secrets through Amazon ECS environment variables: "Specifies the name of the key in a key-value pair with the value that you want to set as the environment variable value. Only values in JSON format are supported." fnox mirrors this client-side with its json_path option (provider docs), including dotted nested paths.
      • Storing several related values as one billed resource instead of one per value. AWS Secrets Manager pricing worked example prices a secret "@ $0.40 / secret / month" — one JSON secret with several fields costs the same as one plaintext secret; splitting the same values into N plaintext secrets costs N times as much.
AWS/Secrets Manager/Secret/Rotation

  • AWS/Secrets Manager secret rotation

    • Overview

      • Rotation replaces a secret's stored value with a new one; see Secret/Rotate for the concept independent of any specific secrets manager. There are three distinct rotation paths, not two, and all of them are opt-in — creating a secret never enables rotation by default. Rotate AWS Secrets Manager secrets — the User Guide's own top-level split: "There are two forms of rotation: Managed rotation ... Managed rotation doesn't use a Lambda function ... Rotation by Lambda function – For other types of secrets, Secrets Manager rotation uses a Lambda function to update the secret." (What that page calls "Lambda function" rotation splits again below into a ready-made-template path and a fully custom path, which is why this page counts three.)

    • Supported

      • Path 1: managed rotation, no Lambda at all — gated by how the secret was created, not by its shape

        • Only for secrets created through the owning service's own integration: Amazon RDS, Aurora, and DocumentDB master credentials, Amazon Redshift admin passwords, ECS Service Connect TLS certificates, and Secrets Manager managed external secrets (held by Secrets Manager partners — not a database at all). Managed rotation for AWS Secrets Manager secrets — this is the definitive list of what qualifies: "Some services offer managed rotation, where the service configures and manages rotation for you. With managed rotation, you don't use an AWS Lambda function..."
        • You cannot get this by hand-crafting your own CreateSecret call, whatever shape you give it — it depends on which service's UI/API created the secret, not on JSON vs. plaintext. CreateSecret API reference, same page cited below for the schema requirement: "For secrets that use managed rotation, you need to create the secret through the managing service."

      • Path 2: AWS's ready-made rotation Lambda templates — this is where AWS/Secrets Manager/Secret/KeyValue vs. AWS/Secrets Manager/Secret/SecretString actually matters

        • Not just RDS/DocumentDB/Redshift — AWS ships ready-to-use templates for every RDS/Aurora engine (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2, single- or alternating-user), DocumentDB, Redshift, and Timestream for InfluxDB. AWS Secrets Manager rotation function templates — the full, current list, with a template per engine: "AWS Secrets Manager provides a set of rotation function templates ... ready-to-use Lambda functions."
        • Every template on that list requires the secret to be an AWS/Secrets Manager/Secret/KeyValue whose JSON matches the expected credential schema (username, password, host, ...) — never a plain AWS/Secrets Manager/Secret/SecretString. CreateSecret API reference, the "For database credentials" paragraph: "For database credentials you want to rotate, for Secrets Manager to be able to rotate the secret, you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret."

      • Path 3: a hand-written Lambda function — works on any secret, either shape, any product at all

        • AWS also ships a generic rotation template as an unopinionated starting point, and nothing stops writing one from scratch for a secret belonging to no AWS product whatsoever (a third-party API key, say). AWS Secrets Manager rotation function templates, same page as Path 2's list: "Secrets Manager also provides a generic template that serves as a starting point for any type of secret." Unlike Path 2's ready-to-use templates, the generic template and a from-scratch function carry no schema assumption, so they work on a plain AWS/Secrets Manager/Secret/SecretString just as well as an AWS/Secrets Manager/Secret/KeyValue — the code decides how to parse and replace the value. This is the only rotation path available to a plain single-string secret, and the only one with no product restriction at all.
        • Turn it on by attaching the function's ARN: aws secretsmanager rotate-secret --secret-id "myapp/database-url" --rotation-lambda-arn "arn:aws:lambda:...". --secret-id names one whole secret — the / inside "myapp/database-url" is not a path into a JSON object; see AWS/Secrets Manager/Secret on why it's just an allowed naming character. Rotation always replaces that one secret's entire SecretString, never a sub-key of it. Example command lifted from fnox's AWS Secrets Manager provider docs, under its "Secret rotation" heading.
        • The four-step contract a hand-written rotation function must implement, per Write a rotation function — the same page the ready-made templates in Path 2 are built from, under "Four steps in a rotation function":
          • createSecret — generate the new value (e.g. a random password) and store it with put_secret_value, tagged AWSPENDING. Quote from that page: "Then it generates a new secret value ... Next it calls put_secret_value to store it with the staging label AWSPENDING."
          • setSecret — push that AWSPENDING value into the actual database or service so the new credential becomes real there. Quote: "The method setSecret changes the credential in the database or service to match the new secret value in the AWSPENDING version of the secret."
          • testSecret — connect using the AWSPENDING value to confirm it actually works before committing to it.
          • finishSecret — promote AWSPENDING to AWSCURRENT; the label that used to be AWSCURRENT moves to AWSPREVIOUS. Quote: "the Lambda rotation function moves the label AWSCURRENT from the previous secret version to this version, which also removes the AWSPENDING label ... Secrets Manager adds the AWSPREVIOUS staging label to the previous version."
          • On an AWS/Secrets Manager/Secret/KeyValue secret, a correctly written createSecret step reads the current AWSCURRENT JSON first and writes back the complete object with only the target field (e.g. password) changed. Secrets Manager itself performs no such merge — that is the function's own job, and it is exactly the job fnox skips, per the hazard noted below.

      • Versioned staging labels, used by every path above

        • Secrets Manager keeps multiple value versions tagged with staging labels, so a rotation stages and tests a new value before promoting it — consumers are never left with zero valid credentials mid-rotation. What's in a Secrets Manager secret?, under "Secrets Manager labels a secret version": "The current version – AWSCURRENT ... The previous version – AWSPREVIOUS ... The pending version (during rotation) – AWSPENDING."

    • Not supported

      • No ready-to-use rotation template for a plain single-string secret. Path 2's templates target the known database/service credential JSON shapes only — see the template list above; an AWS/Secrets Manager/Secret/SecretString holding a bare API key, OAuth token, certificate, or private key has no ready-made equivalent — only Path 3 (a hand-written function, possibly starting from the generic template).
      • Never automatic by default, on any path. A secret sits static until rotation is explicitly attached — either by creating it through a managing service (Path 1) or by attaching a Lambda ARN and schedule (Paths 2–3). Rotate AWS Secrets Manager secrets, same overview page cited at the top: "In Secrets Manager, you can set up automatic rotation for your secrets" — "can," not "does by default."
      • fnox performs no rotation at all. It only reads whatever value AWS currently has. AWS Secrets Manager provider docs, "Secret rotation" section: "Direct reads fetch the current version. Refresh an encrypted sync cache or clear the daemon cache to pick up a rotated value." Rotation is configured only in AWS, never through fnox.

    • Interaction hazard: fnox writes vs. AWS-side rotation

      • fnox set overwrites a secret's entire SecretString with only the one value given on the command line — it has no read-merge-write for json_path. Verified directly in the fnox source at the commit this page cites: put_secret in aws_sm.rs does a bare put_secret_value/create_secret with whatever string it's handed, and the set command's call site passes it the one value the person typed, with no read-first step.
      • On an AWS/Secrets Manager/Secret/KeyValue secret, running fnox set SOME_FIELD newvalue --provider aws against one json_path-scoped field clobbers every other key in that JSON. This is the opposite of the createSecret step described in Path 3 above, which reads AWSCURRENT first and writes back the whole object with only the changed field touched — fnox set has no equivalent read step, rotation-aware or not.

My/Pref/Dev/Tool/Secrets/AWS Secrets Manager
  • When using AWS/Secrets Manager, a single secrets manager secret can either store one secret or a json blob which contains multiple secrets.

    • Honoring My/Principle/Simplify

      • It might be easier at the beginning of an application's history to have a single AWS/Secrets Manager/Secret/KeyValue for a specific environment tier of an application, for example, dev, stage, and prod. That way you might have three AWS/Secrets Manager/Secrets for each application, each with 5-10 secrets stored in their json. Then the AWS/IAM roles can be set up per environment. This is less complex than having many atomic AWS/Secrets Manager/Secret/SecretString

    • Honoring My/Principle/Make the Right Thing Easy and the Wrong Thing Hard

      • Keep in mind that it should be as easy as possible to do Secret/Rotation, preferably on an automatic basis.
