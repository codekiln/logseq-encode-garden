Claude/Routine
  • Management surfaces: claude.ai/code/routines (web), Desktop app (Remote routine), CLI /schedule (schedules only; API and GitHub triggers are configured on the web).
  • Account-scoped, not team-shared: routines belong to the individual claude.ai account; commits and connector actions appear as that user. Teammates do not share routine definitions (as of research preview).
  • Connectors: MCP integrations from the claude.ai account (not CLI-only claude mcp add local servers unless also added as cloud connectors or committed .mcp.json in the repo).
  • Routine starts count toward a per-account daily cap (plan-dependent; shown at claude.ai/code/routines); session work also draws Claude Code subscription usage like interactive sessions.
  • /schedule creates and manages Routines saved to the claude.ai account; runs happen on Anthropic cloud, not in the local process.
  • CLI scope: schedule triggers only. Add API or GitHub triggers in the web editor.
  • Requirements: claude.ai subscription login (not Console API-key / Bedrock-only auth), Claude Code on the web enabled, CLI ≥ v2.1.81. If /schedule is unknown, check auth mode, growthbook/telemetry disable flags, or whether the session is already Claude Code on the web.
  • Bedrock / Vertex / Foundry: bare /loop and dynamic-interval behavior differ (e.g. fixed 10-minute default, no loop.md on some paths); cloud /schedule may also be unavailable when not on claude.ai auth.
  • /loop schedules work inside an open CLI session on the local machine. Desktop → Local scheduled tasks run on the user’s machine. Routines are remote cloud sessions at claude.ai.

Codewall/Blog/26/03/How we hacked McKinsey's AI Platform
  • How We Hacked McKinsey's AI Platform — CodeWall.ai

    • Fun fact: As part of our research preview, the CodeWall research agent autonomously suggested McKinsey as a target citing their public responsible diclosure policy (to keep within guardrails) and recent updates to their Lilli platform. In the AI era, the threat landscape is shifting drastically — AI agents autonomously selecting and attacking targets will become the new normal.

    • 46.5 million chat messages ... Every conversation, stored in plaintext, accessible without authentication.

    • Most required authentication. Twenty-two didn't. ... API documentation publicly exposed

    • .. it recognised a SQL injection that standard tools wouldn't flag (and indeed OWASPs ZAP did not find the issue). From there, it ran fifteen blind iterations — each error message revealing a little more about the query shape — until live production data started flowing back*...

    • Poisoned advice — subtly altering financial models, strategic recommendations, or risk assessments. Consultants would trust the output because it came from their own internal tool.

      • This is the one that seems the most novel to me. A private entity that had purchased access to this vulnerability could have shaped outcomes of human decisions.

    • Data exfiltration via output — instructing the AI to embed confidential information into its responses, which users might then copy into client-facing documents or external emails.

      • If they had access to the database, in theory, they could have exfiltrated data through that mechanism. But most systems at McKinsey scale do have some kind of egress monitoring, which makes it harder to get data out without being detected. But this provides a way to get data out without triggering those warnings.

    • Silent persistence — unlike a compromised server, a modified prompt leaves no log trail. No file changes. No process anomalies. The AI just starts behaving differently, and nobody notices until the damage is done.

      • While silent persistence and "The AI just starts behaving differently, and nobody notices until the damage is done" iis definitely an important threat aspect here, here it seems like that doesn't match up with their example claim that a modified prompt leaves no log trail. If the database row with a prompt was changed, it will have updated the modified time of that row. Also, as they disclosed, all the chat messages were in the database, so they were logged. But definitely, silent persistence would be the worst.
    • My Notes
      • The headline was that they "Hacked McKinsey's AI Platform" but really, what happened was that McKinsey had 22 unauthenticated API endpoints, some even with documentation, that were vulnerable to SQL injection.
      • The main take-away is that people are using agentic tools to hack - and there are actors that will follow responsible use disclosure, and other actors that will not, and will just make use of the data.

        • AI Summary

          • Craig McLuckie critiques the prevailing model of AI code generation, where each product builds an end-to-end vertical stack—including its own LLM, context manager, and workflow engine.
          • These vertically integrated stacks are closed systems that inhibit interoperability, innovation, and reuse.
          • He argues that the next evolution must tip this structure horizontally, enabling shared context management and LLM resources across different applications.
          • This shift mirrors earlier evolutions in tech (e.g. microservices, containerization) that replaced monolithic systems with more modular, composable architectures.
          • Emphasizes the importance of community-led efforts and open standards—like the Model Context Protocol (MCP)—to facilitate this transition.

    • Slide Summary

      • Title Slide
        • "Techniques for Getting High-Quality Code from LLMs"
      • Slide: Prompt Engineering is a Core Dev Skill
        • LLMs are now tools in every developer’s toolbox.
        • Prompt engineering is as fundamental as learning a framework.
      • Slide: Architecture-First Prompting
        • Begin prompts with high-level architecture and design goals.
        • Helps guide LLMs to generate code that fits into existing systems.
        • Example prompt: “I’m building a Flask app with this structure…”
      • Slide: Contextual Scaffolding
        • Provide surrounding code context to situate the LLM.
        • Use file headers, imports, docstrings, and nearby function calls.
        • Helps the LLM understand naming conventions and system patterns.
      • Slide: Task-Specific Prompting
        • Customize prompts for:
          • New feature development
          • Debugging
          • Refactoring
        • Example: For debugging, provide error trace and expected behavior.
      • Slide: Progressive Enhancement
        • Start with a minimal viable prompt.
        • Add detail iteratively to refine the output.
        • Encourages experimentation and layered improvement.
      • Slide: Collaborate, Don’t Delegate
        • Treat the LLM like a junior developer:
          • Guide it.
          • Review output.
          • Improve over time.
        • Emphasizes the importance of human review and iteration.

    • AI Summary

      • Patty O’Callaghan presents a set of practical strategies for getting consistently strong output from LLMs in software engineering tasks.
      • Key idea: don’t expect magic—collaborate with the model by designing thoughtful prompts.
      • Strong prompts lead to better alignment with existing systems and more maintainable code.
      • Encourages iterative development of prompts, tailored to both the task and the architecture.
