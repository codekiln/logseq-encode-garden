Ableton/Live/Report/26/09/Open-source options for controlling Live 11 from coding agents
  • Producer Pal — Live 11 via Max for Live LiveAPI, Node for Max, MCP, and REST. Best documented API architecture and strongest professional provenance; its unauthenticated port 3350 listens on all interfaces. [4]
  • Max for Live LiveAPI is the cleanest supported programmatic substrate. Ableton's documentation explicitly describes the Live API as access to the Live Object Model and supports property access, function calls, observation, and device-parameter control. JavaScript in Max gets a LiveAPI object, while Max patchers can use live.path, live.object, and live.observer. [1] A project can therefore put a Max device into the set, use Max's JavaScript or Node-for-Max facilities as a bridge, and expose an external HTTP/MCP interface. producer-pal is the notable open-source implementation of this architecture. [4]
  • uisato/ableton-mcp-extended explicitly advertises Live 11+ and adds significantly more functionality around the same general Remote Script/socket design, including optional higher-performance UDP communication. The inspected project had nontrivial adoption, but its creator's public GitHub footprint is essentially centered on this project and I found no established-company affiliation comparable to the stronger examples above. [9] Its optional ElevenLabs integration is outside the “free-only” criterion when it requires a paid external service, so I would evaluate only the core Ableton integration. More network transports and more tools are not inherently insecure, but they enlarge the amount of code and protocol surface one has to audit. Given that ahujasid and Wouter already cover this architecture with stronger security signals, I see little security-driven reason to prefer the extended version.
  • On the other hand, this is an enormous authority surface. Its architecture includes TCP 9877, UDP 9882, optional OSC/UDP 9878/9879, and a web dashboard; the README explicitly shows the dashboard on 127.0.0.1, but in the material I inspected I did not find an equivalent security statement establishing authentication or loopback-only defaults for every Remote Script transport. [10] The creator's own GitHub profile says they would like to work for Ableton or Anthropic, which is useful evidence that this is not an Ableton- or Anthropic-affiliated project. [38] I would call it an impressive experimental project, not a trust-minimized production choice.
  • Interestingly, Schoepke has one of the better corporate-engineering provenance signals: in a public Swift discussion he previously identified himself as a UI developer on Microsoft's Windows team. I could not verify that as his current employment in 2026, so it should be treated as historical professional evidence rather than a current Microsoft affiliation. [41] This is a useful reminder that creator pedigree and security architecture are separate axes: I would still reject arbitrary in-Live eval for a production agent integration.
  • Ben Schoepke (ableton-live-mcp): historical Microsoft Windows UI role; strong historical professional evidence, but high-risk bridge architecture. [41]
  • Best overall architecture if Max for Live is available: Producer Pal. It is the only strong candidate I found that stays on Ableton's documented Max for Live API path rather than reaching into the Control Surface Python runtime. Its creator provenance, security documentation, release hygiene, MCP support, and REST API are all unusually good. [1] I would, however, treat the default 0.0.0.0-equivalent network exposure on port 3350 as something to mitigate immediately with a host firewall or other local-network isolation. The project's own security policy acknowledges that it is unauthenticated and LAN-reachable. [21] With that mitigated, this is my preferred option.

    • Rulesync can already provide much of the component conversion layer, especially for rules, skills, agents, commands, hooks, MCP, and permissions. It cannot currently own the complete build because it does not emit Codex, Cursor, Pi, or OpenCode plugin packages, and even its Claude packaging target leaves manifests, catalogs, scripts, and assets outside its control. [27]
    • The most sustainable near-term strategy is therefore:
    • 1. Use Agent Skills as the immutable portable core.
    • 2. Use MCP as the portable external-tool boundary.
    • 3. Maintain normalized source definitions for agents and hooks.
    • 4. Generate separate native plugin packages for each host.
    • 5. Treat Claude compatibility as an optimization, not a guarantee.
    • 6. Run host-specific contract tests, particularly for hook blocking behavior, path variables, subagent isolation, and CLI-versus-IDE parity.
    • 7. Fail builds when a required capability cannot be represented instead of silently dropping it.
    • The final answer to the provider-neutral question is consequently two-part:

    • A provider-neutral definition for skills and many individual configuration components now exists in practice, and Rulesync is a credible implementation of that layer. A provider-neutral definition for an installable, versioned, secure, multi-component agent plugin does not yet exist.

    • The closest available architecture is not “write one plugin and run it everywhere,” but author one canonical agent suite and compile it into several native plugins, preserving standard SKILL.md directories wherever possible and surfacing semantic losses explicitly.
