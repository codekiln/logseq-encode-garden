    • the problem with Nix is its Pur/ity

      • By design, nix is trying to build all software in a pure way, which is a very ambitious and lofty goal.
      • I love this goal, particularly for the reproducibility of software. It ensures that software can be built by people who are independent of the core maintainers. This part reminds me of how the IETF requires multiple, independent reference implementations to move a protocol forward.
      • Part of the design of this system is that the build dependencies are expressed in a terse functional programming language, Nix/Lang. Someone has to write the Nix/flake for each package, which describes how to build the package. Then someone else has to build it. And, preferably, it wouldn't need to be built more than once for each platform.
      • Most of the time, the person who describes how to build the software in a Nix/flake with Nix/Lang is just an enthusiast about the underlying software. They don't have tons of time to set up a robust build pipeline that includes tests. They are most likely just doing it for themselves. Once they get it working, they share that work with others.
      • But this means that the vast majority of people who use Nix/flakes are not getting binaries built by the people who made the software. This is very inefficient. The most knowledgable people about a particular piece of software are the core maintainers. Those maintainers often go out of their way to generate binaries for multiple platforms. And then, most of the time, as far as I understand it, nix doesn't use them, because it wants to build them.
      • For example, the mise Nix/flake here is maintained by a polish developer Person/Konrad Malik. It doesn't use any of the binaries that @jdx has GitHub/Actions generate.
        • If I look at their github surface area, they appear to be a competent dev, and I can see they are struggling with some of the things I am with nix; Person/Konrad Malik/GitHub/neovim-flake has
          • in the assumptions section,
            • keeps all Neovim config in lua as it's supposed to be
            • uses nix for system dependencies, plugins, and packaging
            • That way nix is a layer on top, just used for packaging and reproducibility. It does not interfere with the standard way to configure Neovim.
          • in the experimentation section,

            • One of the cons of using Neovim in nix is - no "dirty" modifications to Neovim to try something out quickly. Experimentation becomes harder. You always need to rebuild it, but nix build and then ./result/bin/nvim is quick and easy enough for it to not be a deal-breaker.

      • As a relatively new adopter of Nix, I don't even know whether there's a convention for how to just "rely on the original binaries" when making a nix flake. It seems like it goes against the whole ethos of the nix ecosystem.
      • It's seems ironic to me that one of the reasons why people choose Nix instead of Docker is performance. They both provide increased reproducibility and require people to pay for that with increased complexity of abstractions. Nix's build-time complexity has less industry support, and so individuals must decide where and how they will add caching.

How can an Obsidian vault declare the community plugins it depends on and install them by script?AI Answer
  • Short answer: The declaration half already exists — .obsidian/community-plugins.json is an array of enabled community plugin IDs that Obsidian itself writes, and committing it makes the plugin set part of the vault. The missing half is the fetch, and there are now four working ways to script it: the official CLI's plugin:install (Obsidian 1.12+), vendoring the plugin payloads into the repo, Nix + home-manager, or a ~20-line resolver against the public plugin registry.

  • 3. Nix + home-manager (fully declarative)

    • The programs.obsidian home-manager module merged in PR #6487 (May 2025) and covers vaults, community plugins with their settings, themes, CSS snippets, and hotkeys.
    • karaolidis/nix-obsidian-extensions supplies the packages: an overlay exposing pkgs.obsidianPlugins and pkgs.obsidianThemes, scraped daily from the official registry, consumed as a flake input and referenced by plugin ID.
    • This is the strongest coupling available — plugin set, plugin settings, and hotkeys all rebuild from one config — at the cost of adopting Nix for the machine.

    • My Notes

      • A key take-away for me is that the NixOS paradigm conflicts with the auto-updaters of big IDEs like VSCode, JetBrains, Windsurf. Every time the OS has an update, it requires Nix-OS-specific workarounds. As a result, Forrest moved from NixOS to omakub, which is Person/David Heinemeier Hansson's opinionated Ubuntu setup. Given Forrest's prior affection for ArchLinux, he's closely watching DHH's Omarchy.

    • AI Notes from highlights #Snipd

      • Early days were great: you customized NixOS (Hyperland, NeoVim, Waybar) in ~6h42m and loved the declarative, rollbackable setup that kept everything intentional and versioned, as noted in your highlights about the “first weeks of NixOS bliss” and declarative configs’ benefits (setup journey, why declarative clicked).
      • Friction emerged with constant updates: JetBrains, Zed, and Windsurf updates repeatedly broke or required deep config debugging, turning simple updates into time sinks (update pain, JetBrains breaking).
      • Software install hurdles: many tools needed unstable packages or custom flakes; common CLIs like Bun/FlyCTL required extra config and dependency wrangling (install issues).
      • Tinkering shifted from fun to forced: you enjoy polishing, but NixOS made you tinker just to keep basics working, eating time you wanted for coding and experiments (tinkering time sink, preference shift).
