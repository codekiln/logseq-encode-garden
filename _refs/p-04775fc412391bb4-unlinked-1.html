1Password/Environment/Q/Can a symlink to a .env created with 1Password Environments work? Can I create a number of different symlinks to the same .env and use it in different places?

  • Can a symlink to a .env created with 1Password/Environments work? Can I create a number of different symlinks to the same .env and use it in different places?

    • AI Answer

      • Short answer: yes to both, with one catch. A symlink is just another path to the same named pipe, so 1Password cannot tell a read through a symlink from a read of the mount itself. Many symlinks to one mount work as long as two programs don't read at the same moment; when they do, one gets the secrets and the other waits or gets nothing.
      • This is reasoned from how named pipes work and from a test with a plain mkfifo pipe on macOS on 2026-10-02. It was not tested against a live 1Password mount.

      • Why a symlink works

        • The mounted .env is a named pipe (FIFO), per Local .env files — 1Password Developer. Opening a symlink opens whatever it points to, so every symlink lands on the same pipe.
        • In the test, a relative symlink (a/.env -> ../real.env) and an absolute one (b/.env -> /…/real.env) both resolved to the same pipe: stat -L gave the same inode and type Fifo File for all three paths.
        • The docs say 1Password makes "no distinction … between different processes reading the file," and it has no way to see which path a reader used either.

      • Many symlinks to one mount

        • One at a time works. When the writer serves each read in turn, cat a/.env then cat b/.env each got a full copy.
        • Two at once does not. With one write and two simultaneous readers, a got K=once and b blocked until the test was killed. The docs warn that mounted files "aren't designed for concurrent access." Several dev servers or agents starting together through different symlinks hit this.
        • It saves mounts. All the symlinks share one mount, so they count once against the limit of ten enabled local .env files per device. For git worktrees, one mount plus a symlink per worktree avoids the cleanup problem in 1Password/Environment → Experiments: deleting a worktree deletes only its symlink.
        • Approval is shared too. Approving the first read unlocks reads through every symlink until 1Password locks.

      • Things that change with a symlink

        • Git tracks it. Git ignores a FIFO but tracks a symlink as a link (mode 120000 in the test). Add .env to .gitignore in each place you put one, or the link gets committed.
        • Use a relative target when the layout is fixed, e.g. worktrees beside each other; an absolute target breaks on another machine or user.
        • File-type checks still see a pipe. Python's os.path.isfile returned False through the symlink, the same as on the pipe itself, so loaders that need a regular file fail either way. The docs list python-dotenv 1.1.2+ as supported.
        • The agent hook may not know the path. The hook that validates mounts in supported IDEs and agents might look only at the mount's own path; whether it accepts a symlink is untested.

Claude/Code/Q/If I want to use Claude Code's skill-directory plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?

  • If I want to use Claude/Code's Claude/Code/Plugin/Skills-Directory Plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?

    • AI Answer

      • Short answer: Yes. Claude Code stats through symlinks when it scans .claude/skills/, so .claude/skills/<skill-name> can be a Symlink to a plain, non-dot folder like skills/<skill-name> — you edit the real files in Obsidian with zero configuration, and Claude Code loads the skill exactly as if it lived under the dot-directory directly. This sidesteps the Obsidian/Q/Can Obsidian be configured to show markdown files in folders that begin with a dot (dot-folders), e.g. to edit .claude/skills/<skill-name>/SKILL.md? problem entirely, since the real content never sits inside a hidden dot-folder.

      • What I verified (Claude Code 2.1.221, darwin-arm64)

        • Created skills/test-skill/SKILL.md with real frontmatter/content, then ln -s ../../skills/test-skill .claude/skills/test-skill (relative symlink) in a scratch project directory.
        • A fresh, non-interactive claude -p session in that directory logged Loaded 1 unique skills (... project: 1 ...) and, when asked, correctly quoted the skill's exact description pulled through the symlink — confirming a plain skill folder resolves fine as a symlink.
        • Repeated the test for a full skills-directory plugin (.claude-plugin/plugin.json + a nested skills/ folder, per Claude/Code/Plugin/Skills-Directory Plugin), also symlinked in. claude plugin list detected it too, reporting it as a found project-scope plugin directory — the manifest was read through the symlink without issue.

      • The one catch: project-scope plugin trust, not the symlink

        • The skills-directory plugin case (manifest-bearing folder) didn't load automatically in the test — but the reason had nothing to do with the symlink. claude plugin list reported it explicitly: "1 project-scope plugin directory under ./.claude/skills/ was not loaded because this workspace was not trusted when plugins were scanned." That is the same trust gate Claude/Code/Plugin/Skills-Directory Plugin documents for any project-scope @skills-dir plugin, symlinked or not — accept the workspace trust dialog (or run /reload-plugins afterward) and it loads.
        • A plain skill (just SKILL.md, no plugin.json) isn't gated the same way — it loaded immediately, even in a fresh non-interactive session with no trust dialog involved.

      • Practical setup

        • Keep the real files outside the dot-directory: skills/<skill-name>/SKILL.md (or the full plugin folder for a skills-directory plugin).
        • Symlink it in with a relative link so it survives clone/move: ln -s ../../skills/<skill-name> .claude/skills/<skill-name>.
        • Edit skills/<skill-name>/SKILL.md directly in Obsidian — skills/ isn't a dot-folder, so none of the dot-folder-visibility plugins are needed for this path.
        • SKILL.md edits take effect immediately in a running Claude Code session; other plugin pieces (hooks/, .mcp.json, agents/) still need /reload-plugins or a restart, per Claude/Code/Plugin/Skills-Directory Plugin.

      • A competing convention worth knowing

        • Some orgs standardize the symlink in the other direction — treat .claude/skills/ as canonical and symlink a plain-named directory (e.g. .agents/skills) to it, so other tools reach the same content without touching Obsidian visibility at all. Either direction is a valid use of the same underlying mechanism (dot-folder scanning follows symlinks); which one to use depends on whether the dot-directory or the plain directory is your source of truth.

        • Plugins reference — Skills-directory plugins
        • Empirical test against locally installed claude 2.1.221 (debug log + claude plugin list output), described above.

Claude/Desktop/Scheduled Task/Q/Is there a way to define a Claude Desktop scheduled task inside a repository's .claude directory so it's scoped to that repo and runs by default on any computer opening it?

  • Symlink workflow

    • Where a session has the scheduled-tasks MCP tools available, Claude/Desktop/Scheduled Task/Q/Is there a declarative, programmatic way to manage Claude Desktop scheduled tasks that's scoped to a specific repo? covers a cleaner, officially-supported alternative to the symlink approach below.
    • A symlink can go further than the reference-workaround above: instead of the Instructions field merely pointing at a repo file, ~/.claude/scheduled-tasks/<task-name>/SKILL.md itself becomes a symlink into the repo, so editing the repo file changes the live task with no copy step.
    • 1. Commit the canonical prompt in the repo, e.g. .claude/scheduled-tasks/<task-name>/SKILL.md.
    • 2. On each machine, create the task once through Desktop's normal New routine → Local flow — this step is unavoidable, since schedule, folder, model, and enabled state are local app state, not file content.
    • 3. Delete the real SKILL.md Desktop just wrote and replace it with a symlink to the repo copy: ln -sf ~/ghq/<host>/<org>/<repo>/.claude/scheduled-tasks/<task-name>/SKILL.md ~/.claude/scheduled-tasks/<task-name>/SKILL.md.
    • Because ghq clones every repo to the same deterministic path on any machine (~/ghq/<host>/<org>/<repo>), that target path is stable — but the symlink itself must be absolute, since the home-directory end sits entirely outside the repo tree.
    • 4. Repeat step 2–3 on each additional machine that runs the task. After that, the prompt body, name, and description stay in lockstep across machines automatically; only the schedule/folder/model/enabled fields remain per-machine and still need manual updates through the Edit form if they change.
    • Risk to check before relying on this: if Desktop's Edit form ever saves SKILL.md by rewriting the file in place rather than only patching prompt text, that write could replace the symlink with a fresh real file and silently break the link.

My/Pref/Dev/AI/Config/Management/Use AGENTS.md Without Symlinks

  • Use AGENTS.md Without Symlinks

    • I prefer AGENTS.md as the neutral project instruction file. Use it alone where the selected clients read it; add a client-specific file only when it is needed.
    • When several client files must stay synchronized, use rulesync to generate ordinary files from one maintained source rather than linking AGENTS.md and CLAUDE.md with a symlink. This follows My/Pref/Dev/AI/Config/Management.

    • Why ordinary files

      • A repository should work on Windows without asking each contributor to enable Developer Mode, change symlink permissions or configure Git to create links.
      • Windows supports symlinks, but their creation depends on permissions and Git configuration. With core.symlinks=false, Git checks out the link target as plain text. A committed directory symlink does not automatically become a Windows junction. See Git for Windows: symbolic links and Git's core.symlinks setting.
      • macOS or Linux success does not establish native Windows compatibility. Test checkout, generation and client loading on Windows before claiming support.

    • When another client file is needed

      • Keep the authored instructions in .rulesync/rules/overview.md, with root: true in the frontmatter. Generate AGENTS.md and any needed client-specific files from that source; edit the source rather than the outputs.
      • Current Claude Code can read AGENTS.md directly, but certain CLAUDE.md and CLAUDE.local.md files take precedence. Check the selected version and actual loading before removing a compatibility file. Claude's instruction-loading rules.
      • Regenerate after source changes and through installed checkout and merge hooks. Check generated files for drift so copies do not become independently maintained instructions.
      • Declare shared skill sources through rulesync/Skill/Declarative Source instead of requiring skill-directory symlinks or a separate installer for each client.

    • Dotfiles example

      • The root rule is the authored source; rulesync.jsonc selects the project targets.
      • The Git hooks run mise x -- rulesync install followed by mise x -- rulesync generate after checkout and merge. mise.toml installs those hooks on entering the repository.
      • The global Rulesync configuration also declares external skill sources. Project configuration and global configuration have separate scopes.

OS/File/System/Link/Concept/Comparison of Different Types
  • The practical difference: hard links cannot go stale because there is no path to become wrong; symlinks can go stale because the stored path may stop resolving.
  • A pathname such as notes/today.md is resolved by walking directory entries. A hard link adds another directory entry to the same file object; a symbolic link inserts a path-redirection step into that walk.
  • Object link vs path link - Hard links connect another name to the same file object; symbolic links connect one path to another path.
  • Equal name vs pointer - Hard-linked names are peers. A symbolic link is visibly a link that points elsewhere.
  • Lifetime follows the model - A hard-linked file survives until the final hard link is removed; a symbolic link can survive after its target path stops resolving.
  • Scope differs - Hard links usually stay within one file system and usually apply to regular files; symbolic links can point across file systems and often point to directories.

  • Symbolic links

    • A symbolic link is a small file-like object whose payload is a target path. When a program opens the symlink normally, the OS resolves that stored path.
    • If the target path does not exist, the symlink is dangling. The link object still exists, but following it fails.
  • Target model - Hard link: file object. Symbolic link: pathname.
  • Rename behavior - Hard link: other names keep working. Symbolic link: may break if the referenced path changes.
  • Deletion behavior - Hard link: content remains until the last link disappears. Symbolic link: target deletion leaves a dangling link.
  • File-system boundary - Hard link: normally cannot cross. Symbolic link: can point across boundaries.
  • Directories - Hard link: usually restricted. Symbolic link: commonly used for directories.
  • Config indirection: ln -s ~/dotfiles/zshrc ~/.zshrc creates a symbolic link. The home-directory path points to the dotfiles path.
  • Tool shims: A version manager may put commands on PATH as symlinks to a dispatcher binary, letting many command names route through one implementation.
  • Project-local references: A repository may symlink local rules or assets into a standard directory, but those symlinks can break when collaborators use a different directory layout.
  • Both names share inode 1234567 and link count 2. A symlink would show a different inode number and an l in the permission field.

  • Read a symlink's stored path with readlink

    • readlink <link> prints the raw path string stored inside the symlink — the thing that can go stale.
    • readlink -f <link> resolves the full chain to a canonical absolute path, or exits non-zero if any step in the chain is broken.
    • sh
      			  readlink ~/.zshrc
			  # /home/user/dotfiles/zshrc
			  readlink -f ~/.zshrc
			  # /home/user/dotfiles/zshrc

  • Find dangling symlinks with find -xtype l

    • -type l matches any symlink. -xtype l matches symlinks whose target cannot be resolved — the practical definition of a dangling link.
    • sh
      			  find . -xtype l
			  # ./broken-link
  • "A symlink contains the target file." False. It contains a path string; the target content lives elsewhere.
  • "Symlinks are always portable." False. Relative and absolute target paths both depend on the layout of the machine or repository where they are resolved.
  • "All file-system links are the same kind of indirection." Too broad. Hard links, symlinks, shortcuts, aliases, mounts, and reflinks each have distinct semantics.

Person/codekiln/GitHub/sourcer/Project/v0 AI Spec/Trust

  • Soft links vs hard dependencies

    • Sourcer supports contextually related repos — libraries you should read, platforms you integrate with, internal docs repos — without git submodules.
    • Submodules remain appropriate when:
      • another repo at a pinned commit is a build input,
      • reproducibility must be encoded in the parent repo's history,
      • consumers must get exact SHAs on clone.
    • Sourcer fits when:
      • relationship is advisory ("onboarding set"),
      • pins can float on branches/tags acceptable for exploration,
      • multiple parent projects share the same cached clone under root.
