Py/Server/ASGI

  • ASGI (Asynchronous Server Gateway Interface) — Conceptual Overview

    • Overview

      • Definition – ASGI is a Python-specific interface that standardises how async-capable web servers hand off requests to applications, covering HTTP/1.1, HTTP/2, and WebSocket, while remaining compatible with traditional WSGI apps. See the official ASGI documentation.

    • Context

      • Why ASGI? WSGI assumes a single, synchronous request–response cycle, which limits long-lived connections and efficient parallel I/O. Modern use-cases—streaming APIs, WebSockets, HTTP/2 multiplexing—demand an asynchronous gateway.
      • Origins – Conceived by Andrew Godwin in the Django Channels project (2016) as “codenamed ASGI”, later formalised into the 2019 ASGI 3.0 spec [PyBay-talk slides].

    • Key Principles

      • Async-first, Sync-friendly – Enables async handlers but provides adapters so classic WSGI apps still run.
      • Protocol-agnostic Core – The spec defines a generic scope/receive/send triad; protocols (HTTP, WebSocket) are layered on top.
      • Minimal Surface – A small, typed dictionary‐based contract keeps servers and frameworks decoupled.

    • Mechanism

      • 1. Scope

        • Immutable dict describing the connection (type, headers, HTTP version, client IP, etc.).

      • 2. receive()

        • Awaitable that yields incoming events (e.g., request body chunks, WebSocket messages).

      • 3. send()

        • Awaitable to emit outgoing events (response headers, body, WebSocket frames).

      • Example

        • python
          			  async def app(scope, receive, send):
			      assert scope["type"] == "http"
			      await send({"type": "http.response.start",
			                  "status": 200, "headers": [[b"content-type", b"text/plain"]]})
			      await send({"type": "http.response.body",
			                  "body": b"Hello, ASGI!"})

    • ASGI vs WSGI

      • Concurrency Model – ASGI uses Py/asyncio/Event Loops; WSGI spawns (threads|processes).
      • Protocol Support – WSGI: HTTP/1.1 only. ASGI: HTTP/1.1, HTTP/2, WebSocket (spec); HTTP/3 via server extensions (e.g., Hypercorn) Hypercorn docs.
      • Long-lived Streams – WebSockets & server-push viable in ASGI; need work-arounds (e.g., polling) in WSGI.
      • Backward Compatibility – ASGI provides a WSGI wrapper, letting legacy frameworks run unchanged.

    • Common ASGI Servers

      • Uvicorn – High-performance asyncio/uvloop server; supports HTTP/1.1 & WebSockets Uvicorn site.
      • Daphne – Original Channels server; supports HTTP/1.1, HTTP/2, WebSockets Django docs.
      • Hypercorn – Sans-IO design, HTTP/1 → HTTP/3, WebSockets, optional Trio workers PyPI.
      • bareASGI / others – Experimental servers showcasing QUIC/HTTP-3 bareASGI guide.

    • What the Spec Does & Doesn’t Include

      • Included
        • HTTP/1.1 request–response cycle.
        • HTTP/2 streams (header ordering & multiplexing guidance).
        • WebSocket handshake and message events.
      • Not Explicitly Included
        • Server-Sent Events (SSE) – Possible at framework level; not mentioned in the core spec Community discussion.
        • HTTP/3 / QUIC – Outside 3.0 spec; available through server implementations (Hypercorn with aioquic).

    • Outside the Python Ecosystem?

      • Name-scope – ASGI is tightly bound to Python’s asyncio & typing; other languages use different gateways (e.g., Node’s http module, Go’s net/http). Referring to “ASGI” in non-Python contexts is uncommon; instead, concepts like “async middleware” or “actor gateways” are used.

    • Misconceptions

      • “ASGI replaces WSGI entirely” → It extends rather than replaces; many stacks run both side-by-side.
      • “ASGI natively handles SSE” → Not in spec; frameworks implement SSE atop HTTP streaming.
      • “All ASGI servers support HTTP/3” → Only some (Hypercorn) do; others remain HTTP/1.1 + WebSocket.

    • Related

      • WSGI · HTTP/3 explainer · Django Channels

  • Model Context Protocol (MCP) is a newer approach that allows AI or natural-language-driven clients (like ChatGPT plugins or Claude AI) to interact with services through a standardized interface. In the Toggl Track context, MCP servers act as an adapter on top of the Toggl API to interpret high-level commands (often in natural language) into Toggl actions. This can be useful if you want to control Toggl via conversational AI or integrate it into an AI agent workflow. Two notable MCP implementations exist for Toggl Track; narrative for each is on Toggl/MCP/Node/louis030195/toggl-mcp and Toggl/MCP/Python/jasleen19/toggl-mcp, under each page's AI/Response heading that cites this report.
  • Python: Officially, Toggl Track doesn't maintain an official Python SDK, but the community has the above-mentioned Toggl CLI (Python) Toggl/CLI/Python/AuHau/toggl-cli which doubles as a library. It provides Python classes for TimeEntry, Project, Client, etc., that you can create, fetch, update, and delete in your own scripts[1]. For example, you can do api.TimeEntry(description="New entry", start=..., stop=...).save() to create an entry, or call api.TimeEntry.objects.all() to list entries[1]. Similarly, api.Project.objects.get(id) and .save() let you update project details[1]. This essentially is an SDK built on the Toggl API. Another third-party library, toggl-track (PyPI) by Maurizio Branca, offers a Pythonic interface and CLI; however, it's relatively new (as of 2025) with fewer users[21]. For most Python integrations, using the toggl-cli's API wrapper or simply calling the Toggl REST endpoints via requests (with the official docs) are common approaches.
