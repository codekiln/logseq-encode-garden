  • LangChain Support Portal - How do I resolve S3 PutObject access denied errors when enabling LangSmith blob storage with KMS encryption requirements?
    • How do I resolve S3 PutObject access denied errors when enabling LangSmith blob storage with KMS encryption requirements?


      Context

      When enabling LangSmith blob storage with S3, you may encounter access denied errors if your S3 bucket has a resource-based policy that requires KMS encryption headers. The error typically appears as:

      AccessDenied: User: arn:aws:sts::account:assumed-role/langsmith-platform-backend-blob-storage-v2-environment/session is not authorized to perform: s3:PutObject on resource with an explicit deny in a resource-based policy

      This occurs when your bucket policy includes aDenyIncorrectEncryptionHeaderstatement that blocks PutObject requests without proper KMS encryption headers.

      Answer

      LangSmith now supports KMS encryption for S3 blob storage. To resolve this issue, configure KMS encryption in your LangSmith deployment:

    • Add the KMS encryption configuration to your LangSmith config:
      				  config:
				  blobStorage:
				    enabled: true
				    engine: "S3"
				    chSearchEnabled: false
				    bucketName: "your-bucket-name"
				    apiURL: "https://s3.your-region.amazonaws.com"
				    kmsEncryptionEnabled: true
				    kmsKeyArn: "arn:aws:kms:your-region:account-id:key/your-kms-key-id"
    • Ensure your IAM roles have the necessary KMS permissions in addition to S3 permissions:
    • kms:Encrypt
    • kms:GenerateDataKey
    • kms:Decrypt
    • Update your service account annotations with the appropriate IAM role ARNs for backend, platformBackend, and queue components.
    • Deploy the updated configuration and verify that objects are being created in your S3 bucket with KMS encryption.


      With KMS encryption enabled, LangSmith will include the required encryption headers in S3 requests, satisfying bucket policies that enforce encryption requirements. You should see objects appearing in your S3 bucket once the configuration is properly applied.

      • LangGraph graphs are not reusable, and overall the configuration approach is poorly designed · langchain-ai/langgraph · Discussion #3225
        • #1Password/Dev/op
          • With LangGraph it is impossible to build and share reusable graphs. What I mean by that is that I cannot build a graph and publish it as a package, so that it is easily redeployed somewhere else by someone else with a different base config.
          • Because the configuration = Configuration.from_runnable_config(config) will always use parent Configuration defaults defined in my package instead of enabling someone to import the graph and provide a different config
          • So there is unfortunately no way to compile a graph and pass it a different default configuration at compile time. It can only be done at runtime.
          • And every single node in the graph is then dependent on the original Configuration which cannot be overridden by anyone wanting to reuse our graph (because we need to do the ugly configuration = Configuration.from_runnable_config(config) at the start of each node to get the default configuration of the graph)
          • It's really bad design from the start for something as simple as a DAG workflow runner. And it's quite concerning because LangGraph is not doing much, it's just yet another DAG runner, but with less feature and that now requires proprietary paying components to be run (cf. #1604)
        • Commenter
          • I've run into this limitation multiple times and I agree there needs to be a way to set Configuration defaults at runtime.
          • On a related note, I haven't been able to get around this limitation when running graphs via Langgraph Studio. Since the configuration set at runtime is a configurable, I can't find a way to configure other RunnableConfig variables, like max_concurrency, at runtime in Studio.
LangSmith/26/09/29 Tue - Deep Agents
  • Managed Deep Agents
    • hosted runtime in LangSmith for creating, running and operating deep agents; CLI-first, in private preview as of the docs
    • provisions threads, runs, a store and a checkpointer
  • LangSmith/Deployment (docs) is built for scale and proven in production
    • 30+ endpoints for agents
    • integrations that are tricky to build yourself, like A2A and MCP; once in place, they give interoperability and make agents more useful
    • purpose-built task queues handle messages from users to the agent securely, reliably and at scale
      • Agent Server: Task queue
        • the API server enqueues each new run; a queue worker picks it up, takes a lease on it, runs the graph and writes checkpoints
        • at most one run executes per thread at a time
        • PostgreSQL holds run data and the queue state with exactly-once semantics; Redis carries only signaling, cancellation and streaming pub/sub
        • each worker runs up to 10 runs at once by default (N_JOBS_PER_WORKER)
      • Agent Server: Runtime architecture has three modes
        • single host: the API server runs the queue itself; the self-hosted default, for development and low traffic
        • split API and queue: queue workers on separate hosts; API servers scale on request volume, workers on pending run count
        • distributed runtime: orchestration and execution in separate processes, for high concurrency
      • the queue is what makes runs durable: any run can be retried, replayed or resumed from the point of interruption (Core capabilities)
    • SDKs for chat, streaming and AI/Workflow/Human in the Loop
    • all of this frees teams to focus on what makes their agent different
  • security and auth are built into Managed Deep Agents, to make deployment and auth for users as easy as possible
  • Agent Server: MCP endpoint at /mcp, over the Streamable HTTP transport
  • per the docs, an agent repo holds AGENTS.md and config and links to separate skill repos, each versioned and reusable across agents (Context Hub concepts)
    • LangSmith/Deep Agents can mount an agent repo as its filesystem with ContextHubBackend, with linked skills under /skills/
  • LangSmith showed the performance change with every change they made
  • bottom-up evaluation: sample a batch of conversations, have humans label them, then a process creates LangSmith evaluators that capture that signal automatically
    • this catches a new signal as behavior changes, and then they strengthen it
  • an experiment is the result of evaluating one version of the app on a dataset: outputs, evaluator scores and traces for every example (Evaluation concepts); two experiments on the same dataset can be compared side by side (Compare experiment results)
  • think in tiers: Managed Deep Agents can be expensive, but it gets you started quickly
  • try the latest LangSmith offerings (LangGraph, LangChain, LangSmith/Deep Agents) as experiments
    • if one works and needs to be faster or cheaper, there are ways to get there from that point
  • LangSmith deployments and Managed Deep Agents provision the checkpointer

LangSmith/Agent/Environment

  • LangSmith Agent Environment

    • Overview

      • In an agent-based LangSmith workspace, an agent identifies an application and an environment identifies where that application ran. Each trace belongs to one agent and one of its environments. LangSmith keeps their traces, alerts, evaluators, and built-in dashboards separate. Agents
      • The environment names are fixed: Production, Staging, Development, Local. They classify traces; choosing one does not change the application's code or instrumentation. Agent environments

    • How this differs from tracing projects

      • A project-based workspace groups traces in named tracing projects. A deployment in that model normally creates a same-named tracing project. An agent-based workspace groups traces under an agent and its fixed environments. These are different ways for a workspace to organize observability data. Observability concepts, LangSmith control plane
      • Agent-based workspaces are in beta. Enabling them for an organization affects new workspaces; existing project-based workspaces do not convert automatically. In the LangSmith UI, a workspace name in the top-left control indicates agent mode. The LangSmith logo there, together with an Application picker in the sidebar, indicates project mode. Agents, Observability concepts
      • The control-plane documentation still describes automatic creation of a tracing project named after each deployment. Read that statement in the context of the project-based model; it does not establish the trace destination of a deployment in an agent-based workspace. LangSmith control plane, Deploy to an agent environment

    • Agent, deployment, and revision

      • An agent has a stable identifier used by trace and deployment addressing, plus an editable display name. An agent created by a deployment, by a new-agent dialog, or by its first addressed trace starts with all four environments. An agent built in the LangSmith UI starts with Production; other environments appear when traces reach them. Agents, Create an agent
      • A deployment is a running Agent Server instance. It can be bound to one agent and one deployable environment: Production, Staging, or Development. Local is for traces from local runs and does not appear in the Deployments environment selector. A deployment has revisions: the initial server version and later iterations when code or secrets change. Deploy to an agent environment, LangSmith control plane
      • A deployment's type describes its hosting or capacity choice. Cloud documentation names Serverless and Dedicated; older deployment types include Development and Production. This setting is separate from the agent environment that receives traces. A deployment name containing stage, a Terraform environment tag, or a development-type capacity choice does not by itself prove that traces go to Staging. Cloud platform features, Deploy to an agent environment

    • Why one deployment can sit beside four environments

      • The four environment labels belong to the agent, not to a count of deployments. An agent created through a deployment begins with all four, even if only one deployment exists. Empty environment views mean no traces are visible there; their presence alone says nothing about which environment a deployment uses. Create an agent, Agent environments
      • LangSmith remembers different environment selections in different views. Tracing may open on Local or the last used environment, while Deployments may open on Production. Select the intended environment before interpreting an empty page. Agent environments

    • Binding and trace routing

      • The documented LangGraph and Managed Deep Agents deployment commands bind a deployment with an agent ID and an environment. Both flags must be supplied together; the allowed deployment environments are development, staging, and production. The agent's Overview lists bound deployments. The presence of the deployment in that list establishes the agent binding; inspect the selected deployment environment as well. Deploy to an agent environment
      • Application traces use agent addressing: LANGSMITH_AGENT_ID and LANGSMITH_AGENT_ENVIRONMENT, or an explicit agent address in code. The environment variable accepts local too. Both variables are required; setting only one leaves the call untraced. An address supplied in code takes precedence over the variables. Log traces to an agent
      • Project addressing uses a tracing project name instead. Agent and project addressing cannot be combined for one trace. A project name supplied in code can override agent environment variables. This matters when custom application traces and hosted Agent Server traces are inspected together. Log traces to an agent, Log traces to a specific project
      • To establish where a running deployment's traces land, inspect its agent and environment binding, then produce a known trace. Open that agent's Tracing view and select the expected environment. Check other environments and explicit trace-addressing settings if the trace is absent. An empty set of environment views cannot establish a destination. Deploy to an agent environment, Log traces to an agent

    • Terraform boundary

      • A Terraform deployment resource can describe a deployment's name and type without revealing its agent-environment trace binding. The documented agent binding uses deployment CLI flags. Check the Terraform provider schema and the resulting LangSmith agent Overview before treating Terraform configuration as evidence of that binding.
