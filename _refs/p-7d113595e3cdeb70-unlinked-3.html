Obsidian/Q/Should a team vault in git commit its community plugins' code, or only the list of plugins?

Page reference

  • Prompted by git status in a work team's knowledge garden on 2026-10-23: Obsidian had updated easy-copy, folder-notes and obsidian-git, so their tracked manifest.json files showed as modified and their main.js, styles.css and data.json showed as untracked.
  • The people opening these gardens include hackathon attendees using Obsidian for the first time.
  • Commit only the list of plugins and install the code with a mise file task, because plugin version bumps are frequent and not worth tracking. See My/Pref/Dev/Tool/Obsidian/Plugins in Git.

  • What Obsidian does with a fresh clone

    • Obsidian does not download a plugin that community-plugins.json lists but .obsidian/plugins/<id>/ lacks. Users in A single button click to reinstall all community plugins after cloning report that none of the plugins are installed after a clone. The thread runs from May 2025 to Aug 2026 and has no reply from Obsidian staff.
    • The older gardens' design says main.js and styles.css are files "that Obsidian re-downloads when plugins are installed". That holds only when someone installs the plugin by hand; nothing re-downloads them on clone.
    • When a vault arrives with plugin code present, Obsidian asks once whether to trust the author and turn on community plugins, or open the vault in restricted mode. See Plugin security. Restricted mode leaves the files on disk and ignores them.
    • Obsidian Sync handles this by syncing the installed plugins themselves, behind the "Active community plugin list" and "Installed community plugin list" options in Sync settings. Sync copies plugin code between devices; it does not keep just a list and fetch the code.
  • Obsidian Git's Tips and Tricks gives three .gitignore choices: all of .obsidian/, only .obsidian/plugins (to keep plugin settings that may hold secrets out of git), or only workspace.json. It does not split main.js from manifest.json.
  • In What should I gitignore for my vault's GitHub repository? (May 2025), the replies track plugin folders by default and ignore specific noisy or oversized files such as workspace.json and large index files.
  • A clone opens with plugins listed as on but not installed. Each person must install them from the Community plugins browser, run obsidian plugin:install (Obsidian 1.12.7+, desktop, after turning on the CLI in Settings), or run a script against the plugin registry.
  • The committed manifest records the version of whoever last updated, not the version anyone has installed. The 2026-10-23 diff was exactly this: three manifests changed by Obsidian's updater, with nothing that would install those versions anywhere else.
  • Ignore .obsidian/plugins and ship a bootstrap script.
    • Same newcomer cost as manifest-only, but with no misleading version record. Approach 4 in Obsidian/Q/How can an Obsidian vault declare the community plugins it depends on and install them by script? is such a script, and it can pin versions.
    • Community Install Manager, now in the community plugin directory, installs plugins and settings from two JSON files, but it must itself be installed first.
  • obsidian-git's data.json holds per-person choices such as auto-commit intervals, and some git plugins keep tokens there. Ignore it, along with obsidian_askpass.sh.
  • The older gardens dropped plugin code after obsidian-git's auto-backup committed its own bundle (commit d979078). With whole-folder commits that is the intended result, but auto-backup will also commit someone's plugin update without review. Turn off auto-commit in shared gardens, or review .obsidian/plugins diffs on pull requests.
  • Unverified: I did not open a fresh clone of a manifest-only garden to confirm the exact message Obsidian shows for an enabled plugin with no main.js, and I did not test the !plugins/folder-notes/data.json exception against the template's other ignore rules.
Obsidian/Q/Using the Obsidian CLI, what one-liner filters obsidian hotkeys to show only actually-mapped commands?

  • Using the Obsidian/CLI, what one-liner filters obsidian hotkeys to show only actually-mapped commands?

    • AI Answer

      • Short answer: obsidian hotkeys | awk -F'\t' '$2'
      • obsidian hotkeys outputs tab-separated lines: command ID in column 1, key binding (if any) in column 2. Unmapped commands have an empty second field. awk -F'\t' '$2' prints only lines where the second field is truthy (non-empty).
      • bash
        		  obsidian hotkeys | awk -F'\t' '$2'
      • Example output (mapped only):

      • Alternative using grep: obsidian hotkeys | grep -P '\t.+' — matches lines with at least one character after the tab.

Obsidian/Q/What Obsidian keyboard shortcuts are most useful for pointing to pages and headings when working with external agentic coding tools like Claude Code?

Page reference

  • Short answer: Obsidian has no built-in hotkey for these by default, but two built-in commands cover files and two community plugins fill the heading-link gap. Assign hotkeys to them in Settings → Hotkeys.

Obsidian/Q/What options do I have for publishing my obsidian vault as a web application

Page reference

  • You can treat “publish the vault as a web app” as a spectrum: hosted product, plugin-driven git deploy, or static-site generator (SSG) pipeline—each with different cost, fidelity to Obsidian features, and ops burden.
  • What it is: Obsidian’s built-in, managed publishing service (obsidian.md/publish)—enable from the app, pick notes, push updates (including mobile).
  • Best for: Lowest friction; readers get Obsidian-like UX (hover previews, graph view, stacked panes, backlinks) without you running infrastructure.
  • Digital Garden (oleeskild/obsidian-digital-garden) — mark notes with frontmatter (e.g. dg-publish: true), push to a GitHub repo, host on GitHub Pages / Netlify / Vercel. Selective publishing by default; widely used for digital gardens.
  • Enveloppe (enveloppe/obsidian-enveloppe) — publish notes to a GitHub repo from Obsidian; supports templates aimed at MkDocs, Hugo, Jekyll, etc.; converts wikilinks and can automate PR merges.
  • Selective Publisher (ivan1248/obsidian-selective-publisher) — filter by tags, paths, or frontmatter before pushing to git; pairs well with an SSG downstream.
  • Best for: Staying in Obsidian for “what goes public” while keeping hosting cheap (often free static hosting).
  • Tradeoffs: You maintain repo + hosting + plugin config; not every Obsidian plugin feature survives export.
  • QuartzMD (quartz.jzhao.xyz) — batteries-included SSG aimed at Obsidian vaults: wikilinks, backlinks, graph, search, SPA routing. Deploy to GitHub Pages, Netlify, Cloudflare Pages, etc. (Node v22+ per current docs).
  • Hugo / MkDocs / Jekyll / Astro / Eleventy — general SSGs; common pattern is export or sync vault → build → deploy. Examples in the wild: Hugo + obsidian-git + Cloudflare Pages (jasonheppler.org Obsidian–Hugo workflow); obsidian-export + Hugo (jacobian.org TIL); MkDocs-oriented tooling (dentropy/obsidian-publisher).
  • obsidian-export (zoni/obsidian-export) — CLI to turn Obsidian markdown into plainer markdown + frontmatter for Hugo and friends.
  • obsidian-hugo-export (sagarbehere/obsidian-hugo-export) — scripts for Hugo paths, wikilink → ref, backlinks, assets.
  • Best for: Vault stays canonical in Obsidian; CI or git hooks run the converter before hugo / mkdocs build.
  • Want Obsidian-native reading UX with minimal ops? → Publish.
  • Want free hosting + selective “public” notes from inside Obsidian? → Digital Garden or Enveloppe (+ GitHub Pages / Cloudflare / Netlify).
  • Want maximum control and Obsidian-like site features without Publish fees? → Quartz (or Hugo/MkDocs + export scripts).

  • GitHub Pages + Obsidian-native static site (recommended stack)

    • Primary pick: QuartzMD (Quartz 4) — SSG built for Obsidian vaults (wikilinks, backlinks, graph, search, popover previews). Official GitHub Pages path: fork/create a Quartz repo, point it at your vault content, add the deploy.yml workflow from Quartz hosting — GitHub Pages, set repo Pages → Source: GitHub Actions, set baseUrl in quartz.config.ts to your https://<user>.github.io/<repo>/ URL, then publish with npx quartz sync after edits. Requires Node v22+ and npm.
    • Typical Quartz + GitHub Pages workflow
      • 1. git clone https://github.com/jackyzha0/quartz.git → npm i → npx quartz create (imports or links vault markdown).
      • 2. Commit; enable GitHub Actions Pages deploy (workflow builds with npx quartz build, uploads public/).
      • 3. Keep editing in Obsidian; sync vault into the Quartz content directory (or use a separate content repo/submodule—many gardens symlink or copy content/).
      • 4. Push to the v4 branch (or whatever your workflow targets); site updates automatically.
    • Alternative on GitHub Pages: Digital Garden plugin — if you want selective publish from inside Obsidian (dg-publish: true per note) rather than building the whole vault, install oleeskild/obsidian-digital-garden, push to a GitHub repo, deploy gh-pages (or the plugin’s documented GitHub Pages flow). Less “full SSG control,” more “mark notes public in Obsidian.”
    • What to skip for this goal — raw markdown on Pages without an SSG (broken wikilinks); Hugo/MkDocs unless you already run an export pipeline (more glue than Quartz for Obsidian-first gardens). Obsidian Publish is not GitHub Pages.
    • Caveats — Community plugins (Dataview, Canvas, etc.) still do not execute on the static site; Quartz documents a trailing-slash quirk on GitHub Pages vs Cloudflare if you care about old URLs (hosting note).

QuartzMD/Plugin/bases-page
  • QuartzMD v5 plugin that renders Obsidian/Feature/Bases as HTML at build time, so a database view authored in Obsidian appears on the published site.
  • Why a build tool outside Obsidian can render a base at all: Obsidian/Explanation/What a Base Is.
  • Obsidian's own kanban layout writes type: kanban, and version 0.2.0 registers that layout under the id board. A view Obsidian saved as kanban therefore renders on the site as the words Unknown view type: kanban. A site can close the gap by registering kanban through the plugin's customViews option in quartz.ts, which takes a renderer and returns JSX.
QuartzMD/Q/Which Obsidian technique for rich todos renders on a QuartzMD site?
  • Short answer: put the fields in frontmatter and let Obsidian/Feature/Bases draw the view. Bases is core to Obsidian, its .base files and base code blocks are plain YAML, and QuartzMD/Plugin/bases-page renders them into HTML when the site builds. Everything else that makes a todo rich lives inside a plugin's own query engine, which never runs on a static site.
  • Quartz renders the Markdown that is on disk. Obsidian community plugins do not execute at build time, so a plugin whose value is a live query surface contributes nothing to the published page (Quartz — Obsidian compatibility).
  • Adds: priority, due date, status and tags as typed frontmatter properties, with filters, formulas, sorting, grouping, column summaries, and a kanban layout over them. Core plugin since Obsidian 1.9.0.
  • What still needs writing: Obsidian saves its kanban layout as type: kanban, and bases-page 0.2.0 registers that layout as board, so a kanban view reaches the site as the words Unknown view type: kanban. A customViews entry in quartz.ts registering kanban, or an upstream alias, fixes it.

  • Obsidian/Plugin/obsidian-tasks

    • Adds: fields on the task line itself — due, scheduled, start, done, priority, recurrence, dependencies — plus vault-wide tasks queries and custom checkbox statuses.
    • Raw Markdown: - [ ] Complete project report 📅 2026-09-16 ⏫, or the same fields as bracketed Obsidian/Plugin/Dataview inline fields.
    • On the site without help: the checkbox renders, and the fields render as the literal emoji and dates that were typed. Readable, and unstyled. A fenced tasks query renders as a code block showing the query.
    • What still needs writing: a stylesheet to turn the emoji into badges, and a Quartz transformer to parse the fields if the site wants to sort or filter on them. Nothing upstream does either.
    • In nvim: the line reads fine; the emoji are just characters.
    • The strength no other candidate has: a todo stays one line inside the page it belongs to.
  • What still needs writing: a transformer to strip or restyle the brackets, and something else entirely to answer the queries. Quartz Syncer is the existing answer — an Obsidian plugin that compiles Dataview output to static HTML before publishing — which moves the build into Obsidian.

  • Kanban plugins and Obsidian/Plugin/Obsidian Todoseq

    • Covered on Obsidian/Q/Does Obsidian have the ability to handle kanban-style TODO DOING DONE todos?. The short of it for a published site: obsidian-kanban board files degrade to headings and bullets and are looking for maintainers, Task List Kanban and Kanban Block produce no board at all, and TODOseq's keyword lines publish as plain list text. Bases now covers the same ground from core.
  • Adds: the properties themselves, with Obsidian's own typed property editor and its tag index.
  • Model a todo that deserves tracking as a page with status, priority, due and tags in frontmatter, and gather them with a base. Both halves are core Obsidian, both are plain text in nvim, and Quartz already renders both.
  • Keep - [ ] lines for the checklist inside a page, where the point is reading the page rather than querying across pages. If those lines need dates and priorities too, Obsidian/Plugin/obsidian-tasks emoji fields cost nothing on the site and can be styled later.
