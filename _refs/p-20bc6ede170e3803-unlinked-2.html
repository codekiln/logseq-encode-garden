  • Docling is an open-source Python library from IBM designed to "parse popular document formats, including PDFs, DOCX, and PPTX, with high speed and ease" (medium.com). It offers advanced document understanding and outputs well-formatted Markdown or JSON. Docling can be used via a simple CLI or as a Python API.
  • Comprehensive format support (PDF, DOCX, PPTX, etc.) in one tool​medium.com.
  • Outputs clean Markdown or JSON without manual intervention​medium.com.
  • Ideal Use: Docling is ideal for users who want an all-in-one, local solution to convert a collection of documents for LLM ingestion without setting up heavy AI models. It's especially useful if you plan to integrate with RAG pipelines (since it plays nicely with LangChain/LlamaIndex) or need to handle a variety of formats consistently. For example, you could point Docling at a directory of reports and quickly get structured Markdown files for each, complete with headings, lists, and tables preserved. If you need image captioning or extra refinements, you can extend it with its plugin/VLM system, though that requires more configuration. Overall, Docling provides a balanced, easy-to-use workflow covering the core needs (format support, structure, OCR) in an open and extensible package​medium.com​github.com.
  • Wide range of supported formats beyond just PDF/DOCX/PPTX (e.g. HTML, images, CSV/JSON to Markdown), which is useful if your directory has mixed content (linkedin.com linkedin.com).
  • Marker is a powerful open-source tool that prioritizes accuracy in converting documents to Markdown (and JSON/HTML) using advanced machine learning. It was developed by Vik Paruchuri and the Datalab team, and has quickly become known for handling extremely complex documents (academic papers, technical reports, etc.) with high fidelity. Marker uses a pipeline of deep learning models for layout analysis, OCR, table detection, math rendering, etc., and can optionally leverage an LLM for even better results (github.com (github.com).
  • Supports all required formats and more, including tricky ones like scanned images/PDFs and output to multiple formats (Markdown or structured JSON) (github.com). It uses a high-quality OCR (the "Surya" OCR toolkit) for scanning text, supporting many languages (github.com, github.com).
  • MinerU is another advanced open-source project that converts documents to Markdown and JSON, originating from the team behind the InternLM large model. It was "born during the pre-training process of InternLM", meaning it was developed to prepare high-quality text datasets (including scientific literature with symbols) for LLM training (github.com). MinerU is similar in spirit to Marker – using a combination of vision models and OCR to handle complex layouts – and it supports all three target formats among others.
  • Features: MinerU supports PDF (scanned or digital), Word (.doc & .docx), PowerPoint (.ppt & .pptx), and images (JPEG, PNG) as inputs (github.com). It provides a staged processing pipeline (with configurable "Stages") where each stage handles a task like layout detection, text extraction, table recognition, etc., and these can be customized or extended (github.com). It outputs structured data in multiple formats, notably "multimodal Markdown" (which likely includes text plus placeholders for images or special tokens) and JSON with reading order preserved (github.com). Key capabilities include advanced table extraction (they integrated models like RapidTable for faster table processing), and formula recognition – MinerU puts special focus on converting scientific formulas correctly into Markdown (potentially using LaTeX syntax) (github.com (github.com). Like Marker, it uses deep learning models (e.g., a YOLO-based layout model for page segmentation, a Unet model for formulas (github.com (github.com). It also provides visualization tools to verify the layout detected, which is useful for developers. MinerU can be used via a Python API – for example, it has a Dataset class to load a folder of documents and process them in bulk through defined stages (github.com). The project is licensed AGPL-3.0 (very open but requires derivative works to also open-source).

  • Large-scale or automated pipelines: If you plan to integrate this conversion into a larger system (say, an automated data ingestion pipeline that runs whenever new files are added), both Docling and MarkItDown have Python APIs you can call from your code github.com pymupdf.readthedocs.io. Docling's DocumentConverter can be invoked on each file programmatically (and even in an async fashion for speed), and MarkItDown's library can be imported to convert files in-memory. This might be preferable to calling subprocesses for each file if you want to avoid I/O overhead. Additionally, Docling's integration with frameworks means you can directly create LangChain Document objects from its output medium.com, which is convenient for building an LLM indexing pipeline. In an automated setting with ongoing document ingestion, consider using these programmatic interfaces and add a step to store metadata (like original file name, creation date) in the Markdown or as YAML frontmatter. Some tools don't do that by default, but you can easily prepend it; this helps trace answers an LLM gives back to the source document.
  • Using cloud services or paid solutions: If installing and managing these tools is not feasible (for example, you're on a restricted machine or the volume is small but the content is very tricky), you could use Azure Document Intelligence's Layout model via its API. Microsoft's cloud will handle PDF, DOCX, PPTX analysis and return a Markdown string for the content stackoverflow.com. The advantage is you get a highly robust parser with zero setup – it's the same service behind Form Recognizer, so it's enterprise-grade. The Markdown it returns is typically well-structured and includes tables (formatted in Markdown) and basic styling. You might still need to insert image links manually, as the API will not host images – but it can give coordinates or references for images if needed. The downside is cost: you pay per page processed, and you must send your documents to the cloud (which may be a security concern for sensitive data). A hybrid approach could be using MarkItDown locally and only falling back to Azure for files that MarkItDown flags as problematic. Likewise, other paid APIs like Google Document AI or Amazon Textract could be used, but they often output JSON rather than Markdown, requiring a custom conversion layer. Azure's ability to output markdown directly is a unique convenience in this context.

AWS/Secrets Manager/Q/What terms does AWS Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?
  • Short answer: there is no distinct secret type for this at the API level — every secret is one opaque AWS/Secrets Manager/Secret. Answer/Official from CreateSecret API reference: "Either SecretString or SecretBinary must have a value, but not both." "Single vs. multi-valued" is codekiln's own shorthand, mapped onto two garden pages: AWS/Secrets Manager/Secret/SecretString (AWS's Plaintext tab — one raw string) is single-valued; AWS/Secrets Manager/Secret/KeyValue (AWS's Key/value pairs tab — the same field holding a JSON object) is multi-valued.
  • Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs, or choose the Plaintext tab and enter the secret in any format." Its examples: an API key → key/value pairs (ClientID, ClientSecret); an OAuth token, certificate, or private key → plaintext.
  • AWS's ready-made rotation Lambda templates. Direct citations and the full picture — including a third, Lambda-less "managed rotation" path that's gated by how a secret was created, not by its shape: AWS/Secrets Manager/Secret/Rotation. Core citation: CreateSecret API reference: "you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret" for those templates to work. AWS/Secrets Manager/Secret/SecretString (single-valued/plaintext) can still be rotated, but only with a fully custom Lambda — there's no ready-made template for it.
  • Pulling one field without app-side parsing. Pass Secrets Manager secrets through Amazon ECS environment variables: "Specifies the name of the key in a key-value pair with the value that you want to set as the environment variable value. Only values in JSON format are supported." AWS/Secrets Manager/Secret/SecretString has no key to address this way. (fnox mirrors this client-side with its json_path option, per its provider docs, including dotted nested paths.)
AWS/Secrets Manager/Secret
  • AWS/Secrets Manager/Secret/KeyValue — a JSON object serialized into that same field (codekiln's multi-valued; AWS console's Key/value pairs tab).
  • The console nudges toward the key/value shape even outside a recognized database type. CreateSecret API reference: "If you create a secret by using the Secrets Manager console then Secrets Manager puts the protected secret text in only the SecretString parameter. The Secrets Manager console stores the information as a JSON structure of key/value pairs that a Lambda rotation function can parse."
  • The / in a name like myapp/database-url is not a path into a JSON object — it is one ordinary allowed character in one flat secret name. CreateSecret API reference: "The secret name can contain ASCII letters, numbers, and the following characters: /_+=.@-." There is no parent/child relationship between secrets in Secrets Manager; / is purely a naming convention people use to group related names, the same way S3 object keys use / without real folders existing.
AWS/Secrets Manager/Secret/KeyValue
  • The same AWS/Secrets Manager/Secret field (SecretString) holding a JSON object instead of a bare string, e.g. {"username":"admin","password":"secret"}. AWS's console calls this the Key/value pairs tab. Answer/Official from Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs..." — its example: an API key entered as ClientID / ClientSecret pairs.
  • codekiln's term for this: multi-valued. There is still exactly one SecretString — "multi-valued" describes how many named fields live inside that one JSON value, not a second storage mechanism.
  • Setting it: console → Store a new secret → Other type of secret → Key/value pairs tab. CLI → aws secretsmanager create-secret --name <name> --secret-string '{"key":"value", ...}' — any valid JSON object string. (Create an AWS Secrets Manager secret)
  • AWS's ready-made rotation Lambda templates for known database-credential shapes — but only one of three rotation paths, and only when the JSON matches the expected schema. Full breakdown with citations: AWS/Secrets Manager/Secret/Rotation.
  • Extracting one field by ARN suffix without app-side JSON parsing. Pass Secrets Manager secrets through Amazon ECS environment variables: "Specifies the name of the key in a key-value pair with the value that you want to set as the environment variable value. Only values in JSON format are supported." fnox mirrors this client-side with its json_path option (provider docs), including dotted nested paths.
  • Storing several related values as one billed resource instead of one per value. AWS Secrets Manager pricing worked example prices a secret "@ $0.40 / secret / month" — one JSON secret with several fields costs the same as one plaintext secret; splitting the same values into N plaintext secrets costs N times as much.
AWS/Secrets Manager/Secret/Rotation
  • You cannot get this by hand-crafting your own CreateSecret call, whatever shape you give it — it depends on which service's UI/API created the secret, not on JSON vs. plaintext. CreateSecret API reference, same page cited below for the schema requirement: "For secrets that use managed rotation, you need to create the secret through the managing service."
  • Every template on that list requires the secret to be an AWS/Secrets Manager/Secret/KeyValue whose JSON matches the expected credential schema (username, password, host, ...) — never a plain AWS/Secrets Manager/Secret/SecretString. CreateSecret API reference, the "For database credentials" paragraph: "For database credentials you want to rotate, for Secrets Manager to be able to rotate the secret, you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret."
  • Turn it on by attaching the function's ARN: aws secretsmanager rotate-secret --secret-id "myapp/database-url" --rotation-lambda-arn "arn:aws:lambda:...". --secret-id names one whole secret — the / inside "myapp/database-url" is not a path into a JSON object; see AWS/Secrets Manager/Secret on why it's just an allowed naming character. Rotation always replaces that one secret's entire SecretString, never a sub-key of it. Example command lifted from fnox's AWS Secrets Manager provider docs, under its "Secret rotation" heading.
  • On an AWS/Secrets Manager/Secret/KeyValue secret, a correctly written createSecret step reads the current AWSCURRENT JSON first and writes back the complete object with only the target field (e.g. password) changed. Secrets Manager itself performs no such merge — that is the function's own job, and it is exactly the job fnox skips, per the hazard noted below.
  • No ready-to-use rotation template for a plain single-string secret. Path 2's templates target the known database/service credential JSON shapes only — see the template list above; an AWS/Secrets Manager/Secret/SecretString holding a bare API key, OAuth token, certificate, or private key has no ready-made equivalent — only Path 3 (a hand-written function, possibly starting from the generic template).
  • fnox set overwrites a secret's entire SecretString with only the one value given on the command line — it has no read-merge-write for json_path. Verified directly in the fnox source at the commit this page cites: put_secret in aws_sm.rs does a bare put_secret_value/create_secret with whatever string it's handed, and the set command's call site passes it the one value the person typed, with no read-first step.
  • On an AWS/Secrets Manager/Secret/KeyValue secret, running fnox set SOME_FIELD newvalue --provider aws against one json_path-scoped field clobbers every other key in that JSON. This is the opposite of the createSecret step described in Path 3 above, which reads AWSCURRENT first and writes back the whole object with only the changed field touched — fnox set has no equivalent read step, rotation-aware or not.
AWS/Secrets Manager/Secret/SecretString
  • The AWS/Secrets Manager/Secret field holding one raw string, no internal structure — an API key, OAuth token, certificate, private key. AWS's console calls this the Plaintext tab. Answer/Official from Create an AWS Secrets Manager secret: "choose Other type of secret. In Key/value pairs, either enter your secret in JSON Key/value pairs, or choose the Plaintext tab and enter the secret in any format."
  • Setting it: console → Store a new secret → Other type of secret → Plaintext tab. CLI → aws secretsmanager create-secret --name <name> --secret-string '<raw value>' with any non-JSON string. (Create an AWS Secrets Manager secret)
  • Accepted values: any string, up to 64 KB. CreateSecret API reference: "Type: String Length Constraints: Minimum length of 1. Maximum length of 65536." Compare AWS/Secrets Manager/Secret/KeyValue — the same field, holding a JSON object instead of a bare string.

    • typescript
      	  import * as fs from 'fs';
	  
	  function extractJsonFromAmxd(amxdFilePath: string, outputJsonPath: string): boolean {
	      try {
	          // Read the .amxd file as a buffer
	          const data = fs.readFileSync(amxdFilePath);
	          let textData = data.toString('utf-8');
	  
	          // Find the start of JSON (first '{')
	          const jsonStart = textData.indexOf('{');
	          if (jsonStart === -1) {
	              console.error("Error: No JSON-like structure found in the .amxd file.");
	              return false;
	          }
	  
	          // Extract only the printable part after the first '{'
	          const jsonDataClean = textData.substring(jsonStart).replace(/[^\x20-\x7E\n\t]/g, '');
	  
	          // Attempt to parse JSON
	          let parsedJson;
	          try {
	              parsedJson = JSON.parse(jsonDataClean);
	          } catch (error) {
	              console.error("Error: Extracted content is not valid JSON.");
	              return false;
	          }
	  
	          // Save extracted JSON
	          fs.writeFileSync(outputJsonPath, JSON.stringify(parsedJson, null, 4), 'utf-8');
	          console.log(`Successfully extracted JSON saved to: ${outputJsonPath}`);
	          return true;
	      } catch (error) {
	          console.error(`Unexpected error: ${error}`);
	          return false;
	      }
	  }
	  
	  if (process.argv.length < 4) {
	      console.log("Usage: ts-node extractAmxdJson.ts <input.amxd> <output.json>");
	      process.exit(1);
	  }
	  
	  const inputAmxd = process.argv[2];
	  const outputJson = process.argv[3];
	  
	  const success = extractJsonFromAmxd(inputAmxd, outputJson);
	  if (!success) {
	      process.exit(1);
	  }

	  def extract_json_from_amxd(amxd_file_path, output_json_path):
	      """
	      Extracts the JSON content from a Max for Live (.amxd) file by removing its binary header.
	      
	      Args:
	          amxd_file_path (str): Path to the .amxd file.
	          output_json_path (str): Path to save the extracted JSON file.
	      
	      Returns:
	          bool: True if extraction and saving were successful, False otherwise.
	      """
	      try:
	          # Read the .amxd file as binary
	          with open(amxd_file_path, "rb") as f:
	              data = f.read().decode("utf-8", errors="ignore")  # Decode, ignoring errors
	  
	          # Find the start of JSON (first '{')
	          json_start = data.find("{")
	          if json_start == -1:
	              print("Error: No JSON-like structure found in the .amxd file.")
	              return False
	  
	          # Extract only the printable part after the first '{'
	          json_data_clean = re.sub(r'[^\x20-\x7E\n\t]', '', data[json_start:])  # Remove non-printable characters
	  
	          # Attempt to parse JSON
	          try:
	              parsed_json = json.loads(json_data_clean)
	          except json.JSONDecodeError:
	              print("Error: Extracted content is not valid JSON.")
	              return False
	  
	          # Save extracted JSON
	          with open(output_json_path, "w", encoding="utf-8") as out_f:
	              json.dump(parsed_json, out_f, indent=4)
	          
	          print(f"Successfully extracted JSON saved to: {output_json_path}")
	          return True
	  
	      except Exception as e:
	          print(f"Unexpected error: {e}")
	          return False
	  
	  
	  if __name__ == "__main__":
	      if len(sys.argv) < 3:
	          print("Usage: python extract_amxd_json.py <input.amxd> <output.json>")
	          sys.exit(1)
	  
	      input_amxd = sys.argv[1]
	      output_json = sys.argv[2]
	  
	      success = extract_json_from_amxd(input_amxd, output_json)
	      if not success:
	          sys.exit(1)  # Exit with error code if extraction fails

ChatGPT/Tool/Idea/Script/To Clean Up Output of Canvas/Report/Deterministic Markdown Formatters
  • Description: Dprint is a pluggable code formatting platform written in Rust. It's like an engine that can host multiple formatter plugins (including officially supported ones for JSON, TypeScript, HTML, etc.). There is an official dprint-plugin-markdown which formats Markdown files. Dprint's goal is to be extremely fast and easily integrable (plugins can run as WASM).
  • Configuration Options: Dprint allows configuring certain formatting decisions in a JSON config. For Markdown, you can set options like lineWidth (to wrap prose), whether to always add a blank line at end, etc. By default, dprint will wrap prose to 80 characters (if I recall correctly, dprint tends to wrap text where possible). However, it may also have a "preserve line breaks" option. This is configurable via the "markdown.textWrap" setting (auto, always, never). So you have flexibility similar to Prettier's proseWrap.
  • CLI & Integration: You'd install dprint (a single binary). To use the Markdown formatter, you add the markdown plugin in dprint.json (it can automatically fetch the plugin WASM). Then running dprint fmt will format all configured file types. Dprint integrates with pre-commit via the dprint hook (or simply as an entry: dprint fmt). It's cross-platform and doesn't require Node or Python at runtime.
  • Dprint for Polyglot Repos: If your repo has multiple languages (say Rust code, docs in Markdown, maybe JSON, etc.), adopting dprint can be efficient – one formatter config for everything. You can add a pre-commit hook for dprint:
    			  - repo: local
			  hooks:
			   - id: dprint
			     name: dprint formatter
			     entry: dprint fmt --check
			     language: system
			     types: [markdown, json, yaml, rust]

    Here language: system means it expects the dprint binary installed (you can also manage it via a cargo install or provide it in the environment). Dprint's dprint fmt --check will check formatting and dprint fmt (without --check) will write fixes. You might run dprint fmt locally and use --check in CI. Just ensure your dprint.json is configured for Markdown (you'd run dprint config add markdown once to set it up). Dprint is a bit more involved to configure initially than Prettier or mdformat, but it pays off with speed and one-tool integration.
