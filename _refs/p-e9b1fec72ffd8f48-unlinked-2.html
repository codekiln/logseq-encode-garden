  • The key distinction in this research is between BYOK transcription and the much weaker pattern of local/vendor transcription followed by BYOK text cleanup.
  • microphone → local application → endpoint/provider chosen by you → transcript
  • Actual transcription path: Local engines or cloud engines you configure. Its OpenAI Compatible add-on is explicitly usable as an STT engine, with server URL, optional API key, model selection, batch/realtime transport and OpenAI-compatible audio endpoints. [7]
  • Actual transcription path: BYOK audio goes straight to the provider whose key you entered, not through OpenWhispr. Supported BYOK providers include OpenAI, Groq, xAI, Mistral, Tinfoil, OpenRouter, Corti, Deepgram and AssemblyAI. Local transcription is also available. [13]
  • Keys / login / telemetry: Settings/provider keys are local in the direct configuration; account/auth is optional rather than required. Current architecture also has optional hosted/sync capabilities, so this has more privacy surface to configure than TypeWhisper. [22]
  • First, OpenWhispr's own cloud service is not BYOK. Its documentation makes the distinction unusually clear: Local sends audio nowhere; Self-Hosted sends it to your server; BYOK sends it directly to the third-party provider; OpenWhispr Cloud sends it through OpenWhispr's infrastructure. Therefore, an OpenWhispr recommendation only satisfies your requirement when configured for BYOK or Self-Hosted—not merely because the app happens to accept API keys elsewhere. [28]
  • Its provider architecture is especially well aligned with an organizational BYOK requirement. Under Settings → Integrations → OpenAI Compatible, you can create a profile with a server URL, optional API key, model and transport; model IDs can be discovered from /v1/models or manually specified. The server can be remote or local, but to serve as STT it must implement an OpenAI-compatible audio-transcription endpoint. That means an approved OpenAI endpoint, an internal gateway that emulates OpenAI's API, or a self-hosted service can all be first-class transcription destinations without TypeWhisper proxying the audio. [7]
  • The security characteristics are also unusually straightforward. TypeWhisper's security policy explicitly says API keys live in the macOS Keychain, its local HTTP API binds to 127.0.0.1 and is disabled by default, and exported diagnostics exclude API keys, audio payloads and transcription history. Its current product documentation states that there is no account requirement and no telemetry, and that cloud speech providers are used only after you add and select them. [8]
  • This is the clearest example of the distinction you asked me to police. Speech recognition itself is local WhisperKit. The OpenAI-compatible provider is for the optional AI rewrite/cleanup stage. Therefore it has BYOK text processing, not BYOK transcription, and is excluded from the primary list. [44]

ChatGPT/Plugin/How To/Develop and Share a Team Plugin for ChatGPT and Claude
  • Develop and test the plugin against editable files on the author's computer before publishing or sharing a release. This local edit-and-test cycle is an expected authoring step in both Claude and ChatGPT/Codex.
  • Claude Code can load the complete plugin directory directly. Local Codex can load skill directories directly; its marketplace workflow tests the complete plugin through a cached installation. A private local cache is an installation mechanism and does not require publishing to an account, workspace, or public directory.
  • A local checkout accessible to the test host. Use Claude Code for Claude directory loading and a supported local Codex session for OpenAI skill discovery. Account plugins in a web chat do not provide access to the checkout's working files.

  • 1. Describe the workflow and request local source files

    • In Chat or Work, select Plugin Creator from the @ menu. Describe the task, inputs, output, and how missing information should be handled. Attach a representative example. Ask for a local source package to edit and test before saving or publishing an account plugin.
    • Example brief:

      • Build a local source package called Team Design Review in plugins/team-review so I can edit and test its files before publishing. Given a design document and our review checklist, draft a review containing the problem, proposed behavior, unresolved decisions, and questions for the author. Cite supporting sections. Mark missing information explicitly. Use the attached example to demonstrate the output. Stop after local testing; account upload and sharing come later.

    • Review the generated instructions and supporting files. If the workflow needs an existing app, name the app and the information or actions it should provide.

  • 2. Define repeatable local checks

    • Keep a familiar input and an input with missing information beside the source package, with the expected output for each. Reuse these checks after every change to a skill, reference, script, or tool.
    • During the direct-source tests below, edit a working file, reload the relevant component, and rerun a check that exercises that edit. Verify the source path as well as the result. Complete this cycle in each target host before testing a release installation.
  • Each SKILL.md starts with YAML name and description, followed by the workflow. Keep references and scripts inside the package. Portable packages discover skills/ at its fixed location. OpenAI presentation settings belong under extensions.com.openai; older local clients can use a synchronized .codex-plugin/plugin.json compatibility manifest. Package format.

  • 5. Test the editable skill directory in local Codex

    • Expose each shared skill directory under the repo's .agents/skills/. Codex follows symlinked skill folders, so edits to the package's SKILL.md, references, and scripts remain edits to the files used by the discovered skill. This loads a plain skill; it does not activate the package's MCP configuration or hooks. Codex local skill discovery.
    • From the repo root, create this link if the destination does not already exist:
      • bash
        				  mkdir -p .agents/skills
				  ln -s ../../plugins/team-review/skills/team-design-review .agents/skills/team-design-review
				  realpath .agents/skills/team-design-review/SKILL.md
    • The resolved path should end in plugins/team-review/skills/team-design-review/SKILL.md inside the current checkout. Relative symlink targets are resolved from .agents/skills/. If the package lives under .claude/skills/team-review/, use ../../.claude/skills/team-review/skills/team-design-review as the target instead. Inspect any existing destination before changing it.

        				  [plugins."team-review@team-plugins"]
				  enabled = false
    • Also deselect account or workspace copies for the test chat where permitted. Repo configuration controls local-marketplace entries; it does not override workspace-managed installation state. Start a fresh local Codex chat in the checkout and explicitly select team-design-review from the skill picker. Restart Codex if discovery has not caught up.
    • Verify both the selected source path and behavior: temporarily add an instruction to the source skill to include LOCAL-DEVELOPMENT-CHECK in its review, run a representative review, and inspect which SKILL.md was loaded. The resolved file should be in the checkout, outside ~/.codex/plugins/cache/. Remove the test instruction after verification. Reading a file on demand alone does not demonstrate that the host selected it as the skill.

Direct Codex skill discovery and these filesystem checks apply to supported local sessions; a web or cloud account installation does not read the checkout automatically.

ChatGPT/Space/Q/Can we add information to ChatGPT Spaces from local folders? If so, how?

  • Can we add information to ChatGPT/Spaces from local folders? If so, how?

    • AI Answer

      • Short answer: Not as a folder. Space takes uploaded files and files from connected apps; neither OpenAI article on Space mentions uploading, syncing, or linking a folder on your computer. You can get a local folder's contents into a Space by uploading its files or by having ChatGPT write them onto a page.
      • Answer/Official from Getting started with Space in ChatGPT and ChatGPT Space
        • Space holds pages, uploaded files, and folders. Those folders are Space's own organizing folders, not folders on disk.
        • Files reach a page in two ways. An uploaded file follows the page's permissions. A file in a connected service, such as Google Drive, keeps that service's permissions, and a link to it does not let page readers open it.
        • The documented way to fill a page from material you have is to open a conversation, attach the files, and ask ChatGPT to create or update a page from them.
      • Ways to get a local folder in
        • Upload the files. Select the files inside the folder and attach them to a page or to a chat that creates the page. A third-party page, fast.io on upload limits, reports no folder upload in ChatGPT and a cap of 80 files every 3 hours; neither claim is confirmed by OpenAI.
        • Sync the folder to a connected service. Put the folder in Google Drive or another service ChatGPT connects to, then link or cite those files from a page. Edits on disk reach Space only through the sync, and readers need access in the source service.
        • Use a desktop local project as the bridge. A local project in the ChatGPT/App/Desktop gives its chats read and write access to folders on your computer, per Projects and chats. Ask a chat in that project to read the folder and write a page into a named space. Neither article says a local-project chat can create Space pages, so this route is untested.
      • Not verified
        • Whether a chat in a local project can write into Space.
        • Whether Space's upload dialog accepts a whole folder in the desktop app. Check it by dragging a folder onto a page.
ChatGPT/Tool/Idea/Script/To Clean Up Output of Canvas/Report/Deterministic Markdown Formatters
  • If you want more advanced formatting (semantic breaks, smart quotes): Flowmark is a compelling option. Since it's new, you'd add it as a local hook in pre-commit (there isn't an official hook repo yet). For example:
    				  - repo: local
				  hooks:
				  - id: flowmark
				    name: Flowmark Markdown Formatter
				    entry: flowmark --width 88 --semantic --smartquotes
				    language: python
				    types: [markdown]

    This assumes flowmark is in your environment (you might add additional_dependencies: [flowmark] under that hook to have pre-commit install it from PyPI). This will run Flowmark with your chosen options (here we enabled semantic line breaks and smart quotes). Flowmark will then reformat markdown files accordingly. Keep an eye on its repository for any changes in usage or new options as it develops.

  • Dprint for Polyglot Repos: If your repo has multiple languages (say Rust code, docs in Markdown, maybe JSON, etc.), adopting dprint can be efficient – one formatter config for everything. You can add a pre-commit hook for dprint:
    			  - repo: local
			  hooks:
			   - id: dprint
			     name: dprint formatter
			     entry: dprint fmt --check
			     language: system
			     types: [markdown, json, yaml, rust]

    Here language: system means it expects the dprint binary installed (you can also manage it via a cargo install or provide it in the environment). Dprint's dprint fmt --check will check formatting and dprint fmt (without --check) will write fixes. You might run dprint fmt locally and use --check in CI. Just ensure your dprint.json is configured for Markdown (you'd run dprint config add markdown once to set it up). Dprint is a bit more involved to configure initially than Prettier or mdformat, but it pays off with speed and one-tool integration.
