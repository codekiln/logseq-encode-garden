AI/Coding/Agents.md/Q/Does the AGENTS.md specification mention a global or home-directory-level AGENTS.md?

  • Does the AI/Coding/Agents.md specification mention a global or home-directory-level AGENTS.md?

    • AI Answer

      • Answer/Official from agentsmd/agents.md GitHub and agents.md
      • Short answer: No — the current AGENTS.md specification only addresses project-level (repository-local) files. Global/home-directory support is an open proposal (issue #91), not yet in the spec.
      • What the spec says about file discovery:
        • AGENTS.md files are discovered by walking the directory tree from the edited file upward to the Git root
        • The closest file wins; explicit user chat prompts override everything
        • Nested AGENTS.md files in monorepos are supported — the nearest file takes precedence for that subtree
        • No mention of ~ or system-wide paths in the specification
      • Each tool currently implements its own global path:
        • ~/.claude/CLAUDE.md — Claude/Code
        • ~/.codex/AGENTS.md — OpenAI Codex CLI
        • ~/.factory/AGENTS.md — Factory droid
        • ~/.config/AGENTS.md — Amp
      • Open proposal — issue #91:
        • Standardize global user-level AGENTS.md at ~/.config/agents/AGENTS.md (OPEN as of 2026-06-18)
        • Proposes ~/.config/agents/AGENTS.md (Linux/macOS, following XDG: $XDG_CONFIG_HOME/agents/AGENTS.md); %APPDATA%\agents\AGENTS.md on Windows
        • Uses a subdirectory (agents/) rather than a lone file to follow XDG convention and allow extensibility (rules/, commands/, templates)
        • Project-level config would take precedence over global; per-tool merging behavior left to implementors
        • Status: open, not yet merged into the spec

ChatGPT/App/Desktop/Q/When does AGENTS.md load in Work and Codex projects with multiple folders?

  • When does AGENTS.md load in ChatGPT/Work and Codex projects with multiple folders?

    • Can a project grant access to ten to fifteen repositories while loading each repository's AI/Coding/Agents.md only when work reaches that directory? Does attaching folders consume context up front, and is the trigger a directory change or a file access?

    • AI Answer

      • Short answer: Attaching secondary folders does not automatically import all their instructions. Automatic loading on first use of a secondary folder is not documented. File access and instruction discovery are separate.
      • Desktop projects: Answer/Official from Projects and chats and the multi-folder project release notes. The primary folder supplies new chats' working directory and automatic discovery of AGENTS.md, skills, and config.toml. Secondary folders remain available for searching, reading, and editing; Codex does not automatically discover those project files from secondary folders.
      • Codex timing: Custom instructions with AGENTS.md describes instruction discovery at startup, once per run, before work begins. It loads global guidance and the instruction files along the path from the project root to the working directory. This establishes startup behavior; it does not promise that a shell cd or an arbitrary file read in another repository triggers instruction injection.
      • Work timing: The installed desktop app, version 26.1007.30912, has separate primary-folder tooltips for Work and Codex. Both identify the primary folder as the source for AGENTS.md, config.toml, and skills. The strings are in app.asar, at webview/assets/app-initial-6350d04672d0.js, under projectSetup.createLocalProject.primarySourceWorkTooltip and projectSetup.createLocalProject.primarySourceCodexTooltip. This corroborates the primary-folder distinction for Work; the precise event that loads secondary-folder instructions in Work remains unverified.
      • Context cost: The documented discovery behavior gives no basis for expecting every attached repository's AGENTS.md to enter the initial prompt. Loaded primary-folder guidance still uses context, as do instructions or files subsequently read. This does not establish that attaching folders has zero overhead or quantify usage charges.
      • A workable arrangement: Keep shared guidance in a small primary-folder AGENTS.md, with a repository directory map and an instruction to read a target repository's AGENTS.md and applicable nested instructions before working there. Attach related repositories as secondary folders. This asks the agent to load guidance on demand; reliable automatic loading on first access remains an open product question. Starting a separate chat with the target repository as its primary folder gives that repository the documented discovery behavior.
      • Skills: Build skills documents progressive disclosure for both ChatGPT and Codex: skill names and descriptions are available initially, and the full SKILL.md is read when selected. Skills therefore have a discovery cost even before their full instructions load. Skill activation is based on relevance or explicit invocation, rather than merely changing directories.
      • Claude comparison: How Claude remembers your project documents startup loading for ancestor CLAUDE.md files and on-demand loading for descendant instructions when a file in that subtree is read, written, or edited. The documented trigger is file use, rather than cd alone. Additional directories supplied with --add-dir have separate memory-loading settings, so nested folders and additional repositories are distinct cases there too.
      • Still open as of October 15, 2026: Whether either desktop experience automatically injects a secondary repository's instructions on first access, which tools trigger that behavior, and whether instructions reload after edits. The available documentation supports the primary-folder rule but does not settle those secondary-folder events.
Claude/Code/Q/What is the MEMORY.md feature in Claude Code, can I customize where these files are stored, and is it based on an open spec like AGENTS.md?

  • What is the MEMORY.md feature in Claude/Code, can I customize where these files are stored, and is it based on an open spec like AGENTS.md?

    • AI Answer

      • AI/Response
      • Short answer: MEMORY.md is the index file for Claude Code's auto-memory system (v2.1.59+), stored by default at ~/.claude/projects/<project>/memory/. The location can be customized via autoMemoryDirectory in user settings. It is not based on an open spec — it is Anthropic-proprietary; AGENTS.md is an OpenAI/Codex convention for agent instructions, which Claude Code does not natively read.
      • What MEMORY.md is:
        • Auto memory lets Claude accumulate knowledge across sessions without manual effort — build commands, debugging insights, architecture notes, code style preferences, workflow habits
        • The memory directory holds MEMORY.md as a concise index plus optional topic files (e.g. debugging.md, api-conventions.md)
        • Only the first 200 lines (or 25 KB) of MEMORY.md are injected into context at session start; topic files are read on demand via file tools
        • Claude decides what is worth saving — it does not write to memory every session
        • Memory is machine-local and shared across all worktrees of the same git repository
      • Default storage location:
        • ~/.claude/projects/<project>/memory/ where <project> is derived from the git repo path
        • Example: /Users/you/.claude/projects/-Users-you-Documents-myrepo/memory/
        • Directory layout:
          • 				  ~/.claude/projects/<project>/memory/
				  ├── MEMORY.md          # concise index, loaded every session
				  ├── debugging.md       # topic file, read on demand
				  └── api-conventions.md
      • Customizing the storage location:
        • Set autoMemoryDirectory in ~/.claude/settings.json:
          • json
            				  {
				    "autoMemoryDirectory": "~/my-custom-memory-dir"
				  }
        • Value must be an absolute path or start with ~/
        • Accepted from policy settings and user settings (and --settings flag)
        • Not accepted from project or local settings — a cloned repo could otherwise redirect writes to sensitive paths
      • Toggle and inspect auto memory:
        • Auto memory is on by default; run /memory in a session to toggle it or browse saved files
        • Disable via settings: "autoMemoryEnabled": false or env var CLAUDE_CODE_DISABLE_AUTO_MEMORY=1
        • All memory files are plain Markdown — edit or delete them at any time
      • Is it based on AGENTS.md or any open spec?
        • No. MEMORY.md is proprietary to Claude Code's auto-memory system; there is no public specification
        • AGENTS.md is a convention from OpenAI/Codex for persistent agent instructions — a different concept (human-written rules, not agent-written notes)
        • Claude Code reads CLAUDE.md for instructions, not AGENTS.md; you can bridge both with @AGENTS.md inside CLAUDE.md so both tools share the same rules without duplication
        • No cross-agent open spec exists that covers MEMORY.md-style auto-written memory files
      • Sources: How Claude remembers your project — Claude Code Docs

My/Pref/Dev/AI/Config/Management/Use AGENTS.md Without Symlinks

  • Use AGENTS.md Without Symlinks

    • I prefer AGENTS.md as the neutral project instruction file. Use it alone where the selected clients read it; add a client-specific file only when it is needed.
    • When several client files must stay synchronized, use rulesync to generate ordinary files from one maintained source rather than linking AGENTS.md and CLAUDE.md with a symlink. This follows My/Pref/Dev/AI/Config/Management.

    • Why ordinary files

      • A repository should work on Windows without asking each contributor to enable Developer Mode, change symlink permissions or configure Git to create links.
      • Windows supports symlinks, but their creation depends on permissions and Git configuration. With core.symlinks=false, Git checks out the link target as plain text. A committed directory symlink does not automatically become a Windows junction. See Git for Windows: symbolic links and Git's core.symlinks setting.
      • macOS or Linux success does not establish native Windows compatibility. Test checkout, generation and client loading on Windows before claiming support.

    • When another client file is needed

      • Keep the authored instructions in .rulesync/rules/overview.md, with root: true in the frontmatter. Generate AGENTS.md and any needed client-specific files from that source; edit the source rather than the outputs.
      • Current Claude Code can read AGENTS.md directly, but certain CLAUDE.md and CLAUDE.local.md files take precedence. Check the selected version and actual loading before removing a compatibility file. Claude's instruction-loading rules.
      • Regenerate after source changes and through installed checkout and merge hooks. Check generated files for drift so copies do not become independently maintained instructions.
      • Declare shared skill sources through rulesync/Skill/Declarative Source instead of requiring skill-directory symlinks or a separate installer for each client.

    • Dotfiles example

      • The root rule is the authored source; rulesync.jsonc selects the project targets.
      • The Git hooks run mise x -- rulesync install followed by mise x -- rulesync generate after checkout and merge. mise.toml installs those hooks on entering the repository.
      • The global Rulesync configuration also declares external skill sources. Project configuration and global configuration have separate scopes.

Person/Przemysław Szypowicz/Blog/26/09/claude-code-reads-agents.md-only-when-telemetry-is-on

  • Claude Code reads AGENTS.md only when telemetry is on

    • Summary

      • Claude Code 2.1.277 announced AI/Coding/Agents.md support, but the loader ships as a built-in plugin gated on a remote feature flag. With telemetry or nonessential traffic disabled, a local AGENTS.md is skipped and nothing says so.
      • The author measured the behavior against Issue #95690 and posted his results there before collecting them here.

    • Notes

      • Where the gate sits

        • The loader is a built-in plugin named agents-md. In the 2.1.280 bundle its isOnByDefault is false, and isAvailable asks a remote flag tengu_agents_md_mod with false as the fallback. A flag that cannot be fetched leaves the plugin unavailable and the local file unread.

      • What he measured

        • A directory holding only an AGENTS.md with a canary word, queried with claude -p. Each configuration needed two sessions, because the first only fetches the flag.
        • CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 blocks the feature, as the issue reports.
        • DISABLE_TELEMETRY=1 blocks it as well, so both had to be cleared.
        • Setting either variable to 0 does not re-enable it — any value counts as set.
        • An env block in a project's .claude/settings.json clearing both has no effect, so there is no per-repo override.
        • claude --settings '{"env":{"DISABLE_TELEMETRY":"","CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC":""}}' does work, from the second session on.
        • The same gate reaches third-party gateways, Claude/Code/Bedrock and Vertex, where the flag cannot resolve to true either.

      • The workaround

        • CLAUDE.md supports @path imports, which do not consult the flag. echo '@AGENTS.md' > CLAUDE.md loads the file with telemetry off, at the price of the extra file that AGENTS.md support was meant to remove.

      • The argument

        • A privacy setting should not switch off unrelated local behavior. Reading a file from the working directory needs no network, yet waits on a server-side switch.
        • The gate lands hardest on the people most likely to want AGENTS.md: anyone keeping one instruction file for several agents is usually deliberate about what each tool sends home, and teams on Bedrock, Vertex or a gateway often disable nonessential traffic by policy.
        • Silence is the sharpest complaint. Without a canary test and a string search through the binary, the symptom reads as a model ignoring instructions, and the time goes into prompts rather than the file that never arrived.
        • His asks: make a local file's loading independent of telemetry, or at minimum warn at startup when an AGENTS.md is present and skipped; and add a user-level AGENTS.md beside the user CLAUDE.md, as Codex has at ~/.codex/AGENTS.md.
