	  function extractJsonFromAmxd(amxdFilePath: string, outputJsonPath: string): boolean {
	      try {
	          // Read the .amxd file as a buffer
	          const data = fs.readFileSync(amxdFilePath);
	          let textData = data.toString('utf-8');
	  
	          // Find the start of JSON (first '{')
	          const jsonStart = textData.indexOf('{');
	          if (jsonStart === -1) {
	              console.error("Error: No JSON-like structure found in the .amxd file.");
	              return false;
	          }
	  
	          // Extract only the printable part after the first '{'
	          const jsonDataClean = textData.substring(jsonStart).replace(/[^\x20-\x7E\n\t]/g, '');
	  
	          // Attempt to parse JSON
	          let parsedJson;
	          try {
	              parsedJson = JSON.parse(jsonDataClean);
	          } catch (error) {
	              console.error("Error: Extracted content is not valid JSON.");
	              return false;
	          }
	  
	          // Save extracted JSON
	          fs.writeFileSync(outputJsonPath, JSON.stringify(parsedJson, null, 4), 'utf-8');
	          console.log(`Successfully extracted JSON saved to: ${outputJsonPath}`);
	          return true;
	      } catch (error) {
	          console.error(`Unexpected error: ${error}`);
	          return false;
	      }
	  }
	  
	  if (process.argv.length < 4) {
	      console.log("Usage: ts-node extractAmxdJson.ts <input.amxd> <output.json>");
	      process.exit(1);
	  }
	  
	  const inputAmxd = process.argv[2];
	  const outputJson = process.argv[3];
	  
	  const success = extractJsonFromAmxd(inputAmxd, outputJson);
	  if (!success) {
	      process.exit(1);
	  }

Claude/Code/Plugin/Marketplace/Auto-Update
  • The use case: a team publishes a Claude/Code/Plugin to a private Claude/Code/Plugin/Marketplace, and everyone consuming it through the Claude/Desktop/Code tab (Windows and macOS) should end up on each new version without manual steps.
  • Bottom line (as of 2026-07-28 Tue): the marketplace file itself cannot declare auto-update, and the built-in per-marketplace auto-update is unreliable for third-party marketplaces — it refreshes the catalog but often fails to move installed plugins forward, silently. The dependable path is version discipline in CI plus a small updater shipped in the marketplace. On macOS that updater runs as a SessionStart hook; on Windows, where plugin hooks silently do nothing before Desktop v1.24012.9, the same script runs instead as a logon Claude/Desktop/Scheduled Task — a delivery path that does not depend on the app's hook system.
  • LayerLocationWhat it is
    Catalog~/.claude/plugins/marketplaces/<name>/A git clone of the marketplace repo. Holds marketplace.json.
    Installed plugin~/.claude/plugins/cache/<name>/<plugin>/<version>/A frozen copy of the plugin at one version.
    Registry~/.claude/plugins/installed_plugins.jsonPoints each installed plugin at its active installPath and version.
  • An update must do both moves: refresh the catalog so the new version becomes visible, and re-install the plugin into a new cache/.../<new-version>/ directory with the registry repointed. The common failure is move 1 happening while move 2 does not — the catalog advances and the running plugin stays put.
  • Version resolution (first one set wins): version in plugin.json → version in the marketplace entry → the git commit SHA. When the resolved version equals the installed one, the update is skipped. That resolution is the lever an author controls.
  • Author control: there is no autoUpdate field in the marketplace.json schema. The marketplace file cannot enable auto-update for the people who add it — that is an installer-side setting. What the author sets is the version numbers.
  • Catalog is fetched but never pulled, so the working tree never advances and the version bump is never seen locally. #49410
  • autoUpdate promotes the runtime version but does not rewrite installed_plugins.json, so bundled hooks stay pinned to the old path; it also runs before SessionStart. #52218

  • Layer 1 — Version discipline

    • Set an explicit version in each plugin's plugin.json and bump it (semver) on every release. A commit without a version bump delivers nothing to existing installs.
    • Automate the bump in CI (conventional-commits → a release bot that bumps plugin.json, syncs marketplace.json, and tags a release) so there is no manual step.
    • Trade-off: omitting version and falling back to the commit SHA makes every commit an update, which suits fast iteration but interacts badly with the fetch-not-pull bug and makes the deployed version hard to read at a glance. For a team marketplace, explicit semver is the safer default.
  • Reads installed_plugins.json (the registry) and the catalog's marketplace.json, and for each installed plugin from this marketplace compares the installed version to the catalog version.
  • When they differ, copies the fresh plugin files into a new cache/<marketplace>/<plugin>/<version>/ directory and repoints the registry entry's version and installPath at it.
  • json
    				  {
				    "name": "updater",
				    "version": "1.0.0",

  • Windows delivery — logon Scheduled Task. Place the script at a fixed path (the plugin cache path changes each version, so a task must not point there) and register a per-user task that runs it at logon; IT can push both steps fleet-wide via MDM. The task updates the on-disk marketplace and registry, and the desktop app picks up the change on its next Code session launch. macOS needs no task; for the same interval behaviour on macOS, run the script from a LaunchAgent or cron.
  • One-session lag. On macOS, version resolution runs before SessionStart hooks (#52218); the hook writes the fresh version to disk, and a session that already loaded the old one picks it up on next launch. The Windows Scheduled Task runs at logon, before any session, so it avoids this.
  • MCP-bearing plugins. Close and reopen the Code session to load the new version. Skills, commands, and agents are lighter but safest to pick up on relaunch.
  • GUI: Plugins → Installed shows each plugin's version and Marketplaces shows the catalog. If Installed lags the catalog, hit Update and relaunch the session.
  • Scriptable: read installed_plugins.json and the catalog's marketplace.json, and for each plugin from the marketplace print its installed version beside its catalog version. Matching pairs are current; a mismatch means the re-install move did not land.

  • Why /plugin update may not help either: Claude Code decides whether an update is needed by comparing the plugin's resolved version, checked in this order: plugin.json version → marketplace-entry version → git commit SHA (only for github/url/git-subdir/relative-path sources inside a git-hosted marketplace) → unknown for local directories that aren't inside a git repo. A plain local-path marketplace with no explicit version set always resolves to unknown on both sides of the comparison, so /plugin update (and background auto-update) reports "already at the latest version" and skips the re-copy.
  • How auto-update interacts with this: auto-update doesn't diff file contents — it re-runs the same version comparison as /plugin update, just on a timer, so it inherits the same blind spot.
    • It's off by default for exactly this kind of marketplace: "official Anthropic marketplaces have auto-update enabled by default. Third-party and local development marketplaces have auto-update disabled by default." Turn it on per marketplace via /plugin → Marketplaces → select the marketplace → Enable auto-update (or, for a team, an admin sets "autoUpdate": true on that marketplace's extraKnownMarketplaces entry in managed settings).
    • Even enabled, whether it can ever notice the edit depends on what my-marketplace/ actually is:
      • Plain directory, no .git: version stays unknown forever, so enabling auto-update changes nothing — there's no version delta for it to detect, ever.
      • my-marketplace is itself a git repo (even with no remote) and the plugin uses a relative-path source: version resolves to that repo's commit SHA, so saving SKILL.md alone still doesn't change anything — you must git commit the change. Once committed, auto-update's next background pass (or a manual /plugin update) sees a new SHA and re-copies.
      • Explicit version set in plugin.json/the marketplace entry: same rule as manual update — auto-update only fires when that string is bumped.
    • Timing, when it does apply: "Claude Code checks for marketplace and plugin updates after your session starts, with a random delay of up to ten minutes, so the running session keeps using the versions it loaded at launch. If any plugins were updated, you'll see a notification prompting you to run /reload-plugins, or the new versions load on your next launch."
    • Net effect for local plugin development: auto-update is built to keep other people's marketplaces fresh in the background, not for a tight edit-save-test loop. Best case (git-backed marketplace, auto-update on) still needs a commit and a ≤10-minute wait before a notification; worst case (plain directory) it never helps at all. --plugin-dir (below) sidesteps all of this.
  • 1. Reinstall: /plugin uninstall my-plugin@my-marketplace then /plugin install my-plugin@my-marketplace. This forces a fresh copy into the cache regardless of the version string. The uninstall command's --keep-data flag exists for exactly this case — the docs note it's for "reinstalling after testing a new version" — to preserve ${CLAUDE_PLUGIN_DATA} across the reinstall.
  • 2. Or set an explicit version in plugin.json (or the marketplace entry) and bump it on every change, then run /plugin marketplace update my-marketplace followed by /plugin update my-plugin@my-marketplace (or let auto-update apply it once enabled for that marketplace).

Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?
  • Answer/Official from Package your plugin — How local marketplaces work, checked October 15, 2026: installed plugins live under ~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/; local plugins use local as the cache directory's version segment. The runtime reads that installed copy.
  • The Codex cache-refresh implementation has both version-conditional refresh and forced reinstall paths. Version-conditional refresh skips installation when the active version matches the source version. A saved file alone therefore does not guarantee that every refresh path copies the change.
  • The authoring documentation recommends restarting the desktop app after source changes. If the old behavior remains, bump the package version and reinstall through the plugin browser, then start a new chat. Verify the changed skill or tool behavior in that chat.
