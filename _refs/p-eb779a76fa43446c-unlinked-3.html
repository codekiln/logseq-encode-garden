git/Alias/md-url
  • git git/Alias GitHub CLI yazi/Keyshort/Copy GitHub markdown link
    • git md-url — markdown link to a path's GitHub web view #card
      • Command: git md-url [--no-copy] <path>...
      • Context: User-defined alias in the chezmoi-managed ~/.gitconfig, backed by ~/.config/git/scripts/generate_markdown_path_link.zsh. Sits beside git md-commit (which links the most recent commit), so the family is enumerable with git md-<TAB>. Clipboard writes route through the sibling git copy-text alias, which picks pbcopy / wl-copy / xclip per platform.
      • Description: Emits [<repo>/<path-from-repo-root>](<github-url>) for each path given — files and directories alike — printing to stdout and copying to the clipboard. --no-copy prints only, for pipelines. Several paths yield one link per line. The URL targets the repository's default branch, never the checked-out branch, since a link into an unpushed branch is a 404 for everyone else.
      • Cost: one network round trip per invocation, ~0.7s, regardless of how many paths are passed. The default branch resolves offline from refs/remotes/origin/HEAD; the base URL comes from a single gh browse -n call and every link is concatenated onto it.
      • Fails loudly: not a repository, no GitHub remote, a path outside the repository, or a missing gh all produce a message on stderr and a non-zero exit, leaving the clipboard untouched. A wrong link is not obviously wrong at paste time, so copying nothing is better.
      • My Notes Bound in yazi as yazi/Keyshort/Copy GitHub markdown link (c then g). The script strips GITHUB_TOKEN / GH_TOKEN itself rather than relying on the gh shell wrapper in .zshrc — that wrapper only exists for interactive shells, so a script behind a git alias would otherwise get the raw binary with the tokens still set.

Glow/Q/How do I use Glow as a default pager for markdown documents when I'm in a terminal?

  • How do I use Glow as a default pager for markdown documents when I'm in a terminal?

    • My Notes

      • 2026-03-23 Mon (“starting to enjoy Glow”).

    • Answer

      • AI/Response
        • Two different meanings of “pager” matter here: (1) when you run glow, you can make its output go through a pager; (2) setting PAGER=glow makes other programs call glow the way they call less — that second case is only sometimes safe, because many tools pass less-specific flags or non‑Markdown content to $PAGER.
        • Use Glow’s own paging (recommended for Markdown you open with glow):
          • CLI: run glow -p (or glow --pager) so rendered Markdown is piped through $PAGER. If $PAGER is unset, Glow defaults to less -r (ANSI‑aware), per the upstream README.
          • Persistent default: run glow config (or edit glow.yml in Glow’s config dir — see glow --help for paths) and set pager: true so you do not need -p every time. Optional: set style, width, etc. in the same file. Glow README — Config File
          • What $PAGER means here: it is the outer pager Glow invokes after rendering (usually still less -R / less -r so colors survive). Glow is not replacing less in that pipeline unless you point $PAGER at something else.
        • Using glow as the global PAGER for the whole terminal (usually a bad default):
          • Tools like git, man, and systemctl often expect a less(1)-compatible pager (options like +line, --, etc.). PAGER=glow can break those flows or render non‑Markdown as if it were Markdown.
          • If you only need stdin as Markdown, some invocations work with glow - (Glow reads - as stdin in the README), but flag compatibility remains the main problem for a global default.
        • Practical patterns for “Markdown in the terminal” instead of a global PAGER:
          • Shell alias or function, e.g. treat “open this .md” as glow -p file.md or glow -p "$@".
          • Git only: consider git config core.pager 'glow -p' (or a small wrapper) if you accept breakage on non‑Markdown pager use cases — many people keep Git on less and use glow only for *.md.
        • Sources:
          • Glow README — Paging, CLI, config pager:
          • charmbracelet/glow issue #109 — -p and $PAGER

Google/Drive/Q/Does Google Drive render relative Markdown links and image embeds?
  • Answer/Official from Use Markdown in Google Docs, Slides, & Drawings, Import and export Markdown in Google Docs, Compose with Markdown in Google Docs on web, and Google Drive API export formats
  • Short answer: No. ![image](./path-to-image.jpg) does not render on any Google Drive surface, and [text](./other-note.md) never becomes a working link to the sibling file. A relative path needs a base directory to resolve against, and no Drive surface supplies one — Drive's viewer never interprets the Markdown at all, and Google Docs converts an imported file into a standalone document with no memory of the folder it came from.
  • "Google Drive renders Markdown" describes three different surfaces that behave differently. Answering each separately matters, because only one of them interprets Markdown syntax at all, and even that one is documented not to handle images.
  • Relative links: no. Relative image includes: no. Neither is interpreted, because nothing interprets the Markdown.
  • Verified — the documentation is silent. Google's file types you can view in Drive covers "videos, PDFs, Microsoft Office files, audio files, and photos" and never mentions Markdown. Use Markdown in Google Docs, Slides, & Drawings routes a .md file in Drive through Open with > Google Docs rather than any Drive-native rendering. No Google page documents a Markdown renderer in the Drive viewer, and none documents its absence either.
  • Inferred — Drive shows .md as raw text. This rests on secondary evidence rather than documentation: browser extensions exist for the sole purpose of fixing it, and describe the default behavior directly. Markdrive states "Google Drive shows .md files as raw text," and Google Drive Markdown Preview exists to render .md in Drive preview mode. If the source is displayed verbatim, the literal characters ![image](./path-to-image.jpg) appear on screen — the question of resolving the path never arises.
  • Verified — what the syntax list covers. Use Markdown in Google Docs, Slides, & Drawings documents headings (# through ######), italics, bold, strikethrough, and links in the [text](url) form. The word "image" does not appear anywhere on that page, and neither does any ![...] syntax. The July 2024 announcement that shipped import and export names no supported or unsupported elements at all.
  • Verified — import is real and is a one-way conversion. File > Open > Upload in Docs, or right-click > Open with > Google Docs in Drive. The result is a Google Doc, not a view of the .md file. The Drive API export table lists text/markdown (.md) as one of eight Docs export formats, alongside .docx, .odt, .rtf, .pdf, .txt, .epub, and zipped HTML.
  • Inferred — images do not come across. The syntax list omits them, and users report the omission as behavior: Google Docs Paste From Markdown Local Images Do Not Paste in the Docs Editors community. A Docs engineer commenting on the Hacker News thread about the launch said only that "Import supports links via upload," which is too thin to build on and appears in no Google documentation. Treat image import as undocumented and unreliable.
  • Not documented, but stated publicly by a Docs engineer — the reverse direction inlines rather than references. Exporting a Doc to Markdown produces base64 data URIs, collected as reference-style links at the bottom of the file: "Export outputs base64 encoded image URLs. We use Markdown reference links to place the large URLs out of the way of reading at the bottom of the file." Users in the SilverBullet community report a 16 MB .md from a single illustrated document. So a round trip never yields a relative ./image.jpg path in either direction — Docs has no concept of a sibling asset file.

  • 3. Markdown pasted into an open Google Doc

    • Relative links: same as import — a hyperlink that does not point at the sibling file. Relative image includes: no.
    • Verified — the feature and how to turn it on. Enable under Tools > Preferences > Enable Markdown, then right-click and choose Paste from Markdown (Docs Editors Help). The July 2024 post notes that Copy as Markdown and Paste from Markdown ship off by default, while import and export are on. Paste-as-Markdown itself dates to the March 2022 rollout.
    • This is the weakest surface for the question, and the reason is structural. A paste has no source file, so there is no folder for a relative path to be relative to — not even in principle. The clipboard carries text; ./elevation-profile.jpg arrives with no way to locate the directory the note came from.
    • Inferred — images are dropped. Same evidence as import: the documented syntax list has no image form, and the community thread above reports local images failing to paste.
  • Convert the vault into Google Docs and insert images natively. Cost: you stop having a Markdown vault. Links between notes become Doc URLs maintained by hand, the sibling-file structure disappears, and there is no clean path back. This is the only option that makes images actually render inside a Google surface.

LazyVim/Q/Does LazyVim support indenting with tabs the way Logseq expects? If so, how do I indent and de-indent with tabs in markdown?

Page reference

  • Does LazyVim support indenting with tabs the way Logseq expects? If so, how do I indent and de-indent with tabs in markdown?

    • AI Answer

      • Short answer: Not out of the box. Logseq writes one literal tab per nesting level, but LazyVim opens markdown with expandtab on and shiftwidth=2, so >> inserts two spaces. Drop an .editorconfig with indent_style = tab at the graph root and the same keys — >> / <<, visual > / <, insert-mode Ctrl-T / Ctrl-D — start writing real tabs.

      • Why the default is spaces

        • Neovim's own ftplugin/markdown.vim would force setlocal expandtab tabstop=4 softtabstop=4 shiftwidth=4, but only when g:markdown_recommended_style is truthy.
        • LazyVim sets vim.g.markdown_recommended_style = 0 in lua/lazyvim/config/options.lua, so markdown buffers skip that block and simply inherit LazyVim's globals from the same file: expandtab = true, shiftwidth = 2, tabstop = 2, smartindent = true.
        • Net effect in a markdown buffer: expandtab on, shiftwidth=2, tabstop=2, softtabstop=0 — two spaces per level. :verbose set expandtab? reports ftplugin.vim as the last setter.

      • Switching the graph to tabs

        • Answer/Official from :help editorconfig: "after running ftplugins and FileType autocommands, the EditorConfig feature searches all parent directories of that file for .editorconfig files, parses them, and applies their properties." Running last is what makes it win over both the runtime ftplugin and the LazyVim globals. An .editorconfig at the graph root scopes the change to the graph and carries to other editors:
          • ini
            				  [*.md]
				  indent_style = tab
        • With that in place >> on a bullet writes a literal \t, and :verbose set expandtab? names editorconfig.lua as the setter.
        • Per-machine alternative — ~/.config/nvim/after/ftplugin/markdown.lua with vim.opt_local.expandtab = false. Simpler, but it applies to every markdown file, not just the graph.
        • Keep shiftwidth equal to tabstop and leave softtabstop=0, so one indent level is exactly one tab and Vim never pads a level with a mix of tabs and spaces.

      • Indenting and de-indenting

        • Normal mode: >> indents the line one level, << outdents. Take a count or a motion for more: 3>> for three lines, >ip for the paragraph. See vim/Keyshort/Indent.
        • Visual mode: V to select whole lines, then > / <. LazyVim remaps these to >gv / <gv in lua/lazyvim/config/keymaps.lua, so the selection survives the shift — >>> walks a whole subtree out three levels without reselecting.
        • Insert mode: Ctrl-T indents and Ctrl-D outdents the current line. This is the closest analogue to Logseq's Tab / Shift-Tab, and it beats <Tab> in practice because it works from anywhere in the line rather than only at column 1. Neither key is remapped by LazyVim.
        • Insert-mode <Tab> at the start of a line does insert one indent level, but blink.cmp claims <Tab> first for completion accept and snippet jumps and only falls through to a literal tab when no menu is open — so it is the least predictable of the three.
        • > and < shift the entire line including the - bullet marker, which is exactly the nesting move Logseq performs.
        • :set list renders tabs as visible glyphs, useful for confirming a page really uses tabs rather than spaces.

  • The markdown_inline treesitter highlights query tags the entire [text](destination) node with its destination, so gx fires from the label as readily as from inside the parentheses. It needs treesitter highlighting live on the buffer, which the Markdown extra provides.
  • A language server advertising textDocument/documentLink would take priority over the treesitter path. Marksman does not advertise it, so on a Markdown buffer here the treesitter path is always the one that runs.

  • The gaps are real: suffixesadd is empty for Markdown, so an extensionless ./file fails until it is set to .md; and a destination containing a space never resolves, with or without the <…> escape, because the filename is read through isfname, which stops at the space.
