  • Release tmux v3.7b · tmux/tmux-builds
    • My Notes
      • I encountered some rendering errors in tmux/v/3.7a.
      • For some reason, my mise/Config/mise.toml/Global/Lockfile had pinned tmux to 3.7a, and mise upgrade tmux / mise upgrade tmux --bump both kept reporting "up to date" even after 3.7b was out — see mise/Config/mise.toml/Global/Lockfile for why.

      • Symptom

        • yazi and Lazygit opened to a blank pane inside tmux, but rendered immediately in a plain Ghostty window outside tmux.
        • Entering tmux copy-mode and leaving it again made the UI suddenly appear — the frame had been drawn the whole time, tmux just never flushed it to the client.

      • Root cause

        • 3.7 added tmux support for synchronized-output escape sequences (DECSET 2026), which yazi and lazygit use to paint a full frame atomically.
        • 3.7a's redraw-on-end-of-sync fix was incomplete, so the pane's client redraw wasn't always triggered when the synchronized update ended — the pane just sat on stale content until something else forced a full repaint, like copy-mode.
        • tmux's CHANGES entry "Fix so that the end of a synchronized update again triggers a redraw" appears for both 3.6b→3.7a and 3.7a→3.7b.

      • Why this surfaced after removing Nix

        • tmux had been Nix-managed, pinned below 3.7, predating synchronized-output support entirely.
        • After My/Dotfiles moved tmux to mise with version = "latest", mise resolved that to 3.7a — new enough to hit this bug.

      • Fix

        • Pinned tmux to 3.7b explicitly in mise/Config/mise.toml/Global (~/.config/mise/config.toml), since "latest" couldn't self-heal past the stuck lockfile entry.
        • Confirmed: yazi and lazygit render immediately inside tmux again, no copy-mode trick needed.

tuicr/Agent/Skill

Page reference

  • The agent skill (skills/tuicr/SKILL.md in agavra/tuicr) is a packaged Claude/agent-tool skill that lets a coding agent talk to tuicr review — the non-interactive CLI side of tuicr — instead of the human-facing TUI.
  • Comments before submit are just session-file rows. Both a human's and an agent's comments live as local draft entries in the same session JSON until a human runs :submit in the TUI; nothing reaches the forge (GitHub/GitLab/etc.) until then.
  • No reply/thread primitive. Comments are flat rows tied to a location, not a thread; adding a second comment at the same spot does not attach it to the first. tuicr/Q/Can I compose a PR comment in nvim to get vim keybindings and markdown rendering?
  • tuicr's comment box has a comment_vim config option (default false); when set (or toggled at runtime with :vim / :set vim!), the box switches to edtui modal editing — hjkl, w/b/e, dd/D/ciw/x, u/Ctrl-r, visual v+y/d/p, :w/:q-style save/cancel.   • Workaround today: enable comment_vim = true for Vim-modal editing inside tuicr, or draft the comment in real nvim and paste the finished Markdown into the comment box for full editor ergonomics plus live Markdown preview (e.g. via a plugin like glow or an in-editor Markdown renderer).
tuicr/Q/Can tuicr show what changed within a single line, the way git diff --word-diff does?
  • The diff never carries intra-line information. tuicr shells out to git for the patch, with git diff --no-ext-diff --raw -z --patch --binary plus the revision arguments, and parses the unified hunks that come back (src/vcs/git/raw.rs). A unified patch has no word-level data in it, so the renderer has none to draw.
  • The display options stop short of it. The settings that change how a diff reads are diff_view (unified or side-by-side, toggled in-app with :diff), ignore_whitespace, wrap (:set wrap!) and search_highlight (CONFIG.md). No key in KEYBINDINGS.md toggles a word or character diff.
  • Read from the local clone github.com/agavra/tuicr at v0.25.0-19-g2e8475c, checking Cargo.toml, Cargo.lock, src/vcs/git/raw.rs, src/ui/ and the docs/ pages named above.
tuicr/Q/If a review comment is marked resolved on a GitHub PR, can tuicr also hide it as resolved?
  • Short answer: yes — :comments unresolved is the default remote-comment mode and already hides threads GitHub reports as resolved; you don't need a separate action to hide them.
  • The resolved/unresolved state itself comes from the forge (GitHub, GitLab, Gerrit, etc.), not from tuicr — tuicr just filters on whatever the API reports. Resolving a thread on GitHub.com (or the equivalent action on another forge) is what changes the state; tuicr reflects it once it has fetched the threads for the current head commit.
  • No per-comment minimize/expand toggle: resolved status controls visibility (via :comments mode) and styling only. Under :comments all, a resolved thread still renders fully expanded — dimmed and carrying a resolved badge — rather than folding to a single collapsed line; there's no fold/unfold action for an individual thread keyed on its resolved state. tuicr does have a separate collapse mechanic for marking a hunk as read (tuicr/Q/In tuicr, how can I mark a hunk as read, rather than a whole file?), but that's independent of GitHub's comment-resolved status.
  • Source: KEYBINDINGS.md on GitHub (":comments unresolved" / ":comments all" rows) and GITEA.md on GitHub ("Outdated threads are not marked" limitation); confirmed by reading src/handler.rs (reload_review), src/app/pr.rs (reload_pull_request_with_backend), and src/ui/comment_panel.rs (format_remote_thread_lines, the resolved-badge/muted-palette rendering with no fold state) in the local agavra/tuicr clone.

tuicr/Q/In tuicr, is the --username on an agent comment tied to a GitHub or forge account, how does tuicr distinguish AI from human comments, and can a whole conversation happen offline before :submit?

  • In tuicr, is the --username on an agent comment tied to a GitHub or forge account, how does tuicr distinguish AI from human comments, and can a whole conversation happen offline before :submit?

    • AI Answer

      • Answer/Official from docs/CONFIG.md, docs/REVIEW_CLI.md, docs/KEYBINDINGS.md, and skills/tuicr/SKILL.md
      • Short answer: --username/author is a purely local, tuicr-only display label — it is not a GitHub/GitLab/forge identity and is never sent to the forge on :submit. tuicr distinguishes comments locally by that author field (TUI coloring, tuicr review comments JSON), but the forge side sees every submitted comment posted under whichever single account gh/glab is authenticated as — there's no built-in per-author signature on the pushed comment text. Yes, an entire back-and-forth (human writes, agent reads and replies with new comments, human reads those, etc.) can accumulate fully offline as local-draft rows in the session file, then one :submit pushes everything to the forge at once.

      • Is --username a forge account?

        • No. The username config key / --username CLI flag is documented as "Display name stamped on local comments and used as the viewer identity for local comment coloring" (see tuicr/Config) — it lives only in tuicr's own session JSON as the author field, independent of whatever account gh or glab is authenticated as when :submit actually pushes to GitHub/GitLab/etc.
        • tuicr/Agent/Skill leans on this: it tells an agent to pass an explicit --username (e.g. "Codex") so its own comments are visually distinguishable from the human's — a convention, not an auth mechanism.

      • How does tuicr distinguish AI from human comments?

        • Locally, yes, two ways:
          • The TUI colors comments based on whether their author matches your configured username (the "viewer identity"), so a human reviewer can visually tell "mine" from "someone/something else's."
          • tuicr review comments returns each comment's author field in JSON — the skill instructs an agent to "check author to distinguish your comments from the user's."
        • On the actual forge PR, not automatically. Nothing in the export or :submit path stamps the per-comment author/username into the pushed comment body — the only built-in prefix is the comment-type tag ([ISSUE], [SUGGESTION], etc.) via comment_type_prefix, not an author signature. All comments submitted in one :submit post as the one authenticated forge account, so a reader on GitHub/GitLab can't tell "written by the agent" from "written by the human" unless the comment text itself says so.

      • Can a whole conversation happen offline, then get pushed on submit?

        • Yes. Comments — from the human in the TUI or the agent via tuicr review add/--input — all land as lifecycle_state: local_draft rows in the same persisted session JSON; there is no live push to the forge as they're written.
        • Multiple rounds are workable: the agent polls tuicr review comments to read what's there, adds its own comments, the human reads/edits/deletes in the TUI, and this can repeat any number of times — none of it touches GitHub/GitLab until a human runs :submit.
        • :submit opens a picker (Comment / Approve / Request changes / Draft) and pushes all pending local comments as a single review event in one shot; there's no per-comment incremental submit. tuicr does support doing this again later for a newer batch of commits (it can preselect just the commits newer than your last submitted review), so "offline round, then submit" can repeat across multiple sessions of the same PR.
        • Caveat: there's no reply/threading — a "conversation" here means a sequence of separate flat comments accumulating on the same location, not a nested thread; see tuicr/Agent/Skill and tuicr/Comment/Type for the flat-comment model.

tuicr/Q/What is PR mode in tuicr?
  • Short answer: PR mode is tuicr reviewing a forge pull request (GitHub PR, GitLab MR, etc.) opened with tuicr pr <target>. A local -r main..HEAD review is not a PR, so :submit refuses.
  • What it is. In the source the TUI holds a DiffSource; :submit runs only when it is DiffSource::PullRequest, otherwise it sets the warning :submit only applies in PR mode (src/app/submit.rs, in start_submit_with and start_submit_action_picker). Help text: tuicr pr is "Review a GitHub pull request or GitLab merge request" with alias mr (tuicr --help).
  • tuicr pr 125 for GitHub, Gitea, Bitbucket, Azure DevOps, or a Gerrit change; tuicr mr 125 for GitLab; tuicr tui pr 125 is the explicit-TUI form (README.md, Quick start).
  • --repo-url <URL> or --remote <NAME> pick the forge repo when the checkout's remote is ambiguous. GitHub needs gh authenticated (README.md, "To GitHub").
  • What :submit does there. It opens a picker for Comment, Approve, Request changes, or Draft. Inline comments land on their lines as a real PR review, and review-level comments become the review summary (README.md, "To GitHub"). Draft sends no event field, so GitHub keeps it as a pending review (SubmitEvent::Draft in src/forge/submit.rs). It also refuses when the PR is closed or otherwise read-only (pr.is_read_only() in src/app/submit.rs).
  • Source: local clone github.com/agavra/tuicr at commit 4a9bda2, plus tuicr --help and tuicr pr --help from the installed 0.27.0.
