Task/Management/Git-Friendly/Report/26/CRDT vs SQLite in git for task management
  • git-sqlite (MIT) – A shell-script toolkit to track a SQLite database in Git [1]. It configures Git diff/merge drivers using SQLite's sqldiff tool. It can initialize a database for Git with UUID primary keys, and provides git-sqlite diff and git-sqlite merge commands. Storage: pure SQLite file. Git Integration: via custom Git attributes (diff=sqlite3, merge=sqlite3). On merge conflicts, the user can git apply-sql after manual edits [1]. License: MIT [1]. Pros: Captures fine-grained diffs (SQL INSERT/UPDATE output), multi-master merges possible. Cons: Alpha-stage, known limitations (issues with triggers, merge conflicts not auto-merged) [1]. Activity: ~220 stars [1], last commit mid-2021 (still workable but somewhat dated).
  • Git usage: Store the canonical text in the repo (perhaps with a custom .gitattributes filter). Optionally keep the binary SQLite off main branch (e.g. orphan branch or LFS). If using a small text format, normal Git can track it; for larger DBs, Git-LFS or a separate branch (like a "data" branch) can isolate bulk binary changes. The tradeoff is: binary branches mean no merge (just replace), while text+CRDT means full history and autosync at cost of bigger diff computation.
  • Overall, a practical design is to export the database to a structured text on each commit (as git-sqlite does [1]) and use CRDTs to combine concurrent edits. For example, each task can have a unique ID (e.g. UUID or ULID) and fields (status, title, etc.). A merge script can diff JSON or SQL inserts, applying CRDT rules (last-writer-wins on timestamps or an OR-set union). Using a standardized line-by-line export (JSONL or SQL DDL/DML) ensures Git can track changes naturally. Optionally, keep the binary DB out of Git (or only as a build artifact) and rely on the text. This approach achieves "serverless sync": collaborators simply git pull && git push to share task updates, with merges resolved by CRDT logic.

  • CLI Tools for Toggl Track

    • Other CLI Tools

      • Aside from the above, there are a few more niche CLI utilities (open-source) for Toggl Track, though with narrower scope or older API versions. For example, toggl-hammer is a Python CLI to quickly add "hour blocks" of time for past dates (useful for back-filling time, but it doesn't let you specify custom start/stop times or descriptions)[18]. It's designed for "lazy" input of fixed-length entries and is not a general-purpose CLI for full CRUD. There are also older CLI projects like joequery/Toggl-CLI and community scripts, but many were built against the now-deprecated API v8. The Toggl Track engineering team maintains a list of third-party tools, and many CLI projects have been updated or forked to work with API v9[18] [19]. When choosing a CLI, ensure it supports API v9, as the older v8 endpoints are no longer available. The three CLI options above (Python, Node, Rust) are among the best-maintained for Toggl Track with API v9 support and cover a range of language ecosystems. All are open source, allowing you to inspect or modify the code if needed.

  • MCP Interfaces for Toggl Track

    • Model Context Protocol (MCP) is a newer approach that allows AI or natural-language-driven clients (like ChatGPT plugins or Claude AI) to interact with services through a standardized interface. In the Toggl Track context, MCP servers act as an adapter on top of the Toggl API to interpret high-level commands (often in natural language) into Toggl actions. This can be useful if you want to control Toggl via conversational AI or integrate it into an AI agent workflow. Two notable MCP implementations exist for Toggl Track; narrative for each is on Toggl/MCP/Node/louis030195/toggl-mcp and Toggl/MCP/Python/jasleen19/toggl-mcp, under each page's AI/Response heading that cites this report.

  • SDKs and Libraries for Toggl Track

    • If you prefer to build your own tools or integrations, there are several software development kits (SDKs) and libraries for Toggl Track. These provide programmatic access to Toggl's API in various languages, abstracting the raw HTTP calls. Below are some of the open-source libraries (and one official, the API itself) that support full time entry CRUD, with notes on projects/clients and reports support:
    • Python: Officially, Toggl Track doesn't maintain an official Python SDK, but the community has the above-mentioned Toggl CLI (Python) Toggl/CLI/Python/AuHau/toggl-cli which doubles as a library. Similarly, api.Project.objects.get(id) and .save() let you update project details[1]. This essentially is an SDK built on the Toggl API. Toggl/CLI/Node/beauraines/toggl-cli
  • Description: A Node.js-based CLI tool (by Beau Raines) inspired by the above Python project. It was updated to use the Toggl Track API v9[3]. This CLI supports starting and stopping time entries, continuing existing entries, and editing the running entry. Notably, it also supports adding manual entries (with specified start and stop times) and deleting entries by ID – features contributed by the community[3]. It provides interactive prompts for some commands and configuration.
  • Projects/Clients: This tool can assign a time entry to a project (you can specify project by name or ID when starting an entry) and likewise assign a client via project selection, but it does not manage project or client objects itself (no commands to list or create projects/clients)[3]. You'd need to create projects/clients in Toggl Track first, then use their names/IDs in the CLI for time entries. The config file supports setting a default workspace and project, and you can also specify a client name when starting an entry which helps select the project[3] (it doesn't create new clients, just filters projects by client name).
Toggl/CLI/Python/AuHau/toggl-cli
  • Description: A popular command-line tool maintained by Adam Uhlir (originally by D.R. Adams) that uses Toggl Track's API. It also provides a Python library (ORM-like wrappers) for scripting[1].
