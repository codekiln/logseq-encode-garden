Ableton/Live/Idea/Declare a Live Set in Logseq

  • Start from a known-good template

    • Build a real template Set in Live 11 and have the compiler change a copy of it, rather than building the XML tree from nothing. Live already supports template Sets with tracks, effects, I/O routing and MIDI mappings.
    • For GitP the template would hold the usual setup: Microfreak MIDI and audio tracks, the commentary microphone, return effects and the usual device chains. The compiler specializes it for one episode.
    • The XML carries internal object IDs, automation references, device state and version-specific fields. Reverse-engineering projects report small edits that produced broken Sets. Copying working structures and changing a few properties is safer than creating devices from XML.
  • Ableton vocabulary gets its own properties. Example page GitPa/017/Ableton Setup (proposed syntax, not a standard; device, port and chain names would need to match the real setup):
    		  - Ableton Session
		    spec-version:: 1
		    live-version:: 11
		    base-template:: gitpa-performance.als
		    tempo:: 96
		    time-signature:: 4/4
		    - Tracks
		      - MicroFreak MIDI
		        track-key:: microfreak-midi
		        type:: midi
		        midi-from:: Launchpad Pro MK3
		        midi-to:: MicroFreak
		        midi-channel:: 1
		        monitor:: auto
		        arm:: true
		      - MicroFreak Audio
		        track-key:: microfreak-audio
		        type:: audio
		        audio-from:: Ext. In 1
		        monitor:: auto
		        device-chain:: microfreak-effects
		      - Commentary
		        track-key:: commentary
		        type:: audio
		        audio-from:: Ext. In 2
		        monitor:: auto
		        device-chain:: voice-processing
		    - Scenes
		      - Introduction
		        scene-key:: intro
		        color:: blue
		      - Improvisation
		        scene-key:: improv
		        color:: purple
		      - Reflection
		        scene-key:: reflection
		        color:: green
  • In the .als: tempo, time signature, track names, colors and order. With template-based XML changes: MIDI and audio tracks, scenes and empty clip slots, and track I/O routing. Device chains are best taken from the template; device parameter values are possible with careful XML handling.
  • Test every generated Set by opening, saving and reopening it in Live 11. Semantic diffs and hashes of the source template make regressions easier to find.
  • Write a standalone Python compiler that reads the page, validates it and makes those few XML changes to a copy of the template.

Architecture/Decision/Record
  • An ADR consists of a short text file (usually one to two pages long) describing a specific architectural decision. While ADRs can be written using plain text or in a wiki page template, they are usually written in some sort of text document format, like AsciiDoc or Markdown.
  • Architecture/Decision/Record/MADR — Markdown Architectural Decision Records: a widely used Markdown template and file conventions maintained in adr/madr (template, npm package madr, optional markdownlint setup).
Architecture/Decision/Record/MADR
  • Markdown Architectural Decision Records (MADR, pronounced like English “matter”[1]) are a lean Markdown template for capturing architecturally significant decisions—each record documents one architectural decision (AD) and its rationale. The project positions “architecture” broadly: technology choices, tooling, libraries, or product behavior can qualify if they affect the system enough to warrant a structured record.
  • Repository: github.com/adr/madr — template files, releases, changelog, rendered decision examples (source)
  • Development template (moving target): adr-template.md on develop
  • General ADR practice is wider than one file format; this page anchors the MADR-specific file shape, filenames, and optional YAML metadata used in the official template. For motivation and team pitfalls around ADRs, start from Architecture/Decision/Record.

  • Template shape (summary)

    • Top matter (optional): YAML for site generators—e.g. title, status, date, decision-makers, consulted, informed (see live template).
    • Title (#): short title of the solved problem and chosen solution.
    • Context and Problem Statement — situation and the question to settle (links to issues/boards welcome).
    • Decision Drivers (optional) — forces and constraints.
    • Considered Options — bullet list of alternatives.
    • Decision Outcome — Chosen option: "…", because …
    • Consequences (optional) — Good/Bad bullets.
    • Confirmation (optional) — how you verify the decision (reviews, tests, ArchUnit-style checks, etc.).
    • Pros and Cons of the Options — per-option Good / Neutral / Bad bullets.
    • More Information (optional) — evidence, links to superseding ADRs, revisit triggers.
  • Layout: create docs/decisions (or another root; MADR does not mandate repo layout). Copy contents of the template/ folder into that directory—includes adr-template.md, lint config, and ancillary files.
  • npm: install published package and copy template:
    • 			  npm install madr && mkdir -p docs/decisions && cp node_modules/madr/template/* docs/decisions/
  • New decision file: copy adr-template.md to NNNN-title-with-dashes.md (consecutive NNNN, lowercase dashed title, .md suffix); convention is documented as ADR-0005. Other filename schemes exist in the wider ADR community but may break tooling.
  • Linting: Markdown style can drift; the repo ships .markdownlint config and an example GitHub Actions workflow using markdownlint.

Arturia/MCC/UG/03 Working with Templates
  • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser

    • 3.3. Project / Template Browser

      • The browser holds archived Templates on the computer in Factory and User groups. A Template usually mirrors the device memory layout, though some devices hold multiple Templates.
      • Templates do not include Device Settings.
      • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/01 Device Templates

        • 3.3.1. Device Templates

          • A Template may contain several data layers. Expand or collapse them with the browser’s plus and minus controls.
      • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/02 Build Library

        • 3.3.2. Building a library

          • Use Recall From to copy changed device memory into a new User Template. MCC gives it a timestamped name, which can be renamed.
          • The User Templates area can hold a library of presets, patterns, or sequences beyond the device’s capacity.
      • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/03 Working Memory

        • 3.3.3. The Working Memory / Working Project

          • When synced, Working Memory represents the device’s active memory and most MCC edits also reach the device.
          • When unsynced, Working Memory is a staging area. MCC edits do not automatically change the device.
          • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/03 Working Memory/01 Live Editing
          • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/03 Working Memory/02 Drag and Drop
      • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/04 Revise Template

        • 3.3.4. Revise a Template

          • Select an archived Template to edit it in MCC. Save or Save As preserves changed computer data.
          • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/04 Revise Template/01 While Synced

            • 3.3.4.1. While synced

              • Selecting a Template sends its data to the connected device. Further MCC edits also affect the hardware; an asterisk signals unsaved Template changes.
          • Arturia/MCC/UG/03 Working with Templates/03 Project and Template Browser/04 Revise Template/02 Not Synced

            • 3.3.4.2. Not synced

              • Edit an archived Template in MCC, then save it. To hear the result on the hardware, drag the revised Template to Working Memory or use Store To.

              • Note/Warning Sending the revised Template overwrites Working Memory and device pattern memory. Preserve existing work before transfer.
