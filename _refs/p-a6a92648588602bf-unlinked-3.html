Claude/Code/How To/Answer Permission Dialog To Record Wildcard Permissions in Local Settings

  • How To Answer the Permission Dialog To Record Wildcard Permissions in Local Settings

    • Overview

      • When Claude/Code asks for permission to run a command, you can edit the suggested permission entry before confirming to make it a wildcard that covers a broader class of commands.
      • This lets you grant bounded-but-flexible permissions that persist in .claude/settings.local.json without having to manually edit that file.

    • Prerequisites

      • Claude/Code installed and running in a project
      • A session where Claude has just asked for permission to run a shell command

    • Steps

      • 1. Wait for the permission prompt

        • Claude will display a prompt asking whether to allow a specific command, e.g.:
          • 				  Allow bash command?
				  1. Yes, allow once
				  2. Yes, allow bd --no-daemon --specific-flag value
				  3. No

      • 2. Select option 2

        • Press 2 and Enter to select the "allow and remember" option.
        • The full specific command string will appear in an editable field.

      • 3. Edit the command to a wildcard

        • Use the Delete (or Backspace) key to remove the overly-specific trailing arguments.
        • Replace them with * to match any arguments with that prefix.
        • Example: bd --no-daemon --specific-flag value → bd --no-daemon *

      • 4. Confirm

        • Press Enter to confirm.
        • Claude/Code writes the permission to .claude/settings.local.json in the form:
          • json
            				  "Bash(bd --no-daemon *)"

      • 5. Verify (optional)

        • Open .claude/settings.local.json and confirm the entry looks as expected.

    • Troubleshooting

      • The field isn't editable — some terminal emulators may not support inline editing at the prompt; try a different terminal.
      • Too broad a wildcard — avoid patterns like rm * that could allow destructive commands. Be specific enough to cover your use case without opening up unintended commands.

Claude/Code/Q/Does editing a plugin's SKILL.md in a local-path Claude Code marketplace require reinstalling, or is restarting Claude Code enough to pick up the change?

  • AI Answer

    • Answer/Official from Plugins reference - Claude Code Docs
      • Short answer: No, restarting alone is not enough. A plugin installed with /plugin install from any marketplace — including one added from a local path via /plugin marketplace add ./my-marketplace — is copied into ~/.claude/plugins/cache at install time. Claude Code loads that cached copy, not the live files under my-marketplace/, so editing SKILL.md in the source tree has no effect until the plugin is reinstalled or updated.
      • Why a restart doesn't help: the cache-vs-source split applies to every marketplace-installed plugin, not only git-hosted ones — "Claude Code copies marketplace plugins to the user's local plugin cache (~/.claude/plugins/cache) rather than using them in-place." A restart just reloads whatever is already sitting in that cache.
      • Why /plugin update may not help either: Claude Code decides whether an update is needed by comparing the plugin's resolved version, checked in this order: plugin.json version → marketplace-entry version → git commit SHA (only for github/url/git-subdir/relative-path sources inside a git-hosted marketplace) → unknown for local directories that aren't inside a git repo. A plain local-path marketplace with no explicit version set always resolves to unknown on both sides of the comparison, so /plugin update (and background auto-update) reports "already at the latest version" and skips the re-copy.
      • How auto-update interacts with this: auto-update doesn't diff file contents — it re-runs the same version comparison as /plugin update, just on a timer, so it inherits the same blind spot.
        • It's off by default for exactly this kind of marketplace: "official Anthropic marketplaces have auto-update enabled by default. Third-party and local development marketplaces have auto-update disabled by default." Turn it on per marketplace via /plugin → Marketplaces → select the marketplace → Enable auto-update (or, for a team, an admin sets "autoUpdate": true on that marketplace's extraKnownMarketplaces entry in managed settings).
        • Even enabled, whether it can ever notice the edit depends on what my-marketplace/ actually is:
          • Plain directory, no .git: version stays unknown forever, so enabling auto-update changes nothing — there's no version delta for it to detect, ever.
          • my-marketplace is itself a git repo (even with no remote) and the plugin uses a relative-path source: version resolves to that repo's commit SHA, so saving SKILL.md alone still doesn't change anything — you must git commit the change. Once committed, auto-update's next background pass (or a manual /plugin update) sees a new SHA and re-copies.
          • Explicit version set in plugin.json/the marketplace entry: same rule as manual update — auto-update only fires when that string is bumped.
        • Timing, when it does apply: "Claude Code checks for marketplace and plugin updates after your session starts, with a random delay of up to ten minutes, so the running session keeps using the versions it loaded at launch. If any plugins were updated, you'll see a notification prompting you to run /reload-plugins, or the new versions load on your next launch."
        • Net effect for local plugin development: auto-update is built to keep other people's marketplaces fresh in the background, not for a tight edit-save-test loop. Best case (git-backed marketplace, auto-update on) still needs a commit and a ≤10-minute wait before a notification; worst case (plain directory) it never helps at all. --plugin-dir (below) sidesteps all of this.
      • To actually pick up the edit:
        • 1. Reinstall: /plugin uninstall my-plugin@my-marketplace then /plugin install my-plugin@my-marketplace. This forces a fresh copy into the cache regardless of the version string. The uninstall command's --keep-data flag exists for exactly this case — the docs note it's for "reinstalling after testing a new version" — to preserve ${CLAUDE_PLUGIN_DATA} across the reinstall.
        • 2. Or set an explicit version in plugin.json (or the marketplace entry) and bump it on every change, then run /plugin marketplace update my-marketplace followed by /plugin update my-plugin@my-marketplace (or let auto-update apply it once enabled for that marketplace).
        • 3. If skills still don't show up after reinstalling, clear the cache outright: rm -rf ~/.claude/plugins/cache, restart Claude Code, and reinstall.
      • Better fit for active plugin development: skip the marketplace-install path and load the plugin for the session with claude --plugin-dir /path/to/my-plugin instead. --plugin-dir plugins are read in place rather than copied to the cache, so edits are picked up on the next session start with no install/update step — the pattern used for rapid local iteration in Claude/Code/Plugin/Marketplace/Report/26/01/Automated Testing.
      • Related, narrower exception: a plugin auto-discovered from a project's skills/ directory via @skills-dir (no marketplace, no install step) is read in place, and edits to its SKILL.md take effect immediately in the current session — but that's a different mechanism from a marketplace-installed plugin, and its other components (hooks, .mcp.json, agents) still need /reload-plugins or a restart.

Claude/Code/Q/How can I keep my private Claude Code plugin marketplaces up to date daily?

  • AI Answer

    • Answer/Official from Create and distribute a plugin marketplace - Claude Code Docs
      • Short answer: run claude plugin marketplace update yourself on a schedule (e.g. a daily cron job or launchd task) rather than relying on Claude Code's built-in auto-update — for a private marketplace, auto-update is both off by default and unreliable over HTTPS, while a manual/scripted update uses your normal git credentials the same as your terminal.
      • Manual/scripted update command: claude plugin marketplace update [name] — omitting [name] updates all registered marketplaces in one call, which is what a daily cron entry would typically run.
      • Why the built-in auto-update doesn't already give you "daily":
        • It's off by default for exactly this case: official Anthropic marketplaces have auto-update enabled by default, third-party and local/private marketplaces have it disabled by default.
        • The only documented way to turn it on is a settings.json field, not a menu action: each extraKnownMarketplaces entry accepts an optional autoUpdate boolean — "autoUpdate": true alongside that entry's source. For a local-directory marketplace the source shape is { "source": "directory", "path": "/absolute/path/to/marketplace" }.
        • In practice, the interactive /plugin → Marketplaces → select-marketplace menu may not expose an "Enable auto-update" action at all for a directory-sourced marketplace — auto-update is fundamentally a background git pull, which doesn't apply to a marketplace that's already just a local folder being re-read. The toggle described in Anthropic's docs is on firmer ground for github/git/url-sourced marketplaces.
        • Even enabled, it isn't a standalone daily timer — it's a background check that runs after a Claude Code session starts (with a random delay of up to ten minutes), so a marketplace only gets checked on days you actually launch a session, and updates apply on /reload-plugins or your next launch.
        • autoUpdate: true also does more than the manual claude plugin marketplace update command: per the settings reference, it "refresh[es] that marketplace and update[s] its installed plugins in the background" — the manual CLI command only refreshes the marketplace catalog, so getting installed plugins onto the new version still needs a separate claude plugin update <plugin>@<marketplace> per plugin (no --all flag exists for plugin update).
      • Private-repository credential caveat that a naive cron job can also hit:
        • Manual/scripted claude plugin marketplace update reuses your existing git credential helpers, so HTTPS via gh auth login/Keychain/git-credential-store, or SSH via a key loaded in ssh-agent, works the same as a normal git pull in your terminal.
        • Background auto-update is more fragile: by default it disables git credential helpers for its git pull, so private HTTPS remotes can't authenticate even with a helper configured; SSH remotes with ssh-agent are unaffected. A failed background pull falls back to a full re-clone (which does use stored credentials but can time out on large repos), so private-marketplace auto-updates "may fail intermittently."
        • To make a scheduled/background update reliable for a private HTTPS marketplace: configure a git URL rewrite scoped to that marketplace's repo or org with an embedded token (so the pull authenticates directly and skips the re-clone path), and/or set CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1 so a failed pull keeps the last-synced clone instead of deleting it. In CI/cron contexts, gh auth setup-git (or an equivalent credential helper) makes the fallback re-clone work unattended too.
      • Recommended daily setup: a cron/launchd job that runs claude plugin marketplace update once a day (or per-marketplace with [name] if you want to script it against a curated list) sidesteps both limitations above — it isn't gated on starting a session, and it authenticates like a normal terminal git pull rather than the more restricted background-refresh path.

        • Type /rewind in the prompt (or double-tap Esc with an empty input) to open a list of every prior user turn as a checkpoint.

    • when claude is in /tui fullscreen mode, it uses an off-screen render buffer, which interferes with tmux
    • inside of claude, use /tui default to disable Claude/Code/TUI mode.

  • AI Answer

    • AI/Response
    • Short answer: Claude/Code TUI mode activates the terminal alternate screen buffer, which never writes to tmux's main scrollback — so copy mode has nothing to scroll through.
    • How the alternate screen buffer works:
      • TUI applications (vim, less, htop, Claude Code) activate the alternate screen on entry via the smcup terminal capability and restore the original screen via rmcup on exit.
      • The alternate screen is a completely separate display area; output written there never flows into tmux's main pane scrollback buffer.
      • tmux copy mode only scrolls through main pane scrollback, so it sees nothing rendered during the TUI session.
    • Workarounds:
      • export CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1 — disables the alternate screen; the inline/scrollback renderer is used instead and conversation output flows normally into tmux scrollback.
      • Use Claude Code TUI's built-in navigation: Page Up/Page Down, arrow keys, and mouse scroll work within the TUI view itself.

Claude/Code/Q/Why does piping claude --help to bat break keyboard scrolling while mise --help works fine?

  • AI Answer

    • AI/Response
    • Short answer: yes, this is a Claude/Code-specific bug, not a bat misconfiguration. Claude/Code enables an enhanced keyboard-input protocol (the kitty keyboard protocol / xterm's modifyOtherKeys, aka XTMODKEYS) on the terminal and doesn't always restore it afterward. The piped --help text itself carries no escape bytes — the terminal is left in this altered input mode from Claude Code's own terminal setup, so it mangles what less (bat's underlying pager) reads back from the keyboard.
    • Why j stops working and ctrl+j scrolls with blank lines:
      • While the enhanced mode is enabled, ordinary keys like j are no longer sent to the terminal as the plain byte j — they arrive as multi-byte CSI u escape sequences instead.
      • less doesn't recognize that sequence as its "scroll down" command, so it falls back to treating the bytes as literal input on its colon-style command line — matching the :jjjjjjj... shown at the bottom of the screen.
      • ctrl+j (linefeed, 0x0A) partially survives this re-encoding, so it does trigger a scroll, but the surrounding altered escape sequences are what produce the extra blank lines.
      • mise --help | bat works because mise never touches these terminal keyboard modes, so the terminal stays in normal input state.
    • Documented in the wild: anthropics/claude-code#38761 ("Terminal left in enhanced keyboard mode after exit — Ctrl-C/Ctrl-D broken") describes exactly this mechanism for Ghostty + tmux and was fixed in Claude Code v2.1.86, but the underlying protocol-restoration problem has recurred since: #62423 (legacy XTMODKEYS still sent even when the terminal advertises the kitty protocol) and #69063 (extra blank lines while scrolling tmux scrollback, same Ghostty + tmux setup) are both still open.
    • Workaround: run printf '\e[<u\e[=0u\e[>0m' (or reset) to force the terminal back to normal keyboard mode after the glitch appears. As a standing fix, a Stop hook in ~/.claude/settings.json that runs that printf on every Claude Code exit prevents the leak from persisting into the next command.
    • Related: Claude/Code/Q/Why can't I scroll up in tmux copy mode when Claude Code is in TUI mode? is a different symptom (alternate screen buffer) from the same general family of Claude Code terminal-mode side effects.

  • AI Answer

    • Short answer: Cowork and Code run the same underlying Claude agent and sub-agent task-decomposition approach, but wrap it in opposite operating surfaces — Cowork is a GUI tab in Claude Desktop built for knowledge work on documents and data inside explicitly granted folders; Code is a terminal/IDE agent built for codebases with full filesystem access, code execution, and git.       • Hands back a finished deliverable (a written report, a filled spreadsheet, a reorganized folder) rather than a diff or instructions to run.

Claude/Desktop/Code/Q/How can I make sure a Routine in Claude Desktop's Code tab has all the permissions it needs to run, since there's no obvious way to set automatic permission mode?

  • AI Answer

    • Short answer: It depends which of the two things Desktop's Routines page created. A Cloud routine has no permission-mode picker at all — that's by design, not a gap: cloud routines always run autonomously with no approval prompts, and their reach is bounded by repositories, the cloud environment, and connectors instead. A Local scheduled task does have a permission-mode picker and a per-task "always allow" approval list — if that's the control that seems to be missing, it's likely because Cloud was picked instead of Local when the routine was created.
    • Answer/Official from Automate work with routines and Schedule recurring tasks in Claude Code Desktop:
    • Cloud routines (Desktop → Routines → New routine → Cloud): "Routines run autonomously as full Claude Code cloud sessions: there is no permission-mode picker and no approval prompts during a run." What a cloud routine can reach is scoped by the repositories selected (and their branch-push rule), the environment's network access and variables, and the connectors included — not by a permission mode.
    • Local scheduled tasks (Desktop → Routines → New routine → Local): these do have a permission mode. The instructions form "includes pickers for the permission mode and model," set per task at creation or edit time; allow rules from ~/.claude/settings.json also apply to scheduled-task sessions.
    • Getting a Local task to run with full automatic permission: if a task runs in Ask mode and hits a tool it isn't allowed to use, the run stalls in the sidebar until approved. To avoid that: click Run now right after creating the task, watch for permission prompts, and choose "always allow" for each one — future scheduled runs then auto-approve those same tools without prompting.     • One caveat: MCP tools an organization set to ask, or any tool marked requiresUserInteraction, always prompt and never offer an always-allow option — a task calling one of those stalls on every run regardless of permission mode.
    • Bottom line: not finding a way to set automatic permission is expected for a Cloud routine — there's nothing to configure, since it's already unattended. For a Local scheduled task, the setting exists; the durable "no more prompts" state comes from one manual Run now with "always allow" clicks, not from a single toggle.

Claude/Desktop/Code/Q/Is there a way to remove recent items from the Claude Desktop Code tab?

  • AI Answer

    • Short answer: There is no in-app control to remove or clear entries from the Recent folder list in the Code tab. The only current workaround is to quit Claude Desktop and delete the entries by hand from the projects key in ~/.claude.json.
    • No in-app removal (as of mid-2026): The Recent list has no right-click menu, hover action, "Remove from recents", or "Clear all" button, and Settings exposes no way to prune it.       • 4. Save, then reopen Claude Desktop.
    • Why duplicate-looking rows appear: entries are keyed by absolute path, so the same folder name opened from two locations (e.g. one under ghq/ and one under Documents/) shows as two separate Recent rows and needs two separate deletions.
    • Caveat: ~/.claude.json also holds CLI settings and per-project state; edit only inside "projects" and keep a backup, since a malformed file can reset other state.
