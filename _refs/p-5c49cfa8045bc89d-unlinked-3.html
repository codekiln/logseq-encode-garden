  • data minimization: From a technical standpoint, several talks reinforced a shift in thinking about defense. In The Zero-Day Deluge: Why Patch-Centric Security Is No Longer Enough (Nathan Hall), the argument was that the window between vulnerability disclosure and exploitation is shrinking so quickly that patching alone cannot keep organizations safe. The more strategic response is data minimization - legal constraints will make it so organizations minimize and reducing the amount of sensitive information stored in systems, so that breaches cause less damage. As someone interested in AI enablement, it made me realize that we are kind of in a golden era right now - AI tools are exciting to try out and they can help us out, but it may be that the drawbridge is being pulled up for reasons beyond the scope of AI security, and soon, it will not be feasible to have AI help us out on enterprise data.

Claude/Code/Q/What does the skill listing truncation warning mean?
  • What the message is: At the start of a turn, Claude Code injects a skill listing into the model context: each discoverable skill’s name plus (normally) its description and when_to_use text so the model knows what exists and when to load it. When that listing would use more than your configured share of the context window, the CLI drops full descriptions for the least-recently-used skills and keeps full text only for skills it considers most-used, then prints the warning you saw (with counts and an estimate of how much of the window the full listing would have taken versus the cap).
  • Where it comes from: This behavior is implemented in Claude Code itself (not your shell). It is controlled by settings documented on Claude Code settings: skillListingBudgetFraction reserves a fraction of the model’s context window for that listing (default 0.01 = 1%). When the listing would exceed the budget, descriptions for the least-used skills are collapsed to bare names so the model can still invoke them but no longer sees why. A companion cap, maxSkillDescriptionChars (default 1536), truncates each skill’s combined description + when_to_use text before the overall budget is applied. See the same settings table rows and the skills guide Extend Claude with skills (frontmatter reference explains the listing and per-skill truncation).

CursorAI/Q/Why does Cursor have token limits that are lower than the model's advertised context limits?
  • Answer/Official from Max Mode on legacy plans and Models & Pricing: Cursor publishes a Default context and a separate Max context per model. The default is intentionally lower than the provider's full window; Max Mode (legacy request-based plans) or an explicit context-size choice in the model picker (usage-based plans) opts into the larger window.
  • Short answer: Cursor caps the default window below the model's advertised max for cost and product defaults — not because the model lacks capacity. Staff have also said Cursor may lower a model's usable limit based on how it performs at that size. The UI meter can look even smaller because system prompts, tools, reasoning, and output reserve share the same window.
  • Default vs max is a product choice. Cursor's models table lists both columns (e.g. many Claude models: default 200k, max 1M). Official Max Mode help: the default window "works well for most coding tasks"; use the larger window when a task needs more. Larger context burns more tokens (and some providers charge more above long-context thresholds).
  • Cursor may also cap below the provider max for performance. Forum staff (Condor): each model has a provider limit, and "We also may set a context limit to a model depending on its performance in non-Max mode." (Max Mode discussion)
  • How to get the larger window. On usage-based plans, pick the context size in the model picker (Max Mode as a separate toggle was removed for those plans; same sizes remain). On legacy request-based plans, toggle Max Mode — billed at API rate plus 20%.
  • Why the usage bar can still look short of even Cursor's limit. Reserved space for system/agent instructions, tool definitions, reasoning tokens, and the reply means the "available" user context is less than the configured window. That is separate from the default-vs-max policy above. (Forum thread on truncated available context)

herdr/Q/Can herdr show the current session name, and how do I switch sessions?
  • Short answer: No on the name — nothing in 0.8.0 renders the session anywhere, and the ui.window_title template that has since landed on main has no {session} token. Switching is CLI-only: detach, then herdr session attach <name>. herdr's own advice is to reach for workspaces instead, which are the real analogue to tmux sessions.
  • ui.window_title exists but has no session token. It writes the outer terminal's title (OSC 0), which is what window managers show in title, tab, and group bars. It defaults to "{hostname}: {workspace}", accepts {hostname}, {workspace}, {tab}, {pane}, and {terminal_title}, and takes "" to leave the outer title alone. It renders on the server, so {hostname} names the host the panes run on even when attaching from a remote client.
  • And it is not in 0.8.0 yet. herdr config check against a 0.8.0 binary answers unknown config key ui.window_title; ignoring key, and the same for ui.tab_bar_right. Both are absent from the 0.8.0 and the current preview docs snapshots — they are on main, headed for a later release. 0.8.0 does not write the outer terminal title at all; src/terminal_effects.rs does not exist at the v0.8.0 tag.
  • Name the workspace after the session. workspace is the one identifier every surface already shows, and it is what {workspace} will resolve to once ui.window_title ships.
