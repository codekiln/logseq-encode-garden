Task/Management/Git-Friendly/Report/26/CRDT vs SQLite in git for task management
  • Modern task systems increasingly target "local-first" and multi-agent workflows. A few emerging tools use CRDTs (Conflict-free Replicated Data Types) or Git-friendly file stores to keep tasks synchronized across devices without a central server. Notable CRDT-based task apps include ff (a CLI note/task manager using RON CRDTs) and HamsterBase Tasks (a local-first to-do app built on the Loro CRDT). Another new entrant, Will Be Done, implements offline-first task sync with a custom in-memory DB and CRDT (AGPL-3.0) for conflict-free merge. On the Git-integration side, Person/Steve Yegge's Beads uses a Dolt (Git-backed SQL) database to version tasks, while Marcus Redwood's td (with the Sidecar UI) uses a SQLite store (single-binary CLI, MIT-licensed). Term/Q/What is a vertical slice in tech?
  • Short answer: A vertical slice is a unit of work that cuts through every layer of a system — UI, business logic, persistence, deployment — to deliver one small piece of functionality that actually works end to end. The contrast is a horizontal slice, where you build one layer in its entirety before starting the next.
  • Vertical: pick one thin behavior — "a user can save a profile" — and build only the schema, endpoint, and UI that behavior needs. It is narrow in features but complete in depth.
  • In games, a vertical slice is a specific production milestone: a small but representative chunk of the game built to near-final quality, proving that gameplay, art, tech, UI, audio, and pipeline all hold together at shipping standard.

UX/Design/Atomic

  • Atomic design is not a linear process, but rather a mental model to help us think of our user interfaces as both a cohesive whole and a collection of parts at the same time.[1]

  • Logseq/Entity/UI/Area and Logseq/Entity/UI/Control map the parts of hardware and software interfaces into pages.
UX/Design/Atomic/L1 - Atom

  • Atoms are UI elements that can’t be broken down any further and serve as the elemental building blocks of an interface.[1]

  • A single knob, button, pad or field — a Logseq/Entity/UI/Control.
UX/Design/Atomic/L2 - Molecule

  • Molecules are collections of atoms that form relatively simple UI components.[1]

UX/Design/Atomic/L3 - Organism

  • Organisms are relatively complex UI components composed of groups of molecules and/or atoms and/or other organisms. These organisms form distinct sections of an interface.[1]

  • A panel section or a view — a Logseq/Entity/UI/Area such as Microfreak/UI/Oscillator or Ableton/Live/UI/Control Bar.
UX/Design/Atomic/L4 - Template
  • A whole interface layout, such as Ableton/Live/UI/Arrangement View with its tracks empty.
UX/Design/Atomic/L5 - Page

  • Pages apply real content to templates and articulate variations to demonstrate the final UI and test the resilience of the design system.[1]

  • Pages are specific instances of templates that show what a UI looks like with real representative content in place.[1]

UX/Pattern/Dark
  • Dark patterns (also called "deceptive patterns") = user interface designs that intentionally mislead or manipulate users into doing things they didn't really want to do—often benefiting the business instead of the user. (Wikipedia)

vim/Q/How can I check whether vim or neovim will yank to the unnamedplus (system) clipboard?
  • Troubleshooting — no visible echo from commands: :set clipboard?, :lua print(...), and :echo has('clipboard') usually print a one-line echo in the message area (easy to miss when cmdheight is 1, another UI plugin steals echoes, or the line scrolls away). Try :set cmdheight=3, rerun :set clipboard?, or :echomsg 'clipboard=' .. &clipboard and then :messages. For Lua, :lua vim.notify(vim.inspect(vim.o.clipboard)) (with nvim-notify) or :put =execute('set clipboard?') drops text into the buffer so you cannot miss it.
  • Troubleshooting — single-register output looks empty: For :reg + and :reg ", (1) :registers with no args is easier than single-register forms; watch for -- More -- and advance the pager. (2) :reg " must end with exactly one " (the register name); an extra " turns it into a different command / error. (3) Empty + may print no line for + in a short listing—use string(getreg(...)) or :put =... so emptiness shows as '' or a blank inserted line. (4) UI plugins (noice.nvim, etc.) sometimes reroute or auto-dismiss multiline :registers output—fall back to :echo string(...) / :put =... or :lua vim.print({ ... }).
  • Troubleshooting — registers output flashes then vanishes: Typical when noice.nvim (often with nvim-notify) shows msg_show output in a notify / mini view that auto-dismisses. Mitigations: enable preset long_message_to_split so long output opens a split you can read; add a route sending event = "msg_show" (or kind = "echo") to view = "split"; raise views.notify.timeout (milliseconds) or false where supported; run :Noice / :Noice history to reopen message history after the popup closes; temporarily :Noice disable to confirm stock msgarea behavior. Bypass the UI entirely: :redir @a | silent registers | redir END then :new :put a (or :put =execute('registers')) so the dump lives in a buffer.

VSCode/Q/Is there anything in VS Code similar to PyCharm's UI buttons for switching between file tree view modes?

  • Is there anything in VSCode similar to PyCharm's UI buttons for switching between file tree view modes?

    • AI Answer

      • Short answer: No built-in equivalent exists. VS Code's Explorer is a single flat file tree with no named view modes. The closest built-ins are collapsible Explorer sections and the Activity Bar's distinct view containers; third-party extensions fill the gap.
      • PyCharm context: PyCharm's Project panel has a dropdown that switches between named modes — Project, Packages, Project Files, Open Files, Production, Tests, Scratches & Consoles — each reorganising the tree differently without leaving the panel.
      • VS Code built-ins:
        • Activity Bar icons — each icon opens a completely different panel (Explorer file tree, Search, Source Control, Run & Debug, Extensions). These are separate tools, not alternative views of the same file tree.
        • Explorer sections — the Explorer panel has collapsible sub-sections: Open Editors, the workspace file tree, Outline, and Timeline. Sections can be hidden or reordered via right-click, but there is no mode switcher.
        • Multi-root workspaces — adding multiple folders to a workspace shows each root as a separate collapsible tree. Useful but not a "mode."
      • Extension options (closest to PyCharm-style view switching):
        • Project Manager — adds a dedicated sidebar view for switching between saved projects; does not remode the file tree itself.
        • Explorer Exclude — toggle visibility of file-type groups via toolbar buttons in the Explorer; conceptually closest to a mode switcher.
        • Custom tree-view extensions (e.g. file grouping by type, by git status) can approximate specific PyCharm modes.
      • Bottom line: VS Code deliberately keeps the Explorer minimal; view filtering is done through files.exclude settings or extensions rather than first-class UI mode buttons. See VSCode/Q/Is there a setting that hides or shows dot folders and dot files in the explorer panel on the left by default? for the settings approach.
