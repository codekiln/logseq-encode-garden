Codex/Plugin/Q/Can you make plugin reference material in both Codex plugins and Claude plugins?

  • Can you make plugin reference material in both Codex/Plugins and Claude/Code/Plugins?

    • AI Answer

      • Short answer: Yes. Both can distribute reference documents alongside a skill. A small SKILL.md describes when the material is relevant and which files to read; the detailed material lives in supporting files.
      • Answer/Official from OpenAI: Build skills — Add supporting resources and Claude Code: Add supporting files.

      • Shared reference layout

        • The same skill and reference files can be packaged for both hosts. For example:
          • text
            				  my-plugin/
				  ├── plugin.json
				  ├── .claude-plugin/
				  │   └── plugin.json
				  └── skills/
				      └── product-reference/
				          ├── SKILL.md
				          └── references/
				              ├── terminology.md
				              └── architecture.md
        • In SKILL.md, name the trigger and link to each document, such as: “When answering questions about product terminology, read terminology.md.” The example link resolves inside the packaged skill directory.
        • OpenAI's portable package uses root plugin.json; .codex-plugin/plugin.json remains a supported compatibility format. Claude Code uses .claude-plugin/plugin.json and discovers skills under root skills/. The reference contents can stay shared while the manifests describe the package for each host. OpenAI package structure, Claude Code standard layout.

      • When the material is read

        • Supporting files are read when needed. Bundling documents does not load all their contents into every conversation. Link the documents from SKILL.md and explain when to consult each one.
        • A reference skill can answer questions from documentation without running scripts or connecting to an MCP server. OpenAI explicitly supports skills containing only packaged instructions and resources; Claude Code describes reference material as a skill content type. OpenAI skills, Claude Code skill content types.
Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?

Page reference

  • Does registering a local Codex/Plugin copy it into a home-directory cache?

    • AI Answer

      • Yes, installation copies it. Registering a marketplace tells Codex where to find a catalog; installing a plugin creates the copy used at runtime. This distinction applies even when the catalog points to a local checkout.
      • Answer/Official from Package your plugin — How local marketplaces work, checked October 15, 2026: installed plugins live under ~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/; local plugins use local as the cache directory's version segment. The runtime reads that installed copy.

      • What happens after a source edit?

        • Edit the checkout named by the marketplace entry. Treat the cache as generated installation output.
        • The Codex cache-refresh implementation has both version-conditional refresh and forced reinstall paths. Version-conditional refresh skips installation when the active version matches the source version. A saved file alone therefore does not guarantee that every refresh path copies the change.
        • The authoring documentation recommends restarting the desktop app after source changes. If the old behavior remains, bump the package version and reinstall through the plugin browser, then start a new chat. Verify the changed skill or tool behavior in that chat.
        • codex plugin marketplace upgrade refreshes configured Git marketplace snapshots. It is distinct from installing a plugin payload. The installed CLI, codex-cli 0.162.1, exposes installation as codex plugin add <plugin>@<marketplace>.

      • Can a repo still enable its own plugin?

        • Yes. A repo marketplace plus a trusted project configuration can enable a local-marketplace plugin; configured plugins can be installed or refreshed during marketplace refresh. This still uses the cache. See Codex/Plugin/Q/Is a Codex skills-only plugin the same idea as a Claude Code skills-directory plugin?.

      • How does this compare with Claude?

        • A Claude marketplace installation also uses a cache. A Claude/Code/Plugin/Skills-Directory Plugin loads from its source directory; its @skills-dir origin identifies that discovery mechanism. Claude plugin loading reference.
        • For editing a Codex skill in place, use a plain Codex/Skill under .agents/skills/<skill-name>/SKILL.md. Codex supports symlinked skill directories and detects skill changes. Build skills — local discovery.
Codex/Plugin/Q/Is a Codex skills-only plugin the same idea as a Claude Code skills-directory plugin?

  • Is a Codex/Plugin built as a "skills-only plugin" the same idea as a Claude/Code/Plugin/Skills-Directory Plugin?

    • AI Answer

      • Answer/Official from Build plugins – Codex and Plugins reference — Skills-directory plugins.
      • Short answer: No. The names collide but the two terms describe different axes. Skills-only is about composition — a plugin whose only component type is skills. Skills-directory is about discovery — a plugin found in place because of where its folder sits.

      • The two axes

        • AxisCodex "skills-only plugin"Claude "skills-directory plugin"
          What variesWhich components the bundle containsHow the host finds and loads the bundle
          Defining traitManifest points at skills/ and nothing elseA .claude-plugin/plugin.json inside a skills directory
          Components allowedSkills only, by definitionAnything — skills, agents, hooks, MCP
          Install stepYes: register in a marketplace source, then installNone: loads on the next session, labeled <name>@skills-dir
          Lives whereAnywhere; the marketplace entry points at it~/.claude/skills/ or a project's .claude/skills/

      • Why the Codex tree is the opposite row

        • The minimal Codex layout is meeting-follow-up/ containing .codex-plugin/plugin.json and skills/meeting-follow-up/SKILL.md. In the table on Claude/Code/Plugin/Skills-Directory Plugin that is the third row — a skill packaged inside a plugin — which that page explicitly separates from the skills-directory case.
        • A skills-directory plugin is the second row: the manifest sits at <skills-dir>/foo/.claude-plugin/plugin.json, so the folder you were already using for a plain skill becomes a plugin without moving or installing anything.

      • What each actually maps to

        • Codex's skills-only plugin ↔ an ordinary Claude plugin that happens to ship only skills. Same idea, both need a marketplace source and an install.
        • Claude's skills-directory plugin ↔ Codex's repo marketplace plus project plugin configuration is the closest supported plugin workflow. Codex still installs a cached copy; it does not document discovering a full plugin merely from a manifest placed inside .agents/skills/.
        • For editing skills in place, use a plain Codex/Skill in a scanned directory: $CWD/.agents/skills, $CWD/../.agents/skills, $REPO_ROOT/.agents/skills, or $HOME/.agents/skills.

      • The practical difference

        • The skills-directory plugin exists to remove the install loop while authoring — edit SKILL.md and the running session picks it up; /reload-plugins for the rest. Codex's plugin workflow uses a marketplace and an installed copy. For its cache and refresh behavior, see Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?.

      • Repo activation in current Codex clients

        • As of October 15, 2026, a repo can expose plugins through .agents/plugins/marketplace.json and enable one through its trusted project .codex/config.toml:
          • toml
            				  [plugins."my-plugin@local-repo"]
				  enabled = true
        • my-plugin matches the catalog entry; local-repo matches the catalog's top-level name. The catalog alone makes the plugin discoverable. Configured plugins can be installed or refreshed during marketplace refresh, even when configured as disabled. Enable or disable a plugin for a repo.
        • This provides a declarative repo setup for supported local Codex clients, subject to project trust and enforced requirements. It does not establish a universal promise that opening a repo activates the plugin in every ChatGPT Work surface. Workspace-imported plugins have separately managed installation and enabled state.
        • To develop and distribute the package, see ChatGPT/Plugin/How To/Develop and Share a Team Plugin for ChatGPT and Claude.
