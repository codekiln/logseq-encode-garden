GitP/How To/Draft an Episode from Session Assets
  • This guide is for the person recording a GitP episode. It describes what to give the AI assistant and what the assistant prepares before publication.
  • Ask the AI assistant to prepare the episode from that log entry. The exported WAV is the episode recording.

  • What the AI prepares

    • Episode page and audio

      • The AI creates the session episode page using Logseq/Entity/Podcast/Episode, linking the music-making log and its project, recording, and other source pointers.
      • The AI converts the exported WAV to an MP3, uploads it to Backblaze B2 at a stable, readable URL, and verifies that the uploaded file matches the prepared MP3.
      • Follow the established WAV-to-MP3 workflow and podcast encoding best practices, including an appropriate bitrate, to keep episode files manageable. The longer GitP/A/Session/26/10/29-Thu/Asset/Audio/Halloween/mp3 had trouble loading; its file size is a suspected cause.

    • MicroFreak presets

      • Every saved preset referenced by the session gets detailed notes upstream, including presets already filed in the garden and sounds used briefly. Header metadata or an empty Notes section is a starting point.
      • The notes explain the saved export and its provenance, oscillator controls, filter, envelopes, LFO, modulation matrix, and performance context. Supported units and cited sources accompany the settings; unknown conversions and session-time changes remain explicit.
      • Existing archived exports can establish the saved baseline without changing the instrument. A factory match does not establish that the session used those exact settings. An unidentified initialized patch stays a plain description rather than an invented saved preset.
      • When a new capture is needed and authorized, protect unsaved sounds and back up the slot before any rename. Upload prepared exports and add their download links. Missing slot identification leaves the instrument unchanged.

    • Session details

      • The AI reads the captured MIDI, the music-making log, and the MicroFreak and Launchpad manuals to explain what happened in the session.
      • It correlates recorded MIDI CC messages with the MicroFreak manual and reads the downloaded presets for oscillator type, preset category, and other supported details. The episode page links the sources for those details.
      • The AI distinguishes recorded changes from the settings in a saved preset. It leaves unknown details out of the episode description.

    • MIDI download

      • Export the full session as a standard MIDI file containing its notes and controller changes, with the tempo aligned to the recording.
      • Upload the MIDI and add a direct download link to the episode so listeners can import it into a DAW.
      • MIDI analysis in episode notes describes how controls vary between chapters.

    • Publication PR

      • Run mise run gitpa:preset:audit --episode 'GitP/A/Session/YY/MM/DD-Day' --check from this garden to find missing preset research before publication. The check reports recorded evidence and coverage; the notes still need review for accuracy. --all reports historical gaps without blocking site deployment.
      • The AI fills in the episode's MP3 and preset links in this garden, then mirrors the episode, every referenced preset and relevant asset pages into Gitpa and prepares a publication PR.
      • The PR includes a direct link to the one episode MP3, its episode title, and a short description so the recording is easy to find and approve.
  • For a no-go, tell the AI to hold the episode. Any changes to the recording follow that decision.

  • AI execution references

    • The gitp-asset-gathering skill describes the assistant's responsibilities. GitP/How To/Prepare Podcast Metadata covers the existing metadata commands.
    • Session-page sync and RSS generation are available. Automatic preset capture, renaming, and MIDI enrichment still need implementation; they are part of the intended workflow above.

Google/Drive/AI

  • AI access to Google Drive, Docs, and Sheets

    • Every option for pointing Anthropic's Claude at Google Drive sorts along two axes, and a comparison that collapses either one is misleading. The first is read versus write: search and retrieval are mature and available nearly everywhere, while writing splits further into file-level writes (create, upload, move, trash, share) and content-level writes (change a paragraph in an existing Doc, set a range of cells in an existing Sheet). The second is which surface Claude is running on — claude.ai in a browser, Claude/Desktop, Claude/Cowork, Claude/Code in a terminal, or the Messages API. An option that exists on one surface frequently does not exist on another.
    • The short form of the whole landscape: nothing Anthropic ships can edit the contents of an existing Google Doc or Google Sheet. That capability exists only where something calls Google's Docs and Sheets APIs directly — a community MCP server, or Claude Code running code you supply.
    • Claims below are marked verified when they come from current first-party documentation, linked at the point of the claim; inferred when reasoned from adjacent documented behaviour, with the basis stated; and silent where the documentation does not address the question.

    • The write gap, stated precisely

      • Three tiers of write, and where each is available:
      • Kind of writeWhat it meansAvailable from Anthropic?
        File-levelUpload, create folder, move, share, trashYes — Google Workspace connector
        New-file authoringProduce a .xlsx/.docx/.pptx/.pdf and save to DriveYes — file creation plus the connector
        Content-level, in placeRewrite a section of a live Doc; set cells in a live SheetNo — no Anthropic-shipped path
      • The gap matters because the last row is what most people mean by "modify a Google Sheet." A connector that uploads a new spreadsheet next to the old one is a different operation from one that edits the sheet a team is already working in.

    • Anthropic's first-party Google Workspace connector

      • Verified. The Google Workspace connectors help article documents the Drive connector's capabilities as four read items and four write items. Read: "Search and retrieve Google Docs from your Drive"; "Look up file metadata and preview directly without searching first"; "Read Sheets, Slides, PDFs, images, and MS Office files"; "View file permissions and list recent changes to your Drive." Write: "Upload any file type, with optional auto-convert to Google formats"; "Create folders"; "Share, move, and trash files in Google Drive"; "Save Claude-generated files directly to your Drive."
      • Verified — the list contains no in-place edit. Nothing in that set addresses the contents of an existing Google-native file. Every write is file-level or produces a new file. The connector directory entry is narrower still, naming only share, move and trash as writes, and stating that the connector "does not support adding comments, converting xlsx to sheets, or converting pptx to slides."
      • Verified — two Drive integrations are documented separately, with different scope. Alongside the connector, the Google Drive integration page documents a narrower document-picker for chats and projects: Google Docs only, up to 10MB, text extraction only, with Google Sheets and Google Slides both marked "Not currently supported," and images, comments and suggestions not extracted. Its stated availability is Pro, Max, Team and Enterprise. Which of the two a given surface exposes is not reconciled anywhere in the documentation.
      • Verified — auth is per-person OAuth, gated by the org on Team and Enterprise. "You must authenticate directly with your Google account before using these connectors." On Team and Enterprise, "an Owner or Primary Owner must enable these connectors at the organization level before individual users can authenticate," and "owners decide whether members can allow these actions to run without asking each time." Claude mirrors existing Google Workspace permissions rather than widening them.
      • Verified — connectors reach Claude/Code, but Drive must be authorized on claude.ai first. Per Claude Code's MCP documentation, servers added in claude.ai "are automatically available in Claude Code," and appear in /mcp marked as coming from claude.ai. That inheritance requires the active credential to be a claude.ai subscription login — it does not happen under ANTHROPIC_API_KEY, Amazon Bedrock, Google Cloud's Agent Platform, or a token from claude setup-token. Some Anthropic-hosted connectors, named as Microsoft 365, Gmail and Google Calendar, "don't support local OAuth from Claude Code because the upstream identity provider only accepts the redirect URL that claude.ai registered."
      • Inferred — Google Drive is very likely in that same category. Drive is not named in the list, but it is an Anthropic-hosted Google connector authorized through the same claude.ai OAuth redirect as Gmail and Google Calendar. The practical consequence either way is the same: connect Drive in claude.ai's connector settings, and it appears in Claude Code afterwards.

Create and edit files with Claude states that "code execution and file creation is available to all Claude users (Free, Pro, Max, Team, and Enterprise) on the web, Claude Desktop, and Claude Mobile."
