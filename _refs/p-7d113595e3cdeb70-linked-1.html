chezmoi/Q/What is the idiomatic way to add the Obsidian CLI to PATH via chezmoi dotfiles and install Obsidian in a Brewfile?

  • What is the idiomatic way to add the Obsidian CLI to PATH via chezmoi dotfiles, and install Obsidian in a Brewfile?

    • AI Answer

      • AI/Response
        • Short answer: Add cask "obsidian" to a run_onchange_before_install-packages-darwin.sh.tmpl heredoc script (the chezmoi-idiomatic package-install pattern), and export the PATH entry in dot_zprofile.tmpl with a macOS template guard.
        • Brewfile / package installation:
          • The idiomatic chezmoi pattern for Homebrew is an inline heredoc inside a run_onchange_ script, not a standalone Brewfile. chezmoi only re-runs the script when its content changes, avoiding redundant brew bundle runs on every chezmoi apply.
          • File: ~/.local/share/chezmoi/run_onchange_before_install-packages-darwin.sh.tmpl
            • bash
              					  {{- if eq .chezmoi.os "darwin" -}}
					  #!/bin/bash
					  brew bundle --no-lock --file=/dev/stdin <<EOF
					  cask "obsidian"
					  EOF
					  {{- end }}
          • Obsidian is a cask (GUI macOS app), not a formula — cask "obsidian" is the correct entry.
        • PATH addition:
          • Obsidian's settings can add /Applications/Obsidian.app/Contents/MacOS to PATH to expose the obsidian CLI binary. To manage this in chezmoi, add the export to dot_zprofile.tmpl.
          • Prefer dot_zprofile over dot_zshrc for macOS PATH additions: .zprofile loads after /etc/zprofile (which runs path_helper), so additions here survive macOS's built-in path reordering; .zshrc is for interactive aliases, not login-shell PATH.
          • File: ~/.local/share/chezmoi/dot_zprofile.tmpl
            • zsh
              					  {{- if eq .chezmoi.os "darwin" }}
					  export PATH="/Applications/Obsidian.app/Contents/MacOS:$PATH"
					  {{- end }}
          • Use .tmpl only if the file has machine- or OS-varying content. If macOS-only, a plain dot_zprofile with a hardcoded export line works equally well.
        • Sources: chezmoi macOS guide · chezmoi: use scripts · Homebrew cask: obsidian
Claude/Code/Q/If I want to use Claude Code's skill-directory plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?

Page reference

  • If I want to use Claude/Code's Claude/Code/Plugin/Skills-Directory Plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?

    • AI Answer

      • Short answer: Yes. Claude Code stats through symlinks when it scans .claude/skills/, so .claude/skills/<skill-name> can be a Symlink to a plain, non-dot folder like skills/<skill-name> — you edit the real files in Obsidian with zero configuration, and Claude Code loads the skill exactly as if it lived under the dot-directory directly. This sidesteps the Obsidian/Q/Can Obsidian be configured to show markdown files in folders that begin with a dot (dot-folders), e.g. to edit .claude/skills/<skill-name>/SKILL.md? problem entirely, since the real content never sits inside a hidden dot-folder.

      • What I verified (Claude Code 2.1.221, darwin-arm64)

        • Created skills/test-skill/SKILL.md with real frontmatter/content, then ln -s ../../skills/test-skill .claude/skills/test-skill (relative symlink) in a scratch project directory.
        • A fresh, non-interactive claude -p session in that directory logged Loaded 1 unique skills (... project: 1 ...) and, when asked, correctly quoted the skill's exact description pulled through the symlink — confirming a plain skill folder resolves fine as a symlink.
        • Repeated the test for a full skills-directory plugin (.claude-plugin/plugin.json + a nested skills/ folder, per Claude/Code/Plugin/Skills-Directory Plugin), also symlinked in. claude plugin list detected it too, reporting it as a found project-scope plugin directory — the manifest was read through the symlink without issue.

      • The one catch: project-scope plugin trust, not the symlink

        • The skills-directory plugin case (manifest-bearing folder) didn't load automatically in the test — but the reason had nothing to do with the symlink. claude plugin list reported it explicitly: "1 project-scope plugin directory under ./.claude/skills/ was not loaded because this workspace was not trusted when plugins were scanned." That is the same trust gate Claude/Code/Plugin/Skills-Directory Plugin documents for any project-scope @skills-dir plugin, symlinked or not — accept the workspace trust dialog (or run /reload-plugins afterward) and it loads.
        • A plain skill (just SKILL.md, no plugin.json) isn't gated the same way — it loaded immediately, even in a fresh non-interactive session with no trust dialog involved.

      • Practical setup

        • Keep the real files outside the dot-directory: skills/<skill-name>/SKILL.md (or the full plugin folder for a skills-directory plugin).
        • Symlink it in with a relative link so it survives clone/move: ln -s ../../skills/<skill-name> .claude/skills/<skill-name>.
        • Edit skills/<skill-name>/SKILL.md directly in Obsidian — skills/ isn't a dot-folder, so none of the dot-folder-visibility plugins are needed for this path.
        • SKILL.md edits take effect immediately in a running Claude Code session; other plugin pieces (hooks/, .mcp.json, agents/) still need /reload-plugins or a restart, per Claude/Code/Plugin/Skills-Directory Plugin.

      • A competing convention worth knowing

        • Some orgs standardize the symlink in the other direction — treat .claude/skills/ as canonical and symlink a plain-named directory (e.g. .agents/skills) to it, so other tools reach the same content without touching Obsidian visibility at all. Either direction is a valid use of the same underlying mechanism (dot-folder scanning follows symlinks); which one to use depends on whether the dot-directory or the plain directory is your source of truth.

      • Sources

        • Plugins reference — Skills-directory plugins
        • Empirical test against locally installed claude 2.1.221 (debug log + claude plugin list output), described above.
Foam/Q/Does Foam have an alias feature like Obsidian does?

  • Does Foam have an alias feature like Obsidian does?

    • AI Answer

      • AI/Response
        • Short answer: Partially — Foam supports a frontmatter alias: key that surfaces aliases in autocomplete, but unlike Obsidian, bare [[alias]] wikilinks do not resolve to the target note; they create a new note instead.

        • Frontmatter alias: (since v0.18.5, June 2022)

          • Declare alternative names in YAML frontmatter using alias: (singular — Foam differs from Obsidian's aliases:):
            • yaml
              					  ---
					  alias: JavaScript, JS
					  ---
          • Aliases appear in wikilink autocomplete; selecting one inserts [[filename|alias]] (display alias, underlying filename preserved).
          • Since v0.28.0 aliases are also indexed for VS Code's "Go To Symbol in Workspace" search.

        • Inline display alias

          • [[note-filename|Display Text]] renders as display text in preview (since v0.13.8).
          • Purely cosmetic — does not enable [[Display Text]] to resolve from elsewhere.

        • Critical limitation vs Obsidian

          • In Obsidian, declaring aliases: [JS] makes [[JS]] resolve to that note anywhere in the vault.
          • In Foam, writing [[JS]] when JS is a declared alias creates a new note instead of navigating to the aliased note. Confirmed in issue #1066, closed as "not planned" — the maintainer cited Markdown compatibility concerns.

        • Workarounds

          • Use the pipe syntax every time: [[high-cycle-fatigue|HCF]] — autocomplete helps insert this form.
          • Use Markdown reference definitions within a single file: [HCF]: high-cycle-fatigue (works only within that file).
          • Name the file with the short form (e.g. hcf.md) and put the long title in a heading.
        • Sources: PR #1014 · Issue #1066 · note-properties.md

LazyVim/Q/In LazyVim, how can I traverse wiki links in an Obsidian knowledge garden?

  • In LazyVim, how can I traverse wiki links in an Obsidian knowledge garden?

    • AI Answer

      • Short answer: the current dotfiles already enable LazyVim/plugins/extras/lang/markdown, which configures the Marksman language server. Open the garden from its root with nvim ., place the cursor inside a wiki link, and press gd. Use <C-o> to return to the previous location and <C-i> to move forward again. Press gr on a link to list references to its destination.
      • Why it works: LazyVim maps gd to the attached language server's “go to definition” action and gr to “references.” Marksman supports those actions for ordinary Markdown links and wiki links, including links to headings. Answer/Official from LazyVim's LSP documentation and the Marksman README.
      • Setup and checks:
        • 1. Start Neovim at the vault root: cd /path/to/vault && nvim ..
        • 2. Run :LazyExtras and check that lang.markdown is enabled. The current dotfiles already import this extra, and the installed Marksman reports version 2026-02-08. Answer/Official from LazyVim's Markdown extra.
        • 3. If gd does nothing, use <leader>cl to open LazyVim's LSP information and check that Marksman is attached to the Markdown buffer. :Mason shows whether the server is installed.
        • 4. If links work only within one file, make the vault a Marksman project by putting an empty .marksman.toml at its root or keeping it as a Git repository. This garden is already a Git repository. Answer/Official from the Marksman FAQ.
      • Optional Obsidian-specific navigation: obsidian.nvim adds :Obsidian follow_link, a smart action that can follow the link under the cursor, a picker for all links in the current note, and actions for moving the cursor to the next or previous valid link. It is useful when Marksman's gd and gr are too limited for the vault workflow.

My/Pref/Dev/Tool/Obsidian/Plugins in Git

Page reference

  • How I handle Obsidian community plugins in a git-committed knowledge garden

    • Applies to any Obsidian vault I keep in a GitHub/Repo, alone or with a team, where mise is the task runner.

    • Commit the list of plugins, not the plugins

      • Commit .obsidian/community-plugins.json. It names the plugins that are on, and it changes only when someone adds or removes one.
      • Ignore the whole plugins folder with one .gitignore line, **/.obsidian/plugins/, under a comment that names the install task.
      • Do not commit a plugin's manifest.json on its own. Obsidian rewrites it on every plugin update, so it churns, and it records the version the last person updated to without installing that version anywhere else.
      • Do not commit main.js or styles.css. Plugin updates are frequent, and a version bump is not worth a commit or a diff to review.
      • Keep the other per-person files ignored as well: workspace.json, workspace-mobile.json, and anything a plugin writes for one machine.

    • Install the plugins with a mise file task

      • Obsidian does not download a plugin that community-plugins.json lists but the vault lacks, so a fresh clone needs an install step.
      • The task is a mise/Task/File named for what it acts on and what it does, such as garden:obsidian:plugins:install at mise-tasks/garden/obsidian/plugins/install. It is not a script in a scripts/ folder called by a wrapper task.
      • Write it in Python as a uv script: a #!/usr/bin/env -S uv run --script --quiet shebang and inline # /// script metadata, using only the standard library, so it needs nothing installed beyond what mise provides.
      • Annotate it with #MISE description= and #USAGE lines, per My/Pref/Dev/mise/Tasks: a --force flag to download again and a --min-age-days <days> flag defaulting to 5.
      • What it does, in order:
        • Finds the vault as the one top-level folder holding .obsidian/community-plugins.json, so the task does not name the garden folder and survives a rename.
        • Looks up each plugin id's GitHub repository in Obsidian's public registry, https://raw.githubusercontent.com/obsidianmd/obsidian-releases/master/community-plugins.json.
        • Lists that repository's releases through the GitHub API, using GH_TOKEN, GITHUB_TOKEN or gh auth token when present to avoid the 60-requests-an-hour anonymous limit.
        • Picks the newest release that is not a draft or prerelease, has manifest.json and main.js assets, and is at least 5 days old. The 5 days match minimum_release_age = "5d" in mise.toml, the same supply-chain delay I use for every other dependency (see My/Pref/Dev/Tool).
        • Downloads manifest.json, main.js and, when the release has one, styles.css into .obsidian/plugins/<id>/, and removes a leftover styles.css the release no longer ships.
        • Keeps a plugin already at that version, and keeps one that is newer, because Obsidian's own updater got there first and going back could undo a settings migration.
        • Never touches a plugin's data.json.
        • Prints one line per plugin, says to restart Obsidian only when something changed, and exits non-zero naming each plugin it could not install.
      • Running it twice in a row downloads nothing the second time.
      • Updating plugins is running the task again. Nothing shows in git status.

    • Plugin settings (data.json)

      • Ignore every data.json by default. It holds one person's choices, and some plugins keep tokens there.
      • Before committing one, check whether the plugin's defaults already give the garden what it needs. Read the plugin's DEFAULT_SETTINGS in main.js. folder-notes, for example, already defaults to a folder note inside its folder named {{folder_name}}.
      • Commit a plugin's data.json only when the garden depends on a setting that is not the default. Know the cost first: everyone who already has that file untracked gets a pull error until they move theirs aside, so add it with a ! exception for that one plugin and tell people before it lands.

    • Document the step where people open the vault

      • The README's "open the garden in Obsidian" line says to run the install task first, then open the folder as a vault and choose Trust author and enable plugins.
      • The repo's agent instructions list the task with the other mise tasks, and say the garden tracks the list of plugins and not the plugins.
      • If the repo uses OpenSpec, record the rule as a requirement, so a later change cannot quietly start tracking plugin files again.

    • Moving a garden that tracked plugin files

      • git rm --cached each tracked manifest.json, main.js, styles.css and data.json under .obsidian/plugins/, and add the ignore line in the same commit.
      • Pulling that commit deletes those files from everyone else's copy, because Git removes a file the pulled commit stops tracking. A plugin without its manifest.json does not load, so say in the commit message, and to the team, to run the install task once after pulling.
      • Turn off auto-commit in obsidian-git for shared gardens, so a plugin update or one person's settings never land in a commit nobody looked at.

    • Limits I accept

      • Plugin versions are not pinned. Everyone gets the newest release that is at least 5 days old when they run the task. If a release breaks the garden, pin that one plugin in the task until a fix ships.
      • iPhone and iPad cannot run mise, so mobile users install plugins from Obsidian's Community plugins browser.
      • Someone who opens the vault in Obsidian before running the task sees the plugins listed but not installed.

Obsidian/Explanation/What a Base Is

Page reference

What a base isOverview
  • Obsidian keeps notes as Markdown files in a folder on disk. A base is a saved view that gathers a set of those files and draws them as a table: one row per file, one column per piece of information the file carries.
What a base isWhy it exists
  • That something used to be a community plugin. Obsidian/Plugin/Dataview brought its own query language in fenced code blocks; Obsidian/Plugin/obsidian-tasks brought its own fields on the checkbox line and its own query blocks. Each works well, and each is a dependency: it has to be installed, kept current, and trusted, and what it draws exists only while it runs.
What a base isWhere a base lives
  • Obsidian/Feature/Bases lists the property names a base can read, the functions a formula can call, the layouts Obsidian can draw, and a worked example of the YAML.
What a base isA row is a file
  • The question a base puts to a vault is therefore which things deserve a page of their own. A checklist inside a page still reads well — Obsidian/Feature/Task_Lists covers what a plain checkbox line holds. What has to be gathered across pages becomes a page.
What a base isHow this compares with Dataview and Tasks
  • Obsidian/Plugin/Dataview keeps fields inline, as [due:: 2026-09-16] anywhere in the body of a note, and answers queries from its own index. Obsidian/Plugin/obsidian-tasks keeps fields on the checkbox line as emoji and dates, and answers tasks queries from its own index. Both indexes live inside the plugin, in Obsidian's memory.
