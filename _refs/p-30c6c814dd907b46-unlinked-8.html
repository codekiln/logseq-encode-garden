Person/codekiln/GitHub/sourcer/Project/v0 AI Spec
  • AI agents suffer from prompt injection attacks. Allowing them to view anything on the internet is dangerous, yet to be productive they do need more context about other libraries than just what's in their pre-training. It's not wise to provide whitelisted access to github or other source code repositories for even trusted libraries may have github issues submited by a malicious actor whose comments contain hidden prompt injection attacks. srcr specifies a way that AI agents can be configured with access to source code without requiring access to the larger public internet. As long as the repositories exist on disk, they can use the source code. Instead of granting agents unrestricted access to all repositories on the internet or the entire local filesystem, Sourcer creates an explicit repository trust boundary. When working with DevContainers, this can be done by pre-cloning libraries into the image.
  • The web documentation for libraries are useful to AI agents, particularly when combined with llms.txt and published at a particular domain that can be whitelisted in a network block to avoid prompt injection.
  • If documentation is only published in a source code repository, it's difficult to provide that to an AI agent without also exposing it to prompt injection attacks from public comments on the repository.
Person/codekiln/GitHub/sourcer/Project/v0 AI Spec/Design/Thinking
  • Thinks: Prompt injection on hosting sites is real; whitelisting github.com is insufficient; local corpus must be bounded and policy-driven.

Page reference

  • Forget "Prompt Engineering." You Need AI Fluency

    • Intake

      • Captured from Readwise shared link and validated against the original Substack post.
      • Published: 2025-10-21.

    • TL;DR

      • The post argues that "prompt engineering" is overemphasized.
      • The core skill is AI Fluency: moving from asking for answers to directing a structured workflow.
      • The author frames AI as an intern/force multiplier, not an oracle or replacement for human judgment.

    • Core Thesis

      • Most poor outcomes come from vague goals, not weak wording tweaks.
      • Reliable AI outcomes come from:
        • Problem decomposition before prompting.
        • Active management of chat context quality.
        • Domain-expert verification of outputs.
        • Curated, high-signal input context.
        • Human-led final editing and integration.

    • 5-Part "Towards AI Fluency" Framework

      • 1. Architect
        • Break complex "human-sized" goals into specific "AI-sized" tasks.
        • Use an upfront project-brief style plan before opening chat.
      • 2. Navigator
        • Detect "correction spiral" and polluted context windows.
        • Restart intentionally when iteration quality collapses.
      • 3. Expert
        • Treat model outputs as plausible drafts, not truth.
        • Use domain knowledge and explicit source-checking to catch hallucinations.
      • 4. Curator
        • Prefer better context over more context.
        • Provide high-signal inputs:
          • Instructional context (how to respond).
          • Exemplar context (what good output looks like).
          • Knowledge context (curated source material).
      • 5. Collaborator
        • Operate with DIY-AI-DIY:
          • Human as Architect.
          • AI as Intern (draft/execution).
          • Human as Editor-in-Chief (verification, synthesis, final quality).

    • Practical Workflow Notes

      • When quality drops after repeated corrections, restarting can be faster than continuing.
      • Pre-work (decompose + curate) is presented as the biggest leverage point.
      • The post emphasizes durable thinking patterns over prompt "hacks."

    • Why This Matters

      • In high-noise AI environments, personal expertise becomes a quality-control layer.
      • The value shifts from "writing clever prompts" to designing and governing a repeatable human-AI workflow.

Person/Fernando Lucktermberg/Blog/26/02/The threat landscape for Agentic AI - What can actually go wrong
  • The main recommendation is defense in depth: isolate execution, gate tool actions with least privilege, constrain prompts and outputs, and continuously monitor.
  • The security model for agents must shift from prompt quality to system architecture.
  • Agent workflows create transitive trust chains across prompts, memory, tools, APIs, and runtime infrastructure.
  • 1. Input and Prompt Layer
    • Prompt injection can override task goals, exfiltrate secrets, or trigger unauthorized tool use.
    • Indirect injection through untrusted artifacts (docs, web pages, issue text, emails) is a key risk for autonomous loops.
    • Training-time or retrieval-time data poisoning can steer behavior toward attacker objectives.
  • Tool over-permissioning turns minor prompt mistakes into major action risks.
  • Prompt injection in ingested content causes the agent to call privileged tools and leak secrets.
  • Maintain high-fidelity logging/telemetry for prompts, tool calls, and state transitions.
  • Security reviews should cover end-to-end chains, not isolated prompt snippets.
  • The article positions agent security as an architectural and operational discipline, not a prompt-writing exercise.
