Logseq/Publish/Explanation/Options for Hosting Larger Files
  • Publishing a Logseq site via GitHub Pages is a convenient way to share notes, but it poses challenges when including large media files (audio 20–80 MB, videos 50–700 MB, images 7–35 MB). GitHub imposes strict file size limits and GitHub Pages does not natively support Git LFS (Large File Storage) for serving assets. This means large files must be handled carefully to avoid exceeding Git limits or incurring performance issues. Below we explore several options for hosting these larger files, considering cost, setup effort, and privacy.
  • Git LFS is an extension for Git that replaces large files in the repository with lightweight pointers, storing the actual content in a separate storage. It integrates into the Git workflow, allowing version control for large files without bloating the repository (Efficiently manage large files in Git with Git LFS, Benefits of managing large files with Git LFS).
    • Pros: Setup is straightforward and keeps media in the same repo. It allows collaborative versioning of media and uses GitHub's infrastructure, avoiding external services (Different version control tool, Earlier versions if necessary).
    • Cons: Git LFS has storage and bandwidth caps: each account gets 1 GB storage and 1 GB/month bandwidth free About storage and bandwidth usage. Exceeding 1 GB/month download bandwidth will disable LFS until the next month (unless more is purchased) (Bandwidth quota, Account until next month). A single 700 MB video viewed just twice could hit this limit. GitHub also blocks normal Git pushes over 100 MB, meaning large files must use LFS.
  • GitHub Pages limitations: GitHub Pages does not directly serve LFS content – if an LFS pointer is pushed, the published site won't retrieve the file. In fact, Pages has no built-in support for LFS GitHub Community Discussion. The workaround is to use GitHub Actions to fetch LFS files at build time and include them in the published site. GitHub now supports deploying Pages via Actions, so by enabling lfs: true in the checkout step, the action downloads the real files (GitHub Community Discussion, Standard deployment). This allows large files to be present in the static site output (bypassing the LFS pointer issue). However, be mindful: if a file exceeds 100 MB, even the Pages artifact may violate GitHub's limits if it were to be stored in a branch. Using the Actions deploy mechanism (which uploads the site via an API rather than a git push) might bypass the 100 MB git limit, but extremely large files could still pose problems or slow deployments.
  • Cost and privacy: Beyond the free tier, Git LFS requires purchasing data packs (e.g. $5 per 50 GB) for additional storage or bandwidth. If the site is low traffic, it might stay within the 1 GB/month free bandwidth, but any spike (e.g. a few people downloading a 700 MB video) would require additional bandwidth quota (Bandwidth quota, Account until next month). Privacy-wise, files in a public GitHub repository (or served via Pages) are accessible to anyone with the URL; there's no difference in privacy between hosting via GitHub vs. an external host since the site is public. One consideration is that using Git LFS means the large files are stored on GitHub's servers (and served from GitHub's CDN if included in Pages), which one may or may not trust for personal content. In general, if an all-in-one solution is preferred and the media usage is modest, Git LFS with a proper Pages Action can work, but it's not cost-effective for large videos or heavy traffic due to the strict quotas.

  • Logseq integration: Currently, Logseq doesn't have native integration to auto-upload assets to an external store, but it can be managed manually. One approach is to keep large files in a local folder (perhaps within the Logseq workspace or elsewhere) and exclude them from the Git repo. When that folder is updated, a script or rclone can be used to sync it to the object storage. Then the Logseq markdown links can be updated if new files were added. This could be semi-automated with a simple shell or Python script that uploads any new files and prints the URLs to use.
  • For an individual, low-traffic Logseq site, the simplest and most cost-effective solution is to offload large media to an object storage with free or cheap egress. Cloudflare R2 is a strong option given its no-egress model and seamless CDN integration on Cloudflare's network – all the described files could likely be hosted essentially for free (within the free-tier limits) and with minimal latency impact. If Cloudflare is already used for the domain, R2 fits in neatly. Backblaze B2 with Cloudflare CDN is another excellent choice, especially if more data is anticipated to be stored long-term (B2's storage cost is lower). B2 is proven and reliable I'm not sure about the reliability, and its free egress to Cloudflare makes it nearly equivalent to R2 for this use case. Git LFS is the most integrated with the GitHub Pages workflow but comes with significant limitations (1 GB/month bandwidth cap, requiring an Actions hack to publish, and potential costs) (About storage and bandwidth usage, Bandwidth quota). It's generally not recommended for serving media to end-users unless the files are very infrequently accessed or very small. Finally, commercial CDNs like Bunny.net can offer great performance (global replication and no fear of violating TOS for videos) at a low price point – if spending a few dollars doesn't matter, Bunny could simplify things by handling both storage and delivery. For truly zero-cost setups, sticking to R2 or B2+Cloudflare is ideal.

MinusXAI/Blog/25/08/What makes Claude Code so damn good

  • 1.1 Keep One Main Loop


    Debuggability >>> complicated hand-tuned multi-agent lang-chain-graph-node mishmash.

    Despite multi agent systems being all the rage, Claude Code has just one main thread. It uses a few different types of prompts periodically to summarize the git history, to clobber up the message history into one message or to come up with some fun UX elements. But apart from that, it maintains a flat list of messages. An interesting way it handles hierarchical tasks is by spawning itself as a sub-agent without the ability to spawn more sub-agents. There is a maximum of one branch, the result of which is added to the main message history as a "tool response".

    If the problem is simple enough, the main loop just handles it via iterative tool calling. But if there are one or more tasks that are complex, the main agent creates clones of itself. The combination of the max-1-branch and the todo list makes sure the agent has the ability to break the problem into sub-problems, but also keep the eye on the final desired outcome.

    I highly doubt your app needs a multi-agent system. With every layer of abstraction you make your system harder to debug, and more importantly you deviate from the general-model-improvement trajectory.

My/Pref/Dev/Tool/Obsidian/Plugins in Git

Page reference

  • How I handle Obsidian community plugins in a git-committed knowledge garden

    • Applies to any Obsidian vault I keep in a GitHub/Repo, alone or with a team, where mise is the task runner.

    • Commit the list of plugins, not the plugins

      • Commit .obsidian/community-plugins.json. It names the plugins that are on, and it changes only when someone adds or removes one.
      • Ignore the whole plugins folder with one .gitignore line, **/.obsidian/plugins/, under a comment that names the install task.
      • Do not commit a plugin's manifest.json on its own. Obsidian rewrites it on every plugin update, so it churns, and it records the version the last person updated to without installing that version anywhere else.
      • Do not commit main.js or styles.css. Plugin updates are frequent, and a version bump is not worth a commit or a diff to review.
      • Keep the other per-person files ignored as well: workspace.json, workspace-mobile.json, and anything a plugin writes for one machine.

    • Install the plugins with a mise file task

      • Obsidian does not download a plugin that community-plugins.json lists but the vault lacks, so a fresh clone needs an install step.
      • The task is a mise/Task/File named for what it acts on and what it does, such as garden:obsidian:plugins:install at mise-tasks/garden/obsidian/plugins/install. It is not a script in a scripts/ folder called by a wrapper task.
      • Write it in Python as a uv script: a #!/usr/bin/env -S uv run --script --quiet shebang and inline # /// script metadata, using only the standard library, so it needs nothing installed beyond what mise provides.
      • Annotate it with #MISE description= and #USAGE lines, per My/Pref/Dev/mise/Tasks: a --force flag to download again and a --min-age-days <days> flag defaulting to 5.
      • What it does, in order:
        • Finds the vault as the one top-level folder holding .obsidian/community-plugins.json, so the task does not name the garden folder and survives a rename.
        • Looks up each plugin id's GitHub repository in Obsidian's public registry, https://raw.githubusercontent.com/obsidianmd/obsidian-releases/master/community-plugins.json.
        • Lists that repository's releases through the GitHub API, using GH_TOKEN, GITHUB_TOKEN or gh auth token when present to avoid the 60-requests-an-hour anonymous limit.
        • Picks the newest release that is not a draft or prerelease, has manifest.json and main.js assets, and is at least 5 days old. The 5 days match minimum_release_age = "5d" in mise.toml, the same supply-chain delay I use for every other dependency (see My/Pref/Dev/Tool).
        • Downloads manifest.json, main.js and, when the release has one, styles.css into .obsidian/plugins/<id>/, and removes a leftover styles.css the release no longer ships.
        • Keeps a plugin already at that version, and keeps one that is newer, because Obsidian's own updater got there first and going back could undo a settings migration.
        • Never touches a plugin's data.json.
        • Prints one line per plugin, says to restart Obsidian only when something changed, and exits non-zero naming each plugin it could not install.
      • Running it twice in a row downloads nothing the second time.
      • Updating plugins is running the task again. Nothing shows in git status.

    • Plugin settings (data.json)

      • Ignore every data.json by default. It holds one person's choices, and some plugins keep tokens there.
      • Before committing one, check whether the plugin's defaults already give the garden what it needs. Read the plugin's DEFAULT_SETTINGS in main.js. folder-notes, for example, already defaults to a folder note inside its folder named {{folder_name}}.
      • Commit a plugin's data.json only when the garden depends on a setting that is not the default. Know the cost first: everyone who already has that file untracked gets a pull error until they move theirs aside, so add it with a ! exception for that one plugin and tell people before it lands.

    • Document the step where people open the vault

      • The README's "open the garden in Obsidian" line says to run the install task first, then open the folder as a vault and choose Trust author and enable plugins.
      • The repo's agent instructions list the task with the other mise tasks, and say the garden tracks the list of plugins and not the plugins.
      • If the repo uses OpenSpec, record the rule as a requirement, so a later change cannot quietly start tracking plugin files again.

    • Moving a garden that tracked plugin files

      • git rm --cached each tracked manifest.json, main.js, styles.css and data.json under .obsidian/plugins/, and add the ignore line in the same commit.
      • Pulling that commit deletes those files from everyone else's copy, because Git removes a file the pulled commit stops tracking. A plugin without its manifest.json does not load, so say in the commit message, and to the team, to run the install task once after pulling.
      • Turn off auto-commit in obsidian-git for shared gardens, so a plugin update or one person's settings never land in a commit nobody looked at.

    • Limits I accept

      • Plugin versions are not pinned. Everyone gets the newest release that is at least 5 days old when they run the task. If a release breaks the garden, pin that one plugin in the task until a fix ships.
      • iPhone and iPad cannot run mise, so mobile users install plugins from Obsidian's Community plugins browser.
      • Someone who opens the vault in Obsidian before running the task sees the plugins listed but not installed.

nvim/Explanation/When to Use a Terminal in nvim and When to Use a tmux Pane
  • A command whose output you are about to act on — a failing test's file and line, a path out of git status, a URL from a build log — costs less in the editor's terminal, because the path you want to open is already under the cursor.
  • Reach for the nvim terminal for a command that finishes and whose output you want to read, search, or open a file from: a test run, git status, a formatter, a one-off script.
