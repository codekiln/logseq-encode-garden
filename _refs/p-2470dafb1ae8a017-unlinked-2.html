AI/Coding/History/Phase/5 - Context Engineering
  • After agentic coding became the dominant paradigm, it took a while for engineers to understand how to let the agentic coding tools take actions in outside of the local filesystem, such as checking CI logs, reading JIRA or GitHub tickets, or opening PRs. After the introduction of MCP made this possible, there was a period of time where developers struggled to understand how agentic tools quickly filled up the AI/Context/Window and led to Context Rot. The term Context Engineering emerged as a way to signal the importance for minimizing the context needed to solve the problem at hand while still providing access to powerful tools.

AI/Cognitive/Science/Report/25/11/Understanding as Compression
  • Andrey Kolmogorov, Ray Solomonoff, and Gregory Chaitin formalized the concept that the complexity of an object (such as a string or dataset) can be measured by the length of the shortest computer program that generates it. This framework, known as Kolmogorov complexity, equates understanding with the ability to compress data into the simplest possible form—intuiting the "program" behind the information. In cognitive terms, learning or generalization can be seen as discovering the shortest (most efficient) models that explain sensory data[1].

AI/The Bitter Lesson/Concept/Overview
  • "the bitter lesson" is a core idea in AI that suggests the approaches which ultimately succeed over the long term are those that leverage massive computation and scalable learning, rather than relying on carefully crafted human insight or expert-designed solutions. This insight comes from decades of AI research and was notably articulated by Richard Sutton in his essay "The Bitter Lesson" (discussion here: (Time 00:24:22)).
  • Specifically, the lesson warns that clever, human-engineered solutions or attempts to insert hand-coded knowledge into AI systems may yield impressive short-term results, but these approaches are eventually outpaced by systems that scale with compute and data, such as deep learning models that eschew detailed human priors (summarized here: (Time 00:49:55)). This is because scalable learning and search algorithms, especially those that take advantage of increased computational resources and large datasets, tend to generalize better and improve further as technology advances (further explained here: (Time 00:49:24)).
  • Real-world examples of this include chess, where early AI programs attempted to encode vast amounts of human knowledge, only to be surpassed by methods that used deep search and scalable computation. The same arc is now being observed in language models and other areas of AI research, where "scaffolding" or making complex, human-designed additions to models may yield short-term improvements but will likely be abandoned in favor of more scalable approaches (see this conversation: (Time 00:24:22)). There's a recognition among researchers that "models just want to learn," and providing a simple, scalable architecture—then throwing more compute and data at it—tends to yield superior results over intricate, hand-designed features and interventions (expanded here: (Time 00:49:24)), (podcast reference: (Time 01:10:39)).

AWS/Secrets Manager/Q/What terms does AWS Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?

  • What terms does AWS/Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?

    • AI Answer

      • Answer/Official from Create an AWS Secrets Manager secret, CreateSecret API reference, and Pass Secrets Manager secrets through Amazon ECS environment variables:
      • Short answer: there is no distinct secret type for this at the API level — every secret is one opaque AWS/Secrets Manager/Secret. Answer/Official from CreateSecret API reference: "Either SecretString or SecretBinary must have a value, but not both." "Single vs. multi-valued" is codekiln's own shorthand, mapped onto two garden pages: AWS/Secrets Manager/Secret/SecretString (AWS's Plaintext tab — one raw string) is single-valued; AWS/Secrets Manager/Secret/KeyValue (AWS's Key/value pairs tab — the same field holding a JSON object) is multi-valued.
      • Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs, or choose the Plaintext tab and enter the secret in any format." Its examples: an API key → key/value pairs (ClientID, ClientSecret); an OAuth token, certificate, or private key → plaintext.
      • What only AWS/Secrets Manager/Secret/KeyValue (multi-valued) can do:
        • AWS's ready-made rotation Lambda templates. Direct citations and the full picture — including a third, Lambda-less "managed rotation" path that's gated by how a secret was created, not by its shape: AWS/Secrets Manager/Secret/Rotation. Core citation: CreateSecret API reference: "you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret" for those templates to work. AWS/Secrets Manager/Secret/SecretString (single-valued/plaintext) can still be rotated, but only with a fully custom Lambda — there's no ready-made template for it.
        • Pulling one field without app-side parsing. Pass Secrets Manager secrets through Amazon ECS environment variables: "Specifies the name of the key in a key-value pair with the value that you want to set as the environment variable value. Only values in JSON format are supported." AWS/Secrets Manager/Secret/SecretString has no key to address this way. (fnox mirrors this client-side with its json_path option, per its provider docs, including dotted nested paths.)
        • Fewer resources for related values, at lower cost. AWS Secrets Manager pricing: worked example prices a secret "@ $0.40 / secret / month" — four related values as one AWS/Secrets Manager/Secret/KeyValue secret cost the same as one AWS/Secrets Manager/Secret/SecretString, versus 4x if split into four single-valued secrets.
      • What single-valued buys you that multi-valued doesn't: nothing capability-wise — it's a strict subset. Its only edge is simplicity for a value that's genuinely atomic (a bare API key, a cert, a private key), where there's no field to key on and no rotation Lambda will ever need named subfields.
