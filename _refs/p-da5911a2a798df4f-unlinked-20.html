mise/Tool/Explanation/When to Declare Tools
  • Mise can be used to install and run tools, launch tasks, and manage environment variables. Choosing where a command lives decides whether it is upgraded by mise or by the command's own update mechanism.
  • Pin runtimes & long-lived CLIs. Anything you expect teammates or CI to call directly (python, terraform, aws_okta_keyman) belongs in [tools]. See Dev Tools Overview.
  • On-demand wrappers stay in tasks. Commands that bootstrap themselves each run (npx, go run, cargo install --locked) should be invoked inside the run = "..." line. See Tasks Guide.
  • Shims & activation. When a tool lives in [tools], mise installs it and places a shim earlier in PATH. Running prettier or aws_okta_keyman now hits that shim. See How it works.
  • exec / run. Tasks inherit the full "mise context" (all shims & env-vars) via mise run or mise exec.
  • sh
    				  mise use -g cargo:ripgrep@14
				  mise use -g npm:prettier@3

    See Getting Started: exec and run.

  • "npx will respect my [tools] pin." Not true; npx downloads a fresh copy into its own cache, bypassing shims. See npx and mise.
  • "pipx: entries auto-update on every run." They install once; updates come from mise up or version bumps.
  • Dev Tools overview – how shims, plugins, and backends work
  • Tasks guide – writing run = "..." blocks with mise run context
  • Configuration reference – complete mise.toml schema

mise/Tool/GitHub/Token/Native/GitHub/OAuth

  • Native GitHub OAuth

    • In upstream mise documentation, Native GitHub OAuth names an experimental built-in path where mise itself runs GitHub’s device flow against a GitHub App client ID (github.oauth_client_id), caches tokens, and can export GITHUB_TOKEN into the environment after mise activate / hook-env / mise env / mise exec—without requiring a PAT, app private key, gh, or ghtkn for mise’s own GitHub API traffic.
    • Enable experimental (for example mise settings set experimental true or MISE_EXPERIMENTAL=1) before relying on it; behavior and cache format may change. First-time setup uses mise token github --oauth for authorization; see the linked section for optional oauth_scopes, oauth_open_browser, and oauth_export_env.
    • Token priority for github.com lists this source after credential_command and before github_tokens.toml; the full ordering and GHE variants are summarized on mise/Tool/GitHub Token.
    • Relationship to Person/Shunsuke Suzuki/GitHub/ghtkn: the mise doc states the native OAuth design was inspired by ghtkn; if you prefer a separate binary and stdout-based wiring, use credential_command with ghtkn get as described under Using ghtkn on the same doc page.
    • GitHub/CLI tokens are a different integration: mise can read gh hosts.yml when no higher-priority token is set—see gh CLI integration on that page (mise reads the file directly; long-lived gh auth login OAuth tokens there are not the same mechanism as mise native OAuth).

mise/unuse

  • mise unuse

    • Usage: mise unuse [FLAGS] <INSTALLED_TOOL@VERSION>…
    • Aliases: rm, remove
    • Source code: src/cli/unuse.rs
    • Removes installed tool versions from mise.toml
    • By default, this will use the mise.toml file that has the tool defined. If multiple config files exist (e.g., both mise.toml and mise.local.toml), the lowest precedence file (mise.toml) will be used. See https://mise.en.dev/configuration.html#target-file-for-write-operations
    • In the following order:
      • If  mise/unuse/--global is set, it will use the mise/Config/mise.toml/Global.
      • If --path is set, it will use the config file at the given path.
      • If --env is set, it will use mise.<env>.toml.
      • If MISE_DEFAULT_CONFIG_FILENAME is set, it will use that instead.
      • If MISE_OVERRIDE_CONFIG_FILENAMES is set, it will the first from that list.
    • Otherwise just "mise.toml" or global config if cwd is home directory.
    • Will also prune the installed version if no other configurations are using it.

mise/upgrade

  • mise upgrade | mise-en-place

    • Usage: mise upgrade [FLAGS] [INSTALLED_TOOL@VERSION]…
    • Aliases: up
    • Source code: src/cli/upgrade.rs
    • Upgrades outdated tools
    • By default, this keeps the range specified in mise.toml. So if you have node@20 set, it will upgrade to the latest 20.x.x version available. See the --bump flag to use the latest version and bump the version in mise.toml.
    • This will update mise.lock if it is enabled, see https://mise.en.dev/configuration/settings.html#lockfile
mise/upgrade/Bypass minimum_release_age for One Upgrade
  • Pass --minimum-release-age 0s and name the tool: mise upgrade --minimum-release-age 0s claude-code
  • The same flag exists on mise/install, so mise install claude-code@latest --minimum-release-age 0s is the fresh-install equivalent.
  • The flag is per-invocation and leaves mise/Config/mise.toml/Global alone. To skip the gate permanently for one tool, set minimum_release_age_excludes = ["claude-code"] in mise/Config/Setting instead.

            My/Pref/Dev/mise/Tasks
            • strongly prefer mise/Task/File over mise/Task/TOML
              • put tasks in (~/.config/mise/)tasks/<namespace>/<subnamespace>/<executable_name>, almost never inline TOML [tasks."..."] entries in mise/Config/mise.toml, unless they are one-liners.
              • don't make a scripts/ folder. When a task needs a real program, write the task file itself in that language, such as a Python task with a #!/usr/bin/env -S uv run --script shebang and inline script metadata, rather than a shell task that calls a script kept elsewhere.
            • be sure to use usageCLI syntax for defining autocompletion parameters
              • Always annotate file tasks with #MISE description="..." and #USAGE directives (flags, args) for autocompletion via usageCLI. See mise docs: file tasks and mise docs: task arguments.
              • install the usage CLI globally so it is available on PATH — mise use -g usage. It is not required to run tasks, but completions of #USAGE-annotated tasks only work when usage is installed. See mise docs: autocompletion.
              • install mise shell completions into the default shell (zsh) so mise run <tab> completes task names and their usage-defined args. Either use the oh-my-zsh mise plugin, or mise completion zsh > "${fpath[1]}/_mise". See mise docs: completion and usage docs: completions.
            • see My/Pref/Dev/mise/Tasks/Discussion for rationelle
            • Document named jobs as Logseq/Entity/Mise/Task pages under the topic they serve. Task references describe the interface, outputs, side effects, dependencies, and source; linked how-tos describe the sequence of work.
            • Why?
              • My/Pref/Dev/mise/Tasks/Discussion
                • Why I prefer to use mise/Task/Files for managing jobs
                  • it integrates with usageCLI which provides Autocomplete at the CLI
                  • it provides an opinionated and yet lightweight way to add descriptive metadata and dependencies
                  • I'm already using mise as an installer, so it avoids additional dependencies
                  • mise/Task/TOML have more features I don't need such as templating when compared with file tasks, and by not using them it's a clear signal that I'm not using and don't need those extra features
                  • they are stackable; my organization can have its file tasks, and I can have my file tasks, and we can use two different dotfiles systems to manage that. if we used toml tasks, we'd be editing the same file.

My/Pref/Dev/Tool/Obsidian/Plugins in Git

Page reference

  • Install the plugins with a mise file task

    • Obsidian does not download a plugin that community-plugins.json lists but the vault lacks, so a fresh clone needs an install step.
    • The task is a mise/Task/File named for what it acts on and what it does, such as garden:obsidian:plugins:install at mise-tasks/garden/obsidian/plugins/install. It is not a script in a scripts/ folder called by a wrapper task.
    • Write it in Python as a uv script: a #!/usr/bin/env -S uv run --script --quiet shebang and inline # /// script metadata, using only the standard library, so it needs nothing installed beyond what mise provides.
    • Annotate it with #MISE description= and #USAGE lines, per My/Pref/Dev/mise/Tasks: a --force flag to download again and a --min-age-days <days> flag defaulting to 5.
    • What it does, in order:
      • Finds the vault as the one top-level folder holding .obsidian/community-plugins.json, so the task does not name the garden folder and survives a rename.
      • Looks up each plugin id's GitHub repository in Obsidian's public registry, https://raw.githubusercontent.com/obsidianmd/obsidian-releases/master/community-plugins.json.
      • Lists that repository's releases through the GitHub API, using GH_TOKEN, GITHUB_TOKEN or gh auth token when present to avoid the 60-requests-an-hour anonymous limit.
      • Picks the newest release that is not a draft or prerelease, has manifest.json and main.js assets, and is at least 5 days old. The 5 days match minimum_release_age = "5d" in mise.toml, the same supply-chain delay I use for every other dependency (see My/Pref/Dev/Tool).
      • Downloads manifest.json, main.js and, when the release has one, styles.css into .obsidian/plugins/<id>/, and removes a leftover styles.css the release no longer ships.
      • Keeps a plugin already at that version, and keeps one that is newer, because Obsidian's own updater got there first and going back could undo a settings migration.
      • Never touches a plugin's data.json.
      • Prints one line per plugin, says to restart Obsidian only when something changed, and exits non-zero naming each plugin it could not install.
    • Running it twice in a row downloads nothing the second time.
    • Updating plugins is running the task again. Nothing shows in git status.
  • The repo's agent instructions list the task with the other mise tasks, and say the garden tracks the list of plugins and not the plugins.
  • iPhone and iPad cannot run mise, so mobile users install plugins from Obsidian's Community plugins browser.

opencommit/How To/Mise OpenCommit with AzureOpenAI
  • One-line command (mise run oco) that reads staged Git changes and writes a Conventional Commit message via OpenAI models running on Azure OpenAI Service.
  • mise ≥ 2025.5 installed and initialised in your shell.

  • 1. Install tools globally with mise

    • bash
      			  mise use -g node@lts         # install Node runtime
			  mise use -g npm:opencommit   # install the CLI from NPM

  • 2. Create or open ~/.config/mise/config.toml

    • The following global config makes the task available in every repo:
      • toml
        				  [tasks.oco]
				  description = "opencommit - AI-generated Conventional Commit on staged files"
				  run = "opencommit"
				  
				  [tasks.oco.env]
				  OCO_AI_PROVIDER = "azure"
				  OCO_API_URL     = "https://your-resource.openai.azure.com/"
				  OCO_API_KEY     = "your-azure-openai-api-key"
				  OCO_MODEL       = "gpt-4o-mini"  # your Azure deployment name
				  OCO_EMOJI       = true
				  OCO_DESCRIPTION = false
    • Save and exit. mise auto-reloads configs on next run.
  • Replace literal values with secret references, e.g.

    OCO_API_KEY = "op://AI/AzureOpenAI/api-key" and OCO_API_URL = "op://AI/AzureOpenAI/endpoint-url" – these resolve at runtime when you wrap the task with op run -- mise run oco. The pattern is identical to other mise examples that embed API secrets inside env blocks.

  • 4. Commit with a single command

    1. Stage your work: git add -A

    2. Run: mise run oco --type feat --scope auth
      OpenCommit streams the generated message, then executes git commit -m "<msg>".
