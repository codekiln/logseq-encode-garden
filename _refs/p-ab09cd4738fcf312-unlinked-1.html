    • considering 1Password/Environments versus fnox
      • Setting up a 1Password Environment by hand is slow and error-prone. I will go to a secret, copy it, then go to an environment, paste it. Each time takes multiple clicks and screens. If I have 3 repos with 3 tiers each, that's something like 50 clicks, each one of which takes 15-90 seconds. That's ~45 minutes, if I do it perfectly the first time. But my clipboard buffer only contains the secret, not the name, so in practice, I need an external staging area, which itself seems like an antipattern.
      • Also, a 1Password Environment can't be shared with other people, unless one is using a team or business account; an Environment is shared through Manage environment > Manage access, per Environment, with view, edit or manage permission for people or groups. The limit I hit is probably the account type, not the feature.
      • Ten local .env files runs out fast with coding agents. The docs say "up to ten enabled local .env files per device", and agents each want a mount per git worktree.
        • A mount is turned off with the Enabled toggle in the desktop app. The docs describe no other way to remove one. GUIs are for human clickers. Not fun.
        • The 1Password/Environment/MCP server has eight tools: append_variables, authenticate, create_environment, rename_environment, create_local_env_file, list_environments, list_variables, list_local_env_files. It can create a mount but has no tool to disable or delete one, so each old worktree's mount would become a chore for a human to clean up.
          • A test run bore this out: deleting a mount's folder left the mount registered. See 1Password/Environment, Experiments.
      • The same docs page warns that mounted files "aren't designed for concurrent access", and that the first read raises an approval prompt. Approval lasts until 1Password locks, with no re-approval for further reads. The file is a UNIX named pipe, so the contents are handed to each reader on demand, but the docs say that once it is unlocked "every process can read it" until 1Password locks or the file is disabled. Approval is not tied to the process that triggered the prompt: the docs say "There's no distinction made between different processes reading the file." (Local .env files)
      • Leaning: use fnox instead of Environments while the secrets still live in 1Password.
        • fnox's op provider reads 1Password references.
        • fnox sync --local-file caches the values encrypted under an age key, optionally kept in the Secure Enclave behind Touch ID through age-plugin-se. See fnox/How To/Use Apple Secure Enclave Touch ID.
        • Each worktree gets an encrypted copy, and deleting the worktree deletes it. Sync guide
        • fnox also has an opt-in in-memory fnox/Daemon; whether worktrees share its cache is untested. I'm a bit hesitant to use this feature, as it's unlikely to be as secure as 1Password.

    • On the Impermanence of Design in the wake of AI

      • The art of Design is a creative seance that begins with a prelude of Questions. Its acolytes construct the liturgy of creation with a prelude of questions to consider before taking any action, making any decision or making anything at all. Each question is a Sample, a marble pulled from a bag, each with a different quality, valence and relevance, that we put up to our eye and that we look through before proceeding, begging us to "choose wisely."
        • What perspectives should we consider?
          • What relevant personas do we not understand enough yet, and what can we do to listen deeper to the people that have them?
        • What would be ideal?
          • In an ideal world with no constraints, what would be possible?
        • What problems exist?
          • Which problems have been hidden, overlooked?
        • What is our purpose?
          • What is our mission?
        • Which creative constraints might be practical or fruitful here?
        • What hypotheses do we have?
          • What tests could we run?
        • What precedents exist?
      • Physicists first articulated the Physics/Observer/Effect after bumping up against the impossibility of perfect objectivity. The way we observe impacts the things we observe. Design flips the script here, in a gesture of Paradox/ical Hubris, asserting that the way we ask questions impacts the things we later make.
      • Lately I can't seem to shake the feeling that the art of design is being challenged by the emergence of AI.
        • We can build something quickly, and then that thing may, or may not, or may to a certain degree result in killing our want for it.
          • Like many people, I'm pro-prototype. I love the idea of them, I love doing them, I love exploring the possibility space.
        • But, design is turning into photography. Photography is a different sort of art. It's about being in many different sorts of places, meeting different sorts of people, taking many shots, and removing many shots. It's very different than painting the Mona Lisa. It's got a bit more of the aspect of a Slot/Machine; it's subject to a Poisson process: yes, no, no, no, yes, no, no.
      • What chance does design have of surviving contact with AI? It's so much more exciting to do than to consider. As AI emerges, will a prelude of questions still be deemed to a necessary antecedent to the act of creation? Humans Satis/fice. Where will we get our recommended daily intake of Vitamin Struggle?

  • The concept of context rot has really come to shape my thoughts about AI assisted dev recently. It's given me a word to apply to that all-too-familiar feeling of when, after the LLM has started to work on a coding task for a while, ingesting the context of the codebase and the back-and forth, it stops adhering to prompting guidelines (CursorAI/.cursor/rules, Claude/Code/Claude.md files, etc). As you add tokens, it gradually fills up the "short term memory" in such a way that decreases the amount of "attention" it can spend on a task.     • In Max's [dbtoa] object, the conversion from decibels (dB) to linear amplitude isn't constrained to the usual 0 to 1 range of a normalized signal. Here's why:

    • The Relationship Between dB and Linear Amplitude


      The formula used by [dbtoa] is:

      Linear Amplitude=10dB20text{Linear Amplitude} = 10\frac{\text{dB}{20}}

      This relationship is based on the way decibels describe the ratio between two power levels or amplitudes in a logarithmic scale. Let’s calculate it for 6 dB6 , text{dB}:

      10620=100.3≈1.995310\frac{6{20}} = 100.3 ≈ 1.9953

      This means that a signal with a gain of 6 dB is approximately 1.9953 times louder in linear amplitude.

    • Why It Exceeds 1

    • The [dbtoa] object doesn't normalize or constrain the output; it's a direct mathematical conversion.
    • The range of 0 to 1 in normalized signals is a convention in audio programming, typically used for gain controls or normalized data representation. However, linear amplitude values in the real world can exceed 1, representing gain boosts.


      For example:

    • 0 dB0 , text{dB} corresponds to 10020=110\frac{0{20}} = 1, which is unity gain (no change in amplitude).
    • 6 dB6 , text{dB} corresponds to a doubling of amplitude.
    • Negative dB values (e.g., −6 dB-6 , text{dB}) produce values less than 1 (attenuation).

    • How This Relates to Normalized Audio Signals


      In Max, signals are often normalized between 0 and 1 to represent relative amplitude levels for practical processing, but if you apply a gain boost (e.g., +6 dB), the amplitude can exceed this range.

      If you want to constrain the output back to 0–1, you could normalize the result manually. Otherwise, [dbtoa] simply converts dB to linear amplitude without applying any clipping or limiting.

AI/Security/Attack/Agentic/Tool Chain/Poisoning

  • My Thoughts

    • Here, in order for an attacker to compromise the MCP/Tool, one of these root problems must be true: Root Problems for MCP Server Attacks
  • My Thoughts
    • This is a tricky one to talk about.
    • Here, CrowdStrike is trying to explain a concept they've called AI Tool Poisoning, which, in my opinion, is basically a supply chain attack applied to an MCP server.
    • Every time someone talks about MCP servers, you should just substitute the word "API server."
    • The problem here is about API security, not about MCP security. In the case of "Permissive Schemas" example, one can provide tool input that elevates them to an admin. So someone has made an API server where apparently an unprivileged user of that API supplies an unprivileged API key and yet it is able to gain access to administrative functionality. This is either because of a security vulnerability in the API server or because the server author hasn't created scoped OAuth permissions. While MCP server authors should responsibility for securing an API is not and should not be on the MCP Server author.
    • To be fair, "admin: true" is just a poor example of why "permissive schemas" are a unique part of the problem with MCP. This one is fundamentally about the thing that makes security people nervous: the more features and permissions a user has, the harder it is to understand how it might be used maliciously. A better example might involve a multipart attack on a user's ability to update their profile and change locale settings, timezone, name, etc.
