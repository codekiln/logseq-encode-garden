FastAPI/Concept/Starlette BackgroundTasks with FastAPI and AsyncIO - Deep Research
  • FastAPI leverages Starlette's in-process background task system to run operations after sending an HTTP response. A background task is a function (sync or async) attached to a response that executes only once the response has been sent to the client (Background Tasks - Starlette). FastAPI provides a BackgroundTasks utility (built on Starlette's BackgroundTask) to collect multiple tasks during request processing and ensure they run post-response (FastAPI/Docs/Tutorial/Background Tasks). This allows you to offload non-critical work (e.g. sending emails, writing logs) so it doesn't block the main request/response cycle (FastAPI/Docs/Tutorial/Background Tasks).
  • Sequential Execution: Tasks run one after the other, in the sequence they were scheduled (Background Tasks - Starlette). They do not all start at once.
  • Post-Response Start: All background tasks begin only after the FastAPI endpoint has returned its response to the client (Background Tasks - Starlette). The HTTP response is sent immediately once ready, and tasks execute asynchronously thereafter.
  • In development (e.g. using Uvicorn with reload, or running under PyCharm/VSCode debugger), this mechanism remains the same. One thing to note during debugging: because sync tasks run in a separate thread, you might need to ensure your debugger is configured to stop on exceptions in all threads. If you set a breakpoint inside a background task function, it will hit when that task executes (which is after the response). Otherwise, an unhandled exception in a background thread might just print to the console. In single-process debug mode, all tasks run on the one event loop (plus threads for any sync tasks), so you can step through them as normal once they start.
  • Using an asyncio.Queue with a Worker: For scenarios where you have many background jobs produced by requests and you want to regulate their execution (for instance, limit how many run at once or process them in order), an architecture with an in-memory queue can be useful. You can create an asyncio.Queue and have a dedicated worker coroutine (started at app startup) that pulls tasks from the queue and executes them one by one. Your request endpoints would queue.put_nowait(job) instead of using BackgroundTasks. This approach gives you more control (you can retry jobs, bulkhead isolate them, etc.), but it's more complex to implement. It also remains in-process; if the server restarts, queued jobs vanish unless you persist them.

  • Does Google Sheets have a way to sort by more than one column at once?

    • AI Answer

      • Answer/Official from Sort & filter your data, SORT function, and SORTN
      • Short answer: Yes, on the web, through one specific dialog. Highlight the cells, then Data > Sort range > Advanced range sorting options, choose the first column and its direction, and click Add another sort column for each further level. That dialog is the only documented multi-column sort in the interface — the right-click commands on a column letter sort by one column only, and the Android and iPhone apps document nothing beyond a single key.
      • The distinction that decides the answer is range versus sheet, not column count. Someone who reaches for sorting by right-clicking a column heading — the faster and more discoverable route — never sees the multi-column option and can reasonably conclude it does not exist.

      • The multi-column dialog, step by step

        • Verified — the full documented sequence.         • Verified — the control is named for repetition, and the wording marks the sort as ordered. The button is Add another sort column, and the preceding step asks for the column to be sorted first. Each rule after the first is a tie-breaker within the rules above it, which is what "sort by more than one column at once" normally means.
        • Verified — each level carries its own direction. The step that picks a column also says "choose a sorting order," and it sits inside the repeated block rather than outside it. Ascending on one column and descending on the next is a documented combination, not a workaround.
        • Verified — header handling is two separate steps. Freezing the first row comes before opening the dialog; Data has header row is ticked inside it. The documentation lists both and explains neither, so do not assume one substitutes for the other.
        • Could not confirm — how many sort columns are allowed. No maximum appears anywhere in the article. The step is phrased as a repeatable action with no stated limit, so there is no documented ceiling to cite and no documented guarantee either.

      • Sorting a range and sorting a whole sheet are different commands, and only one is multi-column

        • Verified — the whole-sheet command takes a single column. The same article's Sort an entire sheet section is three steps: open the spreadsheet, then "At the top, right-click the letter of the column you want to sort by," then "Click Sort sheet A to Z or Sort sheet Z to A."         • Verified — the multi-column dialog lives only on the range path. Advanced range sorting options appears in the article exactly once, inside the Data > Sort range sequence. The whole-sheet section does not reference it and offers no equivalent.

        • Verified — SORT is documented as multi-column in its first sentence. SORT function: "Sorts the rows of a given array or range by the values in one or more columns."   • herdr takes the copy once, at the moment of the keypress, and never updates it. While the editor is open the pane goes on printing into its own history, and the file stays as written.
  • Getting text out of a pane that is awkward to select with the mouse. Once the history is a file, the editor's own copy and clipboard behaviour applies to all of it.

  • On macOS and Linux the editor runs inside a small /bin/sh wrapper. The wrapper runs the editor, keeps its exit status, deletes the file, and exits with that status (src/platform/macos.rs:46-52, src/platform/linux.rs:104-110). So the file is deleted twice, once by the shell and once by herdr.
  • Either way, the file is gone once the editor exits, and herdr has no code path that reads it back into the pane.
  • "The file keeps up with the pane." herdr writes it once, before the editor starts, and the file says nothing about what came after.
