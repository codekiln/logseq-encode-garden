Ableton/Live/Report/26/09/Open-source options for controlling Live 11 from coding agents
  • AbletonOSC and PyLive — Live 11+ Remote Script, OSC, Python API, and CLI. Mature base for a small custom interface; default OSC listener exposes control to the LAN. [7]
  • ableton-live-mcp-server — MCP and OSC wrapper around AbletonOSC, inheriting its unauthenticated UDP listener. [8]
  • OSC/MIDI layers can hide that coupling rather than remove it. AbletonOSC gives external programs a pleasant OSC interface and PyLive wraps that from Python, but AbletonOSC itself is still a MIDI Remote Script operating inside Live. Its README says its goal is to expose the Live Object Model through OSC, and explicitly requires Live 11 or later. [7] This is nevertheless useful architectural separation: an agent can be restricted to sending defined OSC messages instead of receiving a generic Python-evaluation primitive.
  • AbletonOSC + PyLive deserves special treatment because it predates the agent/MCP rush and is arguably the most credible underlying open-source API stack. AbletonOSC has hundreds of commits and substantial community adoption, explicitly supports Live 11+, and exposes a broad Live Object Model-like surface over OSC. It even includes a simple run-console.py interactive CLI, so an agentic coding tool capable of operating a terminal can drive Live without MCP at all. [7] PyLive provides a higher-level standalone Python interface on top of AbletonOSC and similarly targets Live 11+. [31]
  • Unfortunately, AbletonOSC has the clearest network-security defect I found in a mature project. The actual server constructor defaults to local_addr = ('0.0.0.0', OSC_LISTEN_PORT), and its own source explains that this listens on every available local IPv4 interface. The UDP socket is then bound directly to that address. [33] There is no authentication layer in the OSC protocol shown here. Because AbletonOSC provides mutating operations—track creation, parameter changes, playback, clip manipulation, and more—that means another machine able to reach UDP 11000 can potentially control the running Live instance. The README's statement that it “listens on port 11000” understates this important distinction. [7]
  • Simon Kansara's ableton-live-mcp-server essentially turns AbletonOSC into an MCP stack. It uses an MCP server plus an OSC-facing daemon and requires AbletonOSC; the MCP-facing components default to localhost. Its repository had meaningful community interest but only around 18 commits when inspected, so much of its real maturity comes from the older AbletonOSC layer below it rather than from the MCP wrapper itself. [8] The security trap is that putting a localhost MCP server in front does not fix AbletonOSC's own 0.0.0.0:11000/UDP binding. [33] I found no comparably strong professional-maintainer provenance for this wrapper, so I would choose it for convenience, not because it improves the trust story.
  • On the other hand, this is an enormous authority surface. Its architecture includes TCP 9877, UDP 9882, optional OSC/UDP 9878/9879, and a web dashboard; the README explicitly shows the dashboard on 127.0.0.1, but in the material I inspected I did not find an equivalent security statement establishing authentication or loopback-only defaults for every Remote Script transport. [10] The creator's own GitHub profile says they would like to work for Ableton or Anthropic, which is useful evidence that this is not an Ableton- or Anthropic-affiliated project. [38] I would call it an impressive experimental project, not a trust-minimized production choice.
  • Best option for building your own minimal interface: AbletonOSC/PyLive, after fixing network exposure. For an AI architect, this may actually be the most appealing long-term design. AbletonOSC is older, smaller conceptually, Live-11-native, well understood, and already has both a programmatic OSC API and interactive console. [7] Put it on loopback instead of its default 0.0.0.0, expose only a dozen commands through a tiny local stdio MCP server or CLI, and you have a much smaller reviewable trusted-computing base than a 300-tool agent framework. The stock wildcard bind is the part I would not accept. [33]

  • [33] https://github.com/ideoforms/AbletonOSC/blob/master/abletonosc/osc_server.py

Ableton/Live/UG/31 Instrument Reference/10 Sampler
  • Ableton/Live/UG/31 Instrument Reference/10 Sampler/07 The Pitch-Osc Tab

    • 31.10.7 The Pitch/Osc Tab

      • 31.10.7.1 The Modulation Oscillator (Osc)

        • One modulation oscillator per voice performs FM or AM on the samples; it is never heard directly. Subsonic AM varies volume; audible AM creates composite waves.
        • 21 waveforms in Type, a loopable amplitude envelope with the usual levels, and:
          • Volume — modulation depth; Vol < Vel scales it with velocity.
          • Fixed with Freq × Multi — a constant frequency.
          • Coarse (0.125–48) and Fine (0–1000) — tuning when not fixed.

      • 31.10.7.2 The Pitch Envelope

        • A multi-stage envelope on the sample's pitch, and the modulation oscillator's; drag breakpoints or use sliders. Amount sets its range in semitones.
        • Global controls on the right:
          • Spread — two detuned voices per note; doubles CPU.
          • Transp (semitones) and Detune (cents).
          • Zn Shft — shifts which key zone plays without changing pitch, for interesting multisample artifacts.
          • Glide — Glide is monophonic, Portamento polyphonic; Time sets duration.

CNMAT
  • CNMAT externals for Max/MSP – a suite of audio and data processing objects emphasizing time-tagged messaging and OSC (Open Sound Control).
  • OSC (Open Sound Control) – co-developed at CNMAT, this protocol enables high-resolution, symbolic control of musical parameters across networks.
  • javascript
    		  // CNMAT JavaScript example in Max
		  var osc = require("osc");
		  var udpPort = new osc.UDPPort({
		      localAddress: "127.0.0.1",
		      localPort: 57121
		  });
		  udpPort.open();
  • max
    		  // Max patch using CNMAT's [o.route] for OSC message routing
		  [udpreceive 57121]
		  |
		  [o.route /synth/frequency /synth/amplitude]
  • OSC is just another MIDI replacement → OSC is much more flexible, supporting symbolic addressing, bundling, and high-resolution parameters.
Codex/CLI/Q/How can the Codex conversation name become the tmux pane title?
  • Restart Codex, then name the chat with /rename <name>. Codex writes that chat name as the terminal title. tmux receives the same OSC 2 title sequence and stores it as the pane's pane_title, which appears on the pane row when the tmux/session/Picker tree is expanded.
  • allow-rename is unrelated: tmux uses it for a program changing the window name. OSC 2 and select-pane -T set the pane title.
CursorAI/CLI/Q/Can cursor-agent be configured to open a file in Neovim for editing?
  • Click-to-open in terminal: Whether a path in the terminal is clickable and what happens on click is controlled by your terminal emulator, not by cursor-agent. Many terminals (e.g. iTerm2, Kitty, Ghostty, Warp) support clickable file paths (e.g. OSC 8 hyperlinks or Cmd+click). You can often configure the action on click (e.g. run a custom command such as nvim "$path" or open with a specific app). So you can get “click path → open in Neovim” by configuring the terminal, not cursor-agent.
Ghostty
  • Ghostty supports OSC 8 hyperlinks (clickable regions emitted by programs). Linked text is visually distinct (e.g. dotted underline, hover underline)
    • On macOS, ⌘-click opens the link via the platform; on Linux, Ctrl-click is the usual pattern
    • copy_url_to_clipboard can copy the target from regex-detected URLs or OSC 8 hyperlinks
  • URLs vs file paths: https://… style links are the common case. A bare path in compiler output is not automatically clickable unless something wraps it in OSC 8 (or you rely on URL-shaped text Ghostty already recognizes — plain relative paths usually are not)
  • file://: if a tool emits OSC 8 with file:///…, Ghostty still delegates to the OS default for that path/type — often not nvim unless you change file associations or register a custom URL handler / wrapper scheme
  • tmux stack: use a recent tmux (about 3.4+) and declare hyperlink capability (e.g. hyperlinks via terminal-features) so OSC 8 sequences survive inside panes; Ghostty remains the emulator that actually handles the click
  • Reality check for “always nvim”: not a first-class “tmux feature”; you need emitters (build tools, grep wrappers, test runners) that print OSC 8, plus OS or app-level routing if you want nvim instead of the default app — otherwise copy-link / yank-path workflows or editor-native navigation (e.g. quickfix, LSP) stay the reliable path
Ghostty/Q/How can I click on links in Ghostty and have them load in the default browser?
  • tmux-oriented pattern: In copy mode, move to a URL, select it, then either yank to the OS clipboard and paste in a browser (many configs already bridge yank → clipboard) or pipe the selection to open (macOS) / xdg-open (Linux) with copy-pipe-and-cancel so the OS default handler runs—see tmux(1). Garden walkthrough of copy mode ↔ clipboard: tmux/Q/What is a conceptual overview of how copy paste works in oh-my-tmux with nvim?. Caveats: tmux operates on the pane grid (wrap/newlines matter); OSC 8 hyperlinks help only if the whole stack preserves them (tmux version, terminal-features / hyperlinks, emulator)—see discussion #4618.
  • Emulator-side — modifier + click (Ghostty): Plain URLs and OSC 8 hyperlinks are opened with the system default handler (your default browser for https://). You hold a modifier while clicking — not a bare left-click.
    • macOS: ⌘-click (super)
    • Linux (GTK): Ctrl-click (control)
  • Hover feedback: With the modifier held, Ghostty highlights the link (e.g. underline / pointer cursor). If nothing highlights, the text may not be a recognized URL or OSC 8 link (plain file paths in compiler output are usually not clickable unless wrapped in OSC 8).

herdr/Q/Can herdr show the current session name, and how do I switch sessions?
  • ui.window_title exists but has no session token. It writes the outer terminal's title (OSC 0), which is what window managers show in title, tab, and group bars. It defaults to "{hostname}: {workspace}", accepts {hostname}, {workspace}, {tab}, {pane}, and {terminal_title}, and takes "" to leave the outer title alone. It renders on the server, so {hostname} names the host the panes run on even when attaching from a remote client.
  • Set the outer terminal title yourself before launching, from a wrapper that emits OSC 2 alongside herdr session attach <name>. Nothing in 0.8.0 will overwrite it.
