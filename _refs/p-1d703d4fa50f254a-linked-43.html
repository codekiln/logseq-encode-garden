Logseq/Entity/Collection

Page reference

Collection
  • In this garden, the Collection pattern models a curated collection whose members are all instances of some other entity type. It is not instantiated directly — it is specialized per member type as <EntityType>/Collection (e.g. Logseq/Entity/Software/Plugin/Collection), and each specialization points back here for the shared rules.
CollectionDistinct from multiple entity membership
  • This is a different axis from Logseq/Entity → multiple entity membership. Multiple membership = one page is several entity types at once (e.g. Question + Card). The Collection pattern = one page is a single entity whose members are of type X. (A collection page may still use multiple membership for unrelated reasons.)
CollectionSpecializations in this garden
  • Logseq/Entity/Software/Plugin/Collection — curated collections of plugins for a host (LazyVim extras, VS Code Extension Packs, …).
CollectionSpecializations in this garden
  • Ordered sequences of another entity type are Logseq/Entity/Series, not a Collection specialization.

Color Theme
  • In this garden, Color Theme pages model coordinated palette families (foreground, background, accent colors) reused across terminals, editors, multiplexers, file managers, and other UI tools. A color-theme instance is the aesthetic system (e.g. Catppuccin with subpages Catppuccin/Latte, Catppuccin/Frappe, Catppuccin/Macchiato, Catppuccin/Mocha); individual ports often stay Logseq/Entity/Software/Project instance pages that link back to the theme hub.

The theme hub lists app wiring without duplicating full plugin documentation.

Page reference

Mark each page with the most specific entity in each lineage
  • Each page should list only its most specific entities. A musician who is also a knowledge gardener lists Logseq/Entity/Person/Musician and Logseq/Entity/Person/Knowledge Gardener and leaves out Logseq/Entity/Person, because each of those is already a kind of person. Musician, then Person, is one lineage: an entity followed by each entity it is a kind of. This narrows the hypothesis codekiln wrote in the 2026-10-01 Thu journal: the rule covers only a child entity that is a kind of its parent, and it lets one page carry two sibling entities. The Musician, Knowledge Gardener and User Guide definition pages currently say to mark each instance with the parent entity as well.
Mark each page with the most specific entity in each lineageA child entity is either a kind of its parent or a part of it
  • Is-a. Every instance of the child is also an instance of the parent: Logseq/Entity/Article/Blog, Logseq/Entity/Repo/Awesome, the Logseq/Entity/Book/Section levels, Logseq/Entity/Person/Musician, Logseq/Entity/Person/Knowledge Gardener, Logseq/Entity/Book/User Guide.
Mark each page with the most specific entity in each lineageA child entity is either a kind of its parent or a part of it
  • Part-of. The child is a different thing that belongs to the parent: Logseq/Entity/Podcast/Episode in a show, Logseq/Entity/Forum/Post in a forum, Logseq/Entity/Trade-Off/Component in a trade-off. Logseq/Entity/YouTube/Playlist runs the other way: a playlist contains videos.
Mark each page with the most specific entity in each lineageA child entity is either a kind of its parent or a part of it
  • Some segments under Logseq/Entity/ have no definition page and serve only as a namespace. Logseq/Entity/AI is one, so Logseq/Entity/AI/Model has no parent entity.
Mark each page with the most specific entity in each lineageA child entity is either a kind of its parent or a part of it
  • Listing a child entity together with its parent is redundant for an is-a child and false for a part-of child. A page carrying Logseq/Entity/Podcast and Logseq/Entity/Podcast/Episode would claim to be a show and one of its episodes, and no single thing is both. Instance paths already express part-of: Hard Fork/Pod/26/09/A.I. Safety Goes Mainstream + a ‘Hard Fork’ Exit AMA files under Hard Fork/Pod.
Mark each page with the most specific entity in each lineageA child entity is either a kind of its parent or a part of it
  • Only the text of a child definition page says whether the child is a kind of its parent or a part of it. codekiln proposed a frontmatter property that would make this explicit and queryable: logseq-entity-hierarchy-type::, described on Logseq/Entity/Hierarchy/Frontmatter/Type. Logseq/Entity/Hierarchy/Frontmatter/Type/extends
extends
  • The child entity is a kind of its parent: every instance of the child is also an instance of the parent, and the child definition page states only how its instances differ from the parent's. Logseq/Entity/Person/Maker extends Logseq/Entity/Person, and Logseq/Entity/Article/Blog extends Logseq/Entity/Article.
extends
  • Permitted value of Logseq/Entity/Hierarchy/Frontmatter/Type.
Logseq/Entity/Hierarchy/Frontmatter/Type/part-of
part-of
  • The child entity is a different thing that belongs to an instance of its parent. An episode belongs to a show, so Logseq/Entity/Podcast/Episode is part of Logseq/Entity/Podcast, and one page is never both a show and one of its episodes. Whoever files a part-of instance usually puts its page under the page of the thing it belongs to, so an episode's page goes in its show's Pod namespace, as Hard Fork/Pod/26/09/A.I. Safety Goes Mainstream + a ‘Hard Fork’ Exit AMA sits under Hard Fork/Pod.
