1Password/Q/What can I do with 1Password in Claude Desktop's Code tab vs Codex in the ChatGPT desktop app, as of 2026-09-30?

  • What can I do with 1Password in Claude/Desktop/Code vs Codex in the ChatGPT/App/Desktop, as of 2026-09-30?

    • AI Answer

      • Short answer: For 1Password/Environments, the two are nearly the same. 1Password ships a plugin for each, and both plugins wrap the same local 1password-mcp server with the same eight tools and the same 1password-environments skill. The Claude plugin adds one thing the Codex plugin lacks: a hook that stops shell commands when a mounted .env is broken. The loud "1Password for Claude" launch in July 2026 was about something else, browser logins, and it is not aimed at the Code tab.

      • Side by side

        • CapabilityClaude/Desktop/Code + 1PasswordCodex in ChatGPT/App/Desktop + 1Password
          1Password-built plugin1Password/GitHub/1password-claude-plugin1Password/GitHub/1password-codex-plugin
          List, create, rename Environments✓✓
          See variable names, never values✓✓
          Append variables and placeholders✓✓
          Mount an Environment as a local .env✓ macOS, Linux✓ macOS; Windows unclear
          Import-and-mount skill✓ 1password-environments✓ 1password-environments
          Hook that checks mounts before shell commands✓ PreToolUse✗ not shipped
          Install from the GitHub repo as a marketplace✓✓
          op CLI and SSH agent in the terminal✓✓
          Agent browser logins through 1Password~ macOS; for browser tasks, not Code tab✗ none found

      • Environments: what is the same

        • Both plugins register 1password-mcp (1Password/Environment/MCP) and expose authenticate, list_environments, create_environment, rename_environment, list_variables, append_variables, create_local_env_file, and list_local_env_files.
        • The agent sees Environment names, variable names, and mount paths. Values stay in 1Password. The desktop app asks for approval the first time a client touches an Environment.
        • Useful prompts are identical on both sides: "import .env into 1Password and mount it here", "add a placeholder for my OpenAI API key".
        • Outside the plugins, both apps run commands in a local shell, so op run, op read, 1Password/Dev/CLI/Shell Plugins, and the 1Password SSH agent behave the same way in either one.

      • Environments: what differs

        • Mount check hook. The Claude plugin's PreToolUse Claude/Code/Hook runs before every Bash command. It checks that each mounted .env exists, is a named pipe, and is switched on in 1Password, and blocks the command when one is not, so Claude can say "your staging mount is off" instead of your app failing with a missing key. The Codex plugin ships skills and MCP config but no hook. That gap comes from 1Password, not Codex: Codex/Hooks support PreToolUse, and Codex plugins can bundle hooks/hooks.json. 1Password's separate agent-hooks repo lists Cursor, Claude Code, GitHub Copilot, and Windsurf, and does not list Codex.
        • Windows. The Claude plugin says mounts and the MCP server are macOS and Linux only. On Windows its skill switches to op run --environment=<id> -- <command> (1Password/Dev/op/run). The Codex plugin README claims macOS, Windows, and Linux. The Claude README also says "1Password Environments has no local .env mounts on Windows", so on a Windows ChatGPT desktop app, expect the listing and editing tools to work and mounting to fail until 1Password says otherwise.
        • Turning the server on. The Claude README points to a Labs experiment, Settings → Labs → MCP Server (feature flag ai-local-mcp-server). The Codex README points to Settings → Developer. These two 1Password READMEs contradict each other, and the likeliest reason is that the setting moved out of Labs. Check your own 1Password build.
        • Install path.
          • Code tab: /plugin marketplace add 1Password/1password-claude-plugin, then /plugin install 1password@1password. The Code tab uses the same plugin system as the CLI (Claude/Code/Plugin/Marketplace).
          • Codex: codex plugin marketplace add 1Password/1password-codex-plugin, then restart and turn the plugin on (Codex/Plugin). The OpenAI Plugin Directory listing is skills-only, because the directory refuses local stdio MCP servers, so installing from the directory gets the skill without the server. Install from GitHub to get both.
        • Not a Claude Desktop extension. The Claude repo's GitHub description says "Claude desktop extension (MCPB) for macOS", and that is out of date. The repo is now a Claude Code plugin with no .mcpb bundle, so it adds nothing to Claude Desktop's chat or Cowork tabs through Claude/Desktop/Extension.
        • Code tab's own env vars. Claude/Desktop/Code also has a Local environment editor that Claude Desktop stores for you. That is Anthropic storage, not 1Password, and it works independently of the plugin.

      • Browser logins: the part the blog covers

        • The 1Password for Claude launch (July 16, 2026) lets Claude sign in to websites without seeing the password. When Claude needs a login, 1Password asks you to approve with Touch ID, then injects the credential straight into the page, so it never enters Claude's context. The 1Password browser extension adds an Agentic Mode that locks the vault down to only the logins you approved. (Help Net Security, Engadget, 1Password Marketplace)
        • It requires macOS, a paid Claude plan, the Claude desktop app with Claude's browser extension, and the 1Password desktop app with its browser extension. It targets Claude driving your browser, as in Claude/Cowork, not the Code tab's terminal work. The Code tab's built-in Claude/Desktop/Code/Browser pane is not mentioned in any source found, so treat it as unsupported until tested.
        • The ChatGPT desktop app has no counterpart as of 2026-09-30. ChatGPT/Atlas shut down on August 9, 2026, after being folded into the desktop app. Search turned up no 1Password agentic-autofill integration for ChatGPT or Codex. The May 2026 1Password and OpenAI announcement (1Password press) is the Environments MCP server described above.

      • Which to pick

        • For secrets in a repo on a Mac, either works. The Code tab has the edge because the hook catches broken mounts before a command runs.
        • For Claude or Codex to sign in to websites, only Claude has a 1Password integration today, and it lives in Claude's browser tasks rather than the Code tab.

      • Sources and gaps

        • Plugin facts come from the two repos' READMEs and file trees as of 2026-09-30.
        • The 1Password blog and docs sites were blocked from this research session, so the browser-login summary relies on press coverage, and the Labs-versus-Developer setting has not been checked against a running 1Password app.

Claude/Code/Q/If I rename a CLI session with /rename, can I resume it in Claude Desktop's Code tab?

  • If I rename a Claude/Code CLI session with /rename, can I resume it in Claude/Desktop/Code?

    • AI Answer

      • Answer/Official from Manage sessions and Desktop application:
      • Short answer: No. /rename creates a resume handle that only the CLI honors, and the Code tab keeps a session history of its own — a CLI session never appears in its sidebar, named or not. The one bridge runs the other way: /desktop hands the live CLI session over to the app.
      • What /rename buys you, and where: the name shows on the prompt bar and in the /resume picker, and becomes a resume handle — claude --resume <name> or /resume <name>, resolved across the current repository and its worktrees. It replaces the AI-generated session title, which is display-only and is not a resume handle.
      • Why the Code tab can't see it: the docs state plainly that the desktop app, Claude Code on the web, and the VS Code extension "each maintain their own session history." The CLI–Desktop relationship is spelled out under Coming from the CLI?: both can run at once on the same machine and even the same project, and "Each maintains separate session history, but they share configuration and project memory via CLAUDE.md files." Config and memory are shared; the session list is not.
      • There is no /resume in the Code tab to begin with. The CLI-flag equivalence table maps --resume / --continue to "Click a session in the sidebar" — and that sidebar is a list of Desktop's own sessions, filterable by status, project, and environment, with no picker or search that reaches into CLI history.
      • Rename direction that does cross over: renaming a Remote Control session from claude.ai or the Claude app applies the same name in the CLI (needs Claude Code v2.1.221+). The Desktop equivalent does not reciprocate — per the docs, "a desktop-app session resumes in the app, which keeps its own session history."
      • The actual bridge — /desktop: run it in the terminal and Claude saves the session, opens it in the desktop app, and exits the CLI. Constraints: macOS and x64 Windows, signed in with a Claude subscription; unavailable with API-key auth or on Amazon Bedrock, Google Cloud's Agent Platform, and Microsoft Foundry. It is a one-way handoff of the session you are sitting in — not a picker for arbitrary past CLI sessions.
      • A structural reason beyond the store split: every Code tab session in a git repository gets its own isolated worktree under <project-root>/.claude/worktrees/ (see git/worktree), plus the status, PR, and environment metadata the sidebar filters, groups, and auto-archives on. A plain CLI session carries none of that, so there is nothing for the sidebar to file it under.
      • Observed locally, undocumented: CLI transcripts live at ~/.claude/projects/<project>/<session-id>.jsonl, and /rename is recorded inside that transcript as a custom-title entry — so the name travels with the file, which is why the CLI can resolve it from any directory. Desktop tracks its Code tab sessions in a separate registry keyed by local_-prefixed ids. The transcript entry format is documented as internal and subject to change between releases, so don't build on it.
      • Wanted, not shipped: open requests cover this exactly — Desktop app should list and resume CLI sessions from ~/.claude/projects/ and Sync sessions across Claude Code CLI, Desktop app, and web.

Claude/Code/Q/Is there any equivalent functionality in Claude Code's CLI to Claude Desktop's Code tab ability to group related chat histories together?

  • Is there any equivalent functionality in Claude/Code's CLI to Claude/Desktop/Code's ability to group related chat histories together?

    • AI Answer

      • Answer/Official from Manage Claude Code sessions and Agent view:
      • Short answer: Nothing in the CLI matches Desktop's Code-tab sidebar (explicit repo/branch/worktree badges) directly, but the CLI has two mechanisms that get most of the way there: automatic directory-scoped grouping of session history, and an agent view (claude agents) that groups sessions by state or by directory.
      • Directory-scoped grouping (implicit): the CLI stores each session transcript under ~/.claude/projects/<project>/<session-id>.jsonl, keyed by working-directory path. Every session run from a given repo therefore already sits together on disk — an implicit grouping by project rather than an explicit tag or folder.
      • Session picker: /resume (or claude --resume) opens a picker scoped to the current directory by default. From there: Ctrl+W expands to all worktrees, Ctrl+A expands to all projects on the machine, Ctrl+B filters by git branch, and text search matches names/summaries/PR URLs. Sessions can also be given a name (claude -n <name> or /rename) so related ones are easier to pick out.
      • Agent view (closest analogue): claude agents opens a richer view that groups sessions either by state (Pinned, Ready for review, Needs input, Working, Completed — toggle with Ctrl+S) or by directory. Sessions can be pinned (Ctrl+T) to keep related ones at the top, filtered by agent name/state/PR number, and reordered within a group.
      • What's still missing: no free-form tagging, no cross-repo logical grouping (grouping stays either state-based or directory-based, never topic-based), and no visual per-session metadata badges (repo/branch/worktree/env) like Desktop's Code tab shows in its sidebar.

Claude/Code/Q/What is the difference between the schedule command in Claude Code CLI and Routines in Claude Desktop's Code tab?

  • What is the difference between the schedule command in Claude Code CLI and Claude/Routines in Claude/Desktop/Code?

    • AI Answer

      • Answer/Official from Automate work with routines and Schedule recurring tasks in Claude Code Desktop:
      • Short answer: Desktop's Routines page is the umbrella UI for two different scheduling mechanisms under one name — Cloud routines and Local scheduled tasks. The CLI's /schedule command only reaches one of those two — Cloud routines — and has no facility at all for the other.
      • Cloud routines — the part they share: Desktop → Routines → New routine → Cloud, and CLI /schedule, both write to the same account-level list at claude.ai/code/routines. Either surface can create, list, edit, or run these; they are literally the same saved routines, just two front ends onto one backend. Runs happen unattended on Anthropic's cloud infrastructure — no permission-mode picker, no approval prompts — scoped instead by the routine's selected repositories, cloud environment, and connectors.
      • Local scheduled tasks — the part /schedule cannot touch: Desktop → Routines → New routine → Local creates a task that runs on the user's own machine, persisted as ~/.claude/scheduled-tasks/<task-name>/SKILL.md. These have a permission-mode/model picker and use local MCP connectors and local files — the opposite of a cloud routine's autonomy. The CLI has no command, flag, or tool that lists, creates, edits, or deletes these; CronList in a CLI session only reports a third, unrelated mechanism (session-local jobs from /loop/CronCreate, which expire after 7 days and disappear when the conversation ends).
      • Even within Cloud routines, /schedule is narrower than the web UI: the CLI command only configures the schedule trigger. Adding API or GitHub-event triggers to a cloud routine requires the web editor at claude.ai/code/routines.
      • See Claude/Routine for the full mechanism (what's saved, trigger types, run lifecycle, limits) and its Misconceptions section, which calls out this exact confusion directly: "Routines are the same as /loop or local Desktop schedules" is false — /loop and Desktop Local tasks both run on the local machine, while Routines (whether created from Desktop's Cloud option or from CLI /schedule) are remote cloud sessions.

Claude/Desktop/Code/Q/How can I make sure a Routine in Claude Desktop's Code tab has all the permissions it needs to run, since there's no obvious way to set automatic permission mode?

Page reference

  • How can I make sure a Claude/Routine in Claude/Desktop/Code has all the permissions it needs to run, since there's no obvious way to set automatic permission mode?

    • AI Answer

      • Short answer: It depends which of the two things Desktop's Routines page created. A Cloud routine has no permission-mode picker at all — that's by design, not a gap: cloud routines always run autonomously with no approval prompts, and their reach is bounded by repositories, the cloud environment, and connectors instead. A Local scheduled task does have a permission-mode picker and a per-task "always allow" approval list — if that's the control that seems to be missing, it's likely because Cloud was picked instead of Local when the routine was created.
      • Answer/Official from Automate work with routines and Schedule recurring tasks in Claude Code Desktop:
      • Cloud routines (Desktop → Routines → New routine → Cloud): "Routines run autonomously as full Claude Code cloud sessions: there is no permission-mode picker and no approval prompts during a run." What a cloud routine can reach is scoped by the repositories selected (and their branch-push rule), the environment's network access and variables, and the connectors included — not by a permission mode.
      • Local scheduled tasks (Desktop → Routines → New routine → Local): these do have a permission mode. The instructions form "includes pickers for the permission mode and model," set per task at creation or edit time; allow rules from ~/.claude/settings.json also apply to scheduled-task sessions.
      • Getting a Local task to run with full automatic permission: if a task runs in Ask mode and hits a tool it isn't allowed to use, the run stalls in the sidebar until approved. To avoid that: click Run now right after creating the task, watch for permission prompts, and choose "always allow" for each one — future scheduled runs then auto-approve those same tools without prompting. Saved approvals can be reviewed or revoked later from the task's "Always allowed" panel on its detail page.
      • One caveat: MCP tools an organization set to ask, or any tool marked requiresUserInteraction, always prompt and never offer an always-allow option — a task calling one of those stalls on every run regardless of permission mode.
      • Bottom line: not finding a way to set automatic permission is expected for a Cloud routine — there's nothing to configure, since it's already unattended. For a Local scheduled task, the setting exists; the durable "no more prompts" state comes from one manual Run now with "always allow" clicks, not from a single toggle.

Claude/Desktop/Scheduled Task/Q/Is there a declarative, programmatic way to manage Claude Desktop scheduled tasks that's scoped to a specific repo?

Page reference

  • Is there a declarative, programmatic way to manage Claude/Desktop/Scheduled Tasks that's scoped to a specific repo?

    • AI Answer

      • Short answer: Yes — an MCP tool surface (list_scheduled_tasks, create_scheduled_task, update_scheduled_task, delete_scheduled_task) lets a session manage tasks programmatically, and the working folder is bound implicitly to whatever repo the calling session is anchored in. That's what makes it usable per-repo, and it supersedes hand-editing files or filling out the Desktop UI form.

      • The supported mechanism

        • create_scheduled_task(taskId, prompt, description, cronExpression | fireAt) creates a task; update_scheduled_task(taskId, ...) does partial updates (prompt, description, schedule, enabled, notification); list_scheduled_tasks() returns every task's id, schedule, enabled state, and SKILL.md path; delete_scheduled_task(taskId) removes one.
        • None of these take an explicit folder/cwd argument — the task's working folder comes from the session that calls them. Running create_scheduled_task from a session opened in a given repo is what scopes the task there, matching Desktop's own "trusted working folder" model.
        • That turns "define scheduled tasks declaratively for a repo" into: commit a manifest in the repo (task id, schedule, description, prompt — the same shape as the SKILL.md frontmatter + body Desktop already writes) plus a short instruction telling Claude to reconcile it — call list_scheduled_tasks, diff by taskId, create_scheduled_task for anything missing, update_scheduled_task for anything changed. Opening the repo and asking Claude to run that reconciliation once leaves every machine with the same tasks, without ever hand-filling the New Routine form.
        • Net effect versus Claude/Desktop/Scheduled Task/Q/Is there a way to define a Claude Desktop scheduled task inside a repository's .claude directory so it's scoped to that repo and runs by default on any computer opening it?: still not automatic registration on clone — a session still has to run the reconciliation once per machine — but that step becomes one idempotent tool-driven action instead of manual multi-field UI entry, and it goes through a supported API rather than a file hack or symlink.

      • What's actually stored on disk (unofficial, background only)

        • Confirmed by inspecting local application data on macOS and decompiled strings from /Applications/Claude.app/Contents/Resources/app.asar: the registration these tools read and write lives in one JSON file per Claude account: ~/Library/Application Support/Claude/claude-code-sessions/<accountUuid>/<sessionUuid>/scheduled-tasks.json (account UUID is lastKnownAccountUuid in that same folder's config.json).
        • Shape: {"scheduledTasks": [{"id", "cronExpression", "enabled", "filePath", "createdAt", "model", "cwd", "useWorktree", "lastRunAt", "approvedPermissions": [...]}], "recordedSkips": {}} — one array for every task on the machine across all repos, disambiguated only by each entry's own cwd. list_scheduled_tasks doesn't surface cwd at all, consistent with the tool being scoped by the calling session rather than by filtering that field.
        • id must match ^[a-z0-9_-]+$ and equals the folder name under ~/.claude/scheduled-tasks/<id>/. Desktop polls the JSON file (fs.watchFile) and reloads on external change, so a raw file edit would likely still be picked up — but this is undocumented internal state with no compatibility guarantee, so the MCP tools above are the right interface, not this file.
Claude/Desktop/Scheduled Task/Q/Is there a way to define a Claude Desktop scheduled task inside a repository's .claude directory so it's scoped to that repo and runs by default on any computer opening it?

Page reference

  • Is there a way to define a Claude/Desktop/Scheduled Task inside a repository's .claude directory so it's scoped to that repo and runs by default on any computer opening it?

    • AI Answer

      • Short answer: No. Scheduled-task registration is per-machine, home-directory state — there's no supported way to commit a task definition into a repo's .claude/ directory and have Desktop auto-register or auto-run it there on every machine.
      • Answer/Official from Schedule recurring tasks in Claude Code Desktop:
      • A scheduled task's editable prompt file lives at ~/.claude/scheduled-tasks/<task-name>/SKILL.md (or under CLAUDE_CONFIG_DIR if that's set) — always a home-directory path, never something read out of the project's own .claude/ folder.
      • Even that file is only part of the task: "Schedule, folder, model, and enabled state are not in this file: change them through the Edit form or ask Claude." Those fields live in Desktop's own local app state, tied to the machine that created the task — editing SKILL.md by hand changes only the name, description, and prompt body.
      • Creating a task also requires trusting a working folder through Desktop's UI (or a natural-language request in a session) — there's no config format that says "if a repo has this file in .claude/, register a task pointed at it."
      • Net effect: a scheduled task's identity (name, folder, schedule, model, permission mode) is registration state private to one Desktop installation. Nothing about it is discovered from repo contents, so opening the same repo on a second computer doesn't cause its scheduled tasks to reappear — each machine needs its own New routine → Local setup (UI or natural-language) pointed at that folder.
      • Closest available workaround: keep the prompt content itself in the repo — e.g. as a .claude/skills/<name>/SKILL.md or a plain instructions file — and make each machine's task Instructions field just reference it (e.g. "follow the workflow in .claude/skills/daily-review/SKILL.md"). That keeps the task's behavior version-controlled and consistent across machines, but the task's existence, folder binding, and schedule still have to be created once per machine through Desktop.

    • Symlink workflow

      • Where a session has the scheduled-tasks MCP tools available, Claude/Desktop/Scheduled Task/Q/Is there a declarative, programmatic way to manage Claude Desktop scheduled tasks that's scoped to a specific repo? covers a cleaner, officially-supported alternative to the symlink approach below.
      • A symlink can go further than the reference-workaround above: instead of the Instructions field merely pointing at a repo file, ~/.claude/scheduled-tasks/<task-name>/SKILL.md itself becomes a symlink into the repo, so editing the repo file changes the live task with no copy step.
      • 1. Commit the canonical prompt in the repo, e.g. .claude/scheduled-tasks/<task-name>/SKILL.md.
      • 2. On each machine, create the task once through Desktop's normal New routine → Local flow — this step is unavoidable, since schedule, folder, model, and enabled state are local app state, not file content.
      • 3. Delete the real SKILL.md Desktop just wrote and replace it with a symlink to the repo copy: ln -sf ~/ghq/<host>/<org>/<repo>/.claude/scheduled-tasks/<task-name>/SKILL.md ~/.claude/scheduled-tasks/<task-name>/SKILL.md.
      • Because ghq clones every repo to the same deterministic path on any machine (~/ghq/<host>/<org>/<repo>), that target path is stable — but the symlink itself must be absolute, since the home-directory end sits entirely outside the repo tree.
      • 4. Repeat step 2–3 on each additional machine that runs the task. After that, the prompt body, name, and description stay in lockstep across machines automatically; only the schedule/folder/model/enabled fields remain per-machine and still need manual updates through the Edit form if they change.
      • Risk to check before relying on this: if Desktop's Edit form ever saves SKILL.md by rewriting the file in place rather than only patching prompt text, that write could replace the symlink with a fresh real file and silently break the link.
