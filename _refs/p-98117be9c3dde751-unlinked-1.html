Agent/Skills/Support in Multiple Tools
  • The Agent/Skills open standard defines what a skill file contains but does not mandate where skill directories live. Each vendor ships a native directory (.claude/skills/, .gemini/skills/, etc.), and .agents/skills/ is the recommended cross-client interoperability path. The gap between these two conventions is the central challenge of multi-tool skill management.
  • The spec recommends that clients scan .agents/skills/ alongside their native path, but not all vendors have implemented this. A user who installs skills to ~/.agents/skills/ following the ecosystem convention will find those skills invisible in Claude/Code, which only scans ~/.claude/skills/.
  • This gap is documented in a live bug report: Vercel skills issue #693 — skills installed to ~/.agents/skills are silently ignored by Claude/Code.

  • How vendors currently handle .agents/skills

    • GitHub Copilot officially documents both .agents/skills and ~/.agents/skills as valid skill locations alongside its native paths — strong evidence that .agents/skills is becoming a real interoperability target, not just a spec aspiration.
    • OpenAI Codex and Gemini CLI also scan .agents/skills/ natively.
    • Claude/Code (as of mid-2026) does not natively scan .agents/skills/; a community issue (anthropics/claude-code#31005) requests this support.
    • See Agent/Skills/Dir/Compatibility for a full tool-by-tool matrix.
  • Put skills in ~/.agents/skills/, then symlink into ~/.claude/skills/. Multiple practitioners recommend this, including an SSW engineering rule (ssw.com.au/rules/symlink-agents-to-claude) and a dedicated blog post (wow.pjh.is).
  • The spec defines what goes inside a skill file, not where the directory lives. Vendors have pre-existing conventions they cannot rename without breaking existing users. Adopting .agents/skills/ is an additive second lookup, not a rename — which makes adoption optional and therefore incremental.
  • 1. Author skills once, in .agents/skills/ (or ~/.agents/skills/ for user-level)
  • 2. Symlink into vendor-specific directories for tools that don't yet scan .agents/skills/ natively

ChatGPT/Plugin/How To/Develop and Share a Team Plugin for ChatGPT and Claude
  • Expose each shared skill directory under the repo's .agents/skills/. Codex follows symlinked skill folders, so edits to the package's SKILL.md, references, and scripts remain edits to the files used by the discovered skill. This loads a plain skill; it does not activate the package's MCP configuration or hooks. Codex local skill discovery.
  • bash
    				  mkdir -p .agents/skills
				  ln -s ../../plugins/team-review/skills/team-design-review .agents/skills/team-design-review
				  realpath .agents/skills/team-design-review/SKILL.md
  • The resolved path should end in plugins/team-review/skills/team-design-review/SKILL.md inside the current checkout. Relative symlink targets are resolved from .agents/skills/. If the package lives under .claude/skills/team-review/, use ../../.claude/skills/team-review/skills/team-design-review as the target instead. Inspect any existing destination before changing it.
  • Duplicate skill entries: disable the installed copy while testing the source skill. For a packaged release test, temporarily move only the discovery symlink outside .agents/skills/, leaving its source directory in place, then start a fresh chat. Restore the link to resume local development.
Claude/Code/Q/If I want to use Claude Code's skill-directory plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?
  • Some orgs standardize the symlink in the other direction — treat .claude/skills/ as canonical and symlink a plain-named directory (e.g. .agents/skills) to it, so other tools reach the same content without touching Obsidian visibility at all. Either direction is a valid use of the same underlying mechanism (dot-folder scanning follows symlinks); which one to use depends on whether the dot-directory or the plain directory is your source of truth.

Codex/CLI/Q/Why doesn't CodexCLI support slash commands?
  • OpenAI's stated direction: Maintainers describe skills as a superset of what custom slash commands did—reusable instructions, repo-shareable under .agents/skills/ (and related discovery paths), explicit invocation via /skills or $skill-name in the composer, and optional implicit use when enabled. They have no current plans to restore file-based custom slash commands (openai/codex#22674).
Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?
  • For editing a Codex skill in place, use a plain Codex/Skill under .agents/skills/<skill-name>/SKILL.md. Codex supports symlinked skill directories and detects skill changes. Build skills — local discovery.
Codex/Plugin/Q/Is a Codex skills-only plugin the same idea as a Claude Code skills-directory plugin?
  • Claude's skills-directory plugin ↔ Codex's repo marketplace plus project plugin configuration is the closest supported plugin workflow. Codex still installs a cached copy; it does not document discovering a full plugin merely from a manifest placed inside .agents/skills/.
  • For editing skills in place, use a plain Codex/Skill in a scanned directory: $CWD/.agents/skills, $CWD/../.agents/skills, $REPO_ROOT/.agents/skills, or $HOME/.agents/skills.
CursorAI/Q/I have some private Claude plugins in a Claude Plugin Marketplace that I'd like to run in Cursor. What are my options?

Copy or symlink each plugin's skills/<name>/SKILL.md tree into one of those roots; invoke with /skill-name or let Agent pick them up.

rulesync
  • Codex CLI reads agent skills from .agents/skills/ following the agentskills.io open standard:
    • .agents/skills/ — project scope (walked from cwd up to repo root)
    • $HOME/.agents/skills/ — user scope
    • /etc/codex/skills/ — admin scope
  • Use --targets agentsskills to generate skills readable by Codex CLI; the agentsskills adapter correctly writes to .agents/skills/.
  • Note: agentsskills --global is not yet supported (throws); Codex's user-scope at $HOME/.agents/skills/ is therefore unimplemented in rulesync.
skillshare
  • Both tools follow the agentskills.io open standard; see rulesync ## Skills for a note on rulesync's codexcli adapter writing to the wrong directory (.codex/skills/ vs .agents/skills/).
TWG/Agent/Skill
  • The twg binary carries its own copy. twg skills install writes it to ~/.agents/skills (Codex, Cursor, Gemini, Copilot) plus ~/.claude/skills with --agent claude; --local writes into the current directory instead. Each installed skill gets a .twg-install.json marker, which twg upgrade uses to find skills to refresh.
