Claude/Artifact/Concept/Install as Desktop App

  • Claude/Artifact/Concept/Install as Desktop App

    • A published Claude artifact can be installed as its own app on your computer. It gets a dedicated window, an icon in your app launcher, and no browser tab or address bar.
    • The artifact is a web page at a claude.ai URL, so the feature comes from the browser's PWA install, not from a Claude-specific installer.

    • What you see

      • On the artifact page, the title menu (the name with a chevron, top left) lists Export, Copy as Markdown, Install artifact, and Rename.
      • Install artifact opens Chrome's "Install app" dialog: "Access this site in a dedicated window on your computer". It shows the artifact name followed by "Claude artifact" and the domain claude.ai.
      • Next goes to a second dialog showing the icon moving into a Chrome Apps folder. Install finishes it.
      • A confirmation offers Show in Finder and Open tab in app.

    • What you get

      • A standalone window for one artifact, separate from your browser tabs and from the Claude app.
      • A launcher icon: Start menu on Windows, Launchpad and Spotlight on macOS, as listed by web.dev.
      • Entries in the OS app switcher and app search, with the option to pin to the taskbar on Windows.

    • Windows

      • Windows works. Chrome and Edge both install PWAs on Windows, macOS, Linux, and Chromebooks, per web.dev.
      • In Chrome: More (three dots) → Cast, save, and share → Install page as app, or the install icon at the right end of the address bar. See Google's Chrome Help.
      • In Edge: the App available icon in the address bar, then Install. The app lands in the Start menu and taskbar, and appears under Windows Apps & features. See Microsoft's Edge PWA guide.
      • Edge on Windows can also start the app when you sign in (edge://apps → More options → Auto-start on device login).
      • The browser-level install is documented for Edge. Whether claude.ai shows the Install artifact menu item in Edge is undocumented.
      • Edge has one documented gap: PWAs do not survive logoff in FSLogix virtual-desktop profiles.

    • Browser limits

      • Safari on macOS does not support installability (web.dev). Use Chrome or Edge.
      • Firefox on desktop is not covered by those sources.
      • An app cannot be installed twice in the same browser.

    • Managing the app

      • Chrome: open chrome://apps to see installed apps, create shortcuts, or set launch at sign-in. To remove one, open it and choose More → Uninstall.
      • Edge: edge://apps, or Windows Add or remove programs.

    • Official documentation status

      • Answer/Official for the browser mechanism: the Chrome, Edge, and web.dev pages linked above.
      • No Anthropic Help Center article describes Install artifact. The article What are artifacts and how do I use them? covers viewing, editing, sharing, and exporting, and says nothing on installing.
      • The dialogs in the screenshots are Chrome's own PWA install flow with Claude's name and icon filled in.

Claude/Code/Plugin/Marketplace/Auto-Update
  • Bottom line (as of 2026-07-28 Tue): the marketplace file itself cannot declare auto-update, and the built-in per-marketplace auto-update is unreliable for third-party marketplaces — it refreshes the catalog but often fails to move installed plugins forward, silently. The dependable path is version discipline in CI plus a small updater shipped in the marketplace. On macOS that updater runs as a SessionStart hook; on Windows, where plugin hooks silently do nothing before Desktop v1.24012.9, the same script runs instead as a logon Claude/Desktop/Scheduled Task — a delivery path that does not depend on the app's hook system.
  • On desktop, users manage plugins through the GUI, admins through managed settings JSON, and automation through a hook plus a script. The desktop app registers marketplaces by hosted URL only, so a private marketplace is distributed via its git repo URL.
  • The desktop app cannot register a local directory as a marketplace, so a hosted URL is required. #52147
  • Windows delivery — logon Scheduled Task. Place the script at a fixed path (the plugin cache path changes each version, so a task must not point there) and register a per-user task that runs it at logon; IT can push both steps fleet-wide via MDM. The task updates the on-disk marketplace and registry, and the desktop app picks up the change on its next Code session launch. macOS needs no task; for the same interval behaviour on macOS, run the script from a LaunchAgent or cron.
  • Distribution. The desktop app registers marketplaces by hosted URL, so use the private git repo URL (#52147).

Claude/Code/Q/If I rename a CLI session with /rename, can I resume it in Claude Desktop's Code tab?
  • Short answer: No. /rename creates a resume handle that only the CLI honors, and the Code tab keeps a session history of its own — a CLI session never appears in its sidebar, named or not. The one bridge runs the other way: /desktop hands the live CLI session over to the app.
  • Why the Code tab can't see it: the docs state plainly that the desktop app, Claude Code on the web, and the VS Code extension "each maintain their own session history." The CLI–Desktop relationship is spelled out under Coming from the CLI?: both can run at once on the same machine and even the same project, and "Each maintains separate session history, but they share configuration and project memory via CLAUDE.md files." Config and memory are shared; the session list is not.
  • Rename direction that does cross over: renaming a Remote Control session from claude.ai or the Claude app applies the same name in the CLI (needs Claude Code v2.1.221+). The Desktop equivalent does not reciprocate — per the docs, "a desktop-app session resumes in the app, which keeps its own session history."
  • The actual bridge — /desktop: run it in the terminal and Claude saves the session, opens it in the desktop app, and exits the CLI. Constraints: macOS and x64 Windows, signed in with a Claude subscription; unavailable with API-key auth or on Amazon Bedrock, Google Cloud's Agent Platform, and Microsoft Foundry. It is a one-way handoff of the session you are sitting in — not a picker for arbitrary past CLI sessions.
  • Wanted, not shipped: open requests cover this exactly — Desktop app should list and resume CLI sessions from ~/.claude/projects/ and Sync sessions across Claude Code CLI, Desktop app, and web.

Claude/Code/Q/Why does voice dictation work in only one of my Claude Code terminals on macOS when I run several in tmux?
  • Closest match: Issue #94687 (open, filed 2026-09-16), macOS 26.5.1 on Apple Silicon in Terminal.app
    • The same error appears in several parallel sessions, and only a fresh session fixes it. Toggling /voice, /voice tap, /voice hold or changing the input device does not.
    • Root cause from the unified log: a session's auto-updater reinstalls the package and replaces claude.exe. Every session started before the swap keeps running the deleted old image. On its next recording, coreaudiod asks tccd.system for that PID's microphone right, gets an empty reply, and denies input. The addon then receives silence and Claude Code reports "No audio detected".
    • A commenter adds that a stale session can re-trigger a reinstall of a version that is already on disk, which kills voice in a brand new session as well.
    • Workaround from the issue: set "env": { "DISABLE_AUTOUPDATER": "1" } in ~/.claude/settings.json, update manually, then restart sessions.
  • Test the same two-session pattern outside tmux, in two Terminal.app tabs. If it still fails, tmux is not the cause. As far as I can tell, audio-capture.node talks to CoreAudio directly, so tmux is unlikely to matter.

Claude/Code/Skill/run

  • run

    • A bundled Claude/Code/Skill that launches and drives the current project's app to observe a change working.

    • How it works

      • Invoked as /run inside a Claude Code session.
      • Infers the launch method from project type (CLI, server, TUI, browser-driven) and from README, package.json, or Makefile.
      • Drives the app to the relevant state and reports what it observes.
      • Inference becomes unreliable for projects requiring databases, env files, graphical sessions, or multi-step builds — use Claude/Code/Skill/run-skill-generator to record a reliable recipe first.

    • Differs from

      • Claude/Code/Skill/verify — /verify is targeted at confirming one specific code change; /run just launches the app.
      • Claude/Code/Skill/run-skill-generator — generates the per-project recipe that /run follows in complex projects.

    • See also

Claude/Code/Skill/run-skill-generator

  • run-skill-generator

    • A bundled Claude/Code/Skill that teaches Claude/Code/Skill/run and Claude/Code/Skill/verify how to build and launch the current project by recording a reliable per-project recipe.

    • How it works

      • Invoked as /run-skill-generator once per project (and again when the build or launch process changes).
      • Interactively determines what works: install commands, required env vars, launch script, expected output.
      • Commits the result as a per-project skill at .claude/skills/run-<name>/.
      • After that, /run, /verify, and other agents follow the recorded recipe instead of guessing.
      • Solves inference failures for projects requiring databases, env files, graphical sessions, or multi-step builds.

    • Differs from

      • Claude/Code/Skill/run and Claude/Code/Skill/verify — those execute against the project; /run-skill-generator creates the configuration they rely on.

    • See also

      • Extend Claude with skills – Claude Code
Claude/Code/Skill/verify

  • verify

    • A bundled Claude/Code/Skill that builds and runs the app to confirm a code change does what it should, without falling back to tests or type checks.

    • How it works

      • Invoked as /verify inside a Claude Code session, typically after implementing a change.
      • Launches the app (using the same inference or recorded recipe as Claude/Code/Skill/run) and specifically checks whether the targeted change behaves as expected.
      • Does NOT substitute passing tests or type checks — it observes actual runtime behavior.

    • Differs from

      • Claude/Code/Skill/run — /run launches the app to show any change; /verify is scoped to confirming one specific change.
      • Claude/Code/Skill/run-skill-generator — records the launch recipe that /verify depends on in complex projects.
