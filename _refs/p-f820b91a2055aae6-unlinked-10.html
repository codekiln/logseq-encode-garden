pmset

  • pmset

    • Built-in macOS command for reading and changing power management settings: sleep timers, wake events, hibernation, and whether the system sleeps at all.
    • Reading settings works as any user. Changing one needs root, so writes run under sudo.

    • Usage

      • sh
        		  pmset -g                 # settings in use now, plus system-wide settings
		  pmset -g custom          # settings for each power source
		  pmset -g assertions      # processes currently holding the Mac awake
		  sudo pmset -a <setting> <value>
      • -a, -b, -c and -u apply a setting to all power sources, battery, charger, or UPS.

    • disablesleep

      • sudo pmset -a disablesleep 1 stops the system from sleeping, including when the lid closes. sudo pmset -a disablesleep 0 turns sleep back on, which is the macOS default.
      • pmset -g shows the value as SleepDisabled under "System-wide power settings".
      • man pmset does not document this setting.
      • MacOS/How To/Keep a Mac Awake with the Lid Closed uses it, through mise tasks that record the earlier value and restore it.

    • Related settings

      • lidwake wakes the Mac when the lid opens.
      • sleep, displaysleep and disksleep are idle timers in minutes, with 0 meaning never.

    • mise tasks

      • pmset/mise/Task/lid-awake/enable
      • pmset/mise/Task/lid-awake/restore
      • pmset/mise/Task/lid-awake/install-sudoers
Programming/Concept/Copy on Write
  • Why it matters: CoW is a bridge between logical independence ("each side has its own view") and physical efficiency (one set of pages or blocks on disk until divergence).
  • OS virtual memory (illustrative): After fork(), parent and child often map the same physical pages read-only. The first write to such a page triggers a page fault; the kernel copies the page, remaps the writer's address space to the new physical page, and retries the write—classic CoW at page granularity.
  • Unix fork: Child appears to duplicate the address space; many systems implement that logical copy with CoW pages until one process modifies memory.

Task/Management/Git-Friendly/Report/26/CRDT vs SQLite in git for task management
  • "Alternative Dolt" / Branch approaches: Some teams avoid Dolt by using Git branches or LFS for DB. For example, one can maintain an orphan branch containing only the latest SQLite file (as a GitHub Pages–like workflow). Each time the DB updates, the branch is force-pushed, avoiding a growing history. This sidesteps diffing and trimming: the branch always holds the current DB (possibly stored with Git LFS to avoid bloating the repo). Merge behavior: trivial since no history is merged; only the new binary is placed. Pros: Simple concept, no custom tools. Cons: Loses history (unless managed externally), not a true merge – concurrent edits still overwrite each other.
