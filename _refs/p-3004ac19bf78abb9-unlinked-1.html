A2A

  • A2A

    • Overview

      • Agent2Agent (A2A) is an open protocol for communication and interoperability between opaque agentic applications: agents built on different frameworks, by different vendors, on separate servers, collaborate as agents without exposing their internal state, memory, or tools.
      • Created by Google and contributed as an open source project under the Linux Foundation; Apache 2.0 licensed. In August 2026 it was accepted as a Growth Stage project of the Linux Foundation-directed Agentic AI Foundation (AAIF), alongside MCP, goose, and AGENTS.md. (announcement)

    • Normative links

      • A2A Protocol Specification — latest released spec version 1.0.0; earlier versions 0.3.0, 0.2.6, 0.1.0
      • a2aproject/A2A — spec repo; latest release v1.0.1 (2026-05-28), v1.0.0 released 2026-03-12

    • Scope

      • Agent Card — JSON metadata an A2A server publishes describing identity, capabilities, skills, service endpoint, and auth requirements; discovered at /.well-known/agent-card.json, via registries, or by direct configuration.
      • Task — the stateful unit of work with a defined lifecycle; Message — a turn with role user or agent made of Parts (text, file references, structured data); Artifact — a task output made of Parts.
      • Interaction modes: synchronous request/response, streaming over Server-Sent Events, and asynchronous push notifications to a client webhook for long-running tasks.
      • The spec is layered: a canonical data model (Protocol Buffer messages), abstract operations (send message, send streaming message, get / list / cancel task, get Agent Card), and protocol bindings for JSON-RPC 2.0, gRPC, and HTTP+JSON/REST, plus custom bindings.

    • Relationship to MCP

      • MCP connects an agent to tools and resources (vertical: deepens one agent); A2A connects agents to other agents across team or organization boundaries (horizontal). The two are designed as complements. (A2A and MCP)

    • Implementations

      • Official SDKs for Python (a2a-sdk), Go, JavaScript, Java, .NET, and Rust, linked from the spec repo README.
      • LangSmith Agent Server exposes each assistant at /a2a/{assistant_id} (methods message/send, message/stream, tasks/get) and serves its Agent Card at /.well-known/agent-card.json?assistant_id={assistant_id}. (A2A endpoint in Agent Server)
      • A LangSmith Deployment of a LangSmith/Deep Agents agent can expose it via MCP or A2A. (Going to production)

Ad/Block/er/uBlock/Concept/uBlock vs Origin vs Lite
  • Custom Filters and Dynamic Filtering: uBOL does not support custom user-defined filters or dynamic filtering of scripts and iframes. This means users cannot create or modify filter lists beyond what is provided by default. Wikipedia
  • Per-Site Settings: The ability to configure per-site blocking rules or exceptions is absent in uBOL. Users cannot tailor the extension's behavior for specific websites. Wikipedia
  • Element Picker and Cosmetic Filtering: uBOL lacks tools for hiding specific elements on a webpage or applying cosmetic filters to adjust the appearance of a site. Wikipedia
  • Advanced Logging and Debugging Tools: The advanced logger and debugging tools available in uBlock Origin are not present in uBOL, limiting users' ability to diagnose and troubleshoot filtering issues. Wikipedia
  • Advanced Privacy Features: uBOL offers limited privacy protections compared to uBlock Origin. For instance, it does not support advanced features like CNAME uncloaking, which helps in identifying and blocking trackers that use deceptive domain names. Wikipedia
  • Filter List Updates: In uBOL, filter lists are updated only when the extension itself is updated, rather than receiving real-time updates as in uBlock Origin. This can result in slower response to emerging threats. Wikipedia
  • Ad Block Counter: The visual ad block counter feature, which displays the number of blocked requests, is not available in uBOL. All About Cookies
  • UI Customization: uBOL offers a more simplified user interface with fewer customization options compared to uBlock Origin. All About Cookies

AI/Concept/Explore/vs/Exploit
  • The formal problem is the multi-armed bandit: a row of slot machines with unknown payout rates and a limited number of pulls to spend on them. Allied statisticians worked on it during the Second World War and found it so hard that Peter Whittle joked it should be dropped on Germany to waste enemy scientists' time. Herbert Robbins gave the problem its standard form in 1952 in "Some aspects of the sequential design of experiments".
  • In organization theory, James G. March's "Exploration and Exploitation in Organizational Learning" (1991) named the trade-off for firms. Exploitation is refinement, efficiency and execution; exploration is search, variation, risk-taking and discovery. Returns to exploitation are near, certain and fast, while returns to exploration are distant, uncertain and often negative, which is why organizations slide toward exploitation and lose the ability to adapt.
  • In AI/Reinforcement Learning the balance is written into the algorithms (Exploration–exploitation dilemma, Wikipedia). Epsilon-greedy takes the best-known action most of the time and a random one otherwise. Upper-confidence-bound methods add an optimism bonus to actions tried less often. Thompson sampling draws a guess at each payoff from what has been observed and acts as if the draw were true. Exploration bonuses turn curiosity into a reward of its own, so the agent can exploit it.
