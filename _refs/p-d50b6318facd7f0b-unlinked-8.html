Obsidian/Q/Should a team vault in git commit its community plugins' code, or only the list of plugins?

  • Should a team vault in git commit its community plugins' code, or only the list of plugins?

    • Prompted by git status in a work team's knowledge garden on 2026-10-23: Obsidian had updated easy-copy, folder-notes and obsidian-git, so their tracked manifest.json files showed as modified and their main.js, styles.css and data.json showed as untracked.
    • My work gardens follow two rules.
      • The older gardens ignore plugins/*/main.js, plugins/*/styles.css and plugins/*/data.json and commit manifest.json. One of them records why in an OpenSpec spec for a multi-device .gitignore, from a 2026-05-27 change about plugin binaries.
      • The garden template and the gardens made from it commit manifest.json and ignore only workspace.json, so the plugin code is neither tracked nor ignored.
    • The people opening these gardens include hackathon attendees using Obsidian for the first time.

    • Decision

      • Commit only the list of plugins and install the code with a mise file task, because plugin version bumps are frequent and not worth tracking. See My/Pref/Dev/Tool/Obsidian/Plugins in Git.

    • AI Answer

      • Short answer: For a team vault that newcomers clone, commit each plugin's whole folder (manifest.json, main.js, styles.css) and decide data.json plugin by plugin. Committing only manifest.json records versions but installs nothing, so a fresh clone opens with plugins turned on that cannot load.

      • What Obsidian does with a fresh clone

        • Obsidian does not download a plugin that community-plugins.json lists but .obsidian/plugins/<id>/ lacks. Users in A single button click to reinstall all community plugins after cloning report that none of the plugins are installed after a clone. The thread runs from May 2025 to Aug 2026 and has no reply from Obsidian staff.
        • The older gardens' design says main.js and styles.css are files "that Obsidian re-downloads when plugins are installed". That holds only when someone installs the plugin by hand; nothing re-downloads them on clone.
        • When a vault arrives with plugin code present, Obsidian asks once whether to trust the author and turn on community plugins, or open the vault in restricted mode. See Plugin security. Restricted mode leaves the files on disk and ignores them.
        • Obsidian Sync handles this by syncing the installed plugins themselves, behind the "Active community plugin list" and "Installed community plugin list" options in Sync settings. Sync copies plugin code between devices; it does not keep just a list and fetch the code.

      • What the public guidance says

        • Obsidian Git's Tips and Tricks gives three .gitignore choices: all of .obsidian/, only .obsidian/plugins (to keep plugin settings that may hold secrets out of git), or only workspace.json. It does not split main.js from manifest.json.
        • In What should I gitignore for my vault's GitHub repository? (May 2025), the replies track plugin folders by default and ignore specific noisy or oversized files such as workspace.json and large index files.
        • I found no source that recommends the manifest-only rule. It appears to come from treating main.js as build output, which it is for the plugin's author but not for the vault, where it is the installed program.

      • The three rules compared

        • Commit whole plugin folders.
          • A clone works on desktop and iPhone after one trust prompt, with no install step to document.
          • Everyone runs the same plugin versions, and an update shows up as a diff someone reviews before it reaches the team.
          • Costs: about 1.2 MB for the three plugins these gardens use, a large diff on each update, and one person's update reaches everyone on their next pull.
        • Commit manifest.json only (the older gardens' rule).
          • Keeps plugin code out of the repo.
          • A clone opens with plugins listed as on but not installed. Each person must install them from the Community plugins browser, run obsidian plugin:install (Obsidian 1.12.7+, desktop, after turning on the CLI in Settings), or run a script against the plugin registry.
          • The committed manifest records the version of whoever last updated, not the version anyone has installed. The 2026-10-23 diff was exactly this: three manifests changed by Obsidian's updater, with nothing that would install those versions anywhere else.
        • Ignore .obsidian/plugins and ship a bootstrap script.
          • Same newcomer cost as manifest-only, but with no misleading version record. Approach 4 in Obsidian/Q/How can an Obsidian vault declare the community plugins it depends on and install them by script? is such a script, and it can pin versions.
          • Community Install Manager, now in the community plugin directory, installs plugins and settings from two JSON files, but it must itself be installed first.

      • data.json is plugin settings, so decide per plugin

        • The older gardens' design ignores all data.json as "runtime state" while also saying "plugin configuration should be shared". data.json is that configuration.
        • folder-notes' data.json holds storageLocation: insideFolder and folderNoteName: {{folder_name}}, which implement the garden's folder-note naming rule. Commit it.
        • obsidian-git's data.json holds per-person choices such as auto-commit intervals, and some git plugins keep tokens there. Ignore it, along with obsidian_askpass.sh.
        • A .gitignore that ignores plugins/*/data.json and adds !plugins/folder-notes/data.json expresses this.

      • Watch for with whole-folder commits

        • The older gardens dropped plugin code after obsidian-git's auto-backup committed its own bundle (commit d979078). With whole-folder commits that is the intended result, but auto-backup will also commit someone's plugin update without review. Turn off auto-commit in shared gardens, or review .obsidian/plugins diffs on pull requests.
        • Committing plugin code means committing third-party JavaScript that runs with full access to each person's machine. The trust prompt is the same either way; committing it adds a pinned, reviewable version.
      • Unverified: I did not open a fresh clone of a manifest-only garden to confirm the exact message Obsidian shows for an enabled plugin with no main.js, and I did not test the !plugins/folder-notes/data.json exception against the template's other ignore rules.

Person/codekiln/GitHub/logseq-gardener/Analysis/Fable/26/09/12/0658 ET A Logseq-aware git merge driver before a CRDT

Page reference

  • A Logseq-aware git merge driver before a CRDT

    • The Goals page says the implementation should support concurrent writes to the same block using CRDTs as a front end to the cache. The Brief says a CRDT is a long-term direction and no MVP dependency. Resolve the two pages in the Brief's favor, and add a smaller step before either.

    • How concurrent edits arrive today

      • Agents work in git/worktrees on their own branches and merge through pull requests, per My/AI/Rule/Dev/Workflow/Git Worktree PR/Tmux. Two agents editing the same page meet at merge time, in git, as a textual conflict. A person edits in Logseq or nvim on main. The concurrency that exists is a merge problem, and git already has the extension point for it.

    • What a merge driver would do

      • Register a custom merge driver for pages/*.md and journals/*.md through .gitattributes. Git hands it the base, ours, and theirs versions; the driver parses all three as block trees, matches blocks by id:: when present and by parent path plus content otherwise, merges at block granularity, and leaves a textual conflict marker only inside a block both sides changed.
      • It is a small program over garden-core's parser and serializer, it runs wherever git runs, it needs no new storage layer, and it fits My/Principle/Simplify/Prefer Standards and Defaults and My/Principle/Simplify/Fewer and Deeper. It also serves the person in Logseq who merges an agent's branch.

    • What it settles before any CRDT

      • About five hundred blocks in the encode garden carry an id::; the rest have identity only by position. A merge driver forces the block-identity and ordering decisions the Brief lists for the CRDT phase, on real conflicts, while the cost of a wrong rule is one bad merge that git can undo.
      • My/Principle/Make Illegal States Unrepresentable applies once those rules exist: model a block's identity as a sum type, either an explicit UUID or a positional path, so no code path treats a positional block as stable across files.

Person/codekiln/GitHub/logseq-gardener/Project/Brief

  • Working definition


    logseq-gardener is a fast, local-first semantic engine for existing Logseq OG/file-based knowledge gardens.

    Its source of truth is the user's existing Markdown files:

      pages/
  journals/
  assets/
  logseq/


    It should understand those files as a Logseq knowledge graph without requiring the user to migrate them into another canonical database format.

    The project exists partly as an exit strategy from the Logseq application as Logseq shifts active development toward its database-backed product while the older Git-friendly file format enters maintenance mode.

    The goal is not initially to reproduce the Logseq application.

    The goal is to make the data model that made Logseq valuable independently usable.

    At a high level:

      Logseq Markdown
                    pages/ journals/ assets/
                              │
                              ▼
                    ┌──────────────────┐
                    │   garden-core    │
                    │                  │
                    │ parser           │
                    │ graph model      │
                    │ incremental idx  │
                    │ derived cache    │
                    └────────┬─────────┘
                             │
                  one stable semantic API
                             │
        ┌────────────────────┼─────────────────────┐
        │                    │                     │
        ▼                    ▼                     ▼
      CLI                  LSP                Publisher
        │                    │                     │
  humans / agents       Neovim/LazyVim          static HTML
  scripts / tools       completion/gd/gr        SEO/search


    The core principle is:

    >

    Parse Logseq once, model it once, index it once, and allow many tools to consume the same understanding.

  • stored in Git;

  • Source-of-truth rule


    Markdown files are authoritative.

    The cache is not.

      Git-tracked Markdown
        │
        │ parse
        ▼
  derived semantic cache


    The cache must always be reconstructible.

    No user knowledge should exist only in the cache.

    Deleting the entire cache should at worst cause a performance penalty while it is rebuilt.

    The cache should normally live outside the knowledge garden, for example:

      ~/.cache/logseq-gardener/<graph-id>/


    and must never need to be committed to Git.

    An embedded database such as SQLite is acceptable if useful.

    A required external database service is not.

    The project should specifically avoid operational characteristics such as:

      database daemon setup
  ports
  server discovery
  stale background engines
  manually started services


    A user should be able to install one executable and use it.

  • Warm startup and incremental indexing


    A previously indexed graph should not require a whole-graph parse every time a client starts.

    A warm cache should be usable immediately.

    Reconciliation should then determine what changed.

    For Git-backed gardens, Git itself may provide useful invalidation information:

      last indexed commit
        +
  current HEAD
        +
  working-tree changes
        +
  filesystem changes since process start


    The implementation should investigate whether this can sharply reduce startup reconciliation work.

    File watching should allow an active graph to incrementally re-index only files that change.

    The central invariant should be:

      edit one file
     ↓
  reparse only what is necessary
     ↓
  update dependent semantic indexes


    rather than rebuilding the whole garden.

  • Concurrency and CRDT direction


    Concurrent editing is an important long-term use case.

    Human editors and multiple AI agents may eventually operate on the same graph simultaneously, potentially even on the same block.

    The architecture should therefore not foreclose CRDT-backed or otherwise conflict-aware editing.

    However, a CRDT implementation is not an MVP dependency.

    The progression should likely be:

      read-only semantic engine
  
        ↓
  
  safe single-operation mutations
  with revision checking
  
        ↓
  
  operation log / explicit concurrency model
  
        ↓
  
  concurrent block-level editing
  
        ↓
  
  CRDT-backed collaborative mutation where justified


    A CRDT should not replace Markdown as the user's durable canonical representation unless a later explicit design decision changes the project's fundamental goals.

    Instead, a CRDT may eventually serve as a coordination or editing layer that reconciles back to the file-backed graph.

    The design should pay particular attention to:

      stable block identity
  source revisions
  block ordering
  parent/child relationships
  concurrent modification
  merge semantics
  Git interaction

  • Explicit non-goals for the first version


    The first version is not intended to:

      replace every Logseq UI feature
  
  implement the new Logseq DB model
  
  provide real-time collaborative editing
  
  replace Git
  
  become the canonical storage database
  
  implement a browser SPA
  
  implement every Markdown feature itself
  
  rewrite user files during indexing
  
  require a daemon or server setup


    Keeping these out of the initial scope is important.

  • Project thesis


    logseq-gardener should make a Logseq OG garden useful without requiring Logseq.

    A person should eventually be able to point the tool at years of existing Markdown and immediately obtain:

      semantic search
  page and block resolution
  backlinks
  editor completion
  agent tooling
  static publishing
  safe structured mutation


    while retaining the properties that made the file-based Logseq format attractive in the first place:

      plain files
  Git
  portability
  inspectability
  local ownership
  long-term durability


    The long-term aspiration is therefore larger than a Logseq Neovim plugin:

    >

    Preserve the useful semantic model of file-based Logseq as an open, high-performance knowledge-garden substrate that can support editors, humans, AI agents, scripts, and websites independently of the original application.
