fnox/How To/Set Up a Project with age and SSH Keys
  • Commit secrets to a project as age ciphertext in fnox.toml, encrypted to each teammate's existing SSH public key, so anyone with a matching SSH private key can decrypt after a git pull.
  • Each value is encrypted with age to a list of recipients, the public keys in the age provider's recipients array. A recipient can be an SSH public key (ssh-ed25519 or ssh-rsa), a native age1... key, or an age plugin key.
  • Decrypting needs the private half of any one recipient. fnox looks for it in FNOX_AGE_KEY, then the provider's identity, then its key_file, then FNOX_AGE_KEY_FILE, then age.txt in the fnox config directory. For SSH keys, point FNOX_AGE_KEY_FILE at the private key.
  • fnox installed and the age CLI. fnox can encrypt to SSH recipients without it; install it with brew install age if you also want age-keygen for a CI key.
  • Every person has an SSH key of type ed25519 or rsa (2048 bits minimum, 4096 recommended).
  • The SSH private key must not be passphrase-protected. Upstream says password-protected SSH keys are not supported; it advises a dedicated age identity or an age plugin instead of stripping the passphrase from your normal key. See fnox/How To/Use Apple Secure Enclave Touch ID for the plugin route on a Mac.
  • Each person sends the contents of their SSH public key. It is safe to share.
  • Recipients are public. Never paste a private key into this field.

  • 3. Point fnox at your private key

    • bash
      			  export FNOX_AGE_KEY_FILE=~/.ssh/id_ed25519
    • Add the line to your shell profile to keep it.
  • Run fnox set API_KEY --provider age, then commit fnox.toml. fnox encrypts to the current recipient list, so everyone listed can read it after pulling. No re-encryption step.
  • 1. They send their SSH public key.
  • 4. They commit and push. The new member pulls, sets FNOX_AGE_KEY_FILE, and runs fnox get DATABASE_URL.
  • Without step 3 the new person's key is listed but every existing secret is still locked to the old set. Run it once per profile, for example fnox reencrypt -p age -P staging -f.
  • 3. Rotate the underlying secrets. Removing a recipient cannot revoke access to ciphertext already in git history, and the leaver's key still decrypts those old commits. Upstream says to rotate the secret if access must end. The re-encryption changes the wrapping, not the secret's value.

  • Someone loses their SSH key

    • The same as a departure for that key, then the same as a join for their replacement key. Until the old key is removed and secrets rotated, whoever holds the lost key can decrypt history.
  • Give CI its own age key, not a person's SSH key. Generate it with age-keygen -o ci-age.txt, add the age1... public key to recipients, run fnox reencrypt -p age, and store the secret key in the CI system as FNOX_AGE_KEY.
  • no identity matched any of the recipients: the private key in use is not the pair of any listed recipient. Compare your public key with the recipients array.
  • failed to decrypt: FNOX_AGE_KEY and FNOX_AGE_KEY_FILE are both unset and there is no age.txt in the fnox config directory, or the file is unreadable.
  • An inline FNOX_AGE_KEY overrides the provider's identity and key_file. Unset it if you meant to use an SSH key file.
  • SSH key rejected: confirm the type is ed25519 or rsa and the key has no passphrase.
fnox/How To/Use Apple Secure Enclave Touch ID
  • Keep the fnox sync cache's age key inside Apple's Secure Enclave, so decrypting secrets on your Mac can require Touch ID instead of reading a key file from disk.
  • The command prints a public key beginning age1se1.... Copy it.
  • Put the recipient in the global config so every project on the machine reuses the key.
  • toml
    			  # ~/.config/fnox/config.toml
			  [providers.sync-age]
			  type = "age"
			  recipients = ["age1se1..."]
			  key_file = "~/.config/fnox/age-se.txt"
  • age-se.txt holds a reference to the key in the Secure Enclave, not the private key. Treat it like an identity file anyway.

  • 4. Unset FNOX_AGE_KEY

    • If FNOX_AGE_KEY is exported, unset it. It takes precedence over the provider's key_file.
  • A cache written earlier with a file-based age key is encrypted to that old key. Run the sync command from the fnox/Golden Path with --force to rewrite it: fnox sync --provider sync-age --local-file --force.
  • Unverified: fnox's docs describe --force for refreshing a stale cache, not for switching keys. Confirm that it replaces entries encrypted to the old key.
  • The key only decrypts on the Mac that generated it, so a cache synced here cannot be read from another machine. Run the setup on each machine.

Google/Sheet/Q/Does Google Sheets have a way to sort by more than one column at once?
  • Short answer: Yes, on the web, through one specific dialog. Highlight the cells, then Data > Sort range > Advanced range sorting options, choose the first column and its direction, and click Add another sort column for each further level. That dialog is the only documented multi-column sort in the interface — the right-click commands on a column letter sort by one column only, and the Android and iPhone apps document nothing beyond a single key.
  • Verified — the whole-sheet command takes a single column. The same article's Sort an entire sheet section is three steps: open the spreadsheet, then "At the top, right-click the letter of the column you want to sort by," then "Click Sort sheet A to Z or Sort sheet Z to A." One column, one direction, no dialog, no second key.
  • Inferred — how to get a multi-column sort over all the data. Select the rows you want reordered and use the range path; there is no documented whole-sheet route to a second sort key. Google does not describe this substitution, and the selection is what makes it safe or not: a range sort reorders only the cells inside the selection, so selecting some columns of a table and not others leaves the rest of each row behind.
  • Verified — SORTN adds a row limit to the same multi-key sort. SORTN "Returns the first n items in a data set after performing a sort," with signature SORTN(range, [n], [display_ties_mode], [sort_column1, is_ascending1], ...). Its later pairs are "Additional columns and sort order flags used if a tie happens, in order of precedence" — the same precedence model, described from the tie-breaking side.
  • Verified — a sort key may be a column outside the data being sorted. Both pages state that sort_column can be "the index of the column in range or a range outside of range containing the values by which to sort," provided that range "must be a single column with the same number of rows as range." The dialog has no equivalent of this.
  • The mobile intro reads "You can sort columns of cells alphabetically and numerically," whose plural describes which columns are sortable rather than how many keys a single sort can use — the steps that follow it apply one key.
Graph/Database
  • A graph database stores data as nodes and relationships (edges), with properties on both, so the primary question is what connects to what rather than which row matches this key.

  • Key Principles

    • Nodes and relationships are data — the edge is not an afterthought join; it has a type and can carry properties.
    • Local traversal — queries walk neighborhoods (friends-of-friends, citation chains) without scanning the whole store.
    • Index-free adjacency (ideal) — each node knows its neighbors directly; cost grows with the walk, not with table size.
  • ArangoDB — multi-model (document + graph + key-value).
Ham Radio

  • Key Principles

    • A license to transmit. In the United States, an operator must pass an FCC examination before transmitting on the amateur bands. The entry-level license is the Technician class.
    • Listening needs no license. A receiver, including a shortwave set built from a kit, can pull in distant stations without any license. Listening of this kind is called shortwave listening.
    • No business. Amateur bands are for personal, non-commercial communication.
