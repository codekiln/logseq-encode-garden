Claude/Code/Plugin/Marketplace/Auto-Update
  • On desktop, users manage plugins through the GUI, admins through managed settings JSON, and automation through a hook plus a script. The desktop app registers marketplaces by hosted URL only, so a private marketplace is distributed via its git repo URL.

    Catalog~/.claude/plugins/marketplaces/<name>/A git clone of the marketplace repo. Holds marketplace.json.

Claude/Code/Q/Does editing a plugin's SKILL.md in a local-path Claude Code marketplace require reinstalling, or is restarting Claude Code enough to pick up the change?
  • Why a restart doesn't help: the cache-vs-source split applies to every marketplace-installed plugin, not only git-hosted ones — "Claude Code copies marketplace plugins to the user's local plugin cache (~/.claude/plugins/cache) rather than using them in-place." A restart just reloads whatever is already sitting in that cache.
  • Why /plugin update may not help either: Claude Code decides whether an update is needed by comparing the plugin's resolved version, checked in this order: plugin.json version → marketplace-entry version → git commit SHA (only for github/url/git-subdir/relative-path sources inside a git-hosted marketplace) → unknown for local directories that aren't inside a git repo. A plain local-path marketplace with no explicit version set always resolves to unknown on both sides of the comparison, so /plugin update (and background auto-update) reports "already at the latest version" and skips the re-copy.
  • Plain directory, no .git: version stays unknown forever, so enabling auto-update changes nothing — there's no version delta for it to detect, ever.
  • my-marketplace is itself a git repo (even with no remote) and the plugin uses a relative-path source: version resolves to that repo's commit SHA, so saving SKILL.md alone still doesn't change anything — you must git commit the change. Once committed, auto-update's next background pass (or a manual /plugin update) sees a new SHA and re-copies.
  • Net effect for local plugin development: auto-update is built to keep other people's marketplaces fresh in the background, not for a tight edit-save-test loop. Best case (git-backed marketplace, auto-update on) still needs a commit and a ≤10-minute wait before a notification; worst case (plain directory) it never helps at all. --plugin-dir (below) sidesteps all of this.
Claude/Code/Q/How can I keep my private Claude Code plugin marketplaces up to date daily?
  • Short answer: run claude plugin marketplace update yourself on a schedule (e.g. a daily cron job or launchd task) rather than relying on Claude Code's built-in auto-update — for a private marketplace, auto-update is both off by default and unreliable over HTTPS, while a manual/scripted update uses your normal git credentials the same as your terminal.
  • In practice, the interactive /plugin → Marketplaces → select-marketplace menu may not expose an "Enable auto-update" action at all for a directory-sourced marketplace — auto-update is fundamentally a background git pull, which doesn't apply to a marketplace that's already just a local folder being re-read. The toggle described in Anthropic's docs is on firmer ground for github/git/url-sourced marketplaces.
  • Manual/scripted claude plugin marketplace update reuses your existing git credential helpers, so HTTPS via gh auth login/Keychain/git-credential-store, or SSH via a key loaded in ssh-agent, works the same as a normal git pull in your terminal.
  • Background auto-update is more fragile: by default it disables git credential helpers for its git pull, so private HTTPS remotes can't authenticate even with a helper configured; SSH remotes with ssh-agent are unaffected. A failed background pull falls back to a full re-clone (which does use stored credentials but can time out on large repos), so private-marketplace auto-updates "may fail intermittently."
  • To make a scheduled/background update reliable for a private HTTPS marketplace: configure a git URL rewrite scoped to that marketplace's repo or org with an embedded token (so the pull authenticates directly and skips the re-clone path), and/or set CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1 so a failed pull keeps the last-synced clone instead of deleting it. In CI/cron contexts, gh auth setup-git (or an equivalent credential helper) makes the fallback re-clone work unattended too.
  • Recommended daily setup: a cron/launchd job that runs claude plugin marketplace update once a day (or per-marketplace with [name] if you want to script it against a curated list) sidesteps both limitations above — it isn't gated on starting a session, and it authenticates like a normal terminal git pull rather than the more restricted background-refresh path.
Claude/Code/Q/If I rename a CLI session with /rename, can I resume it in Claude Desktop's Code tab?
  • A structural reason beyond the store split: every Code tab session in a git repository gets its own isolated worktree under <project-root>/.claude/worktrees/ (see git/worktree), plus the status, PR, and environment metadata the sidebar filters, groups, and auto-archives on. A plain CLI session carries none of that, so there is nothing for the sidebar to file it under.
Claude/Code/Q/In Claude Code settings, is it possible to declare additional directories that should be checked for the directories that skills are loaded from?
  • Project: .claude/skills/<skill-name>/SKILL.md in the starting directory, every parent up to the git/repo root, and nested .claude/skills/ under subdirectories you work in (monorepos).
Claude/Code/Q/Is there a Claude Code CLI slash command to see a diff of changed files, and why doesn't /diff show the diff content?
  • Short answer: /diff exists; the "New file not yet staged" message for untracked files is a side effect of the Current tab being git diff HEAD under the hood, not intentional concealment — git has no index entry to diff an untracked file against.
  • Per the official reference, /diff has two kinds of tabs: Current (git diff HEAD, all uncommitted changes) and per-turn (T1, T2, …, individual Claude turns). The docs describe switching between them but don't specify the per-turn tabs' data source.
  • Unconfirmed in official docs (seen on a third-party blog): per-turn tabs may reconstruct edits from the conversation record rather than from git, which would let them show new-file content without staging first. Worth testing empirically — arrow to a turn tab (e.g. T6) for an untracked file instead of Current.
  • Running git add <file> stages an untracked file; after that, the Current tab shows its full diff and line counts.

  • Out of scope: commands with external side effects (git push, API calls, package installs) are not reverted — only in-session file edits and conversation turns.
Claude/Code/Q/Is there any equivalent functionality in Claude Code's CLI to Claude Desktop's Code tab ability to group related chat histories together?
  • Session picker: /resume (or claude --resume) opens a picker scoped to the current directory by default. From there: Ctrl+W expands to all worktrees, Ctrl+A expands to all projects on the machine, Ctrl+B filters by git branch, and text search matches names/summaries/PR URLs. Sessions can also be given a name (claude -n <name> or /rename) so related ones are easier to pick out.
