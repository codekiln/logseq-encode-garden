Page reference

Is there a quick way to use glow to preview the current Markdown file while editing in nvim? cardMy Answer

  • Current Workaround - vim/split/v vsplit

    • :vsplit | terminal glow -p % opens a vertical split using nvim's built-in terminal buffer, which renders glow's ANSI output properly.
      • terminal opens a proper PTY (pseudoterminal) buffer in nvim that renders ANSI escape codes; :!glow % runs in a non-PTY subprocess and strips ANSI sequences, showing garbled text
      • In vim's command-line mode, % is a special filename modifier that expands to the current buffer's filename — so glow -p % becomes glow -p /path/to/file.md

    • Extra

      • To map it to <leader>mg, add to init.lua:
        • lua
          					  vim.keymap.set('n', '<leader>mg', ':vsplit | terminal glow -p %<CR>',
					    { desc = 'Glow markdown preview' })
      • Press q to quit the glow pager, then <C-w>c to close the split.
nvim/Q/Once I open a file in read-only mode in vim or nvim, can I flip to edit mode?

  • Once I open a file in read-only mode in vim or nvim, can I flip to edit mode?

    • AI Answer

      • AI/Response
        • Short answer: Yes. Run :set noreadonly (short form: :set noro) to remove the read-only flag and allow normal editing and saving.
        • How read-only mode works: Opening with nvim -R file or view file sets vim's internal readonly option on the buffer. The file is still modifiable — you can enter insert mode, but vim warns you first.
        • If you try to insert before clearing the flag: vim prints W10: Warning: Changing a readonly file. Press Enter to dismiss and continue editing. The buffer now has unsaved changes but is still flagged readonly, so :w will refuse. Clear the flag first:
        • vim
          			  :set noreadonly
        • Then :w saves normally.
        • Toggle shorthand: :set readonly! toggles the flag (readonly → not readonly, or vice versa).
        • If the file's OS permissions also block writing: clearing readonly is not enough — vim will still refuse :w. Use :w! to force (if you have permission), or fix the file permissions externally first.
        • Summary table:
        • SituationCommand
          Clear readonly flag:set noreadonly or :set noro
          Toggle readonly flag:set readonly!
          Force-write (permissions allow):w!

tmux/Q/How can I enable vi keys for everything in tmux from the command prompt without editing the config?

  • How can I enable vim keys for everything in tmux from the tmux/Command/Prompt without editing the config? card

    • tmux/Command/Prompt (Prefix :)
      • set -g mode-keys vi
        • sets vi controls in tmux/Option/mode-keys (scrolling, search, text selection)
      • set -g status-keys vi
        • sets vi controls in tmux/Option/status-keys (tmux/Command/Prompt, rename prompt, search prompts)
      • these are runtime-only; it will be gone again after tmux kill-server

    • AI Answer

      • Short answer: Press Prefix : and run set -g mode-keys vi, then repeat for set -g status-keys vi. Two commands, done. Changes are runtime-only—they vanish after tmux kill-server.

      • The two options

        • tmux/Option/mode-keys — controls tmux/Mode/Copy, scrolling, search, and text selection. Default is emacs.
        • tmux/Option/status-keys — controls the tmux/Command/Prompt (Prefix :, rename prompts, search prompts). Default is emacs unless $VISUAL or $EDITOR contains vi.

      • Steps at the command prompt

        • 1. Prefix : → type set -g mode-keys vi → Enter
        • 2. Prefix : → type set -g status-keys vi → Enter
        • Both options accept vi or emacs. The -g flag applies the change globally (all sessions on the current server) without writing to any file.

      • From the shell (outside tmux)

        • sh
          			  tmux set -g mode-keys vi && tmux set -g status-keys vi
        • Useful when you want to script it or apply it before attaching.

      • Persistence caveat

        • These commands change the running tmux server; they do not touch ~/.tmux.conf. The settings disappear when the server stops (tmux kill-server or system reboot). To make them permanent, add the same two set -g lines to your config and reload with Prefix r (or tmux source-file ~/.tmux.conf).
tmux/Q/Is it possible to split a pane for copy-mode scrollback above and live shell below like vim?

  • Is it possible to split a tmux pane for copy-mode scrollback above and live shell below like vim?

    • Motivation: browse scrollback and copy with visual selection in one area while composing or quoting in another — analogous to two views of one buffer in vim (without shared-buffer semantics).

    • Answer

      • AI/Response
        • Short answer: tmux does not offer a vim-style “one buffer, two views” for a single pane’s scrollback. Copy mode always occupies the whole pane you started it in, and it only shows that pane’s history. A split gives two independent PTYs with separate scrollback buffers, so a copy-mode browser in the top pane is not automatically the same stream as the shell in the bottom pane.
        • What the “other” pane is doing: In a split layout, each pane is just another shell (or another program). There is no built-in “mirror this pane’s scrollback here” mode. The bottom can stay your normal shell; the top would only match that scrollback if you copy data over (see below), not because tmux links two views of one buffer.
        • Practical workflows that get close:
          • Split + copy mode in the pane that owns the history — If all the output you care about is in the bottom pane, enter copy mode there (Prefix+[). You lose simultaneous typing in that same pane until you exit copy mode, but you can yank to tmux’s buffer or the OS clipboard and then move focus to another pane to paste (Prefix+], or Cmd+V if your config bridges to the clipboard). That matches “select upstairs, use downstairs” across panes, but not two live views of one scrollback.
          • Snapshot scrollback into the other pane — From the pane that has the history, push text out with capture-pane and read it in the second pane, e.g. tmux capture-pane -S -5000 -p -t 'session:window.pane' | less or into nvim. That is a point-in-time copy, not a continuously synced second view (re-run to refresh).
          • Log the stream for a true second window — pipe-pane (or shell tee) can append live output to a file; a split can run less +F file / tail -f on that file. Good for forward-looking duplication; older scrollback before logging started is not magically shared.
          • synchronize-panes — Sends the same keystrokes to multiple panes; it does not tie scrollback together like scrollbind, and it is a poor fit for “browse in copy mode while typing elsewhere.” See discussion in this Stack Overflow thread.
        • Bottom line: The vim analogy breaks because a terminal pane is not a text buffer — it is a PTY with one display state. For “read old output while editing,” splitting in tmux helps spatially (reference + work side by side); bridging content is via yank/paste, capture-pane, or logging, not a native dual-view scrollback.
        • Sources:
          • tmux(1) — copy mode, capture-pane, pipe-pane
          • Stack Overflow — tmux scroll two panes like vim scrollbind

    • My Notes

      • Add working bindings or scripts here if you settle on capture-pane or pipe-pane.

      • tmux/Q/What is a conceptual overview of how copy paste works in oh-my-tmux with nvim?

vim/Keyshort/Open/Follow the File Path Under Cursor

Page reference

  • Keyshort vim vim/Keyshort vim/Keyshort/Open
    • Follow the File Path Under the Cursor
      • Shortcut: gf
      • Description: Reads the filename at or after the cursor and edits it in the current window. Stock vim, the same key in nvim, and LazyVim leaves it alone.
      • The Mnemonic: f for file. gf stays inside the editor, while gx hands the target to the operating system.
    • Open the same target somewhere other than the current window
      • KeysWhere the file opens
        gfthe current window
        <C-w>fa horizontal split
        <C-w>v then gfa vertical split
        <C-w>gfa new tab
        gFthe current window, on the line named by a path:12 suffix
        gf in visual modethe current window, taking the whole selection as the name
      • There is no stock vertical-split form of gf. Splitting the window first and following the path in the new one gets there in two keys.
      • <C-o> returns from the jump and <C-i> moves forward again — see vim/Keyshort/Jump/Back and Forward.
    • What decides whether the path resolves
      • isfname decides where the name starts and ends. Two characters a Logseq filename leans on are in it by default: _ carries the triple underscore of a namespace, and % carries the %3F that stands in for a question mark.
      • path is the list of directories the search runs through. Its default .,, means the directory of the file being edited, then the editor's working directory.
      • suffixesadd is empty on a Markdown buffer, so a target written without its .md fails until the option is set.
    • Where it stops
      • A space ends the name early. isfname holds no space, so pages/A Page With Spaces.md is read as pages/A and the search fails. Selecting the whole path and pressing gf in visual mode opens it, since the visual form ignores isfname and takes the selection whole.
      • The list marker counts as part of a filename. - is an isfname character, so gf with the cursor on the - of a bullet reads that dash as the name. From the space after it onward, the whole path is in reach.
      • A buffer-local mapping that steps past the marker puts the key back in reach from column 1 — vim/Q/In (neo-)vim or LazyVim, how can I open a file whose path a Markdown document gives from the repo root? carries it.
    • My Note
      • A path written from the repository root — the shape a garden page uses for journals/2026_08_24.md — resolves under gf only while the editor's working directory is that root. vim/Q/In (neo-)vim or LazyVim, how can I open a file whose path a Markdown document gives from the repo root? has the setting that frees it from the working directory.
      • For a link written as Markdown rather than as a bare path, LazyVim/Q/In LazyVim, how can I open a Markdown link with a keyboard shortcut? compares gf against gx and gd on the same target.

vim/Q/How can I check whether vim or neovim will yank to the unnamedplus (system) clipboard?

  • How can I check whether vim or nvim will yank to the unnamedplus (system) clipboard?

    • Answer

      • AI/Response
        • Read the option: In Ex mode run :set clipboard? (or :echo &clipboard). If you see clipboard=unnamedplus, yanks and deletes that target the unnamed register are also applied to the + register (the system clipboard on X11/Wayland/macOS when clipboard integration works). unnamed wires the unnamed register to * (primary selection on X11) instead of +.
        • Neovim from Lua: vim.o.clipboard and vim.go.clipboard both reflect the global 'clipboard' value; :lua print(vim.o.clipboard) matches :set clipboard?.
        • Neovim — provider, not only a compile flag: nvim still uses 'clipboard' the same way, but it talks to the OS through a clipboard provider (e.g. pbcopy / pbpaste on macOS, xclip / xsel on X11, wl-copy / wl-paste on Wayland). Run :checkhealth and open the clipboard (or provider) section: failures there explain unnamedplus set in config while + never updates or paste-from-OS breaks.
        • Neovim quick probe in Lua: :lua vim.fn.setreg('+', 'nvim-clipboard-test') then paste outside the editor; or :lua print(vim.fn.getreg('+')) after yy with unnamedplus — should echo the yanked text when the provider works.
        • Confirm the build can talk to the OS (Vim-centric): :echo has('clipboard') and :version (+clipboard vs -clipboard) matter most for classic Vim; Neovim builds assume provider integration—trust :checkhealth plus the + register / OS paste checks above when diagnosing nvim.
        • Behavioral check: Yank a distinctive string with yy (or visual then y), then inspect registers. Prefer :registers with no arguments (full list; press Space / j if -- More -- appears). :reg + means :reg then <Space> then + then Enter. The unnamed register’s name is a single ASCII double-quote — the Ex line is :reg " (space, one double-quote, Enter), which is easy to mistype; :echo string(vim.fn.getreg('"')) and :echo string(vim.fn.getreg('+')) in nvim always show something ('' means empty). To force text into the buffer: :put =vim.fn.getreg('"') then :put =vim.fn.getreg('+'). With unnamedplus, + should match the yank; confirm with Cmd+V / Ctrl+V outside the editor.
        • Contrast without unnamedplus: After a normal yy, + may stay unchanged unless you yanked explicitly with "+y; compare :echo string(vim.fn.getreg('"')) vs getreg('+') (or the " / + lines in a full :registers dump) before and after one yank.
        • Troubleshooting — no visible echo from commands: :set clipboard?, :lua print(...), and :echo has('clipboard') usually print a one-line echo in the message area (easy to miss when cmdheight is 1, another UI plugin steals echoes, or the line scrolls away). Try :set cmdheight=3, rerun :set clipboard?, or :echomsg 'clipboard=' .. &clipboard and then :messages. For Lua, :lua vim.notify(vim.inspect(vim.o.clipboard)) (with nvim-notify) or :put =execute('set clipboard?') drops text into the buffer so you cannot miss it.
        • Troubleshooting — checkhealth OK for pbcopy but visual yank skips macOS clipboard: OK only means Neovim can invoke the clipboard tool. It does not set 'clipboard' to unnamedplus. With the default (empty clipboard), y in visual mode fills " / 0, not +, so Cmd+V outside the editor stays unchanged. Fix: set clipboard=unnamedplus / vim.o.clipboard = 'unnamedplus' in config, or yank explicitly with "+y. Right after a yank, use :echo string(vim.fn.getreg('"')) vs getreg('+') or a full :registers dump to see where the text went.
        • Troubleshooting — plain nvim OK, visual yank “doesn’t work” only under tmux: First verify inside tmux that "+y updates + (:echo getreg('+')). If "+y works but y alone does not, you still need unnamedplus (or always "+y). If "+y also fails in tmux while checkhealth is green, run :messages after the yank (Neovim surfaces provider errors there), then test pbpaste from a shell in the same tmux pane after echo test | pbcopy — if the shell cannot round-trip pasteboard while attached to that tmux session, the editor inherits the same limitation (macOS sometimes tied tmux + pasteboard quirks; older setups used reattach-to-user-namespace).
        • Troubleshooting — single-register output looks empty: For :reg + and :reg ", (1) :registers with no args is easier than single-register forms; watch for -- More -- and advance the pager. (2) :reg " must end with exactly one " (the register name); an extra " turns it into a different command / error. (3) Empty + may print no line for + in a short listing—use string(getreg(...)) or :put =... so emptiness shows as '' or a blank inserted line. (4) UI plugins (noice.nvim, etc.) sometimes reroute or auto-dismiss multiline :registers output—fall back to :echo string(...) / :put =... or :lua vim.print({ ... }).
        • Troubleshooting — registers output flashes then vanishes: Typical when noice.nvim (often with nvim-notify) shows msg_show output in a notify / mini view that auto-dismisses. Mitigations: enable preset long_message_to_split so long output opens a split you can read; add a route sending event = "msg_show" (or kind = "echo") to view = "split"; raise views.notify.timeout (milliseconds) or false where supported; run :Noice / :Noice history to reopen message history after the popup closes; temporarily :Noice disable to confirm stock msgarea behavior. Bypass the UI entirely: :redir @a | silent registers | redir END then :new :put a (or :put =execute('registers')) so the dump lives in a buffer.

vim/Q/How can I get a VS Code-style split Markdown preview in (neo-)vim that renders in the terminal (e.g. glow)?

  • How can I get a VS Code–style split Markdown preview in (neo-)vim that renders in the terminal (e.g. glow)?

    • My Notes

      • Want editor split + ANSI/TUI rendering, not browser HTML preview. Still haven't found anything that works. I've seen a few youtubers that had some kind of markdown rendering that worked pretty well, but it wasn't split screen

    • Answer

      • AI/Response
        • Yes — several patterns exist, but there is no single “official” Neovim feature that is exactly VS Code’s Markdown preview with a terminal renderer. You combine splits + :terminal (or a plugin) + a CLI like glow (or mdcat, Pandoc -t ansi, etc.).

        • Plugin-shaped options

          • glow.nvim — wraps the glow binary and shows rendered Markdown inside Neovim (historically popular). The repo has been archived; treat it as “works until it doesn’t,” not a long-term bet. It is still a common reference implementation for “glow inside Neovim.”
          • mdpreview.nvim — described as a live-reloading preview using a configurable CLI renderer (defaults toward glow), with a split window workflow. Marked WIP and low activity; worth a try if you want split + auto-refresh, but expect rough edges.

        • Minimal DIY (split + terminal + glow)

          • Open a vertical split and run glow on the file on disk: e.g. :vsplit | terminal glow -p % (adjust paths; glow must be installed). This approximates “split preview” when you save and re-run or use a mapping.
          • For unsaved buffers, a small Lua pattern is to write a temp file, open :terminal glow -p <tempfile>, and clean up on TermClose; see Haylin Moore’s walkthrough for a concrete example. You can extend that with BufWritePost / TextChanged autocmds if you want nearer-to-live updates (mind performance and flicker).

        • “Smart” preview without a separate terminal pane

          • nvim/Plugin/render-markdown.nvim gives a rich in-buffer Markdown view (headings, callouts, etc.) using Neovim’s UI — not the same as piping through glow, but it matches the “stay in the editor” spirit when HTML preview plugins feel heavy.

        • Outside Neovim

          • A terminal multiplexer split (e.g. tmux) with Neovim in one pane and glow -p (optionally wrapped with watchexec / entr on save) in the other is a dependable pattern when you want zero Lua and true full-terminal rendering.
