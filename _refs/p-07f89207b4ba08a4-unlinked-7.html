Cloudflare/R2/Concept/Pricing Compared with Backblaze B2
  • Cloudflare R2 Standard storage is $0.015 per GB-month, with the first 10 GB-month free each month.
  • Backblaze B2 pay-as-you-go storage starts at $6.95 per TB-month, with the first 10 GB free. At the published rates, B2 storage costs less per GB than R2.
  • R2 includes 1 million Class A operations and 10 million Class B operations monthly. Above those allowances, Standard operations are billed at $4.50 per million Class A requests and $0.36 per million Class B requests. Deletes are free.
  • B2 lists Class A, B, and C transactions as free for pay-as-you-go accounts. The first 2,500 Class D calls per day are free; additional Class D calls cost $0.004 per 10,000. Check the transaction-pricing page for which calls fall into each class.
  • For small libraries within either provider's 10 GB free storage allowance, other usage and workflow fit may matter more than storage price.

      • The document identifies itself as a draft syllabus for Spring 2027. Its filename carries the version label Oct-26; the document does not state a publication date.

      • Purpose

        • An interdisciplinary conversation among university students and practitioners about living through interconnected social and ecological crises, choosing a life’s purpose, and finding useful ways to act.
        • The course examines whether disconnection from oneself, other people, and nature helps explain these crises, and whether personal and collective inner work can contribute to systemic change.
        • Readings, shared practices, and practitioner visits connect personal experience with institutions and social change. Intended outcomes include a sustaining personal practice, a better understanding of how systemic change happens, and possible directions for one’s own life.

      • Attend every class, apart from an absence approved in advance or a genuine emergency.
      • Submit six responses to the readings, each no longer than 500 words. Responses are due approximately every other week on Monday evening before Wednesday’s class; prompts arrive a week beforehand. Specific submission dates are not listed in the draft.
      • Join a small coached learning circle for an hour each week to support mutual learning and explore applications in everyday life. The draft anticipates virtual meetings but does not finalize the format.
      • Spend at least fifteen minutes daily on a grounding or centering practice. Options include time in nature, journaling, gratitude, Tai Chi, and meditation.

      • Experiential Practice

        • Shared exercises include deep listening, working with grief and difficult emotions, considering other perspectives, and noticing reactions to disagreement or challenging ideas.

DevContainer/Report/25/12/Multi-Env DevContainer Setup
  • Example 1 – The Red Guild's Multi-Config Repository: The Red Guild's devcontainer repository offers multiple .devcontainer/… directories, each tailored to a scenario. Notably, it includes a .devcontainer/codespaces/ configuration intended specifically for GitHub Codespaces [9]. Their project structure shows parallel configs for "airgapped", "hardened", "minimal" etc., and a separate "codespaces" variant that omits certain run arguments that might not work in Codespaces [9] [10]. This pattern allows them to maintain a base Dockerfile and vary only what's needed per environment. A developer launching VS Code locally might use one config (with host bind-mount), whereas Codespaces users can explicitly choose the codespaces config (which presumably uses the bind mount of the pre-cloned repository but adjusts other settings), and another environment could be chosen for high-security needs. The ReadMe instructs users to pick the appropriate devcontainer folder and "Reopen in Container," leveraging VS Code's ability to list multiple devcontainer.json options [10].
  • A. Multiple DevContainer Configs: As seen in Section 2, maintaining separate .devcontainer directories for each environment is a straightforward (if duplicated) solution. For example, you might have a base .devcontainer/devcontainer.json (optimized for VS Code and Codespaces using bind mounts) and another at .devcontainer/jetbrains/devcontainer.json (which configures the workspace as a named volume and perhaps includes the SSH server feature needed for Gateway). Developers would then choose the appropriate one. Pros: Clear isolation of settings; each environment gets a config tailored to its needs (no weird hacks). They can diverge on other things too (e.g. JetBrains config might omit VS Code-specific settings and include JetBrains plugin setups instead). Cons: Duplication of a lot of config content – changes have to be propagated to both files. It's mitigated somewhat if you keep most logic in the Dockerfile or Compose and just vary the mount and a few settings. Documentation is needed so users know which config to use (though Codespaces UI and JetBrains's Gateway prompt can list them by name [10]). This approach is currently the most reliable and is officially supported by the spec (which anticipates multiple configs for different scenarios) [1].

  • [10] https://github.com/theredguild/devcontainer

DevContainer/Secrets/Report/26/01/Secrets Management in JetBrains DevContainers
  • JetBrains CodeCanvas example: JetBrains' own cloud-hosted dev environment platform, CodeCanvas, uses a two-phase approach under the hood. Administrators can define a Dev Environment Template that includes an image and then specify Personal Parameters (user-specific secret env vars or files) to inject at startup[8] [9]. CodeCanvas also supports "Cloud policy" credentials – e.g., auto-injecting cloud resource keys – which are applied to the container when it's created[10]. This means the base container is prepared in advance (and even warmed up), and when a developer launches it, their personal secrets get layered in just for their session. In essence, CodeCanvas achieves the ideal two-phase workflow: an admin provides the base devcontainer (phase 1) and the platform injects secrets at runtime (phase 2) in a secure way[11] [12].
  • JetBrains CodeCanvas (Cloud): Platform-managed secrets. CodeCanvas templates allow admins to define Personal Parameters – user-specific secret env vars or files – which are automatically injected into the devcontainer when it starts[8] [9]. Also supports Cloud Policies that auto-inject cloud provider credentials into the environment[10]. This means developers using CodeCanvas get their secrets without manual steps, and secrets stay in the platform's secure storage. (CodeCanvas is analogous to Codespaces for JetBrains, and it addresses secrets as first-class citizens.)

  • [10] https://www.jetbrains.com/help/codecanvas/configure-dev-environments.html
