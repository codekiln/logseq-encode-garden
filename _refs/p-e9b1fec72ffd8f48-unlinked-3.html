Claude/Code/How To/Answer Permission Dialog To Record Wildcard Permissions in Local Settings

  • How To Answer the Permission Dialog To Record Wildcard Permissions in Local Settings

    • Overview

      • When Claude/Code asks for permission to run a command, you can edit the suggested permission entry before confirming to make it a wildcard that covers a broader class of commands.
      • This lets you grant bounded-but-flexible permissions that persist in .claude/settings.local.json without having to manually edit that file.

    • Prerequisites

      • Claude/Code installed and running in a project
      • A session where Claude has just asked for permission to run a shell command

    • Steps

      • 1. Wait for the permission prompt

        • Claude will display a prompt asking whether to allow a specific command, e.g.:
          • 				  Allow bash command?
				  1. Yes, allow once
				  2. Yes, allow bd --no-daemon --specific-flag value
				  3. No

      • 2. Select option 2

        • Press 2 and Enter to select the "allow and remember" option.
        • The full specific command string will appear in an editable field.

      • 3. Edit the command to a wildcard

        • Use the Delete (or Backspace) key to remove the overly-specific trailing arguments.
        • Replace them with * to match any arguments with that prefix.
        • Example: bd --no-daemon --specific-flag value → bd --no-daemon *

      • 4. Confirm

        • Press Enter to confirm.
        • Claude/Code writes the permission to .claude/settings.local.json in the form:
          • json
            				  "Bash(bd --no-daemon *)"

      • 5. Verify (optional)

        • Open .claude/settings.local.json and confirm the entry looks as expected.

    • Troubleshooting

      • The field isn't editable — some terminal emulators may not support inline editing at the prompt; try a different terminal.
      • Too broad a wildcard — avoid patterns like rm * that could allow destructive commands. Be specific enough to cover your use case without opening up unintended commands.

Claude/Code/Q/Does editing a plugin's SKILL.md in a local-path Claude Code marketplace require reinstalling, or is restarting Claude Code enough to pick up the change?

  • Does editing a plugin's Claude Code Skills SKILL.md in a local-path Claude/Code/Plugin/Marketplace require reinstalling, or is restarting Claude Code enough to pick up the change?

    • AI Answer

      • Answer/Official from Plugins reference - Claude Code Docs
        • Short answer: No, restarting alone is not enough. A plugin installed with /plugin install from any marketplace — including one added from a local path via /plugin marketplace add ./my-marketplace — is copied into ~/.claude/plugins/cache at install time. Claude Code loads that cached copy, not the live files under my-marketplace/, so editing SKILL.md in the source tree has no effect until the plugin is reinstalled or updated.
        • Why a restart doesn't help: the cache-vs-source split applies to every marketplace-installed plugin, not only git-hosted ones — "Claude Code copies marketplace plugins to the user's local plugin cache (~/.claude/plugins/cache) rather than using them in-place." A restart just reloads whatever is already sitting in that cache.
        • Why /plugin update may not help either: Claude Code decides whether an update is needed by comparing the plugin's resolved version, checked in this order: plugin.json version → marketplace-entry version → git commit SHA (only for github/url/git-subdir/relative-path sources inside a git-hosted marketplace) → unknown for local directories that aren't inside a git repo. A plain local-path marketplace with no explicit version set always resolves to unknown on both sides of the comparison, so /plugin update (and background auto-update) reports "already at the latest version" and skips the re-copy.
        • How auto-update interacts with this: auto-update doesn't diff file contents — it re-runs the same version comparison as /plugin update, just on a timer, so it inherits the same blind spot.
          • It's off by default for exactly this kind of marketplace: "official Anthropic marketplaces have auto-update enabled by default. Third-party and local development marketplaces have auto-update disabled by default." Turn it on per marketplace via /plugin → Marketplaces → select the marketplace → Enable auto-update (or, for a team, an admin sets "autoUpdate": true on that marketplace's extraKnownMarketplaces entry in managed settings).
          • Even enabled, whether it can ever notice the edit depends on what my-marketplace/ actually is:
            • Plain directory, no .git: version stays unknown forever, so enabling auto-update changes nothing — there's no version delta for it to detect, ever.
            • my-marketplace is itself a git repo (even with no remote) and the plugin uses a relative-path source: version resolves to that repo's commit SHA, so saving SKILL.md alone still doesn't change anything — you must git commit the change. Once committed, auto-update's next background pass (or a manual /plugin update) sees a new SHA and re-copies.
            • Explicit version set in plugin.json/the marketplace entry: same rule as manual update — auto-update only fires when that string is bumped.
          • Timing, when it does apply: "Claude Code checks for marketplace and plugin updates after your session starts, with a random delay of up to ten minutes, so the running session keeps using the versions it loaded at launch. If any plugins were updated, you'll see a notification prompting you to run /reload-plugins, or the new versions load on your next launch."
          • Net effect for local plugin development: auto-update is built to keep other people's marketplaces fresh in the background, not for a tight edit-save-test loop. Best case (git-backed marketplace, auto-update on) still needs a commit and a ≤10-minute wait before a notification; worst case (plain directory) it never helps at all. --plugin-dir (below) sidesteps all of this.
        • To actually pick up the edit:
          • 1. Reinstall: /plugin uninstall my-plugin@my-marketplace then /plugin install my-plugin@my-marketplace. This forces a fresh copy into the cache regardless of the version string. The uninstall command's --keep-data flag exists for exactly this case — the docs note it's for "reinstalling after testing a new version" — to preserve ${CLAUDE_PLUGIN_DATA} across the reinstall.
          • 2. Or set an explicit version in plugin.json (or the marketplace entry) and bump it on every change, then run /plugin marketplace update my-marketplace followed by /plugin update my-plugin@my-marketplace (or let auto-update apply it once enabled for that marketplace).
          • 3. If skills still don't show up after reinstalling, clear the cache outright: rm -rf ~/.claude/plugins/cache, restart Claude Code, and reinstall.
        • Better fit for active plugin development: skip the marketplace-install path and load the plugin for the session with claude --plugin-dir /path/to/my-plugin instead. --plugin-dir plugins are read in place rather than copied to the cache, so edits are picked up on the next session start with no install/update step — the pattern used for rapid local iteration in Claude/Code/Plugin/Marketplace/Report/26/01/Automated Testing.
        • Related, narrower exception: a plugin auto-discovered from a project's skills/ directory via @skills-dir (no marketplace, no install step) is read in place, and edits to its SKILL.md take effect immediately in the current session — but that's a different mechanism from a marketplace-installed plugin, and its other components (hooks, .mcp.json, agents) still need /reload-plugins or a restart.

Claude/Code/Q/What is the difference between the schedule command in Claude Code CLI and Routines in Claude Desktop's Code tab?
  • Short answer: Desktop's Routines page is the umbrella UI for two different scheduling mechanisms under one name — Cloud routines and Local scheduled tasks. The CLI's /schedule command only reaches one of those two — Cloud routines — and has no facility at all for the other.
  • Local scheduled tasks — the part /schedule cannot touch: Desktop → Routines → New routine → Local creates a task that runs on the user's own machine, persisted as ~/.claude/scheduled-tasks/<task-name>/SKILL.md. Claude/Code/Settings
  • Local — .claude/settings.local.json, personal to one person in one repository and kept out of git. Claude Code adds **/.claude/settings.local.json to the global excludes file — core.excludesFile if set, otherwise $XDG_CONFIG_HOME/git/ignore or ~/.config/git/ignore.
  • Since 2.1.211 the local file lives at the git repository root, resolved through worktrees, so it covers every subdirectory. Older locations are still read. It stays in the starting directory in three cases: outside a git repository, when the repository root is the home directory, and in Agent SDK sessions.
  • Answering a permission prompt with "don't ask again" writes the rule to the local file. Those allow rules take effect without workspace trust, because the file is personal — but once the file is committed, workspace trust applies to it again.
  • Highest to lowest: managed, command-line arguments, local, project, user.
  • claudeMdExcludes — glob patterns or absolute paths of CLAUDE.md files to skip. Applies to user, project, and local memory, never to managed instructions. Arrays merge across scopes. Example: ["**/code/CLAUDE.md"].
  • worktree.baseRef — what new worktrees branch from: fresh from the remote default branch, or head from the current local HEAD so unpushed work is present.
Claude/Code/Settings/Override
  • 1. settings.json scopes — a fixed set of locations (user, project, local, managed) combined by a precedence order. There is no directory walk; each scope is a known path.
  • Project (local) — .claude/settings.local.json. Personal, not checked in; Claude Code configures git to ignore it on creation.
  • 3. Local (.claude/settings.local.json) — overrides project and user.
  • For most keys, the highest-precedence scope that defines the key supplies the entire value — lower scopes are ignored for that key. A model set in local replaces the model in project, which replaces the one in user.
  • Within managed settings, managed-settings.json is the base and managed-settings.d/*.json are merged on top alphabetically: "Later files override earlier ones for scalar values; arrays are concatenated and de-duplicated; objects are deep-merged." This deep-merge is specific to the managed drop-in layer, not to the user/project/local layers.
  • Because resolution is per-plugin, a higher scope only overrides the specific plugins it names — you do not have to restate the whole map. Project settings take precedence over user settings, so setting a plugin to false in ~/.claude/settings.json does not disable one the project's .claude/settings.json enables; to opt out on your machine, set that plugin false in .claude/settings.local.json.
  • Source shapes include github (repo, optional ref/path), git (url), url, npm, file, and directory. Prefer github/git for anything checked in — a local directory path won't resolve on a teammate's machine or in a fresh container.
  • The interactive UI (and --scope) let you choose project scope (writes to .claude/settings.json, shared) or local scope (writes to .claude/settings.local.json, personal to the repo). /plugin enable / /plugin disable toggle the corresponding enabledPlugins entry.
  • CLAUDE.md / CLAUDE.local.md: yes. "Claude Code reads CLAUDE.md files by walking up the directory tree from your current working directory, checking each directory along the way." All discovered files are concatenated (root → cwd order), not overridden — so a parent CLAUDE.md and a nested one both apply. Files in subdirectories load on demand when Claude reads files there. .claude/rules/*.md follow the same model.
  • 2. Each person puts their personal plugin toggles in .claude/settings.local.json (gitignored). Since enabledPlugins resolves per-plugin, local only needs the deltas — additional plugins set true, and any baseline plugin they want off set false.
  • 3. Because local > project > user, the local file wins for exactly the plugins it names and leaves the rest of the shared config untouched. Pushing customization into settings.local.json (rather than ~/.claude/settings.json) is what makes per-person opt-out of a project-enabled plugin possible.

Claude/Desktop/Code/Q/How can I make sure a Routine in Claude Desktop's Code tab has all the permissions it needs to run, since there's no obvious way to set automatic permission mode?
  • Short answer: It depends which of the two things Desktop's Routines page created. A Cloud routine has no permission-mode picker at all — that's by design, not a gap: cloud routines always run autonomously with no approval prompts, and their reach is bounded by repositories, the cloud environment, and connectors instead. A Local scheduled task does have a permission-mode picker and a per-task "always allow" approval list — if that's the control that seems to be missing, it's likely because Cloud was picked instead of Local when the routine was created.
  • Local scheduled tasks (Desktop → Routines → New routine → Local): these do have a permission mode. The instructions form "includes pickers for the permission mode and model," set per task at creation or edit time; allow rules from ~/.claude/settings.json also apply to scheduled-task sessions.
  • Getting a Local task to run with full automatic permission: if a task runs in Ask mode and hits a tool it isn't allowed to use, the run stalls in the sidebar until approved. To avoid that: click Run now right after creating the task, watch for permission prompts, and choose "always allow" for each one — future scheduled runs then auto-approve those same tools without prompting. Saved approvals can be reviewed or revoked later from the task's "Always allowed" panel on its detail page.
  • Bottom line: not finding a way to set automatic permission is expected for a Cloud routine — there's nothing to configure, since it's already unattended. For a Local scheduled task, the setting exists; the durable "no more prompts" state comes from one manual Run now with "always allow" clicks, not from a single toggle.

Claude/Desktop/Scheduled Task
  • A Desktop scheduled task is a Local routine: created from Claude/Desktop's Routines sidebar page → New routine → Local. It runs on the user's machine with direct access to local files and tools, starting a new session automatically at a chosen time/frequency.
  • It only fires while Desktop is open and the computer is awake—the opposite tradeoff from a cloud Claude/Routine (Anthropic-managed infrastructure, works even with the machine off, but no local file access).
  • The Desktop Routines page is the shared UI for both kinds: choosing Local creates a scheduled task (this page); choosing Cloud creates a Claude/Routine.
  • Desktop scheduled task ≠ /loop, even though both run on the local machine. The difference is whether a session must already be open:
    • A scheduled task starts a brand-new session by itself at the scheduled time—no session needs to be open beforehand. It survives app restarts because it's saved to disk.
    • /loop only keeps an already-open session repeating a prompt on an interval; it does not create new sessions and stops the moment that session closes.
  • Storage differs accordingly: a scheduled task is a durable file at ~/.claude/scheduled-tasks/<task-name>/SKILL.md (YAML frontmatter name/description + prompt body); a /loop (or CronCreate) task is session-local, restored on --resume/--continue only if unexpired, and expires after 7 days.

Claude/Routine
  • Each successful trigger creates a new cloud session (with a session URL); runs do not require an open local terminal or laptop.
  • Routines move the execution layer to the cloud: the same agentic capabilities (shell, repo clone, MCP connectors, skills in the cloned repo) run without permission prompts and without waiting for a local session.
  • Connectors: MCP integrations from the claude.ai account (not CLI-only claude mcp add local servers unless also added as cloud connectors or committed .mcp.json in the repo).
  • Recurring presets (hourly, daily, weekdays, weekly) or one-off at a future timestamp; wall-clock times use the creator’s local zone.
  • Claude Code in the terminal exposes two different scheduling models: /schedule (same product as cloud Routines) and /loop plus cron tools (session-local, not Routines). Official comparison: Run prompts on a schedule.
  • /schedule creates and manages Routines saved to the claude.ai account; runs happen on Anthropic cloud, not in the local process.

  • /loop and cron tools — session-local (not Routines)

    • /loop repeats a prompt while the current CLI session stays open on the local machine; it inherits session MCP, permissions, and local files. Requires Claude Code ≥ v2.1.72 for scheduled tasks generally.

Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?

  • Does registering a local Codex/Plugin copy it into a home-directory cache?

    • AI Answer

      • Yes, installation copies it. Registering a marketplace tells Codex where to find a catalog; installing a plugin creates the copy used at runtime. This distinction applies even when the catalog points to a local checkout.
      • Answer/Official from Package your plugin — How local marketplaces work, checked October 15, 2026: installed plugins live under ~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/; local plugins use local as the cache directory's version segment. The runtime reads that installed copy.

      • What happens after a source edit?

        • Edit the checkout named by the marketplace entry. Treat the cache as generated installation output.
        • The Codex cache-refresh implementation has both version-conditional refresh and forced reinstall paths. Version-conditional refresh skips installation when the active version matches the source version. A saved file alone therefore does not guarantee that every refresh path copies the change.
        • The authoring documentation recommends restarting the desktop app after source changes. If the old behavior remains, bump the package version and reinstall through the plugin browser, then start a new chat. Verify the changed skill or tool behavior in that chat.
        • codex plugin marketplace upgrade refreshes configured Git marketplace snapshots. It is distinct from installing a plugin payload. The installed CLI, codex-cli 0.162.1, exposes installation as codex plugin add <plugin>@<marketplace>.

      • Can a repo still enable its own plugin?

        • Yes. A repo marketplace plus a trusted project configuration can enable a local-marketplace plugin; configured plugins can be installed or refreshed during marketplace refresh. This still uses the cache. See Codex/Plugin/Q/Is a Codex skills-only plugin the same idea as a Claude Code skills-directory plugin?.

      • How does this compare with Claude?

        • A Claude marketplace installation also uses a cache. A Claude/Code/Plugin/Skills-Directory Plugin loads from its source directory; its @skills-dir origin identifies that discovery mechanism. Claude plugin loading reference.
        • For editing a Codex skill in place, use a plain Codex/Skill under .agents/skills/<skill-name>/SKILL.md. Codex supports symlinked skill directories and detects skill changes. Build skills — local discovery.
