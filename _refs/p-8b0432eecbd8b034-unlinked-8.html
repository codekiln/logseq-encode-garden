pnpm/DevContainer/Concept/Issues with DevContainers

  • Best Practices Summary (Updated with Real Examples)

    • Store Management

      • Container-Only Store (Recommended for most cases): Set pnpm config set store-dir /path/in/container to avoid cross-filesystem issues
      • Shared Store with Volume Mounting: Mount host pnpm store for efficiency in CI/CD environments
      • Avoid Cross-Filesystem Store Locations: Never use host-mounted directories as pnpm store without proper volume mounting

    • Installation Methods (Ranked by Quality)

      • Corepack Integration (Best Practice): Use corepack enable + corepack prepare pnpm@latest --activate for version consistency
      • DevContainer Features: Leverage ghcr.io/devcontainers/features/node:1 with packageManager: "pnpm" option
      • Manual Installation: Only when corepack is not available, use npm i -g pnpm@VERSION

    • Environment Configuration

      • PNPM_HOME: Always set ENV PNPM_HOME=/usr/local/share/pnpm (or similar path)
      • PATH Configuration: Add ENV PATH=$PNPM_HOME:$PATH to make pnpm available globally
      • Package Manager Field: Always specify "packageManager": "pnpm@VERSION" in package.json

    • Build Optimization (Production-Ready Patterns)

      • Multi-Stage Builds: Separate dependency installation from application build
      • BuildKit Cache Mounts: Use --mount=type=cache,id=pnpm,target=/pnpm/store for Docker layer caching
      • Frozen Lockfile: Always use --frozen-lockfile for consistent, reproducible builds

    • Development Workflow

      • PostCreateCommand: Use corepack enable && corepack prepare pnpm@latest --activate && pnpm install
      • UpdateContentCommand: For monorepos, use corepack prepare & pnpm install to handle workspace updates
      • OS Compatibility: Handle different OS versions with separate store directories when needed

    • Monorepo Considerations

      • Workspace Protocol: Use workspace:^ for local package references
      • Store Optimization: Configure store directory early in container lifecycle
      • Parallel Installation: Leverage pnpm's parallel installation capabilities with --parallel flag

  • Common Anti-Patterns to Avoid (Updated)

    • Mismatched Package Managers: Having pnpm install in devcontainer.json but using npm/yarn in package.json
    • Missing Store Configuration: Using pnpm without configuring store directory, leading to cross-filesystem hard link issues
    • Incomplete Corepack Setup: Enabling corepack without properly configuring PNPM_HOME environment variable
    • Cross-Filesystem Store Locations: Binding project directory from host without considering filesystem differences
    • Missing Package Manager Field: Not specifying "packageManager": "pnpm@VERSION" in package.json
    • Ignoring Permission Issues: Not handling file system permissions in mounted volumes
    • OS Version Inconsistencies: Not handling different OS versions in compiled dependencies
    • Missing Frozen Lockfile: Not using --frozen-lockfile for consistent, reproducible builds

Readwise/AI/Report/26/01/AI control of Readwise - Options Jan 2026
  • Official MCP Server: Readwise provides an official MCP server (@readwise/readwise-mcp on NPM) which is maintained by the Readwise team. This server allows AI clients (like Claude or Cursor) to search and retrieve highlights from your Readwise account [4]. It focuses on the main Readwise highlights (e.g. Kindle/book highlights) rather than full Reader documents, and is regularly updated (v0.0.7 as of late 2025).
  • Readwise Reader MCP (edricgsh) – A popular open-source TypeScript MCP server that exposes the entire Readwise Reader API to AI agents [5]. It gives your AI full control over your Reader library, supporting full CRUD on documents (create/save new articles, list/filter documents, update metadata like tags/folder, and delete documents) as well as tag listing and powerful regex search across content [5]. This server is built with the official Claude SDK and is actively maintained; it had ~3.6k downloads by Oct 2025 [5], indicating healthy usage.
  • Readwise Reader API JS/TS SDK – An unofficial JavaScript/TypeScript client (by Scarvy) for the Readwise Reader API [12]. This package simplifies using Reader endpoints in Node.js or browser contexts. Using this, a JS-based AI agent (or tools like a VS Code extension) can add documents, list items, etc., with TypeScript types and convenience methods. It's open-source (≈11⭐) and often updated alongside the CLI tool by the same author. [12]
  • Maintenance: These SDKs are third-party projects. Many are open-source on GitHub with small communities. Before using one, check its last update – e.g., PyReadwise and the TS client have recent commits in 2025, whereas some others might be older. In absence of official SDKs from Readwise, these libraries provide a starting point for integration.
  • Readwise Highlights API (v2) – The primary REST API to Readwise (the original service) supports creating, fetching, and updating highlights [16]. This includes endpoints to get all highlights or filter by book/article, create new highlights (e.g. via POST /api/v2/highlights/), update highlight text or tags, etc. An AI agent could call these endpoints directly using HTTPS. For example, to add a highlight, you would use the Highlight CREATE endpoint with an API token [16]. The API returns structured JSON (books and highlights), and has a generous rate limit (~240 req/min for most calls) [16]. This direct approach gives full control, but requires handling HTTP requests and auth tokens in the agent's code.
  • Readwise Reader API (v3) – A separate set of endpoints dedicated to the Reader service (read-it-later documents). The Reader API allows you to save new documents to Reader and list/search your documents programmatically [20]. For instance, an AI agent can POST to https://readwise.io/api/v3/save/ with a URL (and optional HTML content or tags) to add an article to your Reader library [20]. It can also GET https://readwise.io/api/v3/list/ with query parameters to retrieve documents – filtering by location (new, later, archive, feed), category (article, pdf, email, etc.), tags, or updatedAfter a given date [20]. This enables assembling lists of recently read or highlighted items by specifying a date filter (for example, all items updated in the last week) [20]. Tags can be listed via a GET /api/v3/tags/ endpoint as well [20]. Using the API directly is fully supported (the documentation is available on Readwise's site), though it requires more manual effort.

  • python
    			  import json, os, aiofiles.tempfile, contextlib
			  from stream_chat.async_chat import StreamChatAsync
			  from stream_chat.base.exceptions import StreamAPIException
			  
			  async def upload_json_as_attachment(
			      chat: StreamChatAsync,
			      channel_type: str,
			      channel_id: str,
			      message_id: str,
			      attachment_name: str,
			      payload: dict | str,
			      user_id: str,
			  ):
			      """
			      • Serializes *payload* to JSON (if dict)  
			      • Writes it to a temp file  
			      • Uploads via channel.send_file  
			      • Adds the file as an attachment to *message_id*  
			      • Returns the Stream API response
			      """
			      channel = chat.channel(channel_type, channel_id)
			  
			      # 1 write payload
			      async with aiofiles.tempfile.NamedTemporaryFile(
			          "w", suffix=".json", delete=False
			      ) as tmp:
			          text = json.dumps(payload) if isinstance(payload, dict) else str(payload)
			          await tmp.write(text)
			          await tmp.flush()
			          tmp_path = tmp.name
			  
			      # 2 upload temp file
			      try:
			          resp = await channel.send_file(
			              tmp_path,
			              name=f"{attachment_name}.json",
			              user={"id": user_id},
			              content_type="application/json",
			          )
			      except StreamAPIException as exc:
			          # Enable uploads on the fly if needed
			          if "upload disabled" not in str(exc):
			              raise
			          await channel.update_partial({"config_overrides": {"uploads": True}})
			          resp = await channel.send_file(
			              tmp_path,
			              name=f"{attachment_name}.json",
			              user={"id": user_id},
			              content_type="application/json",
			          )
			  
			      # 3 attach to message
			      url = resp["file"]
			      attachment = {
			          "type": "file",
			          "url": url,
			          "name": f"{attachment_name}.json",
			          "asset_url": url,
			          "mime_type": "application/json",
			      }
			      await chat.partial_update_message(
			          message_id,
			          {"set": {"attachments": [attachment]}},
			      )
			  
			      # 4 clean up temp file
			      with contextlib.suppress(FileNotFoundError):
			          os.remove(tmp_path)
			  
			      return url
  • StepDetail

Toggl/AI/Report/26/01/AI control of Toggl - Options Jan 2026
  • Below is a comparison of CLI tools, MCP (Model Context Protocol) interfaces, SDKs/libraries, and the official Toggl Track API for performing full Create/Read/Update/Delete (CRUD) on time entries. Each option is noted as official or third-party, whether it's open source, its capabilities (time entry CRUD is mandatory; project/client management and reporting are optional), the required environment/language, and any notable caveats. Longer per-option narrative from the original deep-research run lives on each embedded page under an AI/Response heading that cites this report.
  • Table: eight Toggl Track integration options with time entry CRUD (details live on the embedded pages). "Projects/Clients CRUD" on those pages indicates create/update support where applicable. "Reports" denotes summarized-report capability. Third-party options here are open-source; the official row is the documented REST API.
  • Aside from the above, there are a few more niche CLI utilities (open-source) for Toggl Track, though with narrower scope or older API versions. For example, toggl-hammer is a Python CLI to quickly add "hour blocks" of time for past dates (useful for back-filling time, but it doesn't let you specify custom start/stop times or descriptions)[18]. It's designed for "lazy" input of fixed-length entries and is not a general-purpose CLI for full CRUD. There are also older CLI projects like joequery/Toggl-CLI and community scripts, but many were built against the now-deprecated API v8. The Toggl Track engineering team maintains a list of third-party tools, and many CLI projects have been updated or forked to work with API v9[18] [19]. When choosing a CLI, ensure it supports API v9, as the older v8 endpoints are no longer available. The three CLI options above (Python, Node, Rust) are among the best-maintained for Toggl Track with API v9 support and cover a range of language ecosystems. All are open source, allowing you to inspect or modify the code if needed.
  • Python: Officially, Toggl Track doesn't maintain an official Python SDK, but the community has the above-mentioned Toggl CLI (Python) Toggl/CLI/Python/AuHau/toggl-cli which doubles as a library. It provides Python classes for TimeEntry, Project, Client, etc., that you can create, fetch, update, and delete in your own scripts[1]. For example, you can do api.TimeEntry(description="New entry", start=..., stop=...).save() to create an entry, or call api.TimeEntry.objects.all() to list entries[1]. Similarly, api.Project.objects.get(id) and .save() let you update project details[1]. This essentially is an SDK built on the Toggl API. Another third-party library, toggl-track (PyPI) by Maurizio Branca, offers a Pythonic interface and CLI; however, it's relatively new (as of 2025) with fewer users[21]. For most Python integrations, using the toggl-cli's API wrapper or simply calling the Toggl REST endpoints via requests (with the official docs) are common approaches.
