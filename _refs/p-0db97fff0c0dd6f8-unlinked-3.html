ChatGPT/Plugin/How To/Develop and Share a Team Plugin for ChatGPT and Claude

  • How To Develop and Share a Team Plugin for ChatGPT and Claude

    • Overview

      • Develop and test the plugin against editable files on the author's computer before publishing or sharing a release. This local edit-and-test cycle is an expected authoring step in both Claude and ChatGPT/Codex.
      • Follow this order: create the source package, load the working files, change a file and verify the changed behavior, test the installed package, then publish or share it. Keep the reusable skills in one repository when supporting both hosts.
      • Claude Code can load the complete plugin directory directly. Local Codex can load skill directories directly; its marketplace workflow tests the complete plugin through a cached installation. A private local cache is an installation mechanism and does not require publishing to an account, workspace, or public directory.
      • Product behavior and documentation checked October 16, 2026.

    • Prerequisites

      • A local checkout accessible to the test host. Use Claude Code for Claude directory loading and a supported local Codex session for OpenAI skill discovery. Account plugins in a web chat do not provide access to the checkout's working files.
      • A representative input, an example of the desired output, and the reference material the workflow needs.
      • Plugin Creator and permission to use plugins in the intended ChatGPT workspace. Sharing and publishing to the workspace directory have separate permissions. ChatGPT plugin authoring.

    • Steps

      • 1. Describe the workflow and request local source files

        • In Chat or Work, select Plugin Creator from the @ menu. Describe the task, inputs, output, and how missing information should be handled. Attach a representative example. Ask for a local source package to edit and test before saving or publishing an account plugin.
        • Example brief:

          • Build a local source package called Team Design Review in plugins/team-review so I can edit and test its files before publishing. Given a design document and our review checklist, draft a review containing the problem, proposed behavior, unresolved decisions, and questions for the author. Cite supporting sections. Mark missing information explicitly. Use the attached example to demonstrate the output. Stop after local testing; account upload and sharing come later.

        • Review the generated instructions and supporting files. If the workflow needs an existing app, name the app and the information or actions it should provide.

      • 2. Define repeatable local checks

        • Keep a familiar input and an input with missing information beside the source package, with the expected output for each. Reuse these checks after every change to a skill, reference, script, or tool.
        • During the direct-source tests below, edit a working file, reload the relevant component, and rerun a check that exercises that edit. Verify the source path as well as the result. Complete this cycle in each target host before testing a release installation.

      • 3. Keep a source package when developing in a repo

        • Save the generated source files at plugins/team-review/ in the repository and edit that directory throughout development. If the creation chat has no filesystem access, download its source package into the checkout before continuing. An uploaded account plugin does not stay linked to the checkout.
        • For a portable OpenAI package, use this layout:
          • text
            				  plugins/team-review/
				    plugin.json
				    skills/team-design-review/SKILL.md
				    skills/team-design-review/references/checklist.md
        • A minimal root plugin.json:
          • json
            				  {
				    "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
				    "name": "team-review",
				    "version": "0.1.0",
				    "description": "Review team design documents against a shared checklist.",
				    "author": { "name": "Example team" }
				  }
        • Each SKILL.md starts with YAML name and description, followed by the workflow. Keep references and scripts inside the package. Portable packages discover skills/ at its fixed location. OpenAI presentation settings belong under extensions.com.openai; older local clients can use a synchronized .codex-plugin/plugin.json compatibility manifest. Package format.

      • 4. Test the editable plugin directory in Claude Code

        • Add .claude-plugin/plugin.json to the same package:
          • json
            				  {
				    "name": "team-review",
				    "version": "0.1.0",
				    "description": "Review team design documents against a shared checklist."
				  }
        • Keep the skills/ tree shared and synchronize the identity and version in both manifests. Use provider-neutral instructions for the shared workflow. Convert reusable Claude commands and agent procedures into skills; keep host-specific features separate. OpenAI's Claude plugin conversion guide.
        • From the repo root, load the source directory for a Claude Code development session:
          • bash
            				  claude --plugin-dir ./plugins/team-review
        • This loads the directory as team-review@inline. Run /reload-plugins after edits, then invoke /team-review:team-design-review. Pass the directory itself to use the working files; a ZIP is a packaged build. Claude development without a marketplace.
        • If automatic discovery is preferable, keep the source package itself at .claude/skills/team-review/, including .claude-plugin/plugin.json and its skills/ directory. Launch Claude Code from the repo root and accept project trust. It loads as team-review@skills-dir; /reload-plugins reloads changes. Update the Codex symlink and marketplace paths below to this source location. Keep a single editable package, rather than copying it between both locations. See Claude/Code/Plugin/Skills-Directory Plugin and the Claude loading reference.
        • Test tools independently in both products. MCP provides a shared protocol, while connection settings, authentication, hooks, and app interfaces have host-specific behavior. A shared skill does not make those features interchangeable.

      • 5. Test the editable skill directory in local Codex

        • Expose each shared skill directory under the repo's .agents/skills/. Codex follows symlinked skill folders, so edits to the package's SKILL.md, references, and scripts remain edits to the files used by the discovered skill. This loads a plain skill; it does not activate the package's MCP configuration or hooks. Codex local skill discovery.
        • From the repo root, create this link if the destination does not already exist:
          • bash
            				  mkdir -p .agents/skills
				  ln -s ../../plugins/team-review/skills/team-design-review .agents/skills/team-design-review
				  realpath .agents/skills/team-design-review/SKILL.md
        • The resolved path should end in plugins/team-review/skills/team-design-review/SKILL.md inside the current checkout. Relative symlink targets are resolved from .agents/skills/. If the package lives under .claude/skills/team-review/, use ../../.claude/skills/team-review/skills/team-design-review as the target instead. Inspect any existing destination before changing it.
        • Disable the installed team-review@team-plugins plugin while testing the direct skill. In a trusted repo's .codex/config.toml, use:
          • toml
            				  [plugins."team-review@team-plugins"]
				  enabled = false
        • Also deselect account or workspace copies for the test chat where permitted. Repo configuration controls local-marketplace entries; it does not override workspace-managed installation state. Start a fresh local Codex chat in the checkout and explicitly select team-design-review from the skill picker. Restart Codex if discovery has not caught up.
        • Verify both the selected source path and behavior: temporarily add an instruction to the source skill to include LOCAL-DEVELOPMENT-CHECK in its review, run a representative review, and inspect which SKILL.md was loaded. The resolved file should be in the checkout, outside ~/.codex/plugins/cache/. Remove the test instruction after verification. Reading a file on demand alone does not demonstrate that the host selected it as the skill.
        • In Claude, inspect the loaded plugin's origin in /plugin or claude --plugin-dir ./plugins/team-review plugin list, reload, and run the same temporary behavior check. Expect @inline for the directory flag or @skills-dir for automatic discovery. Claude component verification.
        • For MCP tools and hooks, verify their process and script paths separately. Rebuild compiled helpers and restart the relevant process after edits. A live SKILL.md does not establish that a running server has reloaded its code. Direct Codex skill discovery and these filesystem checks apply to supported local sessions; a web or cloud account installation does not read the checkout automatically.

      • 6. Test the packaged plugin through a local marketplace

        • After the direct-source checks pass, test installation and the full bundle through a private local marketplace. This catches packaging, component discovery, and startup problems before publishing. In Codex, this full-plugin test uses a cache even though the source files and catalog are local; direct skill loading above remains the path for editing skills in place.
        • A local-marketplace plugin is a plugin listed in a catalog read by a local client. The catalog can be one JSON file containing one entry. It makes the package discoverable; installation supplies the runtime copy. Add .agents/plugins/marketplace.json at the repo root:
          • json
            				  {
				    "name": "team-plugins",
				    "interface": { "displayName": "Team plugins" },
				    "plugins": [
				      {
				        "name": "team-review",
				        "source": {
				          "source": "local",
				          "path": "./plugins/team-review"
				        },
				        "policy": {
				          "installation": "AVAILABLE",
				          "authentication": "ON_INSTALL"
				        },
				        "category": "Productivity"
				      }
				    ]
				  }
        • The source path is relative to the repository root. To enable the plugin for a trusted project, add this to the repo's .codex/config.toml:
          • toml
            				  [plugins."team-review@team-plugins"]
				  enabled = true
        • Use enabled = true for the packaged-plugin test after disabling direct skill discovery for that test. Supported local Codex clients can install or refresh configured plugins during marketplace refresh. Restart the desktop app and verify the plugin in a new chat. Repo plugin settings.
        • Local marketplace installation loads ~/.codex/plugins/cache/team-plugins/team-review/local/. A local source.path and enabled = true do not turn that copy into a live link. Edit the source package, refresh or reinstall it, and test the installed result separately. See Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache? and How local marketplaces work.
        • For Claude teammates, add a catalog at the repository root's .claude-plugin/marketplace.json pointing at the same package:
          • json
            				  {
				    "name": "team-plugins",
				    "owner": { "name": "Example team" },
				    "plugins": [
				      { "name": "team-review", "source": "./plugins/team-review" }
				    ]
				  }
        • Teammates add the repository through /plugin marketplace add <owner>/<repo> in Claude Code, then run /plugin install team-review@team-plugins. Replace <owner>/<repo> with the team's actual GitHub repository. Claude marketplace setup.

      • 7. Publish or share the tested release

        • Once local source tests and installed-package tests pass, save or update the account plugin from the tested source. Start a new chat, select it with @, and rerun the representative inputs. Check both Chat and Work if teammates use both.
        • Open the plugin's sharing settings and choose the intended people or groups. Include a sample prompt and the maintainer's name. Recipients install the plugin unless an administrator has installed it for them. Each person also needs access to required apps. Testing and team sharing.
        • For GitHub-managed distribution, have a workspace administrator open Admin → Plugins → Add → Import marketplace, enter the repository URL, and select a branch or revision. Review the imported plugins and configure installation policy for the intended roles. Use Sync now to test an update; new marketplaces also sync daily. Workspace plugin management.
        • This workspace import supports Codex catalogs, Claude catalogs, and standalone Claude plugins. Imported packages declaring MCP servers are currently desktop-only, including packages whose server uses HTTPS. For web use, verify the supported app-connection route before sharing.

    • Troubleshooting

      • Source edit does not appear: edit the marketplace source, bump the package version, reinstall or refresh through the supported client flow, and start a new chat. The runtime uses a cached installation. See Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?.
      • Duplicate skill entries: disable the installed copy while testing the source skill. For a packaged release test, temporarily move only the discovery symlink outside .agents/skills/, leaving its source directory in place, then start a fresh chat. Restore the link to resume local development.
      • Teammate sees the listing but cannot use it: check installation, workspace role policy, and the required app connection separately.

ChatGPT/Project/How To/Refine the Project Prompt using ChatGPT

  • How To Refine a ChatGPT Project #Prompt Using o3

    • My Notes

      • 2025-05-16 Fri
        • I've had great luck using this template to iteratively improve the ChatGPT/Project/Instructions to align with my expectations. These models are excellent prompt engineers, but, perhaps ironically, they need to be prompted a certain way in order to access their highest capabilities in this regard. For example, I used it to dramatically increase the alignment of ChatGPT/Project/Instruction/Diataxis Logseq quickly, using ChatGPT/Dictation

    • Goal

      • Produce a concise, well-structured prompt that meets project-specific length or formatting targets (e.g., 7 000 – 7 500 chars) by iterating with a reasoning model such as o3, using ChatGPT/Code/Interpreter to measure length.

    • Preconditions

      • Access to ChatGPT with the o3 reasoning model.
      • Code Interpreter (python_user_visible) enabled.
      • A draft prompt that needs trimming or re-organization.
      • Knowledge of your project’s formatting rules (length limits, required sections, special markup, etc.).

    • Procedure

      • 1. Map Your Existing Prompt

        • Skim the draft and label logical parts (intro, bad example, critique, current rules, request).
        • Note all hard requirements (length cap, mandatory headings, prohibited markup, etc.).

      • 2. Build a Generic Prompt Template Skeleton

        • Ask ChatGPT to extract section headings and convert them into a reusable template.
        • Use the structure below; fill [placeholders] with topic-specific text:
          markdown
          			  # Prompt Template: Refine Project Rules
			  
			  ## 1 Context  
			  > Currently in your project instructions: **[summary of situation]**
			  
			  ## 2 Anti-Pattern Example  
			  <EXAMPLE_OF_HOW_NOT_TO_DO_IT>  
			  **[paste flawed sample]**  
			  </EXAMPLE_OF_HOW_NOT_TO_DO_IT>
			  
			  ## 3 Problem Analysis  
			  The above example has problems:  
			  1. **[issue A]**  
			  2. **[issue B]**  
			  3. **[issue C]**
			  
			  ## 4 Current Project Rules  
			  <PROJECT_RULES>  
			  **[paste current rules]**  
			  </PROJECT_RULES>
			  
			  ## 5 Refinement Request  
			  Please rewrite the rules so that **[desired outcome]**.  
			  **Constraints:**  
			  - Keep length within 7000-7500 characters (it MUST be <8000 characters).  
			  - Follow all formatting guidelines in Section 4.

      • 3. Instruct the o3 Model to Rewrite

        • Send the filled-in template to ChatGPT (o3). You may need to select o3 from the model drop-down at the top.
        • Explicitly request: “Use Code Interpreter to count characters and iterate until the result fits the required range.”

      • 4. Measure with Code Interpreter

        • When ChatGPT returns a draft, have it run:
          python
          			  rules = """...rewritten text..."""
			  print(len(rules))
        • If the count is outside your target range, ask for automatic trimming or expansion and re-run the count.

      • 5. Validate Output

        • Confirm the rewrite matches all project formatting rules (headings, markup, fences, etc.).
        • Ensure no prohibited elements remain (e.g., unsupported tags or placeholders).

      • 6. Finalize

        • Save the approved prompt to your documentation repo or knowledge base.
        • Archive the template for future refinements across other projects.

    • Troubleshooting

      • Output exceeds length requirement → Ask o3 to “compress explanatory prose, keep tables.”
      • Key formatting rule ignored → Remind model: “Ensure compliance with project’s formatting checklist.”
      • Prohibited markup persists → Reinforce rule: “Strip all unsupported tags or symbols.”
      • Code Interpreter unavailable → Manually copy text into a local script (e.g., wc -m) to count characters.

    • References

      • OpenAI Platform documentation.
      • Prompt Engineering best practices (OpenAI Cookbook).

ChatGPT/Q/How can I measure usage in ChatGPT Work and in ChatGPT Codex? I'd like to know how much usage each thread has consumed
  • Answer/Official from Reviewing Work and Codex usage and using Personal Analytics in ChatGPT Desktop:
    • Per-thread usage: In ChatGPT Desktop, open a Work or Codex chat and select the usage indicator in the chat header. Where the feature is available, it shows the chat's lifetime credits, an estimated cost, and the model, reasoning effort, and speed associated with that usage. The total generally refreshes about once per minute.
    • Find the biggest threads: Open Settings → Usage & billing. The Top consuming chats list ranks locally available Work and Codex chats active in the last 30 days by lifetime credit usage. The 30-day period controls which chats appear; the displayed total covers the available lifetime history of each listed chat.
    • Overall allowance: Settings shows the monthly Work-and-Codex allowance, credits used, remaining allowance, and reset information where the workspace exposes those details. Work and Codex generally draw from the same allowance rather than separate pools. See Using Codex with your ChatGPT plan.
    • Tokens and broader analysis: Usage history can separate uncached input, cached input, and output tokens. If the workspace has enabled Personal Analytics, mention @personal-analytics in Work or Codex and ask for a usage summary or a breakdown by model, reasoning effort, speed, tokens, credits, or date range.
    • Important limit: Per-chat usage is an estimate for the main conversation, not a complete billing ledger. Sub-agents, separate tasks, some tools such as image generation, background activity, and recent or unavailable records may be omitted. For complete spend information, use workspace billing and usage records.
    • Eligibility: The detailed Usage & billing and per-chat views are documented for eligible Enterprise/Edu workspaces with credit-based billing, and availability depends on the account and workspace settings. If the usage indicator or per-chat list is absent, the account may only expose aggregate limits or reset information. In Codex CLI, /status reports the active allowance and reset information, but it is not a per-thread lifetime-usage report.

ChatGPT/Sites

  • ChatGPT Sites

    • A feature of ChatGPT that builds, hosts, and shares a website or small web app from a conversation. The user describes the site in chat and ChatGPT generates it and publishes it at a URL.
    • Launched 2026-07-09 on paid plans except Free and Go. It reached the UK, EEA, and Switzerland on 2026-07-20, per Stacktree.
    • Every deployment URL is a production URL; there is no staging environment, per PlayCode.

    • Data and connections

      • The official Data and connections guide recommends Cloudflare/D1 for durable, structured site data such as saved records, user progress, or scores.
      • The guide recommends Cloudflare/R2 for uploaded files such as images, documents, audio, and video. When uploaded files need searchable metadata, store metadata in D1 and file contents in R2.
      • Avoid persistent storage for temporary presentation choices, such as a selected theme or a dismissed banner; use it for product data a hosted site should remember.
      • Public sites can offer optional Sign in with ChatGPT. Authorization decisions belong in server-side code; the guide documents authenticated email and optional full-name request headers.
      • Workspace-private sites can use plugins to load connected-app data under each visitor's own connection and permissions. Sharing a site does not share the author's connected accounts.
    • Viewing is public or limited to signed-in invited users. There is no passcode option.

ChatGPT/Sites/Q/To what extent is it possible, either using Claude artifacts or using ChatGPT sites, to have a database that backs the site?

  • To what extent is it possible, either using Claude artifacts or using ChatGPT sites, to have a database that backs the site?

    • AI Answer

      • Yes. A visitor can submit a comment, the app can save it in shared persistent storage, and a later visitor can load the saved comment. Both products document the storage needed for this behavior; the comment form and read/write logic still need to be built.
      • Claude Artifacts
        • Answer/Official from Anthropic: Store data in an artifact.
        • Shared storage exposes the same saved data to everyone using the artifact. Personal storage keeps each person's data private. A shared comment feed uses shared storage.
        • Storage is available on Pro, Max, Team, and Enterprise on web and desktop, with a text-only limit of 20 MB per artifact. JSON can represent comment records within text storage.
        • New artifacts can save before publication. Legacy artifacts require publication, and unpublishing a legacy artifact deletes its stored data.
        • Editors can also upload images, PDFs, and CSVs to an artifact; no storage quota for uploads is published. See Claude/Artifact/Q/How much storage comes with Claude artifacts?.
        • Anthropic documents persistent storage, but does not establish SQL queries, relational constraints, transactions, or concurrent-write guarantees in this help article. Treat those capabilities as unverified.
      • ChatGPT Sites
        • Answer/Official from OpenAI: Data and connections.
        • Sites supports D1, a relational database for durable structured data, and R2 for uploaded files. A comments table can hold the page, author, text, and submission time.
        • Public sites can offer optional Sign in with ChatGPT while allowing signed-out visitors to browse. Server-side code controls who can post, edit, or delete comments.
        • The Sites overview lists a 10 GB D1 limit per site. Sites is in public beta on Plus, Pro, Business, Enterprise, and Edu, with plan-specific usage limits.
      • Applying this to comments — implementation guidance inferred from the documented storage capabilities.
        • The submit action saves a comment to shared storage. Opening or refreshing the page reads the saved comments. Instant updates in an already-open browser need an additional refresh mechanism.
        • Store each comment independently so simultaneous submissions do not replace an entire shared comment list. Test simultaneous submissions, persistence after reload, and visibility from another account or browser.
        • Decide whether posting requires sign-in, who can delete comments, and how moderation works. Shared visibility alone does not define those permissions.
        • Sites is the stronger fit for a public comment site with accounts and structured records. Claude shared storage can support a small collaborative comment feed within the artifact experience.
      • Example Sites prompt: Build a public site with a comment section on each article. Store comments in D1 so visitors share the same comments across browsers and visits. Let anyone read; require Sign in with ChatGPT to post. Add author deletion, administrator moderation, and server-side permission checks.
ChatGPT/Space/Q/Can we add information to ChatGPT Spaces from local folders? If so, how?
  • Short answer: Not as a folder. Space takes uploaded files and files from connected apps; neither OpenAI article on Space mentions uploading, syncing, or linking a folder on your computer. You can get a local folder's contents into a Space by uploading its files or by having ChatGPT write them onto a page.
  • Answer/Official from Getting started with Space in ChatGPT and ChatGPT Space
    • Space holds pages, uploaded files, and folders. Those folders are Space's own organizing folders, not folders on disk.
    • Files reach a page in two ways. An uploaded file follows the page's permissions. A file in a connected service, such as Google Drive, keeps that service's permissions, and a link to it does not let page readers open it.
    • The documented way to fill a page from material you have is to open a conversation, attach the files, and ask ChatGPT to create or update a page from them.
  • Upload the files. Select the files inside the folder and attach them to a page or to a chat that creates the page. A third-party page, fast.io on upload limits, reports no folder upload in ChatGPT and a cap of 80 files every 3 hours; neither claim is confirmed by OpenAI.
  • Sync the folder to a connected service. Put the folder in Google Drive or another service ChatGPT connects to, then link or cite those files from a page. Edits on disk reach Space only through the sync, and readers need access in the source service.
  • Use a desktop local project as the bridge. A local project in the ChatGPT/App/Desktop gives its chats read and write access to folders on your computer, per Projects and chats. Ask a chat in that project to read the folder and write a page into a named space. Neither article says a local-project chat can create Space pages, so this route is untested.

Claude/Cowork/Q/Can each hackathon team share one API key through Claude Enterprise connectors, and how does ChatGPT secrets management differ?

  • Can each hackathon team share one API key through Claude Enterprise connectors, and how does ChatGPT secrets management differ?

    • AI Answer

      • Short answer: Neither product has a general secrets vault that a team member can add a key to. Claude's closest feature is a custom connector with a stored request header, which an Owner sets up once for the organization, so team members never handle the key. ChatGPT's closest features are GPT Action API-key auth and Codex cloud environment secrets.
      • Claude: how a stored key works
        • Answer/Official from Anthropic: Add a connector that isn't in the directory.
          • An Owner (or, on Enterprise, a member with a custom role that manages the organization's libraries) adds a custom MCP connector under Organization settings > Connectors. Members then see it under Customize > Connectors and click Connect.
          • If the server uses an API key, choose No sign-in and put the key under Request headers. Claude stores each header value securely, does not show it again after saving, and sends it on every request.
          • Request headers suit a credential the whole organization shares, such as a service account. For per-person access, use OAuth.
          • Up to four headers. Header names are reviewed by Anthropic before Claude sends them, with authorization, x-api-key, and x-auth-token offered by default.
          • Authentication settings cannot be edited after the connector is created; remove it and add it again.
          • Request headers are in beta for a limited set of organizations. If the section is missing from the dialog, the organization does not have it yet.
        • Gaps for the hackathon plan
          • A team member cannot add their own key to their own account as a stored secret. The Owner-added connector is the stored-secret path, and the key sits with the Owner, not the team member.
          • One connector holds one key. Ten teams with ten keys need ten connectors, and I found no documented way to give each connector to one group of members only. Claude/Cowork and chat both see whatever connectors the member has enabled, so a team could use another team's connector unless an admin scopes it.

The article does not say which authentication types it covers or where credentials are stored, so I could not confirm it works with a plain API key.

        • Answer/Official from Anthropic: Getting started with local MCP servers on Claude Desktop. Desktop extensions (MCPB) mark fields as "sensitive": true in the manifest, and Claude/Desktop encrypts those values with the operating system's secure store (Keychain on macOS, Credential Manager on Windows).
        • This is per machine and per user: each team member would install the extension and paste the key once. It does not travel to other devices, other people, or cloud sessions.

        • Anthropic has no account-level secrets vault for chat, Cowork, and Claude Code. A feature request for one, account-level secrets vault, was closed as not planned.

        • GPT Actions. OpenAI: GPT Action authentication. The GPT builder can set API key auth (Basic, Bearer, or custom header) or OAuth, and the key is encrypted when stored. Codex/Q/What does "New remote project" do in the ChatGPT desktop app, and does it need a host I already have running?
  • Answer/Official from Remote connections
    • Short answer: Yes. "New remote project" connects the ChatGPT desktop app to a project folder on an existing SSH-reachable machine — a devbox, an EC2 instance, a home server, anything you already have SSH access to. Codex does not provision or spin up a host for you; it only auto-discovers hosts already defined in your local ~/.ssh/config.
    • The remote host must already have the codex CLI installed and on PATH for the login shell the SSH connection uses, since the app starts a remote Codex app server over SSH using that shell.
    • Setup order: add a concrete Host alias to ~/.ssh/config (pattern-only entries are ignored), confirm ssh <alias> works from the machine running the desktop app, then in Settings > Connections add/enable that SSH host and pick a remote project folder.
    • This is distinct from the mobile Remote feature, which pairs a phone with an already-running desktop app host (Mac/Windows) via QR code; SSH remote projects are a separate way to point the desktop app itself at a folder on another machine's filesystem and shell.
    • Security note from the docs: keep the remote host under normal SSH hygiene (trusted keys, least-privilege accounts, no unauthenticated public listeners), and don't expose the remote Codex app-server transport directly on a shared or public network — use a VPN or mesh network instead if you need off-network access.

  • Because of that flow, changes to your project's Dockerfile or to the feature list/order can invalidate caches and cause longer rebuilds — this is a documented/observed pain point in the community. GitHub
