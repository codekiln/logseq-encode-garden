Term/Q/What is a vertical slice in tech?

Page reference

  • Tracer bullet — from The Pragmatic Programmer: fire one shot all the way through the system to see where it lands. Person/Steve Yegge uses exactly this framing for agent work — find the thinnest end-to-end workflow you can get running and hang the rest of the project on it.

  • As a leading word for coding agents

    • Coding agents default to horizontal work — all the schema, then all the endpoints, then all the front end — because they optimize for the stated goal rather than for early feedback.
    • Person/Matt Pocock treats "vertical slice" as a leading word: rather than instructing an agent "don't code layer by layer," name the pattern, because the phrase is well-established enough in developer writing to trigger the model's priors, and it then echoes the phrase back in its reasoning traces.
    • The weak fix is to say "don't code layer by layer." The strong fix is to name the thing: vertical slice, "a pretty well-known terminology in development, and so this will hopefully trigger the agent's priors."
    • The verification trick is to watch for the phrase reappearing in the agent's thinking — if it says "we'll do this as a thin vertical slice," the steer landed. Relevant to AI/Coding prompt and skill design generally.

tuicr/Agent/Skill

Page reference

  • The agent skill (skills/tuicr/SKILL.md in agavra/tuicr) is a packaged Claude/agent-tool skill that lets a coding agent talk to tuicr review — the non-interactive CLI side of tuicr — instead of the human-facing TUI.
  • Design line from the skill file itself: "the TUI is where the human reviews code; the CLI is how the agent discovers active sessions, reads user comments, and, only when appropriate, adds agent-authored comments."
  • Video coverage: 10:20 Agent skill in Person/Omer Hamerman/YouTube/26/07/The Holy Grail of Code Review TUIs — install via the packaged pi-tuicr skill rather than reinventing it; inline agent comments beat a generic AI summary.
  • User-led review of agent-generated changes — the agent only reads the human's comments (tuicr review comments), polling on demand; it must not add its own comments and must never write comments that impersonate the user.
  • Agent review of an AI-generated patch — the agent inspects the diff itself and adds findings with tuicr review add, tagged with an explicit --username so they're visually distinguishable from the human's, only after the user approves writing them in.
  • Pull, not push. There is no event stream from tuicr to the agent — comments are read by polling tuicr review comments on demand (roughly every 30s while actively waiting), not pushed to the agent as they're typed.
  • Comments before submit are just session-file rows. Both a human's and an agent's comments live as local draft entries in the same session JSON until a human runs :submit in the TUI; nothing reaches the forge (GitHub/GitLab/etc.) until then.
  • Adding a comment. tuicr review add --session <slug> --target-file ... --line ... --type issue --username "Codex" "..." writes a local-draft comment (line, range, file, or review-level) into the session file; it shows up in the human's TUI (colorcoded, in the file tree) the next time they look, and in later tuicr review comments output with lifecycle_state: local_draft and the agent's author.
  • Reading comments. tuicr review comments --session <slug> returns every comment (human- or agent-authored) as JSON with id, location, comment_type, author, lifecycle_state, and content — this is the primary loop for the user-led workflow.
  • No reply/thread primitive. Comments are flat rows tied to a location, not a thread; adding a second comment at the same spot does not attach it to the first. For remote forge threads (GitHub/GitLab/Gitea/Bitbucket/Azure DevOps/Gerrit), tuicr fetches and displays existing comments but treats them as read-only for everyone, human or agent — the Gerrit docs state this explicitly ("existing comments are read-only in tuicr, as on every other forge").
  • No fallback without a session. Per the skill's own instructions, an agent should not silently review "locally only" when no active tuicr session exists — it should tell the user it's waiting, or start a new pane itself when a supported multiplexer (cmux/tmux/Zellij/Herdr) is available.
  • Agent polls tuicr review comments every ~30s while the human reviews in the TUI, then summarizes the human's issue/suggestion comments once tuicr-summary: reports reviewed_count == file_count.
  • Agent runs tuicr review add --type suggestion --username "Codex" --target-file src/main.rs --line 42 "Consider handling the empty case." after being asked to critique its own patch — the human then sees and can edit/delete that comment in the TUI before deciding to :submit.
  • Not real-time. There's no push notification when a comment is added — the agent (or a human waiting on the agent) has to poll.
  • Not license to impersonate the user. In the user-led workflow the agent's job is strictly read-only — the skill explicitly forbids adding or faking comments as if they were the user's.

tuicr/Q/In tuicr, is the --username on an agent comment tied to a GitHub or forge account, how does tuicr distinguish AI from human comments, and can a whole conversation happen offline before :submit?

  • In tuicr, is the --username on an agent comment tied to a GitHub or forge account, how does tuicr distinguish AI from human comments, and can a whole conversation happen offline before :submit?

    • AI Answer

      • Answer/Official from docs/CONFIG.md, docs/REVIEW_CLI.md, docs/KEYBINDINGS.md, and skills/tuicr/SKILL.md
      • Short answer: --username/author is a purely local, tuicr-only display label — it is not a GitHub/GitLab/forge identity and is never sent to the forge on :submit. tuicr distinguishes comments locally by that author field (TUI coloring, tuicr review comments JSON), but the forge side sees every submitted comment posted under whichever single account gh/glab is authenticated as — there's no built-in per-author signature on the pushed comment text. Yes, an entire back-and-forth (human writes, agent reads and replies with new comments, human reads those, etc.) can accumulate fully offline as local-draft rows in the session file, then one :submit pushes everything to the forge at once.

      • Is --username a forge account?

        • No. The username config key / --username CLI flag is documented as "Display name stamped on local comments and used as the viewer identity for local comment coloring" (see tuicr/Config) — it lives only in tuicr's own session JSON as the author field, independent of whatever account gh or glab is authenticated as when :submit actually pushes to GitHub/GitLab/etc.
        • tuicr/Agent/Skill leans on this: it tells an agent to pass an explicit --username (e.g. "Codex") so its own comments are visually distinguishable from the human's — a convention, not an auth mechanism.

      • How does tuicr distinguish AI from human comments?

        • Locally, yes, two ways:
          • The TUI colors comments based on whether their author matches your configured username (the "viewer identity"), so a human reviewer can visually tell "mine" from "someone/something else's."
          • tuicr review comments returns each comment's author field in JSON — the skill instructs an agent to "check author to distinguish your comments from the user's."
        • On the actual forge PR, not automatically. Nothing in the export or :submit path stamps the per-comment author/username into the pushed comment body — the only built-in prefix is the comment-type tag ([ISSUE], [SUGGESTION], etc.) via comment_type_prefix, not an author signature. All comments submitted in one :submit post as the one authenticated forge account, so a reader on GitHub/GitLab can't tell "written by the agent" from "written by the human" unless the comment text itself says so.

      • Can a whole conversation happen offline, then get pushed on submit?

        • Yes. Comments — from the human in the TUI or the agent via tuicr review add/--input — all land as lifecycle_state: local_draft rows in the same persisted session JSON; there is no live push to the forge as they're written.
        • Multiple rounds are workable: the agent polls tuicr review comments to read what's there, adds its own comments, the human reads/edits/deletes in the TUI, and this can repeat any number of times — none of it touches GitHub/GitLab until a human runs :submit.
        • :submit opens a picker (Comment / Approve / Request changes / Draft) and pushes all pending local comments as a single review event in one shot; there's no per-comment incremental submit. tuicr does support doing this again later for a newer batch of commits (it can preselect just the commits newer than your last submitted review), so "offline round, then submit" can repeat across multiple sessions of the same PR.
        • Caveat: there's no reply/threading — a "conversation" here means a sequence of separate flat comments accumulating on the same location, not a nested thread; see tuicr/Agent/Skill and tuicr/Comment/Type for the flat-comment model.

vim/Q/What exactly are vim marks, and what are they good for?
  • Can an AI/Agents set marks and point attention there? Yes, if it can talk to a running nvim instance (msgpack-RPC / --listen socket, nvr, or an MCP that wraps those).
