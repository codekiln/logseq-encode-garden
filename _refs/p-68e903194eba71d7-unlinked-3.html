Plugin/Manager

  • Vim / Neovim

    • Traditional Vim

      • vim-plug
        • Minimal, fast; declarative Plug 'owner/repo' in vimrc; supports lazy loading and post-update hooks.
      • Vundle
        • Plugin list in vimrc; :PluginInstall; precursor to many modern managers.
      • Pathogen
        • Only adds plugin directories to runtimepath; no install/update; manual git clone into a bundle dir.
      • dein.vim
        • TOML/config-driven; lazy load by file type or command; cache and parallel install.

    • Neovim

      • packer.nvim
        • Lua-based; use 'owner/repo'; lazy loading via opt, ft, cmd, etc.
      • lazy.nvim
        • Lua; lazy-by-default; spec in lua/plugins/*.lua; lockfile and robust dependency handling.
      • vim-plug also works in Neovim.
  • Declarative vs imperative: vim-plug, packer, lazy, sheldon use config files; Pathogen is “add dirs yourself.”
  • Lazy loading: reduces startup time; common in vim (dein, packer, lazy) and zsh (zinit turbo, zplug).

tmux/Q/Is it possible to split a pane for copy-mode scrollback above and live shell below like vim?
  • Short answer: tmux does not offer a vim-style “one buffer, two views” for a single pane’s scrollback. Copy mode always occupies the whole pane you started it in, and it only shows that pane’s history. A split gives two independent PTYs with separate scrollback buffers, so a copy-mode browser in the top pane is not automatically the same stream as the shell in the bottom pane.
  • synchronize-panes — Sends the same keystrokes to multiple panes; it does not tie scrollback together like scrollbind, and it is a poor fit for “browse in copy mode while typing elsewhere.” See discussion in this Stack Overflow thread.
  • Bottom line: The vim analogy breaks because a terminal pane is not a text buffer — it is a PTY with one display state. For “read old output while editing,” splitting in tmux helps spatially (reference + work side by side); bridging content is via yank/paste, capture-pane, or logging, not a native dual-view scrollback.
  • Stack Overflow — tmux scroll two panes like vim scrollbind

tmux/Q/Is there a way to do rectangular selection when using oh-my-tmux and tmux with vim visual selection mode?

  • Is there a way to do rectangular selection when using oh-my-tmux and tmux with vim visual selection mode?

    • My Notes

      • I haven't done this successfully yet. I find it difficult to quickly determine what to edit at which layer - of configuration; there's tmux itself, then there's oh-my-tmux, then there are my configurations layered on top in the .tmux.conf.local. Could use some CLI/Coaching.

    • Answer

      • AI/Response
        • Yes. tmux copy mode with vi keys supports rectangular (block) selection. Behavior depends on your bindings.

        • Default / toggle-based (no config) AI/Need/Confirmation

          • Enter copy mode: Prefix+[
          • Press v to toggle rectangle mode on/off (in default vi copy mode, v is bound to rectangle-toggle)
          • Press Space to start the selection (required)
          • Move with h/j/k/l to define the block
          • Press Enter (or y if bound) to copy; paste with Prefix+]

        • Vim-like bindings (recommended)

          • If oh-my-tmux has already bound v to begin-selection, rectangle mode can be unavailable unless you add explicit bindings. In .tmux.conf.local (oh-my-tmux's user override - .tmux.conf.local), you can make it behave like vim:
          • v = character-wise selection, C-v = rectangular selection, y = yank. No need to press Space after C-v:
          • text
            				  bind -T copy-mode-vi v   send -X rectangle-off \; send -X begin-selection
				  bind -T copy-mode-vi C-v send -X rectangle-on \; send -X begin-selection
				  bind -T copy-mode-vi y   send -X copy-selection-and-cancel
          • Use rectangle-on / rectangle-off rather than rectangle-toggle so v and C-v don't flip state in confusing ways.

        • tmux version

          • Syntax is for tmux 2.4+ (key table copy-mode-vi, send -X). For older tmux, use the vi-copy table and bind-key -t vi-copy ... (see sources).

        • Sources

          • tmux copy mode - select text block (Super User)
          • tmux PR #2546 — rectangle-on/rectangle-off
tmux/Q/What does the light blue tinge for window logo mean in oh-my-tmux
  • In oh-my-tmux, <prefix> Tab runs last-window, which jumps back to the faint-blue-highlighted window. This is analogous to vim's Ctrl-^ (Ctrl-6) for switching to the alternate file.

  • Can you go backwards multiple levels like vim's jumplist?

    • No -- tmux does not have a built-in window history stack. The last-window command only tracks one previous window, so <prefix> Tab toggles between two windows rather than walking back through a stack like vim's Ctrl-O / Ctrl-I jumplist.
    • There is no official tmux plugin that provides a full jumplist either. Possible workarounds:
      • 1. Script your own using the after-select-window tmux hook to push window indices onto a stack stored in a tmux environment variable, then bind a key to pop from that stack
      • 2. Use <prefix> w (the interactive window/session tree picker) as a quick way to jump to any window visually
      • 3. Use choose-tree which provides a searchable, navigable tree of sessions and windows

tuicr/Q/Can I compose a PR comment in nvim to get vim keybindings and markdown rendering?
  • tuicr's comment box has a comment_vim config option (default false); when set (or toggled at runtime with :vim / :set vim!), the box switches to edtui modal editing — hjkl, w/b/e, dd/D/ciw/x, u/Ctrl-r, visual v+y/d/p, :w/:q-style save/cancel. That is a real Vim-modal emulation built into the comment box, not nvim itself — no plugins, no LSP, no Markdown rendering. Verified in agavra/tuicr: docs/CONFIG.md, docs/KEYBINDINGS.md ("Comment mode"), and src/app/comment_vim.rs.
  • Workaround today: enable comment_vim = true for Vim-modal editing inside tuicr, or draft the comment in real nvim and paste the finished Markdown into the comment box for full editor ergonomics plus live Markdown preview (e.g. via a plugin like glow or an in-editor Markdown renderer).

Username/luixos/YouTube/26/01/Neovim on NixOS - Nixvim vs NixCats vs NVF

  • nvf (Nix Vim Framework)

    • Philosophy:
      • Go fully Nix-first: everything about Neovim is defined declaratively in Nix.

    • How it works

      • Plugins, LSP, treesitter, themes, lazy loading, all declared in Nix
      • Lua is optional and used only when necessary
      • Configuration becomes a single Nix derivation

    • Pros

      • Extremely modular
      • Fully reproducible
      • Built-in lazy loading
      • Flexible plugin sources
      • Can run standalone (nix run) or integrate with NixOS/Home Manager

    • Cons

      • Requires stronger Nix knowledge
      • Harder if you're coming from a Lua-based config
      • Steeper learning curve

    • Best for

      • People who:
        • Want maximum reproducibility
        • Prefer Nix for everything
        • Are comfortable with advanced Nix usage.
