AWS/Secrets Manager/Q/What terms does AWS Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?
  • AWS's ready-made rotation Lambda templates. Direct citations and the full picture — including a third, Lambda-less "managed rotation" path that's gated by how a secret was created, not by its shape: AWS/Secrets Manager/Secret/Rotation. Core citation: CreateSecret API reference: "you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret" for those templates to work. AWS/Secrets Manager/Secret/SecretString (single-valued/plaintext) can still be rotated, but only with a fully custom Lambda — there's no ready-made template for it.
AWS/Secrets Manager/Secret/Rotation
  • Rotation replaces a secret's stored value with a new one; see Secret/Rotate for the concept independent of any specific secrets manager. There are three distinct rotation paths, not two, and all of them are opt-in — creating a secret never enables rotation by default. Rotate AWS Secrets Manager secrets — the User Guide's own top-level split: "There are two forms of rotation: Managed rotation ... Managed rotation doesn't use a Lambda function ... Rotation by Lambda function – For other types of secrets, Secrets Manager rotation uses a Lambda function to update the secret." (What that page calls "Lambda function" rotation splits again below into a ready-made-template path and a fully custom path, which is why this page counts three.)
  • Not just RDS/DocumentDB/Redshift — AWS ships ready-to-use templates for every RDS/Aurora engine (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2, single- or alternating-user), DocumentDB, Redshift, and Timestream for InfluxDB. AWS Secrets Manager rotation function templates — the full, current list, with a template per engine: "AWS Secrets Manager provides a set of rotation function templates ... ready-to-use Lambda functions."
  • Every template on that list requires the secret to be an AWS/Secrets Manager/Secret/KeyValue whose JSON matches the expected credential schema (username, password, host, ...) — never a plain AWS/Secrets Manager/Secret/SecretString. CreateSecret API reference, the "For database credentials" paragraph: "For database credentials you want to rotate, for Secrets Manager to be able to rotate the secret, you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret."
  • AWS also ships a generic rotation template as an unopinionated starting point, and nothing stops writing one from scratch for a secret belonging to no AWS product whatsoever (a third-party API key, say). AWS Secrets Manager rotation function templates, same page as Path 2's list: "Secrets Manager also provides a generic template that serves as a starting point for any type of secret." Unlike Path 2's ready-to-use templates, the generic template and a from-scratch function carry no schema assumption, so they work on a plain AWS/Secrets Manager/Secret/SecretString just as well as an AWS/Secrets Manager/Secret/KeyValue — the code decides how to parse and replace the value. This is the only rotation path available to a plain single-string secret, and the only one with no product restriction at all.
  • No ready-to-use rotation template for a plain single-string secret. Path 2's templates target the known database/service credential JSON shapes only — see the template list above; an AWS/Secrets Manager/Secret/SecretString holding a bare API key, OAuth token, certificate, or private key has no ready-made equivalent — only Path 3 (a hand-written function, possibly starting from the generic template).

chezmoi/Q/How can I get my editors to do syntax highlighting on the dotfiles? Is there an accepted way that chezmoi allows this?
  • Editing directly in the source directory: chezmoi does not ship editor integrations for every editor. For Vim/Neovim, the Editor user guide documents alker0/chezmoi.vim, which maps dot_* names to real paths for filetype detection and, for *.tmpl, layers go-template highlighting on top of the underlying language. The same guide lists Lilja/vim-chezmoi (apply on save with chezmoi edit) and xvzc/chezmoi.nvim. For Emacs, chezmoi.el is the documented option.
  • Templates: plain chezmoi edit gives correct highlighting for non-template targets. For *.tmpl in the source tree, use chezmoi.vim (or similar) so you get both the base language and template syntax; some dotfiles repos also add modelines such as vim:ft=toml.gotexttmpl in template headers as a local convention.
  • Bottom line: chezmoi’s accepted, documented approach is chezmoi edit → editor sees destination filenames; for source-directory and template editing, use editor plugins or modelines listed in the Editor guide and design FAQ, especially chezmoi.vim on Vim/Neovim.

DevContainer/Secrets/Report/26/01/Secrets Management in JetBrains DevContainers
  • JetBrains CodeCanvas example: JetBrains' own cloud-hosted dev environment platform, CodeCanvas, uses a two-phase approach under the hood. Administrators can define a Dev Environment Template that includes an image and then specify Personal Parameters (user-specific secret env vars or files) to inject at startup[8] [9]. CodeCanvas also supports "Cloud policy" credentials – e.g., auto-injecting cloud resource keys – which are applied to the container when it's created[10]. This means the base container is prepared in advance (and even warmed up), and when a developer launches it, their personal secrets get layered in just for their session. In essence, CodeCanvas achieves the ideal two-phase workflow: an admin provides the base devcontainer (phase 1) and the platform injects secrets at runtime (phase 2) in a secure way[11] [12].
  • To avoid interactive login each time, 1Password recommends using a Service Account token for non-interactive use. If you create a 1Password Service Account, you get an API token that can be used to authenticate the CLI in headless environments. The suggestion from 1Password forums was: provide the service account token to the container via an env var like OP_SERVICE_ACCOUNT_TOKEN, then the op CLI can operate without any prompts[21]. In practice, that means you still need to smuggle that one token into the container (which could be via an environment variable on launch, a Kubernetes secret if you were on K8s, or even a manual paste the first time followed by caching it). But once OP_SERVICE_ACCOUNT_TOKEN is set, you can run commands like op read "op://vault/secret" or use op inject to replace placeholders in files. For example, you might keep a template config file in the repo with op:// references and have a post-start command op inject -i config.template -o config.json to produce a file with real secrets[22].
  • Commit a Template and Use Vaults: It's common to include a non-secret template in the repo – e.g. an .env.template file listing the required keys (but with dummy values). Developers can use this as a checklist. From there, they might use a secrets vault CLI to populate it. For instance, you could have a script fetch-secrets.sh that reads from a service (1Password, Vault, AWS SecretsManager, etc.) and creates a real .env. This script can be written to detect the environment: if it's running in Codespaces, maybe skip because Codespaces already set env vars; if running locally or in JetBrains, use the CLI. Some sophisticated setups even use the presence of certain env vars to detect environment (e.g., Codespaces sets CODESPACES=true internally).
  • Example – Unified Approach: Let's illustrate a hypothetical pattern: Suppose your app needs DB_URL and API_KEY. You decide those will be environment vars. You commit an .env.template with:
          DB_URL=<insert database URL>
      API_KEY=<insert API key>

    In your devcontainer.json (used by both VS Code and JetBrains), you reference these vars if available:

          "containerEnv": {
          "DB_URL": "${localEnv:DB_URL}",
          "API_KEY": "${localEnv:API_KEY}"
      }

    This means: if the developer has those set on their host, the container will get them. In Codespaces, the host env is pre-populated by Codespaces secrets (so it works automatically)[26] [27]. In JetBrains, if the developer exports those in their terminal before launching the container (or sets them in their OS user env and restarts the IDE), the Dev Containers plugin will substitute them in[4]. As a fallback, if not provided, the app might fail until they supply them – but it won't accidentally use a wrong value.

      • --alias: Optional. Sets the prefix for the copied files. Default is the package name.

        		  pnpm maxmsp add @not251/not251 --alias not251 --files "index.js, index.map.js"

      • node_modules/@not251/not251/dist/index.js
      • node_modules/@not251/not251/dist/index.map.js


        To:

      • lib/not251/not251_index.js
      • lib/not251/not251_index.map.js

GitHub/CLI/Q/What's the most idiomatic way to use gh search repos while also displaying primary language and number of stars in a table?
  • Short answer: use --json fullName,language,stargazersCount with --template and gh's tablerow/tablerender extensions to Go/StdLib/text/template — no jq required.
  • bash
    			  gh search repos "your query" \
			    --sort stars \
			    --limit 30 \
			    --json fullName,language,stargazersCount \
			    --template '{{tablerow "REPO" "LANGUAGE" "STARS"}}{{range .}}{{tablerow .fullName .language .stargazersCount}}{{end}}{{tablerender}}'
