Atlassian/Confluence/API/Concept/GraphQL vs REST
  • GraphQL and REST are two distinct API paradigms available in Atlassian Confluence Cloud, each offering different approaches to data retrieval and integration
  • Understanding the differences helps developers choose the right API approach for their specific integration needs
  • Write Operations: Both APIs support CRUD operations, but with different approaches. GraphQL provides mutations like createPage, updatePage, and deletePage for content management. REST provides comprehensive endpoints including dedicated operations like copying pages (POST /wiki/rest/api/content/{id}/copy) that don't have direct GraphQL equivalents
  • REST API Approach:
    • Uses HTTP methods (GET, POST, PUT, DELETE) on resource-based endpoints
    • Endpoints are organized by resource type (e.g., /wiki/rest/api/content, /wiki/rest/api/space)
    • Returns complete resource representations unless filtered server-side
    • Versioning handled through URL paths (/api/v1/, /api/v2/)
    • Authentication via OAuth 2.0 or Basic auth
  • GraphQL API Approach:
    • Single endpoint for all queries and mutations (typically /graphql)
    • Clients send queries specifying exact fields and relationships needed
    • Mutations available for creating, updating, and deleting content (e.g., createPage, updatePage, deletePage)
    • Query language allows nested data fetching in one request
    • Schema introspection enables self-documenting APIs
    • Authentication via OAuth 2.0 or JWT for cloud apps
    • Beta fields marked for experimental features that may change
  • REST API Example: Fetching a page and its space requires multiple requests:
    • Request 1: GET /wiki/rest/api/content/{id} to get page details
    • Request 2: GET /wiki/rest/api/space/{spaceKey} to get space information
    • Result: Two separate HTTP requests with potential over-fetching
  • GraphQL API Example: Fetching the same data in a single query:
    			query {
			  content(id: "123") {
			    title
			    space {
			      key
			      name
			    }
			  }
			}
    • Result: One request fetching only the specified fields
  • Duplicating Pages: While both APIs can duplicate pages, REST provides a dedicated copy endpoint (POST /wiki/rest/api/content/{id}/copy), while GraphQL requires fetching the original page content via query, then creating a new page via mutation
  • Documentation focuses on describing capabilities rather than prescribing when to use each API
  • Use REST API when:
    • You need mature, stable, well-documented interfaces
    • Your use case requires specialized operations (e.g., direct page copying)
    • You prioritize maximum feature coverage and tooling support
    • You have existing REST integrations or team familiarity with REST
  • Consider GraphQL API when:
    • You need efficient data retrieval with related entities in single queries
    • You want to minimize over-fetching and reduce request count
    • You can work with evolving APIs (GraphQL was in beta as of March 2022)
    • Your use case benefits from schema introspection and strongly-typed queries
  • See also: Confluence GraphQL API Documentation, Community Performance Discussion

AWS/Secrets Manager/Q/What terms does AWS Secrets Manager use for single-valued vs. multi-valued secrets, and what can each do that the other can't?
  • Answer/Official from Create an AWS Secrets Manager secret, CreateSecret API reference, and Pass Secrets Manager secrets through Amazon ECS environment variables:
  • Short answer: there is no distinct secret type for this at the API level — every secret is one opaque AWS/Secrets Manager/Secret. Answer/Official from CreateSecret API reference: "Either SecretString or SecretBinary must have a value, but not both." "Single vs. multi-valued" is codekiln's own shorthand, mapped onto two garden pages: AWS/Secrets Manager/Secret/SecretString (AWS's Plaintext tab — one raw string) is single-valued; AWS/Secrets Manager/Secret/KeyValue (AWS's Key/value pairs tab — the same field holding a JSON object) is multi-valued.
  • Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs, or choose the Plaintext tab and enter the secret in any format." Its examples: an API key → key/value pairs (ClientID, ClientSecret); an OAuth token, certificate, or private key → plaintext.
  • AWS's ready-made rotation Lambda templates. Direct citations and the full picture — including a third, Lambda-less "managed rotation" path that's gated by how a secret was created, not by its shape: AWS/Secrets Manager/Secret/Rotation. Core citation: CreateSecret API reference: "you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret" for those templates to work. AWS/Secrets Manager/Secret/SecretString (single-valued/plaintext) can still be rotated, but only with a fully custom Lambda — there's no ready-made template for it.
  • What single-valued buys you that multi-valued doesn't: nothing capability-wise — it's a strict subset. Its only edge is simplicity for a value that's genuinely atomic (a bare API key, a cert, a private key), where there's no field to key on and no rotation Lambda will ever need named subfields.
AWS/Secrets Manager/Secret
  • A secret is one opaque value in a single field — SecretString (text) or SecretBinary (bytes), never both. CreateSecret API reference: "Either SecretString or SecretBinary must have a value, but not both."
  • The console nudges toward the key/value shape even outside a recognized database type. CreateSecret API reference: "If you create a secret by using the Secrets Manager console then Secrets Manager puts the protected secret text in only the SecretString parameter. The Secrets Manager console stores the information as a JSON structure of key/value pairs that a Lambda rotation function can parse."
  • The / in a name like myapp/database-url is not a path into a JSON object — it is one ordinary allowed character in one flat secret name. CreateSecret API reference: "The secret name can contain ASCII letters, numbers, and the following characters: /_+=.@-." There is no parent/child relationship between secrets in Secrets Manager; / is purely a naming convention people use to group related names, the same way S3 object keys use / without real folders existing.
AWS/Secrets Manager/Secret/KeyValue
  • The same AWS/Secrets Manager/Secret field (SecretString) holding a JSON object instead of a bare string, e.g. {"username":"admin","password":"secret"}. AWS's console calls this the Key/value pairs tab. Answer/Official from Create an AWS Secrets Manager secret: "In Key/value pairs, either enter your secret in JSON Key/value pairs..." — its example: an API key entered as ClientID / ClientSecret pairs.
AWS/Secrets Manager/Secret/Rotation
  • You cannot get this by hand-crafting your own CreateSecret call, whatever shape you give it — it depends on which service's UI/API created the secret, not on JSON vs. plaintext. CreateSecret API reference, same page cited below for the schema requirement: "For secrets that use managed rotation, you need to create the secret through the managing service."
  • Every template on that list requires the secret to be an AWS/Secrets Manager/Secret/KeyValue whose JSON matches the expected credential schema (username, password, host, ...) — never a plain AWS/Secrets Manager/Secret/SecretString. CreateSecret API reference, the "For database credentials" paragraph: "For database credentials you want to rotate, for Secrets Manager to be able to rotate the secret, you must make sure the JSON you store in the SecretString matches the JSON structure of a database secret."
  • AWS also ships a generic rotation template as an unopinionated starting point, and nothing stops writing one from scratch for a secret belonging to no AWS product whatsoever (a third-party API key, say). AWS Secrets Manager rotation function templates, same page as Path 2's list: "Secrets Manager also provides a generic template that serves as a starting point for any type of secret." Unlike Path 2's ready-to-use templates, the generic template and a from-scratch function carry no schema assumption, so they work on a plain AWS/Secrets Manager/Secret/SecretString just as well as an AWS/Secrets Manager/Secret/KeyValue — the code decides how to parse and replace the value. This is the only rotation path available to a plain single-string secret, and the only one with no product restriction at all.
  • No ready-to-use rotation template for a plain single-string secret. Path 2's templates target the known database/service credential JSON shapes only — see the template list above; an AWS/Secrets Manager/Secret/SecretString holding a bare API key, OAuth token, certificate, or private key has no ready-made equivalent — only Path 3 (a hand-written function, possibly starting from the generic template).
AWS/Secrets Manager/Secret/SecretString
  • The AWS/Secrets Manager/Secret field holding one raw string, no internal structure — an API key, OAuth token, certificate, private key. AWS's console calls this the Plaintext tab. Answer/Official from Create an AWS Secrets Manager secret: "choose Other type of secret. In Key/value pairs, either enter your secret in JSON Key/value pairs, or choose the Plaintext tab and enter the secret in any format."
  • Accepted values: any string, up to 64 KB. CreateSecret API reference: "Type: String Length Constraints: Minimum length of 1. Maximum length of 65536." Compare AWS/Secrets Manager/Secret/KeyValue — the same field, holding a JSON object instead of a bare string.

c74/M4L/Idea/Alits
  • The Max for Live API that's accessible in Javascript is not a typical JS or typescript API. Much if not most of the Max/MSP language is about sending messages to objects, and Ableton Live API designed for Max for Live (M4L) inherits the characteristics and assumptions of that approach. Fundamentally, the Ableton Live API in Max/MSP is a string manipulation and messaging API. In c74/max/obj/js, the Ableton/Live Object Modelrelies heavily on instantiating c74/M4L/obj/LiveAPI with c74/M4L/obj/live.path strings, calling getters and setters with strings, and using callbacks rather than promises to receive updates to properties.
  • A typical API in js/ts would mirror the UML diagram or Entity Relationship Diagram in API objects that return references to each other. For example, a Track object would have a get_clips() function that returned Clip objects.
  • In the Max/MSP-centric M4L API, however, one needs to construct paths and validate them. For example, to get clips from a track, one needs to construct a Live Object Model path using a live object model string path, and then instantiate a new LiveAPI with that path. As described in the c74/M4L/Ref/Live API Overview,

    • Live objects are accessed using paths according to the Live Object Model. For example, the first clip in the third track can be accessed by the path live_set tracks 2 clip_slots 0 clip. Alternatively, it can be accessed via live_set scenes 0 clip_slots 2 clip. Or, if the clip is shown in the detail view, via live_set view detail_clip.

  • After obtaining a reference to an object that points to an entity in Ableton Live, calling methods on that object requires some string processing and validation to send messages to it. Quoting the c74/M4L/Ref/Live API Overview/Functions section here,

    • Many Live objects have functions which can be called by sending call and the function name to live.object, like call create_scene for a Song object.

  • See also c74/M4L/Ref/Creating Devices that use the Live API/Calling a function section here, which describes the Max/MSP Live API method of calling a function.
  • A typical API in js/ts would allow access attributes directly, for example, Clip.get_file_path() or Clip.get_length(), rather than calling .get(attribute) and then validating if the attribute exists and coercing the results to types in javascript.
  • Accessing any of the object's members is also string- and messaging-centric; quoting c74/M4L/Ref/Creating Devices that use the Live API here,

    • The live.path object is used to navigate to the Live objects whose functions you want to call. Each property of the Live object model in a session is associated with an id specific to that particular Song, Track, Clip, Clip Slot, Device, etc.

    • Sending a message to a live.path object results in an object id being sent out the left outout (where the id follows the object) or middle outlet (where the id follows the path).

  • This API is mirrored in the c74/M4L/Ref/jsliveapi/Methods/get (see get reference documentation here), where to get a property, one needs to call the <LiveAPIInstance>.get(property), where property here is, for example, in the case of Clip, file_path, length, or any other instance.
  • After after obtaining an array of Clip object references with getClips(track), accessing the members of the objects is also done using a string-based API, as one can see from these lines above:

  • Suggested API - An #Observable Typescript/Library for Live API

    • The core characteristics of a more idiomatic typescript library would be:
      • The library would be oriented towards a Functional Reactive Programming paradigm using RxJS.
      • The library would abstract away and hide the details of using the Ableton/Live Object Model paths from c74/M4L/obj/live.path and treat that as a low-level implementation detail. Advanced users could still utilize methods that enabled using this functionality, but the core assumption of the Alits API is that it would no longer be necessary.
      • Each object in the Ableton/Live Object Model would have its own Typescript class.
        • Each object would have a get_children() function that would return an Array of objects of the appropriate Typescript classes in the API.
        • Each property
          • that has get access has a <ObjectInstance>.get_<propertyname>() method.
          • that has set access has a <ObjectInstance>.set_<propertyname>(...) method.
          • that has observe access has a <ObjectInstance>.observe_<propertyname>(...) method that returns an observable. Internally, this would call RxJS/subscribe (see also docs for Subscription).
        • Each method would be proxied appropriately onto the object. For example, the typescript class corresponding to Clip would have a Clip.add_new_notes(...) method.
      • The library would come with first-class support for logging and error handling.
    • The library that implements this API could be written using the GitHub/Repo/Template that Person/Alessandro Petrone wrote for maxing max/msp libraries in #Typescript - GitHub/aptrn/maxmsp-ts-library-template. As the README from that template mentions,

      • This is a turborepo monorepo (turborepo) template with the following structure:

        • 				  ├── apps
				  │   └── maxmsp-test
				  └── packages
				      └── my-library

      • my-library: Contains your TypeScript library

      • maxmsp-test: Contains an instance of this template  (GitHub/aptrn/maxmsp-ts-example) with my-library as a dependency.

      • Since this is is a turborepo monorepo, the library could develop the core of this library in its own package, alits-core.
        • Most users will not need the entire API, which could be broken up to simplify versioning and minimize merge conflicts. Other sub-libraries could focus on isolated portions of the library:
          • alits-max-device -

    • The strongest supported API

      • GitHub now has a documented REST endpoint specifically for an individual user's AI-credit billing usage.
