  • please create Logseq/Entity/Series. A Series should be combined with another entity to represent a sequence. By default, Series should appear in the Logseq namespace after the entity type and before the entity, and the parts of the series will appear clustered by the series as well as in order on the filesystem when sorted Lexicographically. For example, while Logseq/Entity/Book would imply that Philip Pullman's book His Dark Materials should have a page at Person/Philip Pullman/Book/95/The Golden Compass, if a page is both a Book and a Series entity, it should then be rightly be placed instead at Person/Philip Pullman/Book/Series/His Dark Materials/<Appropriately Zero-Padded ordinal>/95/The Golden Compass, or Person/Philip Pullman/Book/Series/His Dark Materials/95/1 - The Golden Compass. If a page is both a Podcast and a Series entity, similar rules should apply, and similar combinations for other entities that form a series. 1 here is an optional appropriately zero-padded ordinal. If the series currently terminates in n digits of ordinal references, then all instances should be zero padded to n digits so that sorting them lexicographically does not perturb the intended order. The intention of the ordinal is to aid in memorization or identification. In the case of a podcast, an ordinal number should never be given unless the podcast's published feed and/or title references that ordinal number such that one can google "<podcast name> episode <number>" and reliable get to the episode in the top hits. Hard requirement: the entity definition for a series must not imply that "series" is particular to books and podcasts and must be stated in a way that generalizes across the garden to its applications elsewhere. 1Password/Environment/Q/Can a symlink to a .env created with 1Password Environments work? Can I create a number of different symlinks to the same .env and use it in different places?
  • In the test, a relative symlink (a/.env -> ../real.env) and an absolute one (b/.env -> /…/real.env) both resolved to the same pipe: stat -L gave the same inode and type Fifo File for all three paths.
  • File-type checks still see a pipe. Python's os.path.isfile returned False through the symlink, the same as on the pipe itself, so loaders that need a regular file fail either way. The docs list python-dotenv 1.1.2+ as supported.
