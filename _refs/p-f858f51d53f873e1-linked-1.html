Skills-Directory PluginOverview
  • A skills-directory plugin is an ordinary Claude/Code/Plugin that Claude Code finds because it sits inside a skills directory — ~/.claude/skills/ or a project's .claude/skills/. One file flips a plain skill folder into a plugin: any folder there that holds a .claude-plugin/plugin.json manifest loads as a plugin named <name>@skills-dir on the next session, with no marketplace and no install step.
Skills-Directory PluginOverview
  • The @skills-dir suffix is the plugin's source label, the slot where a marketplace name would otherwise go. Claude Code reads such a plugin from where it lives; a Claude/Code/Plugin/Marketplace install instead copies the plugin into the cache at ~/.claude/plugins/cache. Discovery in place is what lets you edit the files directly and have the graph pick them up.
Claude/Code/Q/Does editing a plugin's SKILL.md in a local-path Claude Code marketplace require reinstalling, or is restarting Claude Code enough to pick up the change?

  • Does editing a plugin's Claude Code Skills SKILL.md in a local-path Claude/Code/Plugin/Marketplace require reinstalling, or is restarting Claude Code enough to pick up the change?

    • AI Answer

      • Answer/Official from Plugins reference - Claude Code Docs
        • Short answer: No, restarting alone is not enough. A plugin installed with /plugin install from any marketplace — including one added from a local path via /plugin marketplace add ./my-marketplace — is copied into ~/.claude/plugins/cache at install time. Claude Code loads that cached copy, not the live files under my-marketplace/, so editing SKILL.md in the source tree has no effect until the plugin is reinstalled or updated.
        • Why a restart doesn't help: the cache-vs-source split applies to every marketplace-installed plugin, not only git-hosted ones — "Claude Code copies marketplace plugins to the user's local plugin cache (~/.claude/plugins/cache) rather than using them in-place." A restart just reloads whatever is already sitting in that cache.
        • Why /plugin update may not help either: Claude Code decides whether an update is needed by comparing the plugin's resolved version, checked in this order: plugin.json version → marketplace-entry version → git commit SHA (only for github/url/git-subdir/relative-path sources inside a git-hosted marketplace) → unknown for local directories that aren't inside a git repo. A plain local-path marketplace with no explicit version set always resolves to unknown on both sides of the comparison, so /plugin update (and background auto-update) reports "already at the latest version" and skips the re-copy.
        • How auto-update interacts with this: auto-update doesn't diff file contents — it re-runs the same version comparison as /plugin update, just on a timer, so it inherits the same blind spot.
          • It's off by default for exactly this kind of marketplace: "official Anthropic marketplaces have auto-update enabled by default. Third-party and local development marketplaces have auto-update disabled by default." Turn it on per marketplace via /plugin → Marketplaces → select the marketplace → Enable auto-update (or, for a team, an admin sets "autoUpdate": true on that marketplace's extraKnownMarketplaces entry in managed settings).
          • Even enabled, whether it can ever notice the edit depends on what my-marketplace/ actually is:
            • Plain directory, no .git: version stays unknown forever, so enabling auto-update changes nothing — there's no version delta for it to detect, ever.
            • my-marketplace is itself a git repo (even with no remote) and the plugin uses a relative-path source: version resolves to that repo's commit SHA, so saving SKILL.md alone still doesn't change anything — you must git commit the change. Once committed, auto-update's next background pass (or a manual /plugin update) sees a new SHA and re-copies.
            • Explicit version set in plugin.json/the marketplace entry: same rule as manual update — auto-update only fires when that string is bumped.
          • Timing, when it does apply: "Claude Code checks for marketplace and plugin updates after your session starts, with a random delay of up to ten minutes, so the running session keeps using the versions it loaded at launch. If any plugins were updated, you'll see a notification prompting you to run /reload-plugins, or the new versions load on your next launch."
          • Net effect for local plugin development: auto-update is built to keep other people's marketplaces fresh in the background, not for a tight edit-save-test loop. Best case (git-backed marketplace, auto-update on) still needs a commit and a ≤10-minute wait before a notification; worst case (plain directory) it never helps at all. --plugin-dir (below) sidesteps all of this.
        • To actually pick up the edit:
          • 1. Reinstall: /plugin uninstall my-plugin@my-marketplace then /plugin install my-plugin@my-marketplace. This forces a fresh copy into the cache regardless of the version string. The uninstall command's --keep-data flag exists for exactly this case — the docs note it's for "reinstalling after testing a new version" — to preserve ${CLAUDE_PLUGIN_DATA} across the reinstall.
          • 2. Or set an explicit version in plugin.json (or the marketplace entry) and bump it on every change, then run /plugin marketplace update my-marketplace followed by /plugin update my-plugin@my-marketplace (or let auto-update apply it once enabled for that marketplace).
          • 3. If skills still don't show up after reinstalling, clear the cache outright: rm -rf ~/.claude/plugins/cache, restart Claude Code, and reinstall.
        • Better fit for active plugin development: skip the marketplace-install path and load the plugin for the session with claude --plugin-dir /path/to/my-plugin instead. --plugin-dir plugins are read in place rather than copied to the cache, so edits are picked up on the next session start with no install/update step — the pattern used for rapid local iteration in Claude/Code/Plugin/Marketplace/Report/26/01/Automated Testing.
        • Related, narrower exception: a plugin auto-discovered from a project's skills/ directory via @skills-dir (no marketplace, no install step) is read in place, and edits to its SKILL.md take effect immediately in the current session — but that's a different mechanism from a marketplace-installed plugin, and its other components (hooks, .mcp.json, agents) still need /reload-plugins or a restart.
Claude/Code/Q/How can I keep my private Claude Code plugin marketplaces up to date daily?

Page reference

  • How can I keep my private Claude/Code/Plugin/Marketplaces up to date daily?

    • AI Answer

      • Answer/Official from Create and distribute a plugin marketplace - Claude Code Docs
        • Short answer: run claude plugin marketplace update yourself on a schedule (e.g. a daily cron job or launchd task) rather than relying on Claude Code's built-in auto-update — for a private marketplace, auto-update is both off by default and unreliable over HTTPS, while a manual/scripted update uses your normal git credentials the same as your terminal.
        • Manual/scripted update command: claude plugin marketplace update [name] — omitting [name] updates all registered marketplaces in one call, which is what a daily cron entry would typically run.
        • Why the built-in auto-update doesn't already give you "daily":
          • It's off by default for exactly this case: official Anthropic marketplaces have auto-update enabled by default, third-party and local/private marketplaces have it disabled by default.
          • The only documented way to turn it on is a settings.json field, not a menu action: each extraKnownMarketplaces entry accepts an optional autoUpdate boolean — "autoUpdate": true alongside that entry's source. For a local-directory marketplace the source shape is { "source": "directory", "path": "/absolute/path/to/marketplace" }.
          • In practice, the interactive /plugin → Marketplaces → select-marketplace menu may not expose an "Enable auto-update" action at all for a directory-sourced marketplace — auto-update is fundamentally a background git pull, which doesn't apply to a marketplace that's already just a local folder being re-read. The toggle described in Anthropic's docs is on firmer ground for github/git/url-sourced marketplaces.
          • Even enabled, it isn't a standalone daily timer — it's a background check that runs after a Claude Code session starts (with a random delay of up to ten minutes), so a marketplace only gets checked on days you actually launch a session, and updates apply on /reload-plugins or your next launch.
          • autoUpdate: true also does more than the manual claude plugin marketplace update command: per the settings reference, it "refresh[es] that marketplace and update[s] its installed plugins in the background" — the manual CLI command only refreshes the marketplace catalog, so getting installed plugins onto the new version still needs a separate claude plugin update <plugin>@<marketplace> per plugin (no --all flag exists for plugin update).
        • Private-repository credential caveat that a naive cron job can also hit:
          • Manual/scripted claude plugin marketplace update reuses your existing git credential helpers, so HTTPS via gh auth login/Keychain/git-credential-store, or SSH via a key loaded in ssh-agent, works the same as a normal git pull in your terminal.
          • Background auto-update is more fragile: by default it disables git credential helpers for its git pull, so private HTTPS remotes can't authenticate even with a helper configured; SSH remotes with ssh-agent are unaffected. A failed background pull falls back to a full re-clone (which does use stored credentials but can time out on large repos), so private-marketplace auto-updates "may fail intermittently."
          • To make a scheduled/background update reliable for a private HTTPS marketplace: configure a git URL rewrite scoped to that marketplace's repo or org with an embedded token (so the pull authenticates directly and skips the re-clone path), and/or set CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1 so a failed pull keeps the last-synced clone instead of deleting it. In CI/cron contexts, gh auth setup-git (or an equivalent credential helper) makes the fallback re-clone work unattended too.
        • Recommended daily setup: a cron/launchd job that runs claude plugin marketplace update once a day (or per-marketplace with [name] if you want to script it against a curated list) sidesteps both limitations above — it isn't gated on starting a session, and it authenticates like a normal terminal git pull rather than the more restricted background-refresh path.
Claude/Code/Q/If I want to use Claude Code's skill-directory plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?

Page reference

  • If I want to use Claude/Code's Claude/Code/Plugin/Skills-Directory Plugin feature but edit skills in Obsidian, can I symlink .claude/skills/<skill-name> to skills/<skill-name>?

    • AI Answer

      • Short answer: Yes. Claude Code stats through symlinks when it scans .claude/skills/, so .claude/skills/<skill-name> can be a Symlink to a plain, non-dot folder like skills/<skill-name> — you edit the real files in Obsidian with zero configuration, and Claude Code loads the skill exactly as if it lived under the dot-directory directly. This sidesteps the Obsidian/Q/Can Obsidian be configured to show markdown files in folders that begin with a dot (dot-folders), e.g. to edit .claude/skills/<skill-name>/SKILL.md? problem entirely, since the real content never sits inside a hidden dot-folder.

      • What I verified (Claude Code 2.1.221, darwin-arm64)

        • Created skills/test-skill/SKILL.md with real frontmatter/content, then ln -s ../../skills/test-skill .claude/skills/test-skill (relative symlink) in a scratch project directory.
        • A fresh, non-interactive claude -p session in that directory logged Loaded 1 unique skills (... project: 1 ...) and, when asked, correctly quoted the skill's exact description pulled through the symlink — confirming a plain skill folder resolves fine as a symlink.
        • Repeated the test for a full skills-directory plugin (.claude-plugin/plugin.json + a nested skills/ folder, per Claude/Code/Plugin/Skills-Directory Plugin), also symlinked in. claude plugin list detected it too, reporting it as a found project-scope plugin directory — the manifest was read through the symlink without issue.

      • The one catch: project-scope plugin trust, not the symlink

        • The skills-directory plugin case (manifest-bearing folder) didn't load automatically in the test — but the reason had nothing to do with the symlink. claude plugin list reported it explicitly: "1 project-scope plugin directory under ./.claude/skills/ was not loaded because this workspace was not trusted when plugins were scanned." That is the same trust gate Claude/Code/Plugin/Skills-Directory Plugin documents for any project-scope @skills-dir plugin, symlinked or not — accept the workspace trust dialog (or run /reload-plugins afterward) and it loads.
        • A plain skill (just SKILL.md, no plugin.json) isn't gated the same way — it loaded immediately, even in a fresh non-interactive session with no trust dialog involved.

      • Practical setup

        • Keep the real files outside the dot-directory: skills/<skill-name>/SKILL.md (or the full plugin folder for a skills-directory plugin).
        • Symlink it in with a relative link so it survives clone/move: ln -s ../../skills/<skill-name> .claude/skills/<skill-name>.
        • Edit skills/<skill-name>/SKILL.md directly in Obsidian — skills/ isn't a dot-folder, so none of the dot-folder-visibility plugins are needed for this path.
        • SKILL.md edits take effect immediately in a running Claude Code session; other plugin pieces (hooks/, .mcp.json, agents/) still need /reload-plugins or a restart, per Claude/Code/Plugin/Skills-Directory Plugin.

      • A competing convention worth knowing

        • Some orgs standardize the symlink in the other direction — treat .claude/skills/ as canonical and symlink a plain-named directory (e.g. .agents/skills) to it, so other tools reach the same content without touching Obsidian visibility at all. Either direction is a valid use of the same underlying mechanism (dot-folder scanning follows symlinks); which one to use depends on whether the dot-directory or the plain directory is your source of truth.

Codex/Plugin/Q/Is a Codex skills-only plugin the same idea as a Claude Code skills-directory plugin?

  • Is a Codex/Plugin built as a "skills-only plugin" the same idea as a Claude/Code/Plugin/Skills-Directory Plugin?

    • AI Answer

      • Answer/Official from Build plugins – Codex and Plugins reference — Skills-directory plugins.
      • Short answer: No. The names collide but the two terms describe different axes. Skills-only is about composition — a plugin whose only component type is skills. Skills-directory is about discovery — a plugin found in place because of where its folder sits.

      • The two axes

        • AxisCodex "skills-only plugin"Claude "skills-directory plugin"
          What variesWhich components the bundle containsHow the host finds and loads the bundle
          Defining traitManifest points at skills/ and nothing elseA .claude-plugin/plugin.json inside a skills directory
          Components allowedSkills only, by definitionAnything — skills, agents, hooks, MCP
          Install stepYes: register in a marketplace source, then installNone: loads on the next session, labeled <name>@skills-dir
          Lives whereAnywhere; the marketplace entry points at it~/.claude/skills/ or a project's .claude/skills/

      • Why the Codex tree is the opposite row

        • The minimal Codex layout is meeting-follow-up/ containing .codex-plugin/plugin.json and skills/meeting-follow-up/SKILL.md. In the table on Claude/Code/Plugin/Skills-Directory Plugin that is the third row — a skill packaged inside a plugin — which that page explicitly separates from the skills-directory case.
        • A skills-directory plugin is the second row: the manifest sits at <skills-dir>/foo/.claude-plugin/plugin.json, so the folder you were already using for a plain skill becomes a plugin without moving or installing anything.

      • What each actually maps to

        • Codex's skills-only plugin ↔ an ordinary Claude plugin that happens to ship only skills. Same idea, both need a marketplace source and an install.
        • Claude's skills-directory plugin ↔ Codex's repo marketplace plus project plugin configuration is the closest supported plugin workflow. Codex still installs a cached copy; it does not document discovering a full plugin merely from a manifest placed inside .agents/skills/.
        • For editing skills in place, use a plain Codex/Skill in a scanned directory: $CWD/.agents/skills, $CWD/../.agents/skills, $REPO_ROOT/.agents/skills, or $HOME/.agents/skills.

      • The practical difference

        • The skills-directory plugin exists to remove the install loop while authoring — edit SKILL.md and the running session picks it up; /reload-plugins for the rest. Codex's plugin workflow uses a marketplace and an installed copy. For its cache and refresh behavior, see Codex/Plugin/Q/Does registering a local plugin copy it into a home-directory cache?.

      • Repo activation in current Codex clients

        • As of October 15, 2026, a repo can expose plugins through .agents/plugins/marketplace.json and enable one through its trusted project .codex/config.toml:
          • toml
            				  [plugins."my-plugin@local-repo"]
				  enabled = true
        • my-plugin matches the catalog entry; local-repo matches the catalog's top-level name. The catalog alone makes the plugin discoverable. Configured plugins can be installed or refreshed during marketplace refresh, even when configured as disabled. Enable or disable a plugin for a repo.
        • This provides a declarative repo setup for supported local Codex clients, subject to project trust and enforced requirements. It does not establish a universal promise that opening a repo activates the plugin in every ChatGPT Work surface. Workspace-imported plugins have separately managed installation and enabled state.
        • To develop and distribute the package, see ChatGPT/Plugin/How To/Develop and Share a Team Plugin for ChatGPT and Claude.

CursorAI/Q/I have some private Claude plugins in a Claude Plugin Marketplace that I'd like to run in Cursor. What are my options?

  • I have some private Claude/Code/Plugins in a Claude/Code/Plugin/Marketplace that I'd like to run in CursorAI. What are my options?

    • AI Answer

      • Answer/Official from Plugins | Cursor Docs, Agent Skills | Cursor Docs, Third Party Hooks | Cursor Docs, and MCP | Cursor Docs
        • Short answer: CursorAI does not install Claude/Code/Plugin/Marketplace plugins as drop-in bundles. Treat the marketplace as source material, then pick a path by what you need: reuse compatible pieces in place, repackage as a Cursor plugin (local or team marketplace), or keep running Claude Code inside Cursor for the full Claude plugin lifecycle.
        • 1. Reuse pieces without a Cursor plugin (lowest effort)
          • Skills: Cursor discovers Agent Skills from Claude paths too — project .claude/skills/ and user ~/.claude/skills/ (plus .cursor/skills/, .agents/skills/, and Codex equivalents).           • MCP: Same protocol, different config path — put servers in .cursor/mcp.json or ~/.cursor/mcp.json (or install via Customize / team marketplace). Claude plugin .mcp.json is not auto-imported.
        • 2. Repackage as a Cursor plugin (best for a private bundle you want to install as one unit)
          • Cursor plugins use .cursor-plugin/plugin.json (not .claude-plugin/) and can ship rules, skills, agents, commands, hooks, and MCP together.
          • Local/private-to-you: put the plugin under ~/.cursor/plugins/local/<name> (symlink the repo for iteration), then reload the window.
          • Private-to-a-team: on Teams/Enterprise, import a GitHub repo as a team marketplace from Dashboard → Plugins (Claude's marketplace.json / HTTP marketplace URLs are a different system).
          • Public Cursor Marketplace listing requires open source + Cursor review — not the path for private plugins.
        • 3. Run Claude Code inside Cursor (full Claude marketplace lifecycle, not Cursor Agent)
          • Install Anthropic's Claude Code extension in Cursor and/or run the standalone claude CLI in Cursor's terminal. Plugin marketplaces, /plugin install, and ~/.claude/plugins/cache stay on Claude Code's system; Cursor Agent still won't "see" those marketplace installs as Cursor plugins unless you also use options 1–2 for the pieces you care about in Agent.
        • Practical chooser
          • Mostly SKILL.md workflows → option 1 (skills dirs).
          • Hooks already in .claude/settings.json → option 1 (third-party hooks toggle).
          • Need one installable private package for a team in Cursor Agent → option 2.
          • Need Claude's marketplace UX / cache / slash-plugin tooling as-is → option 3.
