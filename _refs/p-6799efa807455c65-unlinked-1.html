brew/Q/What does brew bundle dump do?

  • What does brew bundle dump do?

    • AI Answer

      • Answer/Official from Homebrew Bundle README
      • Short answer: it writes the current machine's installed state (taps, formulae, casks, and other supported package managers) out to a brew/file, so that state can be captured, version-controlled, and diffed over time.
      • By default it writes ./Brewfile in the current directory, or a custom path via --file (--file=- pipes to stdout/stdin).
      • What it dumps, by default: taps, formulae (brew), and casks (cask). Each of these can be toggled independently with --formula/--no-formula, --cask/--no-cask, --tap/--no-tap.
      • It can also dump entries for several other package managers if present, each gated by a --no-dump-<manager> flag (or the matching HOMEBREW_BUNDLE_DUMP_NO_* env var): mas (Mac App Store), whalebrew, vscode extensions, Flatpak, WinGet, Krew plugins, and npm packages.
      • --describe (default on) adds a comment above each entry describing the package; --no-describe omits those comments.
      • -f/--force overwrites an existing Brewfile at the target path instead of erroring.
      • --global reads/writes the global Brewfile location ($HOMEBREW_BUNDLE_FILE_GLOBAL, $XDG_CONFIG_HOME/homebrew/Brewfile, or ~/.Brewfile) instead of the current directory's.
      • --install runs brew bundle install first, so the dump reflects the post-install state.
      • It is effectively the inverse of brew bundle (a.k.a. brew bundle install), which reads a Brewfile and installs/updates the system to match it — dump goes system → Brewfile, install goes Brewfile → system.

chezmoi/Q/What is the idiomatic way to add the Obsidian CLI to PATH via chezmoi dotfiles and install Obsidian in a Brewfile?
  • The idiomatic chezmoi pattern for Homebrew is an inline heredoc inside a run_onchange_ script, not a standalone Brewfile. chezmoi only re-runs the script when its content changes, avoiding redundant brew bundle runs on every chezmoi apply.
  • bash
    					  {{- if eq .chezmoi.os "darwin" -}}
					  #!/bin/bash
					  brew bundle --no-lock --file=/dev/stdin <<EOF
					  cask "obsidian"
					  EOF
					  {{- end }}

My/Dotfiles/Process/Adding a New Global Dependency/Idea

  • Try-before-commit window (Homebrew case)

    • Homebrew is the one dotfiles backend where installing and declaring are separate actions: brew install x works whether or not x is in the Brewfile. That gap is the low-friction "try it out" move this Idea already asks for — install something to try it, live with it a few days, then decide.
    • The corresponding rule is My/Principle/Declarative over Imperative applied to Homebrew: chezmoi/Brewfile is meant to be the complete record of everything brew manages, not a hand-picked subset. A brew install absent from the Brewfile is fine while under evaluation, not fine as a permanent state.
    • The garden-side ritual: once a week or so, compare what's actually brew-installed (formulae marked --installed-on-request, plus casks) against the Brewfile, and uninstall anything not explicitly committed. This applies the outer loop's weekly check to Homebrew specifically — same "surface the gap, close it" pattern as the rest of this Idea, on a regular schedule instead of lazily.
    • This is the other half of My/Dotfiles/openspec/specs/brewfile-style (only what mise can't do belongs in the Brewfile): what does belong there must actually be there.

Scoop/Q/Is Scoop secure?
  • Manifests are executable. installer, pre_install, and post_install run PowerShell as your user at install time, and there is no per-package allowlist for that — scoop bucket add grants a third-party repo the same trust as the core buckets. This puts Scoop in the same category as Homebrew and Chocolatey, and behind winget, whose manifests are non-executable descriptions of a signed installer plus a checksum.
