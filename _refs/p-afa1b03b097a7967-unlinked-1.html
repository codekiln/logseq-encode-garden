  • cargo-nextest is a binary tool (cargo subcommand), not a Rust library. Binary tools must be installed via cargo install, not added to Cargo.toml dev-dependencies.
  • Cargo only manages libraries you compile into your project. Cargo.toml is a crate manifest, not a general dependency manifest. Unlike JS (package.json) or Python (requirements.txt), it doesn't manage binary tools.
  • Rust ecosystem assumes tools are installed globally via cargo install, Nix, Docker, or OS package managers. This matches systems languages like Go/C++/Zig, not Python/JS.
  • Version-locking tools happens outside Cargo via devcontainer.json, Dockerfiles, Nix flakes, CI scripts, or a tools/ workspace crate.
  • Bottom line: Cargo intentionally separates build tools from build inputs. For reproducible tooling, use devcontainer/Docker/Nix/CI scripts, not Cargo.toml.
arXiv/Article/26/02/Auditing Rust Crates Effectively
  • Introduces Cargo Scan, an interactive Rust auditing tool for third-party crate review.
  • Reports that Cargo Scan reduced potentially dangerous audit work to a median of 0.2% of lines of code in the evaluated crates, and could automatically classify about 3.5K of the top 10K crates on crates.io as safe.
  • Cargo Scan sits between manual reading and broad static-analysis alerts: it tries to find the code paths a human should inspect instead of declaring an entire dependency graph trustworthy.

  • Dprint for Polyglot Repos: If your repo has multiple languages (say Rust code, docs in Markdown, maybe JSON, etc.), adopting dprint can be efficient – one formatter config for everything. You can add a pre-commit hook for dprint:
    			  - repo: local
			  hooks:
			   - id: dprint
			     name: dprint formatter
			     entry: dprint fmt --check
			     language: system
			     types: [markdown, json, yaml, rust]

    Here language: system means it expects the dprint binary installed (you can also manage it via a cargo install or provide it in the environment). Dprint's dprint fmt --check will check formatting and dprint fmt (without --check) will write fixes. You might run dprint fmt locally and use --check in CI. Just ensure your dprint.json is configured for Markdown (you'd run dprint config add markdown once to set it up). Dprint is a bit more involved to configure initially than Prettier or mdformat, but it pays off with speed and one-tool integration.

Lockfile
  • Manifests (pyproject.toml, package.json, Cargo.toml, mise/Config/mise.toml) describe what a project wants; lockfiles describe what a resolver actually picked, including transitive dependencies the manifest never names.
  • cargo — Cargo.lock; applications check it in, while libraries often leave it out so downstream consumers resolve their own versions.
  • "Lockfiles are only for applications" — Ecosystem-dependent; library authors often skip committing one (e.g. Cargo.lock for a library crate) so consumers resolve against their own constraints, while applications and services almost always commit one.

Mr Boxington
  • A shared cache for cargo builds, run as the mbx command. Cargo still resolves dependencies, plans builds, and runs tools; mbx restores matching compiler outputs from one shared store and compiles the rest. No daemon or cache server is needed for local use. [1]
  • Independent Cargo commands share CPU and memory permits and deduplicate identical compilations in flight.
  • Install with mise (mise use --global --tool-option mr_boxington=true rust mr-boxington), or with cargo install mbx --locked followed by mbx setup.
  • Set the mr_boxington option on the rust tool and add mr-boxington as its own tool. Cargo then runs through mbx under mise exec, mise tasks, activated shells and mise's shims, with no mbx setup step. [2]
    • toml
      		  [tools]
		  rust = { version = "latest", mr_boxington = true }
		  mr-boxington = "latest"
  • Calling a toolchain's cargo directly, such as ~/.cargo/bin/cargo, skips mbx. Check with command -v cargo. [2]

  • [2] https://github.com/jdx/mise/blob/main/docs/lang/rust.md#share-cargo-builds-with-mr-boxington

Rust/script
  • rust-script is a lightweight tool that allows you to run single-file Rust programs as scripts—similar to how you might use Python, Ruby, or Node.js—without manually creating a full Cargo project.
  • Dependency resolution via Cargo
  • Compared with writing a whole Cargo project, it's dramatically quicker for small tasks.
  • Add dependencies right in the file (much like Rust's cargo-script used to allow):
  • rust
    			  //! cargo-deps: reqwest = "0.11", tokio = { version = "1", features = ["full"] }
			  
			  #[tokio::main]
			  async fn main() {
			    let body = reqwest::get("https://example.com").await.unwrap().text().await.unwrap();
			    println!("{body}");
			  }
  • rust-script reads these headers, generates a temporary Cargo project, compiles it, and caches it.

  • 4. Cargo-like experience, minimal ceremony

    • It automatically:
      • Creates an implicit Cargo manifest
      • Pulls dependencies
      • Compiles and caches binaries
    • You stay focused on the code.
  • cargo-script: Similar predecessor; rust-script is generally more up-to-date and idiomatic.
  • cargo + fn main: Standard approach, but requires project scaffolding.
  • shebang with cargo run: Possible but much heavier.
  • cargo/install is used to install binary crates (executables) globally, not libraries. Libraries are added as dependencies in Cargo.toml.
