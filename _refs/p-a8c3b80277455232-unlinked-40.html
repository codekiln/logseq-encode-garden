  • typecraft-dev/dotfiles

    • Public dotfiles for Person/Chris Power (typecraft), tracking the Linux desktop and nvim setups demonstrated on their channel. No README and no license file; the directory layout is the documentation.
    • Written in Lua (the nvim config dominates the repo by volume).
    • GitHub/Star: 1433 (checked 2026-08-04); 267 forks — an unusually high fork-to-star ratio, consistent with an audience cloning along with video tutorials rather than depending on it as a library.

    • Layout

      • Each top-level directory is a GNU Stow package whose contents mirror $HOME, so nvim/.config/nvim/ symlinks to ~/.config/nvim/. Stowing selects configs per machine instead of applying one monolithic tree, which is the lighter-weight alternative to the templated dotfile/Managers (chezmoi and friends) used elsewhere in this garden.
      • Two parallel Linux desktop stacks live side by side: Wayland (Hyprland with hypridle/hyprlock/hyprpaper, waybar, wofi) and X11 (i3, picom, polybar, rofi, .Xresources). Useful as a diff between the two ecosystems for the same person's taste.
      • Three terminals are configured — Ghostty, Alacritty, and kitty — alongside starship, zsh (zshrc/.zshrc), and tmux.
      • Catppuccin Mocha is applied consistently across Alacritty, rofi, waybar, hypr, and nvim; see Catppuccin.

    • nvim

      • lazy.nvim bootstrapped in init.lua, with one file per plugin under lua/plugins/ and options factored into lua/vim-options.lua. The plugin-per-file split is the trait worth borrowing: each plugin's spec is independently readable and removable.
      • nvim/.config/nvim/lua/plugins — Avante and Copilot for AI assistance, oil.nvim for file editing, snacks.nvim, treesitter, none-ls, plus Rails and vim-test for a Ruby workflow.

    • tmux

      • tmux/Config tmux/.config/tmux/tmux.conf
      • Uses tpm for plugins and vim-tmux-navigator for unified pane/split motions with nvim.

            				  git add .cursor/rules/logseq-cursor-rules .gitmodules

          • bash

          • bash
            				  cd .cursor/rules/logseq-cursor-rules

    • About

      • logseq-gardener is a command-line tool, called lsg, for people and coding agents to manage Logseq/OG knowledge gardens from the terminal and Neovim. Version 0.0.1 shipped on 2026-10-31 Sat.
      • lsg lookup NAME --graph PATH --filename-format triple-lowbar prints the file of the page named by its title, an alias or a journal date. lsg publish generates selected local HTML pages, and lsg help documents every command.

    • Install

      • mise installs the latest release on every machine that My/Dotfiles sets up, through the line "github:codekiln/logseq-gardener" = "latest" in the global mise config (dotfiles#183 Install Logseq Gardener (lsg) globally with mise).
      • A project that uses lsg writes the same line under [tools] in its mise.toml, and mise runs the globally installed version there. This garden's mise.toml does so.

  • The Brief's premise holds. Logseq split the file version into logseq/og, whose commits since May 2026 are Electron and dependency bumps, and the DB documentation says file graphs are no longer supported in the browser.
  • ParserLanguageLicenseMaintainerLast pushNotes

  • Tine is a Logseq-compatible outliner that reads and writes the same pages/, journals/, assets/, and logseq/config.edn as Logseq, with a pure-Rust core and an in-memory cache for search, backlinks, and queries. It ships static HTML export with offline search and a native Android build. It was created in late June 2026 and was last pushed today.
  • If lsdoc fails on constructs the encode garden uses, build on mldoc in OCaml. Logseq is rewriting core pieces in OCaml: datascript-ocaml, a persistent sorted set, an FSRS library, and the official Logseq CLI are all OCaml. That CLI compiles to JavaScript through Melange, targets DB graphs only, and runs a db-worker-node server with a lock file and a random port, which is the operational shape the Brief rules out. It is prior art for command vocabulary and for a .mli-first spec style, and it is a reason to expect mldoc to stay maintained.

  • 3. Static knowledge-garden publishing


    garden publish should eventually use the same parsed graph to produce a static website.

    The initial motivating publication corpus is:

      https://github.com/codekiln/logseq-encode-garden


    The current Logseq SPA publication model effectively serializes the graph into a large browser-side database and requires the visitor to load a substantial portion of the garden before rendering individual content.

    The replacement should instead be able to generate:

      one page
        ↓
  one independently useful HTML document


    A page request should not require downloading the entire garden.

    Static output should eventually support:

      real page HTML
  stable URLs
  SEO metadata
  search-engine indexing
  backlinks
  internal references
  incremental rebuilds
  sitemaps
  optional client-side search
  optional graph visualization loaded only when requested


    The publisher should be another client of garden-core, not a separate Logseq parser.
