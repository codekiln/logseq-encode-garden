Architecture/Decision/Record
  • A decision is made early in the life of a product. Later, an individual or team decides to change that decision. Without knowing how and why the initial decision was made, the change may cause huge problems. Maybe a particular technology was chosen to meet one or more requirements, and overriding that choice means those requirements are no longer met. You may not realize this until a lot of time and money have been wasted.

AWS/Secrets Manager/Secret/Rotation

  • Path 3: a hand-written Lambda function — works on any secret, either shape, any product at all

    • AWS also ships a generic rotation template as an unopinionated starting point, and nothing stops writing one from scratch for a secret belonging to no AWS product whatsoever (a third-party API key, say). AWS Secrets Manager rotation function templates, same page as Path 2's list: "Secrets Manager also provides a generic template that serves as a starting point for any type of secret." Unlike Path 2's ready-to-use templates, the generic template and a from-scratch function carry no schema assumption, so they work on a plain AWS/Secrets Manager/Secret/SecretString just as well as an AWS/Secrets Manager/Secret/KeyValue — the code decides how to parse and replace the value. This is the only rotation path available to a plain single-string secret, and the only one with no product restriction at all.
    • Turn it on by attaching the function's ARN: aws secretsmanager rotate-secret --secret-id "myapp/database-url" --rotation-lambda-arn "arn:aws:lambda:...". --secret-id names one whole secret — the / inside "myapp/database-url" is not a path into a JSON object; see AWS/Secrets Manager/Secret on why it's just an allowed naming character. Rotation always replaces that one secret's entire SecretString, never a sub-key of it. Example command lifted from fnox's AWS Secrets Manager provider docs, under its "Secret rotation" heading.
    • The four-step contract a hand-written rotation function must implement, per Write a rotation function — the same page the ready-made templates in Path 2 are built from, under "Four steps in a rotation function":
      • createSecret — generate the new value (e.g. a random password) and store it with put_secret_value, tagged AWSPENDING. Quote from that page: "Then it generates a new secret value ... Next it calls put_secret_value to store it with the staging label AWSPENDING."
      • setSecret — push that AWSPENDING value into the actual database or service so the new credential becomes real there. Quote: "The method setSecret changes the credential in the database or service to match the new secret value in the AWSPENDING version of the secret."
      • testSecret — connect using the AWSPENDING value to confirm it actually works before committing to it.
      • finishSecret — promote AWSPENDING to AWSCURRENT; the label that used to be AWSCURRENT moves to AWSPREVIOUS. Quote: "the Lambda rotation function moves the label AWSCURRENT from the previous secret version to this version, which also removes the AWSPENDING label ... Secrets Manager adds the AWSPREVIOUS staging label to the previous version."
      • On an AWS/Secrets Manager/Secret/KeyValue secret, a correctly written createSecret step reads the current AWSCURRENT JSON first and writes back the complete object with only the target field (e.g. password) changed. Secrets Manager itself performs no such merge — that is the function's own job, and it is exactly the job fnox skips, per the hazard noted below.

  • OpenWhispr is the best alternative, especially if you use a standard supported provider such as OpenAI rather than a custom authenticated organizational endpoint.   • The security characteristics are also unusually straightforward. Its current product documentation states that there is no account requirement and no telemetry, and that cloud speech providers are used only after you add and select them. [8]
  • What gives me pause is architectural churn. Whispering moved from its former repository into the larger Epicenter monorepo, with Epicenter now owning the Tauri runtime. Direct provider mode satisfies your BYOK rule, but the product can also use Epicenter's hosted gateway and optional auth/sync functionality. That creates more configuration states in which “Whispering is using BYOK” is not enough—you must verify that the direct connection mode is selected. [24]

It therefore fails your OSS requirement irrespective of technical capability. [50]
