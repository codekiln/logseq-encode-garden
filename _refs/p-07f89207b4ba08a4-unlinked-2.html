      • 2025-10-04 Sat - git/.gitignore issues

        • Yesterday I discovered that the rulesync/gitignore command implies a usage of rulesync in which the configuration files for any given tool are treated as compiled build artifacts. I was curious about trying out this workflow, so I ran it, which added a bunch of rules to .gitignore for each AI/Coding/Tool - CursorAI, Claude/Code, etc.
        • Today, on another computer I discovered the classic problem with introducing git/.gitignore rules after some subset of files have been tracked to the repo. I asked Claude Code about it.

          • AI/Response

            • The .gitignore patterns (lines 24-25 and 29-31) will only prevent untracked files from being added, but they don't affect files that are already in the git repository.
            • Here's what happened:
              • 1. These files were previously committed to your repository
              • 2. When you ran rulesync generate, it modified these already-tracked files
              • 3. Git shows them as modified because they're already being tracked
              • 4. The .gitignore patterns don't apply to files already in git's tracking
            • To fix this, you have two options:
              • Option 1: Remove these files from git tracking (recommended if you want rulesync to manage them independently):
                • git rm --cached .cursor/rules/*.mdc .github/instructions/*.instructions.md CLAUDE.md .claude/memories/*.md
              • Option 2: Keep them tracked and commit the changes (if you want these in version control):
                • `git add .cursor/rules/ .github/instructions/ CLAUDE.md .claude/memories/

                  git commit -m "chore: update generated AI tool rules"`

          • So, what do I want to do?

            • Option 1 - Remove AI configuration files in repo

              • Pros
                • Some Search tools (like PyCharm) can respect git/.gitignore, and it would be convenient to not pollute the search space with a bunch of duplicate information.
                • It will be clearer to AI coding tools that respect gitignore which are the "canonical" versions of the files, which will be particularly useful in the common use case of asking AI tools to updating AI rules files.
              • Cons
                • Sometimes when I talk to people about how I accomplish certain things with AI, it's helpful to be able to hyperlink them to the exact prompt I use, and for many, it would be less confusing if that rule were in the format that they know.
                • I have to regenerate them regularly, which implies running them in a post-checkout hook.

            • Option 2 - Keep AI configuration files in repo

              • Pros
                • No need to regenerate them each time; one would regenerate every time a rule is updated, and then commit the changes
                • I can refer coders (be they human or AI) to a file in github that has the version of my rule in their framework of choice.
              • Cons
                • Often times I update AI configuration files in the middle of a task. Explaining to AI how to carefully stage only the items related to an AI configuration change when the git stage is dirty might be tricky and unreliable.
          • I ended up filing rulesync/GitHub/Issue/25/10/Feature request rulesync githook

  • 2026-10-02: more than one mount, and deleting a mount's folder

    • Observations from one run at about 12:20 ET on macOS, with the 1Password desktop app, 1Password CLI 2.39.0 and the 1Password/Environment/MCP server (1password-mcp). They are not documented behaviour, except where a link says so. Nothing was read from the mounted file.
    • One Environment can have more than one mount.
      • The server's create_local_env_file added a second local .env mount of a test Environment, in a scratch folder, beside an existing mount.
      • list_local_env_files listed both as enabled, and the desktop app showed both under Connected to.
      • The new file was a named pipe (prw-------).
    • Deleting a mount's folder does not remove the mount.
      • After rm -rf of the scratch folder, list_local_env_files still listed the mount as enabled a minute later, and the desktop app still showed it.
      • 1Password did not recreate the file in the 30 seconds watched.
      • Removing a git worktree deletes its folder the same way, so it would leave its mount registered. That mount probably still counts toward the limit of ten enabled local .env files per device; this was not checked.
    • No program was found that removes a mount.
      • The installed MCP binary names only its eight tools, and none removes a mount.
      • The CLI reference lists one op environment subcommand, read (reference), and op 2.39.0 has no environment command.
      • The ⋮ menu on the mount in the desktop app is the only way found.
    • For coding agents that mount one .env per git worktree, each finished worktree leaves a mount to remove by hand, inside a limit of ten per device.

Ableton/Live/Report/26/09/Open-source options for controlling Live 11 from coding agents
  • ahujasid/ableton-mcp — Live 10+ Remote Script with loopback TCP and MCP. Largest agent-specific adoption; anonymous telemetry is enabled by default. [6]
  • AbletonBridge — Live 10/11/12 Remote Script and optional Max for Live bridge; expansive tool surface. [10]
  • ahujasid/ableton-mcp is the adoption leader among the purpose-built MCPs I found. The inspected repository had roughly 3,100 stars, hundreds of forks, dozens of commits, active issues and pull requests, and straightforward support for Claude Code through uvx ableton-mcp. Its README says Live 10 or newer, so Live 11 is squarely in scope. [6] Architecturally it is the classic approach: an MCP server talks over JSON/TCP to a Python MIDI Remote Script running as a Live Control Surface. [6]
  • AbletonBridge is the technically most expansive community project I found. Its current README describes 359 tools, with roughly 340 core tools, a Control Surface Remote Script over TCP/UDP, an optional Max for Live bridge for deeper access, an HTTP status dashboard, and explicit Live 10/11/12 fallbacks. It also claims 214 tests and documents measures such as input validation, size limits, concurrency controls, hard tool timeouts, bounded worker pools, and chunked communications. [10] Those are better engineering signals than the project's modest GitHub popularity might suggest.
  • On the other hand, this is an enormous authority surface. Its architecture includes TCP 9877, UDP 9882, optional OSC/UDP 9878/9879, and a web dashboard; the README explicitly shows the dashboard on 127.0.0.1, but in the material I inspected I did not find an equivalent security statement establishing authentication or loopback-only defaults for every Remote Script transport. [10] The creator's own GitHub profile says they would like to work for Ableton or Anthropic, which is useful evidence that this is not an Ableton- or Anthropic-affiliated project. [38] I would call it an impressive experimental project, not a trust-minimized production choice.
  • I would not make AbletonBridge or ableton-mcp-extended my first trust-sensitive choice despite their capabilities; both add a lot of code and interface surface without a corresponding improvement in maintainer provenance or security documentation over the top three. [10] I would also exclude bschoepke's arbitrary-eval bridge from a security-conscious deployment and from the verified-Live-11 shortlist, notwithstanding the author's credible professional background.           • Save the versions into the same Project, usually the one created with the first version. The Project keeps one copy of the samples they share.
      • Ableton/Live/UG/05 Managing Files and Sets/10 File Management FAQs/04 Where Should I Save My Live Sets

        • 5.10.4 Where Should I Save My Live Sets?

          • Anywhere, but save into an existing Project only when the Set is related to it, such as an alternate version of a song already there.
      • Ableton/Live/UG/05 Managing Files and Sets/10 File Management FAQs/05 Can I Use My Own Folder Structure Within a Project Folder

        • 5.10.5 Can I Use My Own Folder Structure Within a Project Folder?

          • Yes, then relink with the File Manager:
            • Reorganize the folder in the browser or the operating system.
            • Choose Manage Project from the folder's context menu in the browser.
            • If Missing Samples shows moved files, press Locate, open Automatic Search, turn on Search Project and Fully Rescan Folders, and press Go.
            • Press Collect and Save to update the Project.
