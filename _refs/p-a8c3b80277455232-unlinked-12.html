GeminiCLI/Hook

  • Hooks reference – Gemini CLI

    • GeminiCLI's implementation of AI/Agent/Hook: scripts run at points in the agentic loop, synchronously — the CLI waits for every matching hook before continuing. Communication is JSON over stdin and stdout, and a stray print before the JSON breaks parsing.
    • Events: BeforeTool, AfterTool, BeforeAgent, AfterAgent, BeforeModel, BeforeToolSelection, AfterModel, SessionStart, SessionEnd, Notification, PreCompress.
    • That naming is the clearest evidence that hook events are not standardized. Gemini's BeforeTool is Claude/Code/Hook's PreToolUse and CursorAI/Hook's preToolUse, and PreCompress is what the others call compaction — three hosts, three vocabularies for the same moment.
    • Configured in settings.json under a hooks object, one array of definitions per event. A GeminiCLI/Extension ships them as hooks/hooks.json. Conceptual overview: Gemini CLI hooks.

ghq/Q/Can GitHub Desktop and ghq be configured to clone repositories to the same directory?
  • Short answer: not automatically — GitHub Desktop has no configurable default clone directory or awareness of ghq.root, but the two tools are compatible if bridged manually in each direction.
  • ghq → GitHub Desktop: a repo cloned with ghq get under ghq's <ghq root>/<host>/<owner>/<repo> layout can be opened in GitHub Desktop via File → Add local repository..., pointing at that existing folder. Desktop only needs a valid local git repo path, so it works regardless of directory layout.
  • GitHub Desktop → ghq layout: Desktop's clone dialog has no persistent "default root" setting — it just remembers the last path used, seeded from ~/Documents/GitHub (%USERPROFILE%\Documents\GitHub on Windows). The Local Path field is a plain editable text/browse field, so a <ghq root>/github.com/<owner>/<repo> path can be typed or browsed to on each clone, and Desktop will clone there.
  • Answer/Official from Cloning and forking repositories from GitHub Desktop
  • Option for changing default directory missing (desktop/desktop#2889)

ghq/Q/With ghq, what's the workflow for creating a repository and pushing it to github?

  • With ghq, what's the workflow for creating a repository and pushing it to github?

  • Short answer: ghq handles the local repo location and layout; gh handles creating the GitHub remote. A common local-first workflow is:
  • ghq create github.com/OWNER/REPO
  • cd "$(ghq list -p -e github.com/OWNER/REPO)"

git/Alias/md-url
  • git git/Alias GitHub CLI yazi/Keyshort/Copy GitHub markdown link
    • git md-url — markdown link to a path's GitHub web view #card
      • Command: git md-url [--no-copy] <path>...
      • Context: User-defined alias in the chezmoi-managed ~/.gitconfig, backed by ~/.config/git/scripts/generate_markdown_path_link.zsh. Sits beside git md-commit (which links the most recent commit), so the family is enumerable with git md-<TAB>. Clipboard writes route through the sibling git copy-text alias, which picks pbcopy / wl-copy / xclip per platform.
      • Description: Emits [<repo>/<path-from-repo-root>](<github-url>) for each path given — files and directories alike — printing to stdout and copying to the clipboard. --no-copy prints only, for pipelines. Several paths yield one link per line. The URL targets the repository's default branch, never the checked-out branch, since a link into an unpushed branch is a 404 for everyone else.
      • Cost: one network round trip per invocation, ~0.7s, regardless of how many paths are passed. The default branch resolves offline from refs/remotes/origin/HEAD; the base URL comes from a single gh browse -n call and every link is concatenated onto it.
      • Fails loudly: not a repository, no GitHub remote, a path outside the repository, or a missing gh all produce a message on stderr and a non-zero exit, leaving the clipboard untouched. A wrong link is not obviously wrong at paste time, so copying nothing is better.
      • My Notes Bound in yazi as yazi/Keyshort/Copy GitHub markdown link (c then g). The script strips GITHUB_TOKEN / GH_TOKEN itself rather than relying on the gh shell wrapper in .zshrc — that wrapper only exists for interactive shells, so a script behind a git alias would otherwise get the raw binary with the tokens still set.

GitHub/Action/Concept/Workflows vs Actions for DRY in Local Repository
  • Both workflows and actions can help reduce duplication in GitHub Actions, but they operate at different levels. Choosing correctly depends on whether you want to DRY steps inside a job or entire jobs across workflows.
  • Usually in programming languages, a file reference that begins with ./xyz means "in the current directory, find xyz." Here, it does not! Instead, in github actions, it refers to the repository root.
  • GitHub provides two main tools to reduce duplication:
    • Composite actions (bundling steps together).
    • Reusable workflows (bundling whole jobs or pipelines).
  • Locality matters: Within one repo, prefer ./.github/... references, but understand that they are resolved differently for actions vs workflows.
  • Define in .github/actions/<name>/action.yml.
  • Invoked inside a job step:
    yaml
    			  steps:
			   - uses: ./.github/actions/setup-node
    • Note: even though this looks like a relative path (./...), it is not!
  • Here, uses: ./... really is a filesystem path. GitHub Actions resolves the path relative to the repository root, not the workflow file. So ./.github/actions/setup-node resolves to .github/actions/setup-node/action.yml in the repo.
  • Define in .github/workflows/<name>.yml with on: workflow_call.
  • Invoked as a job:
    yaml
    			  jobs:
			   tests:
			     uses: ./.github/workflows/test-matrix.yml
    • Note: even though this looks like a relative path (./...), it is not!
  • Here, uses: ./... looks like a relative path, but GitHub interprets it as a workflow reference. Just like with composite actions, the resolution is anchored at the repository root, not relative to the calling workflow file. That’s why you must put reusable workflows under .github/workflows/.
