Ableton/Live/Report/26/09/Open-source options for controlling Live 11 from coding agents
  • The practical consequence is that Live-version compatibility is empirical. Wouter Stierhout's project is a good example: its September 17, 2026 release had to handle a Live-11-specific difference involving the embedded Python 3.7 environment and socket.timeout. That is precisely the sort of compatibility edge one expects when building against the Remote Script runtime rather than a conventional supported external SDK. [16]
  • wstierhout/ableton-live-mcp is almost the inverse tradeoff. It is new—its GitHub history showed only about 20 commits when inspected—and its GitHub adoption is tiny compared with ahujasid or AbletonOSC. [5] But the implementation makes a number of security-conscious choices I would have made myself: 156 specific tools with validated arguments, no generic arbitrary-code tool, a Remote Script bound to 127.0.0.1:9877, an explicit security document acknowledging that the socket has no authentication, a version handshake between MCP package and Live-side script, an installer that refuses unexpected replacement without an explicit flag and retains backups, a doctor command, tests, linting, and multi-version CI. [5]
    • My Question

      • security document acknowledging that the socket has no authentication

        • TODO What does it actually mean for a Socket to have Authentication? Ghost Gardener please add a Logseq/Entity/Question for this.
  • It is also one of the projects with particularly clear Codex/Claude Code ergonomics: its documentation gives pinned commands such as uvx mcp-server-ableton-live@1.8.1, including direct codex mcp add and claude mcp add examples. Pinning the package version in the recommended install is a small but meaningful supply-chain improvement over documentation that simply executes whatever the current package version happens to be. [5] Version 1.8.1, released September 17, 2026, specifically addressed a Live 11 embedded-Python compatibility issue, which is stronger evidence than a generic “Live 11 supported” badge. [16]
  • uisato/ableton-mcp-extended explicitly advertises Live 11+ and adds significantly more functionality around the same general Remote Script/socket design, including optional higher-performance UDP communication. The inspected project had nontrivial adoption, but its creator's public GitHub footprint is essentially centered on this project and I found no established-company affiliation comparable to the stronger examples above. [9] Its optional ElevenLabs integration is outside the “free-only” criterion when it requires a paid external service, so I would evaluate only the core Ableton integration. More network transports and more tools are not inherently insecure, but they enlarge the amount of code and protocol surface one has to audit. Given that ahujasid and Wouter already cover this architecture with stronger security signals, I see little security-driven reason to prefer the extended version.
  • Finally, Ben Schoepke's ableton-live-mcp is worth knowing about precisely because its design illustrates what I would not expose to an autonomous coding agent on an important machine. The project's README explicitly says the agent can evaluate arbitrary Python running inside Ableton, while also providing optimized tools for common operations. [11] That gives it extraordinary flexibility but largely destroys capability isolation: instead of “the agent may create a clip and set a parameter,” the primitive is effectively “the agent may execute Python in the DAW's embedded interpreter.” The author also warns users to back up sets, and the version I examined documented testing on Live 12 rather than Live 11, so I do not count it as a verified Live-11 option. [11]
  • Wouter Stierhout's project has the best default capability/network combination I found. It exposes explicitly typed operations rather than Python eval, validates inputs, binds the Live-side socket to loopback, documents the lack of authentication, supplies pinned package invocation examples, backs up replaced scripts, maintains a server/Remote-Script version handshake, and runs tests and linting in CI. [5] The reason I stop short of calling it the overall safest choice is maturity: roughly 20 commits and a tiny user population cannot tell you as much about weird edge cases as years of use can. [5]
  • Best out-of-the-box network posture without Max for Live: wstierhout/ableton-live-mcp. It is the one I would test first with Codex CLI or Claude Code on a security-conscious workstation: loopback-only socket, no arbitrary Python tool, explicit security documentation, pinned installation examples, version-matched Live bridge, safe-ish installer behavior, and actual Live-11-specific compatibility work. [55] The price is novelty. I would review the source and pin a known commit/version rather than assigning it the trust normally earned by years of deployment.
  • Best mature ready-made MCP ecosystem: ahujasid/ableton-mcp. It has vastly more adoption than Wouter's project and a creator with a demonstrated record of successful creative-application MCPs. [6] Its current loopback binding is good. [27] I would launch it with telemetry explicitly disabled and pin the package version rather than use the bare uvx ableton-mcp example. [6]
