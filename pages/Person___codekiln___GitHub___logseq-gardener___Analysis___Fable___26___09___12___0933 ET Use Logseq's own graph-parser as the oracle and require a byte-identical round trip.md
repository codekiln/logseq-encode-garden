- # Use Logseq's own graph-parser as the oracle and require a byte-identical round trip
	- Codex's [[Person/codekiln/GitHub/logseq-gardener/Analysis/Codex/26/09/12/0733 ET Test graph meaning and preserve the original source text]] adds two tests to the parser decision in [[Person/codekiln/GitHub/logseq-gardener/Analysis/Fable/26/09/12/0658 ET Pick the parser first and let the language follow]]: compare the graph the tool builds with the graph Logseq builds, and keep the original text so a later edit changes only the bytes it means to. Both tests are right, and both can run this week with tools already on this machine. Logseq's `graph-parser` is the reference answer: whatever it says a graph contains is what the new tool has to match.
	- ## Logseq's own parser can produce the answers to compare against
		- lsdoc's differential test compares its syntax tree with mldoc's on a normalized projection of blocks, inline nodes, and references, and its README says spans are excluded from that comparison ([lsdoc README, The oracle](https://github.com/martinkoutecky/lsdoc#the-oracle)). Page naming, alias and tag extraction, journal conversion, block order, and duplicate-ID handling sit above that tree, in Logseq's [extract.cljc](https://github.com/logseq/logseq/blob/master/deps/graph-parser/src/logseq/graph_parser/extract.cljc), so the differential test says nothing about them.
		- `nbb-logseq` is installed here through mise, the link-hygiene and flashcard skills already run ClojureScript scripts under it, and its README says the graph-parser's namespaces all load under it ([nbb-logseq README](https://github.com/logseq/nbb-logseq#readme)). A short script can therefore run Logseq's own `extract` over the encode garden and write pages, aliases, tags, block parents, references, and explicit UUIDs to JSON. That file is the golden fixture the new tool's output is compared with, page by page, with the graph-parser version recorded beside it.
		- Run the comparison after edits as well as after a cold load, as Codex asks: remove an alias, move a block that carries an `id::`, delete the last link to a fileless page, and compare the incremental answer with a fresh rebuild.
	- ## The round trip is a pass-or-fail test
		- Parse every file in the encode garden, serialize it back, and require identical bytes. A parser that passes can support small edits. A parser that fails needs a separate layer that keeps original text and spans, which is what Codex describes. Tine's README says tine-core's tests include a parse/serialize round trip, that round-trip parsing is validated against a real Logseq graph, and that `tine-check` proves byte-faithful serialization without reading note content ([Tine README, Testing](https://github.com/martinkoutecky/tine#testing)). Running `tine-check` on the encode garden is the cheapest way to learn whether that claim holds for this corpus.
		- Files the round trip cannot reproduce are findings. Each one is either a construct the parser should learn or a file this garden should fix, and the list of them is the compatibility report the Brief asks for.
	- ## What the decision rule becomes
		- Rust on lsdoc and tine-core stays the path when lsdoc's differential test, the graph-parser comparison, and the byte round trip all pass on the encode garden. A failure in the graph comparison points at `extract` code the new tool must port; a failure in the round trip points at the serializer. OCaml on mldoc remains the fallback when the syntax comparison itself fails, and since Logseq's graph layer is ClojureScript, that path ports `extract` as well.
