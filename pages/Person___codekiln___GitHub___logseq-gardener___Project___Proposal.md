- # logseq-gardener: Project proposal
	- logseq-gardener is a proposed command-line tool, called `lsg`, for managing Logseq knowledge gardens. It will help people and coding agents find notes, follow links, review changes, and eventually edit and publish their gardens. The aim is to make years of accumulated notes easy to use from the terminal and Neovim, with continued support for the existing Markdown files and Git workflow.
	- ## Why build it?
		- A Logseq garden contains relationships that ordinary file tools cannot fully explain. A page can exist through links from other notes even when it has no file. An alias can give a page another name. A reference can point to an individual bullet and its children, which Logseq calls a block. Searching filenames alone misses these relationships.
		- People need those relationships when navigating their notes; coding agents need them when choosing where to put new information. Today, agents repeatedly search this repository to reconstruct enough context to make an edit. `lsg` will provide a consistent way to ask the garden directly and identify the source of each answer.
		- The longer-term benefit is freedom to choose how to work with the garden. A person should be able to write in Neovim, delegate maintenance to an agent, and publish readable web pages while retaining the connections that make the notes useful.
	- ## Use cases
		- **Find the right place for a note.** Before creating a page, an agent runs `lsg page resolve "Logseq/Publish"`. The result identifies the page, explains how the name matched, and gives a source location. If several pages claim the name, the command lists the candidates for review.
		- **Write with links in Neovim.** While a person types a page link, the editor offers matching names and aliases. Following a link opens the note; finding references lists the places that use it. For a page without a file, the editor shows the notes that mention it.
		- **Understand a change before committing.** Suppose Studio has the alias Workshop and a journal links to Workshop. Removing that alias changes what the journal link means, even though the journal text stays the same. `lsg diff --staged` will show the removed alias and the journal links affected by it.
		- **Share a readable garden.** `lsg export` will prepare pages for a static website, including links, embedded notes, and referenced assets. A visitor will be able to open a page and read its content without first downloading the whole garden.
		- **Maintain notes with an agent.** Later editing commands will preview a page rename or block move, including changes to references elsewhere. A person can review the patch before applying it, and `lsg` will detect intervening edits before writing.
	- ## First release
		- Start with commands for finding and inspecting information. These commands will read the garden and maintain a reusable index of its pages, blocks, and references. The first release will leave garden files unchanged, making it suitable for daily use on real notes while compatibility is established.
		- The initial command set:
			- `lsg page resolve "Logseq/Publish"` — identify a page and explain the match.
			- `lsg page complete "Logseq/Pub"` — suggest page names and aliases.
			- `lsg page backlinks "Logseq/Publish"` — find notes that link to a page.
			- `lsg block get <uuid>` — retrieve a block by its saved identifier, with its source location.
			- `lsg search "publishing"` — search note text and show matching locations.
		- Output will be readable by default. `--json` will return the same information in a documented structure for scripts and agents. Batch page resolution will accept names from standard input so a link checker can inspect a draft in one invocation.
		- Page resolution will distinguish a match, competing matches, no match, and an incomplete search. A match will also say whether a content file exists. The quiet `lsg page exists` command will expose those outcomes through documented exit codes; scripts must distinguish an incomplete search from an absent page before creating anything.
		- The release is ready for regular use when this repository's link-hygiene workflow can resolve names through `lsg`, explain its findings with source locations, and pass the compatibility tests below. Repeated commands must reuse prior parsing work.
	- ## Technical design
		- ### Shared graph model
			- A core library will read Logseq files and represent pages, nested blocks, properties, aliases, and references. The CLI, Neovim integration, and exporter will call this library so they agree about what a name or reference means.
			- `lsg` will select the nearest garden containing `logseq/config.edn`, or use an explicit `--graph <path>`. The core will read the garden's naming configuration before interpreting filenames, titles, and journal dates. Every lookup will belong to a specific garden.
			- Each page and block will retain its source file and text location. Blocks with an explicit UUID will keep that identity when moved. For other blocks, the core will record their location in the current outline and report uncertainty when comparing possible moves between versions.
		- ### Parser and compatibility
			- Rust is the proposed starting language, with [lsdoc, a Rust parser for Logseq Markdown](https://github.com/martinkoutecky/lsdoc), as the parser candidate. Rust offers a direct route to a native executable and reuse of existing Logseq tooling. Evaluate reusable code from [Tine, a Logseq-compatible outliner](https://github.com/martinkoutecky/tine), by adapting the library or bringing the needed code into this project. Record dependency revisions and license requirements before adopting code.
			- Test the candidate against [Logseq's file-graph parser at release 0.10.15](https://github.com/logseq/logseq/tree/0.10.15/deps/graph-parser). The comparison must cover page identities, aliases, block hierarchy, and references as well as Markdown syntax. A parser can recognize a link correctly while the surrounding application resolves it to the wrong page.
			- Keep the original file text and test source locations separately. Parsing and writing a file without edits must preserve every byte. Later editing tests must also prove that a small requested change leaves surrounding text intact.
			- If lsdoc requires extensive syntax repairs on the test gardens, compare that effort with using [mldoc, Logseq's parser written in OCaml](https://github.com/logseq/mldoc), before settling the language. Either implementation must pass the same graph tests.
		- ### Index and responsiveness
			- Store a rebuildable SQLite index outside the garden, under `$XDG_CACHE_HOME/logseq-gardener/`, using `~/.cache` when the variable is unset. Give each garden checkout its own directory, keyed by its real path, so separate Git worktrees can contain different notes safely. Deleting the index will cause `lsg` to rebuild it from the files.
			- Commands will refresh changed files and reconsider references affected by those changes. For example, removing an alias requires resolving links in other notes again, while reusing their parsed text. File content hashes, configuration, and parser versions will determine whether cached information is current. Database transactions will keep partial updates out of query results.
			- Neovim will start `lsg lsp`, a process that communicates through the Language Server Protocol over standard input and output. The server will load cached information when a garden file opens, parse the current file first, and continue indexing in the background. Completion can return available candidates promptly; a definitive existence check must finish the relevant search or report that it is incomplete.
			- The language server will keep unsaved editor text separate from the saved index and discard parsing results for older buffer versions. Terminal commands will answer from saved files. Installation will provide the `lsg` executable; Neovim will manage the language server's lifetime.
		- ### Review, export, and editing
			- `lsg diff` will compare complete garden versions so it can explain effects in unchanged files. The staged form will compare the last commit with Git's staged contents, using each version's configuration. It will report changed link targets, missing block references, and changed block relationships with source locations.
			- `lsg export` will produce ordinary Markdown for a site generator, beginning with a trial of [Quartz](https://quartz.jzhao.xyz/). The exporter will resolve links and embeds and copy referenced assets. Unsupported queries or macros will get visible placeholders and a local report. Publication filtering must also cover embedded text, backlinks, and assets so excluded notes stay out of the website.
			- Editing commands will prepare patches from original text and check that affected files still match the preview before applying them. Multi-file operations will record recovery information before writing. After interruption, recovery must preserve any newer edits and report files requiring attention.
	- ## Starting tasks
		- **Build a compatibility test set.** Use this public garden, the public Logseq documentation garden, and small examples of aliases, fileless pages, journal names, nested blocks, and UUID references. Pin the reference parser and record expected results. Completion means a repeatable comparison that identifies each disagreement and its source file.
		- **Choose the parser.** Run lsdoc on the test set, check graph results and source preservation, and measure parsing time and memory. Inspect the useful parts of Tine. Completion means a short decision record naming the implementation, dependency licenses, and compatibility repairs needed to proceed.
		- **Deliver page resolution with a reusable index.** Implement graph selection, `lsg page resolve`, JSON output, and batch input. Add tests for duplicate aliases, fileless pages, changed configuration, deleted files, and changed content with unchanged file size and timestamps. Completion means an updated index produces the same answers as a clean rebuild and separate worktrees remain independent.
		- **Use the CLI in garden maintenance.** Add completion, backlinks, block lookup, and text search, then integrate batch resolution into this repository's link-hygiene workflow. Completion means an agent can find an existing destination for a note and check its links with actionable source locations.
		- **Measure everyday speed.** Record cold startup, repeated commands in fresh processes, and the time for a saved edit to appear in backlinks. Use larger generated gardens and heavily linked pages alongside real notes. Set response-time targets from those measurements and keep the slow runs visible. Before delivering Neovim support, also measure completion while background parsing is busy.
	- ## Subsequent work
		- Deliver Neovim completion and navigation after the CLI is useful in daily maintenance. Test unsaved aliases, unfinished links, Unicode cursor positions, and delayed parsing results by replaying editor requests.
		- Add graph comparison to commit checks and PR review, then export the public garden and measure how quickly visitors can read a page. Test partially staged edits for comparison and nested embeds with mixed publication settings for export.
		- Add page and block editing once reading and comparison are dependable. Test preview accuracy, intervening edits, and interrupted multi-file writes.
		- Support concurrent work through a Git merge driver that combines edits to confidently matched independent blocks and exposes structural conflicts for a person to resolve. Validate references across the whole garden after merging. Later, evaluate live shared editing with conflict-free replicated data types, which coordinate concurrent edits, when simultaneous work in the same files requires it.
